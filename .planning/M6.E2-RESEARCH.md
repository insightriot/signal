## 1. The harness is general — verified by reading the contract, not inferred from the registry

`defineCheck` (`state-drift.js:110`) validates and freezes a definition of
`{id, healCategory, applicability(ctx), run(ctx), healMechanism?, describe?}`. The context built by
the runner is `Object.freeze({baseDir, planningDir, state, files, stateBody})` (`:200`) — **it carries
`baseDir`**, so a check can read any `.planning/` file, not only `STATE.md`.

`runDriftChecks(baseDir, checks = STATE_DRIFT_CHECKS)` (`:227`) takes the registry as an **argument**
with a default. Composing a second registry needs no change to the runner.

Reached from two commands, both of which run in any project:
- `/sig:sweep` — `sweep.js:542`, `runDriftChecks(baseDir, STATE_DRIFT_CHECKS)`
- `/sig:resume` — `resume.md:80`, `runDriftChecks(baseDir)`, fail-open to `null`

**Why this was checked first.** The Epic was pitched on "these are new registry entries, not a new
mechanism." All 8 registered checks are STATE-shaped, so that could have been an inference from a
sample rather than a property of the contract. It is a property of the contract. Had it not been,
the Epic was materially bigger and the requirements would have had to say so.

## 2. `compareBugTally` has exactly one caller, and it is a test

`grep` across `plugin/`, `tools/`, `tests/`: the only import of `compareBugTally` is
`tests/bugs-tally.test.js`. `backlog.js:597` imports `walkBugEntries` from the same module — the
entry walker, not the comparison. So the derive-then-compare logic fires **only** under Signal's own
vitest run: only in this repository, and only after a write has already gone in.

It supplies more than the comparison. `readPublishedTally` returns **`lineNumber`** alongside the
parsed cells, and `formatTallySegment(derived)` renders the corrected line. Both are needed by FR1
and neither had a non-test caller.

## 3. ⚠ FR1's assumed approach does not work — the inbox footer helpers do not transfer

**The requirement says `captureToFutureIdeas` "already solves this" with `insertAboveFooter` +
`rewriteFooter`. Measured against the real file, that is half true: the *pattern* transfers, the
*helpers* do not.**

- `FUTURE_IDEAS_FOOTER_RE` is `/^\*Last updated:[^*]*\*\s*$/` — it requires the line to **begin**
  `*Last updated:` and forbids any interior `*`.
- `BUGS.md`'s footer begins `*0 needs-triage · **2 captured-untriaged** · …` and contains bold spans.
  It matches neither half of that regex. Confirmed by running it: **false**.
- Worse, `BUGS.md`'s tally is **no longer the trailing line at all**. It sits at line 184 of 201, with
  the two `/sig:add` captures and a trailing `---` below it. The file's own summary is already
  mid-document — which is the filed defect, observed rather than predicted.

**Consequence for the plan.** FR1 is not "call the existing helper." It is a `BUGS.md`-specific
insert path anchored on `readPublishedTally().lineNumber`, rewriting the line with
`formatTallySegment(deriveBugCounts(content))`. The pieces exist; they are in `bugs-tally.js`, not
`add.js`. The `repaired`-style announce (`AC1.4`) has to be authored, not inherited.

**This finding came from the "what does this Epic run for the first time" step**, which is the step
that scheduled the check. It would otherwise have surfaced in EXECUTE against a half-written slice.
