### 3. Dependency correctness — **PASS (corrected at review)**

**Two dependency errors were found by re-reading the plan against the code rather than against
itself.** Both are fixed above; recorded here because a validation that passes a graph it did not
check is the failure this dimension exists to catch.

- **S3 did not depend on S1.** The draft asserted the dependency *and* "no slice waits on work it does
  not consume" in the same document. The walk needs only `canary.trace.functionName`, which exists
  today, and S3.t5's coupling guard is precisely the assertion that it consumes nothing from S1. S3
  moved to wave 1.
- **S1 was under-scoped and would have shipped a red suite.** Replacing `deleteSection` with
  `deletions[]` breaks **ten** reader sites (`adherence-run.js:376-378,666,668` and
  `adherence-verdict.test.js:158-160,199,217-220`), while the runner rewire sat two waves later —
  `canary.deleteSection` would be `undefined` and `applyDeletion(src, undefined)` throws. The whole
  migration is now one task, S1.t4.

Corrected graph: wave 1 is four slices with **no shared file** (`adherence-verdict.js`+`adherence-run.js`,
`adherence-log.js`, new `adherence-leak.js`, `adherence-harness.js`). S5 needs S1+S3; S6 needs S3;
S7 needs all. Minimal: no slice waits on work it does not consume.
