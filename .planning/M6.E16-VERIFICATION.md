**PASS with documented limits — 36 of 36 acceptance criteria met (8 of them with a limit stated
below) and 3 of 3 non-functional requirements. One of the 36 rests on a judgment call, and it is
AC6.4.** Suite, lint, build and plugin validation are clean and equal the baseline.

**The judgment call, stated so it can be overruled.** AC6.4 failed twice. As reworded in loop 2 it
says what a project with no unit records gets identically to `v0.1.50`, and three kinds of
difference. Measured here on four kinds of project (604 answers from each tree, not the helper's
72), **every difference found is something this Epic adds, a consequence of the unit-name rule, or
wording — and no closure answer, archive move, item answer or report line that `v0.1.50` already
gave came out differently.** But four of the differences are inside kind (a) only by its label,
*"what this Epic adds"*, and not by the three things (a) goes on to list:

1. **The first-time migration.** `/sig:docs-migrate --work-store` on a project that is not on the
   store now also proposes unit records in its dry run and writes `work/units/` in its apply
   (AC9.1). Kind (a) names the dry run "on a project already on the store" (AC9.2) and not this
   one. After the apply the project has unit records, even when it named no unit at all.
2. **A refusal `v0.1.50` gave is gone.** On a project with a `.planning/archive/epics/<ID>/` folder
   and no store, `v0.1.50`'s first-time apply throws `SCHEMA` — it fails its own check of the
   `EPICS.md` it has just written — and writes nothing. The branch applies. Measured on four
   project shapes; `v0.1.50` fails on that one only.
3. **`WORK.md`'s text.** The file written when a store is created from v1 item files gains one
   line about `units/` and one reworded line about `epics/`.
4. **A new flag.** `parseMigrateArgs` reads `--also`; `v0.1.50` ignored it.

**Read as kinds — which is what the criterion says it is ("said by kind, not as a list of
functions") — these four are kind (a), and AC6.4 is met.** Read as a closed list of three, they
are outside it and AC6.4 fails a third time. This report takes the first reading, because the
first-time migration is the feature AC9.1 asks for and item 2 removes a crash, not a rule. The
remedy is the same either way and is one clause of text, no code: add "the first-time migration
(AC9.1), the `WORK.md` it writes, and `--also`" to kind (a), and add the first-time dry run to
`tests/helpers/units-off-parity.js` so the test can see that path. **Recommended before SHIP; not
a blocker as judged here.**

## v2.3, tried to break

Unit text is cleaned by every writer (`clean`, `plugin/tools/lib/unit-records.js:530`, over
`printable`, `plugin/tools/lib/printable-text.js:18`) and again by both renderers. A value holding
NUL, ESC, U+202E, a tag character, a line break, `|`, `<!-- signal:epics:end -->` and a second
comment opener, and a 20 kB value, were put through `openUnit`, `editUnit`, `closeUnit`,
`holdUnit`, `reopenUnit` and `importUnits`, and through records written past the writer.

**Nothing reached a view.** After all of it `work/EPICS.md` and the marked milestone table held no
NUL, ESC, override or tag character; no line break made a new line or row; the end marker and
every `<!--` from a record were taken apart; the bytes outside the markers were unchanged;
`checkUnits` reported nothing; and all 48 of this repository's records validate. Five findings,
none failing a criterion:

1. **The caller is not told its text was changed or cut.** A 20 kB title is stored as 200
   characters ending in `…`; a title with a line break is stored as one line; the returned entry
   has the same keys as before and no sign of either. The only trace is the `…`.
2. **`by` is stored as given** — NUL, ESC, override, tag character and line break included, with no
   limit. It is printed in no unit view (searched), so it reaches no reader today.
3. **One over-limit record written past the writer stops every write.** With a unit record placed
   by hand holding a 3,000-character title: `checkUnits` reports it clearly by ID, path and field,
   and the other records still read — but `regenerateViews` refuses for the whole store, so
   `newItem`, `openUnit` and `holdUnit` on a good unit are all refused, and `editUnit` on the bad
   record is refused too, because it validates on read. No library call repairs it, and the hook
   blocks the hand edit; it takes a shell command or git. This is how item records already behave.
   No record in this repository is near a limit (longest title-like field 120; longest cell 3,048
   of 8,000), and no other project has unit records.
4. **A `|` in an old row's cell adds cells to its milestone row, through `importUnits` too** — a
   row came out with 4 cells and one with 5. The progress file says this is kept on purpose for
   `M5.E18`'s real row. It cannot add a row or a marker. A cell may be 8,000 characters, so a row
   can be an 8 kB line.
5. **A title of only invisible characters is refused with `(got "")`** — what the cleaner left, not
   what was sent. A required field never becomes empty silently: the schema refuses it. Two
   different titles can clean to the same text, and that is harmless: a title is never a key —
   `editUnit` to such a title answers "every field already holds its new value".

IDs are not cleaned at all: an ID with any such character is refused (AC1.3), so two IDs cannot
collide by cleaning.
