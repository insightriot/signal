(`D-M6E16-20`) reworded the criterion to name those four and added a test "so the list cannot grow

   quite true either. No real Epic ID is that long — nobody is affected — but it is a refusal that
   differs.

   `.planning/work/units/*.json` on any v2 store, with or without unit records. `main` allows it.
   AC2.2 asks for the block; AC6.4 does not name it.
3. **A refusal that is gone.** `/sig:docs-migrate --work-store` on a project already on the store
   was refused on `main`; it now prints a units-only dry run. AC9.2 asks for this; AC6.4 does not
   name it, and the apply's refusal text differs too.
4. **A second added field.** `senseArchiveTree` returns a new `held` list (empty here). Same kind as
   accepted difference 3, on a function the criterion does not name.
5. **Difference 2 reaches the readers.** A record placed on disk that names `phase-11` was reported
   as invalid by `checkRecords` and `listRecords` on `main`; it is now listed as queued for
   `phase-11` with no finding about the record. The criterion describes the schema change, not this consequence.

No closure answer and no file move differed anywhere in the wider run. None of the five is a wrong
decision by the code; three are asked for by other criteria.

### Hostile old rows (the view loop 1 changed)

Old-row text is text a person wrote in another project's file. A fixture here imported 13 units
through `importUnits`, each with a crafted status cell, then regenerated the views three times:

| Attack on the status cell | Result in `work/EPICS.md` |
|---|---|
| Line breaks followed by `# heading`, `## Closed`, `### M9.E99 — open` (LF, CRLF, vertical tab, form feed, U+0085, U+2028) | One heading line. The file has 1 `#`, 1 `##` and 13 `###` lines for 13 units. |
| The `signal:epics` begin and end markers; the "generated by" first-line marker | Printed as text in the heading. Nothing reads `EPICS.md` back, and the milestone table escapes `<!--`, so the next regeneration is not refused. |
| NUL, BEL, ESC colour codes, U+202E (right-to-left override), U+200B, U+FEFF, tag characters | Removed from the old-row text. |
| A 10,000-character cell; 198 characters followed by emoji | Cut at 200 characters with `…`, no half character. |
| HTML and script tags, a `javascript:` link, code fences, pipes | Printed as text on the one line. |

**Nothing broke the view:** it stayed one heading per unit, stable across regenerations, and
`checkRecords` / `checkUnits` reported nothing. Three things are weaker than that sentence sounds:

- **`close.pr` and `close.release` are not cleaned.** `importUnits` cleans `legacy_row` cells and a
  close's words (`plugin/tools/lib/unit-records.js:738`, `:749`) and not these two;
  `unitCloseLine` folds whitespace only (`plugin/tools/lib/work-views.js:325-326`). In the fixture
  NUL, BEL, ESC, U+202E, U+200B, U+0085 and tag characters reached `EPICS.md` through the PR text.
  No shipped caller passes hostile text there today — the migration passes neither field, and 0 of
  this repository's 43 legacy closes carry one — so this is a gap waiting for a caller, not a
  failed criterion. It predates loop 1.
- **A comment opener is printed as written in the heading.** A cell holding `<!--` reaches
  `EPICS.md` unchanged; the milestone table takes the same opener apart (`milestone-table.js:36`).
  Whether any Markdown renderer hides text after it was not tested here — no renderer was run.
- **A record that did not come through the writer is printed as it is.** With a record written
  straight to disk (a merge or a shell command; the hook stops Edit and Write only), the milestone
  row kept a bare `|` (so the row gains cells), a 20,000-character cell uncut, and U+202E and BEL;
  the schema reported it as valid. The heading in `EPICS.md` was still one clean line.
