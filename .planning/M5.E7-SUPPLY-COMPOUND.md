## 1. The agent/persona architecture, mapped

### 1.1 There are no agents. The directory name is vestigial.

The single most important structural fact: **compound-engineering no longer ships agents at all**, in the Claude-Code sense of a registered, dispatchable `subagent_type`. What lives under `references/agents/` and `references/personas/` are *prompt assets* — markdown bodies that a skill reads and injects into a **generic** subagent dispatch.

This is stated as a prohibition in the skill bodies themselves, not merely implied:

- `skills/ce-code-review/SKILL.md:143` — "Each selected reviewer is a generic subagent seeded with a local prompt file from `references/personas/`; **do not dispatch standalone agents by type/name.**"
- `skills/ce-code-review/references/dispatch-reviewers.md:57` — "spawn a generic subagent using the subagent template. **Do not use `subagent_type`, typed `Agent` names, or platform-level CE agent registration.**"
- `skills/ce-compound/SKILL.md:244` — "dispatch a generic subagent using that prompt content. **Do not dispatch a standalone agent by type/name.**"
- `skills/ce-compound/SKILL.md:503` — "dispatch generic subagents seeded with local prompt assets from `references/agents/`. Do not dispatch standalone agents by type/name."
- `README.md:45` and `README.md:65` — "Specialist reviewer and research behavior lives inside the skills as **local prompt assets**; no separate custom-agent install step is required."

`CLAUDE.md:272` reinforces that these files are not agents by forbidding agent-shaped metadata on them: *"These prompt assets must not include YAML frontmatter. Model selection, tool constraints, and dispatch policy belong in the calling skill's `SKILL.md`, not in the prompt asset."* Dispatch policy was **hoisted out of the role definition and into the caller** — that is the architectural move, and the empty-frontmatter rule is how it is enforced.

So the honest description of the layout is: *a skill owns a workflow and carries the prompt text for the subagents that workflow needs, inside its own directory.* "Agent" is a legacy path segment.

### 1.2 Why per-skill nesting rather than a global registry — rationale IS stated, and recorded in a requirements doc

This was recorded, not merely inferred.

**(a) The rule, `CLAUDE.md:276` (identical text at `AGENTS.md:276`):**

> Each skill directory is a self-contained unit. A SKILL.md file must only reference files within its own directory tree (e.g., `references/`, `assets/`, `scripts/`) using relative paths from the skill root. Never reference files outside the skill directory — whether by relative traversal or absolute path.

**(b) The three stated reasons, `CLAUDE.md:286-288`:**

> - **Runtime resolution:** Skills execute from the user's working directory, not the skill directory. Cross-directory paths and absolute paths will not resolve as expected.
> - **Unpredictable install paths:** Plugins installed from the marketplace are cached at versioned paths. […] the version segment changes on every release.
> - **Converter portability:** The CLI copies each skill directory as an isolated unit when converting to other agent platforms. Cross-directory references break because sibling directories are not included in the copy.

The converter reason is real and checkable: `src/converters/` holds seven targets (`claude-to-codex`, `-antigravity`, `-copilot`, `-droid`, `-kiro`, `-opencode`, `-pi`). A skill that reaches outside its own directory cannot be copied as a unit.

**(c) The consequence, made explicit — `CLAUDE.md:290`:**

> If two skills need the same supporting file, **duplicate it into each skill's directory.** Prefer small, self-contained reference files over shared dependencies.

`CLAUDE.md:292` adds a dated caveat that this is a workaround, not a preference: *"**Note (March 2026):** This constraint reflects current Claude Code skill resolution behavior and known path-resolution bugs ([#11011], [#17741], [#12541]). If Anthropic introduces a shared-files mechanism or cross-skill imports in the future, this guidance should be revisited."*

**(d) The migration that produced the layout.** `docs/brainstorms/2026-06-19-agentless-plugin-surface-reduction-requirements.md` is the requirements doc for the change. Its problem frame (`:22-24`):

> The standalone-agent model creates portability and install friction. Codex native plugins load the CE skills, but standalone agent registration has required a second Bun install path that converts Claude Markdown agents to Codex TOML agents. That split is brittle, profile-sensitive, and prevents the Codex plugin from behaving as a normal self-contained plugin.
>
> Other plugin ecosystems, **including Superpowers**, use a cleaner pattern: the skill owns the workflow and carries prompt templates for subagents in its own directory. That gives the skill custom subagent behavior without requiring a platform-level custom-agent registry.

Its decisions (`:28-31`) include: *"Delete standalone CE agents,"* *"**Prefer skill-local duplication over shared agent infrastructure.** Duplicating prompt text across a few skills is acceptable when it removes cross-platform agent registration and makes each skill self-contained,"* and *"Do not preserve compatibility wrappers. This migration intentionally uses maximum deletion."*

Requirements `R1`–`R3` and `R14` (`:142`, `:144`, `:157`) make it testable: *"R1. No surviving CE skill may dispatch a standalone `ce-*` agent by name."* / *"R3. No `plugins/compound-engineering/agents/` directory remains after migration."* / *"R14. Static validation proves there are no surviving CE standalone-agent dependencies."*

The doc also carries the full agent-by-agent disposition table (`:87-138`) — every one of the ~40 pre-migration agents mapped to a destination skill or to Delete. This is the closest thing to a migration ledger, and it is the primary evidence for §6.

**Net:** the rationale is explicit and multi-sourced. The layout is not accidental drift; it is a deliberate trade of DRY for per-skill self-containment, forced by converter portability and skill path-resolution bugs.

### 1.3 The agent-vs-persona distinction is **positional, not contractual**

Two names exist in both trees, which makes this directly testable:

| Name | As agent | As persona |
|---|---|---|
| `data-migration-reviewer` | `skills/ce-plan/references/agents/` | `skills/ce-code-review/references/personas/` |
| `deployment-verification-agent` | `skills/ce-plan/references/agents/` | `skills/ce-code-review/references/personas/` |

Both pairs differ. Diffing `ce-plan/references/agents/data-migration-reviewer.md` against `ce-code-review/references/personas/data-migration-reviewer.md` shows the divergence is entirely about **invocation context**, not about role identity:

- agents copy `:3` — "Evaluate **planned or existing** migration work"; persona copy `:3` — "Evaluate **every migration-related diff**"
- agents copy `:11-13` adds an `## Invocation Contract` section absent from the persona: *"For planning invocations, **do not emit review-style JSON.** Convert migration analysis into plan requirements: expand/contract sequencing, backfill and batching strategy […] and explicit acceptance criteria."*
- The persona copy assumes a PR ("in this PR's diff", `:33`); the agent copy generalizes to "the provided change".

So the working distinction is:

- **persona** — a role the `ce-code-review` (or `ce-doc-review` / `ce-simplify-code`) orchestrator *selects from a catalog* and which must return **schema-valid JSON** against `findings-schema.json`.
- **agent** — a prompt asset a skill seeds a generic subagent with, returning **unstructured prose** for the orchestrator to fold into its own artifact.

The catalog itself corroborates this: `persona-catalog.md:50` heads a section "**CE Conditional Local Prompt Assets** (migration-specific)" whose column is `Prompt asset`, not `Persona` — the repo distinguishes the two even inside the persona directory. And `dispatch-reviewers.md:101,103` confirms the output contract is the discriminator: the "CE generic conditional local prompt assets (`agent-native-reviewer`, `learnings-researcher`)" and "CE conditional local prompt assets (`deployment-verification-agent`)" are dispatched through the same batch but "**Their output is unstructured and synthesized separately in Stage 6**", versus the structured personas that write schema JSON.

**Consequence:** a file's directory tells you its output contract, not its subject matter. `learnings-researcher` and `deployment-verification-agent` sit in `personas/` but behave as agents (prose out). This is a naming inconsistency in the source, and worth knowing before porting on the assumption that "persona" means one thing.

## 2. `ce-compound` — what the Compound phase actually does

`skills/ce-compound/SKILL.md`, 786 lines. Frontmatter `:2-4`: *"Document a recently solved problem as a durable repo learning, or capture project vocabulary in CONCEPTS.md. Use when capturing a learning after work."*

### 2.1 The core loop

**One learning per run** (`:28`) — a hard rule, not a guideline: *"The workflow's grounding, overlap detection, and cross-referencing all assume a single solved problem. When a session produced multiple distinct learnings, run the skill once per learning, sequentially."* The named failure it prevents is drafting-context numbering ("Learning 3") leaking into written docs.

**Two modes**, chosen by the agent and never asked (`:84-90`): Full (default) vs Lightweight (single-pass, no subagents, "ONLY under real context pressure"). The stated reason for not asking is a design principle worth recording verbatim (`:84`):

> `ce-compound` does not ask the user which mode to run or whether to search session history. Both are decisions the agent is better positioned to make: mode depends on context budget the agent can observe, and session-history value is unknowable a priori to *either* party […]. The only interactive prompt in the whole workflow is the Discoverability Check consent, because that one edits a tracked instruction file.

A third axis, **headless** (`:34-45`), is orthogonal: `mode:headless [depth:lightweight|full]`. Headless never edits instruction files and skips Phase 3.

### 2.2 Step by step (Full mode)

| Phase | What happens | Reads | Writes |
|---|---|---|---|
| **0.5** Auto Memory Scan (`:113-132`) | Scans the Claude Code auto-memory block in the system prompt for relevant entries; passes a labeled excerpt to two Phase 1 subagents. Content sourced this way is tagged `(auto memory [claude])` in the final doc. | system prompt | — |
| **1** Research (`:134-302`) | Creates a run dir, then dispatches **3 parallel subagents** + an internal session-history flow. | `references/schema.yaml`, `references/yaml-schema.md`, live glob of `<root>/solutions/` | scratch only |
| — Context Analyzer | Classifies **track** (bug vs knowledge), problem type, component, category dir, filename | schema files | `{run_dir}/context.json` |
| — Solution Extractor | Writes the full doc-body prose | schema | `{run_dir}/solution.md` |
| — Related Docs Finder | Grep-first search of the corpus; scores **overlap** across 5 dimensions | corpus | `{run_dir}/related.json` |
| — Session History | Two-stage probe; synthesis subagent seeded from `references/agents/session-historian.md` | `~/.claude`, `~/.codex`, `~/.cursor`, `~/.pi` session files via bundled scripts | `{run_dir}/session-history.md` |
| **2** Assembly & Write (`:304-356`) | Orchestrator Reads the artifacts back, applies the overlap decision table, assembles, validates frontmatter | run artifacts, `assets/resolution-template.md` | **the solution doc** |
| **2.4** Vocabulary Capture (`:358-378`) | Scans doc + conversation for qualifying domain terms | `references/concepts-vocabulary.md` | **`CONCEPTS.md`** |
| **2.45** Grounding Validation (`:380-398`) | Mechanical claims check + a semantic validator subagent | `references/grounding-validation.md` | fixes to the doc |
| **2.5** Selective Refresh Check (`:400-449`) | Decides whether older docs are now stale; 6 do-invoke and 4 don't-invoke conditions | — | recommendation only |
| **Discoverability** (`:451-493`) | Checks whether AGENTS.md/CLAUDE.md would lead an agent to find the store | `AGENTS.md`/`CLAUDE.md` | **instruction-file edit**, interactive Full only, after consent |
| **3** Optional Enhancement (`:495-511`) | Problem-type-routed review of the *documentation* | `references/agents/{performance-oracle,security-sentinel,data-integrity-guardian}.md` | doc edits only |

### 2.3 Where memory persists — three write targets, one deliverable

`:100-111` is a `<critical_requirement>` block: *"The primary deliverable is ONE file - the final documentation."* Subagents write **only** scratch and "must not touch `docs/`, project instruction files, or any tracked path." The three write-target classes (`:104-106`):

1. **`<root>/solutions/…`** — the primary deliverable, always.
2. **`CONCEPTS.md`** — repo-root domain glossary, created or updated in Phase 2.4.
3. **A project instruction file** (AGENTS.md or CLAUDE.md) — small edit, interactive Full only, after consent.

The scratch-artifact pattern has a recorded empirical cause (`:110`) worth quoting because it is a general lesson about subagent returns:

> **Why the scratch artifact (issue #956):** a subagent asked to return a long prose body as its inline response intermittently returns an executive summary instead ("Doc body complete — six sections filled. Returning above."), and the original prose is then unrecoverable from the orchestrator side. Writing to disk first means the full output always survives; the inline confirmation is just a pointer.

**The corpus layout.** `<root>/solutions/<category>/<slug>.md`, with 9 bug-track categories (`build-errors/`, `test-failures/`, `runtime-errors/`, `performance-issues/`, `database-issues/`, `security-issues/`, `ui-bugs/`, `integration-issues/`, `logic-errors/`) and 8 knowledge-track (`architecture-patterns/`, `design-patterns/`, `tooling-decisions/`, `conventions/`, `workflow-issues/`, `developer-experience/`, `documentation-gaps/`, `best-practices/` — the last explicitly "fallback only") (`:599-620`). Each doc carries YAML frontmatter validated against `references/schema.yaml`.

**The overlap decision table** (`:315-321`) is the anti-duplication mechanism — High overlap (4-5 of 5 dimensions) means *update the existing doc*, not create a second one, with the stated reason: *"two docs describing the same problem and solution will inevitably drift apart."*

**Grounding is enforced twice.** Phase 1's Solution Extractor is told (`:190`) to *"Read the defining line at the current tree and cite `file:line` alongside the claim. A claim that cannot be verified against the tree is softened or attributed […] never stated as fact"*, and (`:191`) to *"Cite PR numbers rather than bare commit SHAs — SHAs are rewritten by rebase/squash merges."* Phase 2.45 then re-checks mechanically (`scripts/validate-doc-claims.py`: cited paths, commit SHAs, relative links, dangling drafting scaffold) and semantically (a read-only subagent that must quote the defining source line). The mechanical check's flags are **adjudicated, not auto-fixed** (`:396`): *"A doc may legitimately cite a path deleted by the very fix it documents; a flag is a question, not a failure."*

### 2.4 Could this run against a `.planning/` directory?

**Yes for the primary artifact; no for two of the three write targets.** The artifact root is configurable through a marked block at `skills/ce-compound/SKILL.md:74-80`:

> **Read** `docs_root` from `<repo-root>/.compound-engineering/config.local.yaml`, then `config.yaml`; first non-empty value wins […]. Unset -> `<root>` is `docs`, exactly as before.
> **Validate** a set value: a repo-relative directory whose real, symlink-resolved path stays inside the repo and is neither the repo root nor under `.git/`. Otherwise stop with an error naming `docs_root` and the value -- never fall back to `docs`.

`.planning` satisfies every validation clause (repo-relative, inside repo, not the root, not under `.git/`), so learnings would land at `.planning/solutions/<category>/<slug>.md`.

**The precise caveat:** `CONCEPTS.md` is written at **repo root**, not under `<root>` (`:105`, `:362`, and the bootstrap preamble at `:372`), and the Discoverability Check targets `AGENTS.md`/`CLAUDE.md` at repo root (`:455`). Neither is redirectable by `docs_root`. So the accurate statement is: *the learning corpus is redirectable to `.planning/solutions/`; the glossary and the instruction-file edit are root-anchored and not configurable.*

Two further couplings that survive redirection: the session-history probe reads from `~/.claude/projects/`, `~/.codex/sessions/`, `~/.cursor/projects/`, `~/.pi/agent/sessions/` (host-level, outside any repo), and `docs-root-literals.test.ts` / `docs-root-rule-parity.test.ts` exist to keep the `<root>` block byte-identical across consuming skills — meaning the block is a shared asset in the *guarded* duplication regime (§1.4), unlike the role prompts.

## 3. `session-historian` — what it produces

`skills/ce-compound/references/agents/session-historian.md`, 84 lines. Sole copy in the tree; **it is under `ce-compound`** — prior recon confirmed.

It is a **synthesis-only** prompt asset (`:5`): *"Your scope is **synthesis only**. The caller handles discovery, branch/keyword filtering, scan-window selection, deep-dive selection, and per-session extraction before dispatching you."* The heavy lifting lives in `skills/ce-compound/scripts/session-history/` — `discover-sessions.sh`, `extract-metadata.py`, `extract-skeleton.py`, `extract-errors.py` — which the orchestrator runs itself before dispatch.

**Input contract** (`:9-21`): `problem_topic` (one sentence), `scratch_dir`, a `sessions` array of **at most 5** pre-extracted sessions each carrying `path`, optional `errors_path`, `platform` (`claude`|`codex`|`cursor`|`pi`), `branch`, `cwd`, `ts`/`last_ts`, `match_count`/`keyword_matches`, and an optional `output_schema` to honor verbatim.

**Output** (`:58-77`): text only, never files. A one-line provenance header — `**Sessions read**: [count] ([N] Claude Code, [N] Codex, [N] Cursor, [N] Pi) | [date range]` — then prose under four headings, omitting any with no findings:

```
- What was tried before
- What didn't work
- Key decisions
- Related context
```

If nothing relevant: the literal string `no relevant prior sessions`.

**What it looks for** (`:46-54`): investigation journey (what failed and why), **user corrections** (*"Moments where the user redirected the approach. These reveal what NOT to do and why"*), decisions and rationale, error patterns, evolution across sessions, **cross-tool blind spots** (duplicated effort across Claude Code and Codex days apart; gaps neither touched), and **staleness** (*"Older sessions may reflect conclusions about code that has since changed […] Caveat older findings rather than presenting them with the same confidence as recent ones"*).

**Guardrails worth noting** (`:31-38`): read only the orchestrator-supplied scratch paths, never the MB-scale source session files; **never invoke the Skill tool** — *"This agent runs in subagent context where Skill calls deadlock"*; never reproduce tool-call inputs/outputs verbatim; never surface thinking/reasoning blocks; never analyze the current session; *"Surface technical content, not personal content. Sessions contain everything — credentials, frustration, half-formed opinions."*

**Standalone fallback** (`:25`): dispatched without a `sessions` array it returns `no relevant prior sessions` and stops — *"direct dispatch without an orchestrator is not a supported pattern."* There is no standalone session-history product surface; `SKILL.md:94` states it explicitly. The former `ce-sessions` skill was deleted and folded in (migration doc `:47`).

| Conditional (`:27-39`) | 7 | `security`, `performance`, `api-contract`, `data-migration`, `reliability`, `adversarial`, `previous-comments` |

The 16th file is `deployment-verification-agent.md`, which the catalog places in a separate section (`:50-56`) headed "**CE Conditional Local Prompt Assets** (migration-specific)" with the column header `Prompt asset` — explicitly not a persona (§1.3).

### 5.2 Selection is agent judgment over the diff, and it is fail-closed in one place

The catalog says so directly (`:29`): *"Spawned when the orchestrator identifies relevant patterns in the diff. The orchestrator reads the full diff and reasons about selection -- **this is agent judgment, not keyword matching.**"* Repeated at `:62`: *"read the diff and decide whether its domain is relevant. This is a judgment call, not a keyword match."*

The **seven selection rules** (`:58-66`):

1. *"**Always spawn correctness.** Spawn project-standards only for a non-empty applicable standards path list; **skip it on a successful empty search and fail closed by spawning it when discovery is uncertain.**"*
2. *"**For each generic conditional**, require its explicit surface. […] **Absence means skip, not "run just in case."**"*
3. Cross-cutting conditionals: read the diff, judge relevance.
4. Stack-specific: file types are a *starting point*, then judge — *"**Do not spawn language-specific reviewers just because one config or generated file happens to match the extension.**"*
5. `data-migration` requires actual migration/schema artifacts — *"Do **not** spawn for model-only or query-only changes without those files."*
6. `deployment-verification-agent` only when the migration gate applies **and** the change is risky.
7. *"**Announce the team** before spawning with a one-line justification per conditional reviewer selected."*

**The anti-over-spawn rules are written as negations of specific failure modes**, which is the notable design property — each gate names the tempting-but-wrong trigger and forbids it:

- `testing` (`:22`): *"Production-file presence alone and non-behavioral edits do not select it."*
- `maintainability` (`:23`): requires "at least 200 executable changed lines" or genuinely structural work.
- `performance` (`:34`): *"Async/concurrent code or a cache data structure alone does not select it when correctness/reliability already own the changed semantics."*
- `api-contract` (`:35`): *"A new or changed exported symbol inside one module is insufficient by itself."* — requires "evidenced downstream callers."
- `learnings` (`:25`): *"Run a cheap search first; **corpus existence alone does not select it.**"*
- `previous-comments` (`:39`): *"**PR-only AND comment-gated.** […] Skip entirely when no PR metadata was gathered in Stage 1, OR when Stage 1's `hasPriorComments` flag is false."*

**Fail-closed** appears exactly once, on `project-standards` (rule 1, and `SKILL.md:147`): a *successful empty search* is a disclosed skip, but *uncertain discovery* spawns the reviewer anyway. The asymmetry is deliberate — `SKILL.md:147` gives the reason: *"this persona is not allowed to invent standards beyond those files."*

### 5.3 The surrounding stage machine

Selection is Stage 3 of a ten-ish-stage spine in `skills/ce-code-review/SKILL.md` (555 lines). The stages that bear on dispatch:

- **Stage 1** (`:213`) — determine scope; three modes: `local-aligned`, `pr-remote`, `branch-remote`. Gathers PR metadata and the `hasPriorComments` flag.
- **Stage 1b** (`:319`) — *"Compute scope signals (cheap, deterministic)"* via `scripts/review-scope.py`. Returns `exec_lines`, `uncounted_files`, `lite_eligible`, and path signals. Critically (`:337`): *"`signals` are path heuristics, **not selection decisions** […] Use `test_files_changed`, `agent_surface`, and `has_learnings_corpus` as inputs to the generic reviewer gates, **not as automatic spawn decisions.**"* — the deterministic helper *informs* judgment; it does not replace it.
- **Stage 2** (`:339`) — intent discovery. `:360`: *"Intent shapes **how hard each reviewer looks**, not which reviewers are selected."*
- **Stage 2b** (`:364`) — plan discovery, extracting `R`-IDs and implementation units for Stage 6 requirements verification. Settlement annotations from the plan are **orchestrator-only**: `:380` — *"exclude them from the Stage 2 intent summary and from every reviewer bundle […] **Reviewer independence is the point:** lenses must stay free to re-derive the rejected alternative on the merits."*
- **Stage 3** (`:388`) — read the diff, read the catalog, select.
- **Stage 3b** (`:411`) — discover project standards paths.
- **Stage 3c** (`:424`) — small-diff lite path. Four AND-ed conditions (`:430-433`): `lite_eligible` (1-39 executable changed lines, zero uncounted files, no path signals), **and** no content-based risk read from the diff (auth, payments, data mutation, external API, secrets/permissions, deserialization, crypto, concurrency, filesystem/process execution), **and** standards discovery completed successfully, **and** no conditional persona other than `project-standards` selected. Lite roster = fast pass + `correctness` (+ `project-standards` if applicable). `depth:full` hard-disables the gate.
- **Stage 3d** (`:441`) — bind the adversarial route and final roster.
- **Stage 4** (`dispatch-reviewers.md`) — inline fast pass, then bounded foreground concurrent batch.
- **Stage 5 / 5b / 5c** — merge, validate, optionally apply.

**Model tiering** (`dispatch-reviewers.md:24-28`) is a per-persona property, not per-run: *"Three reviewers inherit the session model with no override: `correctness-reviewer`, `security-reviewer`, and `adversarial-reviewer`. These perform the highest-stakes analysis […] If the user is on Opus, these get Opus. All other persona subagents and CE local prompt assets use the platform's mid-tier model."* `:42` calls the override *"a correctness guarantee, not cosmetics."*

**The independence rule** is the spine of the whole design (`dispatch-reviewers.md:49`): *"Reviewers are independent by construction (none is fed another's output)."* The **inline fast pass** (`:3-22`) — the orchestrator's own quick scan — is explicitly *not* an independent reviewer and is penalized for it (`:11-16`): capped at anchor 50, *"never counts toward cross-reviewer promotion,"* and *"Do not feed `fast-pass` candidates into the persona or validator prompts — those agents review the raw diff independently, and seeding them would **manufacture the false agreement this cap exists to prevent.**"*

**The `adversarial` dispatch rule** (catalog `:38`, recorded as architecture only — the capability is t6b's): the lens runs through the detached cross-model peer when a sanctioned peer starts; the in-process `adversarial-reviewer` persona is spawned **only when the peer cannot start**. *"A started peer and the fallback are mutually exclusive."* `dispatch-reviewers.md:109` adds that the peer's findings enter ordinary synthesis but *"agreement promotion requires top-level `independence_verified: true`; false or absent independence is useful evidence, not different-model corroboration,"* and that Coverage must state which route ran.

### 5.4 Difference from a fixed panel, stated precisely

Signal runs a fixed 3-specialist panel (`code-reviewer`, `security-auditor`, `test-engineer`) on every REVIEW. The upstream shape differs on five independent axes:

| Axis | Fixed panel | compound-engineering |
|---|---|---|
| **Roster size** | Constant 3 | Variable 2–16; floor is 2 (`correctness` + fast pass) via Stage 3c lite, ceiling is the full catalog |
| **Selection input** | The phase | The diff — read in full, reasoned over |
| **Selection mechanism** | Static list | Agent judgment against per-persona gates that name their own false-trigger |
| **Default on absence** | N/A (always runs) | **Skip.** *"Absence means skip, not 'run just in case'"* (`:61`) |
| **Failure direction** | N/A | Fail-**closed** on exactly one persona (`project-standards`, on uncertain discovery); every other gate fails open (skip) |

The direction of the difference is the point: a fixed panel spends a constant budget and accepts that 2 of 3 lenses may have no surface in a given diff; the conditional model spends variable budget and accepts that a lens whose surface the orchestrator misjudged never runs at all. The catalog's anti-over-spawn language shows which error the source decided to optimize against — it is written almost entirely to suppress *spurious* spawns, not to catch missed ones.

## 6. The narrowing away from stack-philosophy personas

### 6.1 The limiting language, quoted

`persona-catalog.md:41-43`, heading the Stack-Specific tier:

> ## Stack-Specific Conditional (2 personas)
>
> These reviewers cover specialized runtime behavior. **Structural and maintainability concerns live in the conditional `maintainability` persona — do not spawn extra stack reviewers for philosophy or convention-only passes.**

Reinforced by selection rule 4 (`:63`):

> **For each stack-specific conditional persona**, use file types and changed patterns as a starting point, then decide whether the diff actually introduces meaningful work for that reviewer. **Do not spawn language-specific reviewers just because one config or generated file happens to match the extension.**

Two constraints are doing separate work here: a **cap** (the tier is titled "2 personas" and contains exactly 2), and a **scope restriction** (runtime behavior only — philosophy and conventions are routed to `maintainability`).

### 6.2 Correction to prior recon: named personas are not gone

Prior recon recorded *"Named language-style agents (DHH Rails etc.) are GONE."* That is too strong. **`julik-frontend-races-reviewer`** (`persona-catalog.md:47`, `references/personas/julik-frontend-races-reviewer.md`, 3,684 bytes) is a surviving named-person persona, selected when the diff touches *"Stimulus/Turbo controllers, DOM event wiring, timers, async UI flows, animations, or frontend state transitions with race potential."*

The distinction that actually held is **behavior vs. philosophy**, not named vs. unnamed. A named persona scoped to a concrete failure class (frontend race conditions) survived; a named persona scoped to a style philosophy did not.

### 6.3 What was removed, and whether a rationale is recorded

The DHH artifacts are gone from `skills/` and appear only in the cleanup registries:

- `src/utils/legacy-cleanup.ts:65` `"dhh-rails-style"`, `:102` `"ce-dhh-rails-style"`, `:185` `"ce-dhh-rails-reviewer"`, `:202` `"dhh-rails-reviewer"`
- `src/data/plugin-legacy-artifacts.ts:52` `"ce-dhh-rails-style"`, `:86` `"dhh-rails-style"`

The registries preserve their descriptions, which is how we know what was cut. `legacy-cleanup.ts:643` (the reviewer): *"Conditional code-review persona, selected when Rails diffs introduce architectural choices, abstractions, or frontend patterns that may fight the framework. **Reviews code from an opinionated DHH perspective.**"* And `:516` (the skill): *"…Embodies REST purity, fat models, thin controllers, Current attributes, Hotwire patterns, and the \"clarity over cleverness\" philosophy."*

**Is a rationale recorded?** Partly — and the honest answer has two halves.

**Recorded:** the *skill* `ce-dhh-rails-style` was deleted under a stated principle. `docs/brainstorms/2026-06-19-agentless-plugin-surface-reduction-requirements.md:11` — *"**Public skills should represent user-facing jobs, not convenience wrappers around specialist agents.**"* — and `:29` — *"**Delete redundant public skills.** Public skills must map to real user jobs. Skills that only make an agent easy to call should be removed."* Its Delete-table row (`:42`) reads simply `ce-dhh-rails-style | Delete.` with no per-item reason; the section-level principle is the rationale.

**Could not verify:** a per-item, written justification for retiring the `dhh-rails-reviewer` *persona* specifically. It does not appear in the migration doc's agent Delete table (`:131-138`), which lists only four agents — `ce-ankane-readme-writer` (*"No runtime consumer"*), `ce-design-implementation-reviewer` (*"No runtime consumer"*), `ce-design-iterator`, and `ce-code-simplicity-reviewer` — and DHH is not among them. Nor is it in the Preserve table. Its absence from *both* tables of the June 2026 migration doc implies it was already gone before that migration; the deepened 550-commit history did not surface the removing commit, and I did not find a separate doc for it. **The catalog line at `:43` is a rule without an attached "why."**

### 6.4 The design lesson, stated as the source's own

Read as a lesson rather than a removal, the shape is: **a review lens earns a slot by naming a failure mode it can find, not by holding a point of view.** Three pieces of evidence converge on it —

- philosophy passes are explicitly forbidden a spawn (`:43`),
- structural/convention opinions were consolidated into one generic `maintainability` persona rather than distributed across per-stack opinionated reviewers,
- the two surviving stack personas are both scoped to concrete runtime failure classes (frontend races; Swift/iOS entitlements, privacy manifests, code-signing) rather than to idiom.

**The following paragraph is my inference, not the source's stated reasoning** — §6.3 records that no written rationale for retiring the DHH persona was found, and this is a candidate explanation, not a recovered one. The confidence machinery in §7 gates a finding on quoting the verbatim line that makes it true. An opinionated reviewer's output cannot clear that gate: "this fights the framework" has no single triggering line to quote, so such findings would cap at anchor 50 and be suppressed before reaching a user. A lens scoped to a failure mode can satisfy the quote-the-line gate; a lens scoped to a philosophy structurally cannot. The two changes are compatible in that direction, but the source nowhere connects them.

## 7. The machine-checkable findings contract

### 7.1 `findings-schema.json` — the reviewer output contract

`skills/ce-code-review/references/findings-schema.json`, 101 lines, JSON Schema draft-07, titled "Code Review Findings".

Top level requires `reviewer`, `findings`, `residual_risks`, `testing_gaps`. Each finding requires **eleven** fields: `title`, `severity`, `file`, `line`, `why_it_matters`, `autofix_class`, `owner`, `requires_verification`, `confidence`, `evidence`, `pre_existing`.

The fields that carry the design:

- **`severity`** — enum `P0|P1|P2|P3`. Answers *urgency* only (`SKILL.md:126`).
- **`confidence`** — enum **`[0, 25, 50, 75, 100]`**, not a free integer. Each anchor carries a behavioral criterion the reviewer must self-apply (`:75`): 0 = *"a false positive that does not stand up to light scrutiny, or a pre-existing issue this PR did not introduce"*; 25 = *"could also be a false positive; the reviewer could not verify from the diff and surrounding code alone"*; 50 = *"a real issue but it may be a nitpick […] Style preferences and subjective improvements land here"*; 75 = *"double-checked […] will affect users, downstream callers, or runtime behavior in normal usage"*; 100 = *"verifiable from the code itself -- compile error, type mismatch, definitive logic bug, or an explicit project-standards violation with a quotable rule. No interpretation required."*
- **`evidence`** — array, `minItems: 1`, and the home of the **quote-the-line gate** (`:79`): *"For any finding at confidence anchor 75 or 100, the first item MUST be the verbatim motivating line(s) with file:line -- the exact code text that makes the finding true. **A finding whose triggering line cannot be quoted must step down to anchor 50.**"* Plus a provenance rule: when the claim depends on line history, add one concise `git blame`/`log` line — *"never replace the quote-the-line item, never dump full-file blame."*
- **`autofix_class`** — enum `gated_auto|manual|advisory`. Explicitly *"Routing hint for the caller after review (**this skill does not apply fixes**)."*
- **`owner`** — enum `downstream-resolver|human|release`.
- **`pre_existing`** — *"True if this issue exists in unchanged code unrelated to the current diff."*
- **`suggested_fix`** — optional, and carries the longest description in the schema (`:70`), aimed at one named failure: *"'I need &lt;specific input&gt; to commit' is a **soft punt**: the right question is 'what code change would I propose if I had to choose now?' […] A bad suggestion is still worse than none, but a soft punt is the failure mode this field is designed to prevent."*

A **two-tier return** splits cost from completeness (`dispatch-reviewers.md:72-99`): each reviewer writes *full* JSON to `{run_dir}/{reviewer_name}.json` and returns only merge-tier fields inline. So `evidence` — required by the schema — lives in the **artifact only**; the compact return carries `first_evidence` in its place, the one detail-tier field promoted inline because *"mandatory for every finding at anchor 75 or 100 (the gate is unenforceable without it in-band)."* The failure this shape courts is named at `:99`: writing the compact shape to the artifact is *"a common reviewer slip"* that *"silently strips the detail Coverage and the keyed detail lines depend on"* — the artifact must be the fat one, the return the thin one, and reviewers get it backwards.

**The `ce-doc-review` sibling is a different contract, not a copy.** `skills/ce-doc-review/references/findings-schema.json` (85 lines, titled "Document Review Findings") keeps the same `severity` and `confidence` enums but swaps the location and routing fields: it drops `file`, `line`, `owner`, `pre_existing`, `requires_verification` and adds **`finding_type`** and **`section`**. Same grammar of severity + anchored confidence, different nouns — appropriate, since a document finding has a section rather than a line.

### 7.2 `findings-mechanics.py` — the deterministic merge

`skills/ce-code-review/scripts/findings-mechanics.py`, 252 lines, Python 3 stdlib only. Docstring (`:2`): *"Apply deterministic validation, exact dedup, confidence gates, and numbering."* Reads an array of reviewer returns on stdin, writes one JSON object on stdout.

What it enforces mechanically, in order:

1. **Validation** (`:35-64`). Malformed returns and malformed findings are *counted and dropped*, not repaired — the output carries `malformed_returns` and `malformed_findings` so the loss is visible rather than silent.
2. **The fast-pass cap** (`:165-166`): `if reviewer == "fast-pass": finding["confidence"] = min(finding["confidence"], 50)`. The prose rule from `dispatch-reviewers.md:13` is enforced in code, not left to the orchestrator.
3. **Exact dedup by fingerprint** (`:67-72`): `(file.lower(), str(line), normalized-whitespace title.lower())`. Deliberately exact — semantic dedup is the orchestrator's job downstream.
4. **Independence** (`:75-80`) — the mechanism that makes corroboration meaningful:
   ```python
   def independent_reviewer(name, source):
       if name == "fast-pass":
           return False
       if name.startswith("adversarial-"):
           return source.get("independence_verified") is True
       return True
   ```
   The orchestrator's own read never counts as a corroborating voice, and a cross-model peer counts only on a verified independence flag.
5. **Promotion on agreement** (`:83-84`, `:124-125`): `{50: 75, 75: 100, 100: 100}`, applied only when `len(independent) >= 2 and has_first_evidence`. Two independent reviewers hitting the same fingerprint bump the anchor one notch — but **only if the quote-the-line evidence survived the merge**.
6. **The gate re-applied at merge** (`:121-123`): `if confidence >= 75 and not has_first_evidence: confidence = 50`. A finding cannot arrive at the actionable tier without its verbatim line, even if the reviewer claimed the anchor.
7. **Conservative field merge** (`:104-118`): `autofix_class` and `owner` take the *higher* enum index; `requires_verification` ORs; `pre_existing` is `all(...)` — with a comment (`:91-92`) explaining that *"A current-diff classification wins a disagreement so an exact duplicate cannot disappear merely because the pre-existing reviewer arrived first."*
8. **Suppression** (`:197-209`) — the surface gate:
   ```python
   if finding["pre_existing"]: → pre_existing bucket
   if confidence < 75 and severity != "P0" and not settled_conflict: → suppressed bucket
   else: → survivors
   ```
   Anything below anchor 75 is suppressed unless it is a P0 or flags a conflict with a settled decision. Nothing is discarded: the output object carries `findings`, `suppressed_findings`, `pre_existing_findings`, `residual_risks`, `testing_gaps`, and a `suppressed_by_confidence` histogram.
9. **Deterministic sort and numbering** (`:211-230`): `(severity, -confidence, file.lower(), line, title.lower())`, then stable `#` numbers assigned to survivors only — so finding numbers do not depend on which reviewer returned first.

**What the contract amounts to.** Severity and confidence are decoupled and separately anchored; confidence must be *earned* by quoting a line; agreement between *independent* reviewers is the only thing that raises it; the orchestrator's own read is structurally barred from being that agreement; and the whole reduction is a deterministic script rather than a synthesis prompt. `tests/ce-code-review-mechanics.test.ts` covers it.
