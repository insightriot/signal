# M6.E5 — Requirements

**Epic goal:** `/sig:permissions` proposes an intentional permission set for this project, and the
user installs it. Signal supplies legibility; authority stays where the platform put it.

Scoped by `D-BR0826-1` (2026-08-26) from `analysis/PERMISSIONS-SPIKE.md`. The spike's three
rules-out are load-bearing and are **not** re-litigated here: no Signal permission *model* (not
available to plugins, and a prose one is `B75`), no Signal consent vocabulary (the platform ships
`default` / an `allow` rule / `dontAsk`), and no configurable read-only stance for the scanners
(it converts a hard stop into a suggestion while reading as a control).

## S1 — The candidate set: derived, then classified

**The shape:** derivation supplies candidates so nothing is missed and the set cannot silently fall
out of date; a committed classification decides what may be proposed. Neither half works alone —
derivation alone proposes `rm`, and a hand-written table alone is `light`-vs-`strict`, the remedy
`B75` measured the ceiling on.

### FR1.1 — A deterministic scan of what the flow prescribes

A JS module walks the plugin payload and returns every prescribed command invocation with its
source file, reading the **prompt layer** (backticked strings in `commands/`, `agents/`, `skills/`,
`references/`) and the **deterministic layer** (`execFileSync` / `exec` call sites in `tools/` and
`hooks/`) as two separately-labelled sources.

- **AC1.1a** — Given this repository, the scan returns at least the pairs measured above, each
  carrying the file and line that prescribed it.
- **AC1.1b** — The two layers are distinguishable on the record. A rule traceable to an
  `execFileSync` call site is a stronger claim than one traceable to prose, and the report says
  which it is.
- **AC1.1c** — An unreadable or absent payload directory renders **`cannot-check`**, never an empty
  clean result (`B39`).
- **AC1.1d** — The scan reads the payload **from disk**, not from a committed list of files.

### FR1.2 — A committed classification, enforced by a whole-population test

Every binary the scan can return carries one of three verdicts: `propose-allow`, `propose-deny`,
`never-propose`.

- **AC1.2a** — `rm` is classified `never-propose`. A proposed allowlist containing `Bash(rm *)`
  fails the suite.
- **AC1.2b** — `git reset`, `git rebase`, `git revert` and `git push --force` are **not**
  `propose-allow`. History-rewriting and working-tree-destroying operations are the user's to grant
  deliberately.
- **AC1.2c** — **A binary the scan returns that the classification does not know fails the test
  suite.** The test reads the scan's live output rather than a fixture list, so a new command file
  prescribing a new tool cannot ship unclassified. This is the whole-population assertion
  `v0.1.30` used for the scanner corpus, applied here.
- **AC1.2d** — The classification lives in one place and is read by both the generator and the
  test. Two copies is `B82`.

## S2 — Read the current state, propose a delta

**Why this is not optional:** a generator that ignores installed rules re-proposes rules the user
already has. On this repo that is 43 lines of noise around whatever is new.

### FR2.1 — Read all readable settings scopes

- **AC2.1a** — The user scope (`~/.claude/settings.json`), the project scope
  (`.claude/settings.json`) and the local scope (`.claude/settings.local.json`) are each read if
  present.
- **AC2.1b** — A scope that is absent is reported as **absent**; a scope that is present but
  unreadable or malformed is reported as **`cannot-check`**. Neither renders as "no rules"
  (`B39`).
- **AC2.1c** — The proposal is a **delta**: a rule already granted in any readable scope is not
  re-proposed, and the report states how many were suppressed for that reason.

### FR2.2 — State plainly that the read is an approximation

- **AC2.2a** — The report carries a stated limit, in the output and not only in the docs: the
  rules read here are **not the effective permission set**. `PreToolUse` hooks can block a call
  every rule allows; managed/enterprise and CLI-flag scopes are not read; precedence across five
  scopes means a local read approximates.
- **AC2.2b** — The limit renders whenever the read renders. It is not a footnote in a reference
  file that the output points at.

## S3 — The host project's stack

**Decided 2026-08-26 against the DISCUSS recommendation.** Flow-only was recommended on the grounds
that stack mentions in the corpus are contamination; the answer was flow **plus** detected stack,
on the grounds that stopping the prompts a user actually hits is the argument the whole decision
rests on. Recorded as `D-M6E5-3` with the cost that was accepted.

### FR3.1 — A small deterministic manifest reader

- **AC3.1a** — Detection reads manifests: `package.json`, `pyproject.toml`, `setup.py`,
  `Cargo.toml`, `go.mod`, `Gemfile`, `composer.json`. File presence plus shallow parse; no agent is
  spawned and no command is executed to detect anything.
- **AC3.1b** — For a Node project, proposed scripts are read from `package.json`'s `scripts` keys —
  so `Bash(npm run <script>:*)` is proposed for scripts that **exist**, not for a guessed set.
- **AC3.1c** — A project with no recognised manifest yields **no stack rules** and says so. It does
  not fall back to a default stack.
- **AC3.1d** — Stack-derived rules are labelled as such in the report, separately from flow-derived
  rules, so the user can install one half and refuse the other.

### FR3.2 — Name what this reader is, and is not

- **AC3.2a** — ⚠ **This is a new detector, not a reuse.** `/sig:init`'s four scanners are agent
  prose holding `Bash`; there is no deterministic stack-detection function in `plugin/tools/lib/`
  to call. Claiming reuse would be false. Claiming it is therefore `B82`'s duplicate-implementation
  shape would also be false — `B82` was two implementations of one rule, and here there is one.
- **AC3.2b** — The overlap with the scanners is **recorded as a real future hazard**: if a
  deterministic detector is ever wanted by `/sig:init` too, this module is the one to extend, not
  the second one to write.

## S4 — The deny proposal: small, conservative, obvious

**In scope per `D-BR0826-1`:** 43 allow rules and zero deny rules is a protective half that is empty
**by construction**, because *"yes, and don't ask again"* only ever teaches the system to say yes.

### FR4.1 — A short proposed deny list

- **AC4.1a** — The proposed deny set is small enough to read in one screen and every entry names
  why it is there.
- **AC4.1b** — ⚠ **Deny is absolute and cannot carry exceptions** — a broad deny beats a narrower
  allow. The report states this at the deny list, because a rule that is slightly too broad is a
  work stoppage with a confusing message rather than a prompt.
- **AC4.1c** — Deny rules are proposed, never installed, on exactly the same footing as allow rules.
- **AC4.1d** — The report states that no `defaultMode` is set and what the three modes are, by
  their platform names. It proposes no fourth name (`B75`).

## S5 — The output: a report and a tracked artifact

### FR5.1 — `/sig:permissions` is dry-run by default and never writes a settings file

- **AC5.1a** — No code path in the command writes to any file under `.claude/` or `~/.claude/`.
- **AC5.1b** — The command names the install route in its output and does not perform it. The
  `update-config` skill is named as the route the spike confirmed by experiment; the command does
  not invoke it.
- **AC5.1c** — The report renders when nothing is proposable, saying so, rather than rendering
  nothing.

### FR5.2 — The proposal is written to a tracked artifact

- **AC5.2a** — The proposal is written to `.planning/PERMISSIONS.md` — a reviewable report with the
  installable rules in a fenced JSON block. Same shape as `ENVIRONMENT.md` (*what an agent can't
  see*) with *what an agent may do* alongside it, which is the pairing the spike named.
- **AC5.2b** — **The recommended install target is `.claude/settings.json`, the tracked project
  scope — not `.claude/settings.local.json`.** The report says why: the local file is gitignored, so
  a rule installed there cannot be shared, committed, or carried to another machine, and every repo
  on every machine re-accumulates its own from empty.
- **AC5.2c** — Writing `.planning/PERMISSIONS.md` is idempotent — an unchanged proposal does not
  rewrite the file (`/sig:index`'s contract).
- **AC5.2d** — Nothing downstream consumes `.planning/PERMISSIONS.md`. No phase command reads it,
  gates on it, or fails without it. It is a document for a person.

### FR5.3 — A repository with no `.planning/` still gets an answer

⚠ **Raised because the scope argument and the deliverable do not currently line up.**
`D-BR0826-1` rests on `O(repos × machines)` — *"every repo on every machine starts empty and
re-accumulates its own."* A command whose only output lands in `.planning/` reaches
**Signal-initialized repos**, which is a strictly smaller set than *every repo*. Left implicit,
that is the completeness-claim class this same document warns about twice.

- **AC5.3a** — In a repository with no `.planning/`, the command still runs and still prints the
  full report. The flow-derived half needs only the plugin payload; the stack-derived half needs
  only the host manifests. Neither requires `.planning/`.
- **AC5.3b** — In that case the tracked-artifact step is **reported as skipped with its reason**
  (*no `.planning/` to write to*), not silently omitted, and the report names the install target
  anyway.
- **AC5.3c** — The command does **not** create `.planning/`. Creating project scaffolding is
  `/sig:new-project` and `/sig:init`; a permissions report that quietly initializes a project is a
  side effect nobody asked for.
- **AC5.3d** — ⚠ **Reach is stated in the docs, not implied.** The report reaches any repository;
  the *tracked artifact* reaches Signal projects only. Saying so is `M6.E2`'s rule — publish the
  reach next to the capability.

## Non-functional requirements (FEATURE tier)

The FEATURE NFR set — error handling at boundaries, log lines for failures, basic input validation.
The FULL set (health probes, graceful shutdown, structured request logging, security headers, rate
limiting) is **N/A and not asked**: this is a local read-only CLI report, not a service. Recording
that as five `N/A` lines is the present-but-vacuous failure `M5.E10` shipped a check against.

- **NFR1** — Every file read is wrapped. A malformed settings file, an absent directory, or a
  permission error on the read itself renders `cannot-check` for that scope and the report
  continues. The command never dies on one unreadable input.
- **NFR2** — Every failure is visible in the report, not only in a log. A scope that could not be
  read is a line the user sees.
- **NFR3** — Input validation: the only user input is flags. An unrecognised flag is rejected with
  the valid set named, rather than ignored.
- **NFR4** — Offline and deterministic. No network call. Two runs on an unchanged tree produce
  byte-identical output.

## Blast radius — what this touches that we are not changing

- **The published command count.** Signal ships **21** commands; this makes 22. `CLAUDE.md`,
  `README`, `references/command-taxonomy.md` and `/sig:doctor`'s roster check all carry or derive
  that number, and `M6.E2`'s published-fact checks fire on exactly this. The count must be updated
  everywhere it is stated, and the new command placed in a taxonomy group.
- **A new coupling from the payload to a generator.** The scan reads `commands/`, `agents/`,
  `skills/` and `references/` from disk, so **adding, renaming, or rewording any command file can
  change this command's output**. No such coupling exists today. `AC1.2c` is what keeps it honest:
  a new binary fails the suite rather than silently entering a proposal.
- **`.planning/`**, which gains a file. It is tracked (and, since `M6.E1`, no longer copied into
  users' plugin caches).
- **Not touched:** the four `/sig:init` scanners and their hard-coded read-only stance, which
  `D-BR0826-1` rules out changing; any phase command's behaviour; `PROFILE.md`'s schema.

## Outcome

**How we will know this worked.**

**The metric exists, and it is available at SHIP rather than months later.** `D-BR0826-1` finding 2
is that hand-cleaning the rules *wrote the generator's target output by hand*: the 43 surviving
rules are a human-curated ground truth for what this flow actually needs.

**So: run the generator against this repository and compare its flow-derived proposal to those 43
hand-cleaned rules.** It works if it substantially reproduces the flow-relevant subset a person
arrived at independently. Two failure directions, both diagnostic and both worth publishing rather
than tuning away:

- **Under-proposes** — rules the human kept that the generator misses. Each one is either a real
  gap in the scan or evidence that the rule was never about the flow.
- **Over-proposes** — rules the generator emits that the human deleted. Each one is a
  classification the committed table got wrong.

⚠ **The number is published, not targeted.** A generator tuned until it matches 43/43 has been
fitted to one machine's history, which is the opposite of the point. The honest deliverable is the
comparison with both directions itemised.

## What this explicitly does NOT unblock

⚠ Stated because three separate documents flag that a plan will want to claim it. Shipping this
Epic does **not** unblock the readiness scorecard's **agent-executability dimension**, and does not
unblock the **environment-readiness baseline**. Both are blocked on *being permitted to run things*
— an act a person performs in a file Signal cannot write. This command makes that act easier to
perform correctly; it does not perform it. Any later artifact asserting otherwise is a completeness
claim written from the shape of the work rather than from the artifact.
