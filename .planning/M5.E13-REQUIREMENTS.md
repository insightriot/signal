# M5.E13 — Guards that don't guard

**Epic:** M5.E13 · **Tier:** FULL (inherited from project `PROFILE.md`) · **Opened:** 2026-07-28
**Target release:** v0.1.14

---

## Why this Epic

Four open defects look like four small bugs. They are one story: **something was built to catch a
mistake, and it does not catch it.** `B48` is an instruction so unconditional that a correct agent
refused it. `B39`, `B46` and `I2` are the class M5.E8 named — *a guard written, shipped, and never
called*. `B36` is a release gate that has skipped silently three times, most recently on M5.E8's own
ship. `B49`'s remainder is a version check that works and looks at two of the three places a version
is written.

Fixing them separately means fixing the same thing four times and probably a fifth.

**One finding shaped this Epic before it opened.** M5.E8's retrospective proposed a mechanism for
the class: *a hygiene check asserting every `--check`-style guard in `tools/` has a caller.* Checked
against the artifact, `--check` appears in **exactly one file** in all of `tools/`
(`adherence-ceiling.js` — which is `I2` itself). `B39` is an instruction in a document that no
command implements (`grep -ril watchlist commands/ tools/` → nothing). `B46` is a data write-back
that nothing ran (0 disposition stamps in `ISSUES-INBOX.md`). **The proposed mechanism covers one of
its own three examples** — a completeness claim written from the shape of the most recent instance
rather than from all three, which is exactly the class
[`../analysis/CLAIM-INTEGRITY-ANALYSIS.md`](../analysis/CLAIM-INTEGRITY-ANALYSIS.md) names. The
scope below reflects the corrected reading, not the retro's.

## Functional requirements

### FR1 — `B48`: the phase-entry instruction stops demanding a false record

**Problem.** M5.E9's FR6 tells the agent to call `transitionPhase(baseDir, 'X')` *"before any
Workflow step"*, with no precondition clause, in `plan.md` / `execute.md` / `verify.md` /
`review.md`. Observed live 2026-07-28 during M5.E8's first adherence run: against a fixture with no
PLAN artifact, `/sig:execute` halted at its preconditions and the agent **declined** the write,
reasoning that obeying would record `phase: EXECUTE` for a project with nothing to execute. The
agent was right. Obeying corrupts the ledger M5.E9 had just made honest; disobeying reproduces
`B41`, the defect FR6 exists to fix.

**Decision (D-M5E13-4):** fix both halves — reword the instruction *and* guard the code beneath it.

- **FR1.1** All four commands state the transition as conditional on preconditions passing, in a
  single shared wording so the four cannot drift apart.
- **FR1.2** `recordPhase` (`tools/lib/state.js`) refuses to append a phase whose artifact does not
  exist on disk, resolved through the existing `resolveArtifactPath` rather than new detection
  logic. Refusal is explicit and named — never a silent no-op.
- **FR1.3** The adherence canary `B41-phase-entry` is re-run after the rewording, because rewording
  a measured instruction invalidates the `OBEYED` verdict recorded against it. This is the first use
  of the harness for its intended purpose rather than to prove itself.

- **FR1.4 (`B51`, added at DISCUSS close — found by dogfooding this Epic's own DISCUSS).**
  `commands/discuss.md:158-161` still instructs the DISCUSS close to set `phase: PLAN` — the
  pre-M5.E9 convention where the **outgoing** command advanced the phase. M5.E9 moved that to the
  **incoming** command, and both instructions survive. Obeying both makes `/sig:plan`'s at-entry
  `transitionPhase` resolve `leaving` to **PLAN** and append `PLAN (date)` **before PLAN has run** —
  and `recordPhase` is deliberately append-only with no dedupe (D-M5E9-5), so the false entry is
  permanent. Remove the stale closing instruction. **`calibrate.md` and `ship.md` also called
  `transitionPhase` before M5.E9 and get the same read** — the audit is FR1.4's scope, not just the
  one file.

**Acceptance criteria**
- AC1.1 — All four commands carry the conditional wording; a grep for the old unconditional phrasing
  returns nothing.
- AC1.5 — No command instructs a phase transition that the *next* command also performs. A test
  asserts `discuss.md` no longer sets `phase: PLAN`, and the `calibrate.md` / `ship.md` audit is
  recorded with its finding either way — *"checked, nothing to change"* is a result, not a skip.
  **Proof-of-fail: red against `main`.**
- AC1.2 — `recordPhase` called for a phase with no artifact on disk refuses and names the missing
  artifact; called with the artifact present, it appends as before. **Proof-of-fail: both tests red
  against pre-change `state.js`.**
- AC1.3 — A legitimately artifact-less phase (one whose artifact is written *after* the transition
  by design) is not blocked; the case is enumerated in the tests, not assumed absent.
- AC1.4 — `node tools/adherence-run.js --canary B41-phase-entry` produces a fresh as-written vs.
  instruction-deleted verdict pair against the reworded text, and `ADHERENCE-LOG.md` carries it.

### FR2 — The never-called-guard class: three fixes, one narrow mechanism, an honest label

**Decision (D-M5E13-3):** fix the three instances individually; build the `--check`-has-a-caller
test; **state its scope in the code and the retro** rather than presenting it as covering the class.

- **FR2.1** `B39` — `/sig:plan`'s drain walks the trigger watchlist the standing `ISSUES-INBOX.md`
  entry instructs, or the standing entry is rewritten to match what the command actually does. One
  of the two, not neither.
- **FR2.2** `B46` — the 45 dispositions in `M5.E7-DISPOSITIONS.md` are stamped back into
  `ISSUES-INBOX.md` so they stop resurfacing at every drain. **Explicit non-goal: no new
  status-tracking schema or stamp-maintenance tooling** — this is a one-time data correction. Status
  as a durable concern belongs to the tracker Epic (D-M5E13-7).
- **FR2.3** `I2` — the `--check`-has-a-caller hygiene test, with a comment and a test name stating
  it covers **code-shaped guards only**, and that the document-shaped instances (`B39`, `B46`) are
  outside it.

**Acceptance criteria**
- AC2.1 — After the fix, a fired trigger in the watchlist is visible at the next `/sig:plan` drain
  without the author going to look for it; or the standing entry no longer claims a walk happens.
- AC2.2 — `listDrainCandidatesWithRecovery` returns only genuinely undecided candidates; the 45
  dispositioned ones do not reappear. Count before and after is recorded.
- AC2.3 — Deleting the sole caller of `adherence-ceiling.js --check` fails the hygiene test.
  **Proof-of-fail against `main` required.**
- AC2.4 — The test's own name or docstring states its scope limit. A reader cannot mistake it for a
  check that covers the class.

### FR3 — `B36`: the release gate stops skipping silently, and the retro index checks itself

**Problem.** The FR1 retro gate in `/sig:ship` Step 0.5 skips when the milestone row is stale or
non-shipped. Sighted live three times — M5.E6, M5.E9, and M5.E8's own ship, where the
retrospective existed only because someone wrote it before the gate ran. On that same ship
`RETROSPECTIVES.md` was missing its M5.E8 row entirely, and nothing noticed.

- **FR3.1** A stale or non-shipped milestone row no longer produces a silent skip. The gate either
  runs or reports, in the ship output, that it did not and why.
- **FR3.2** A retro-index freshness check, sibling of `checkIndexFreshness`. `regenerateIndexCore`
  is already deterministic and compare-before-write (`tools/lib/retro-index.js:240` — returns
  `{written:false, reason:'unchanged'}`), so the check is "would a regen write? then the index is
  stale."

**Acceptance criteria**
- AC3.1 — With a stale milestone row, the ship output names the skip and its cause. **Proof-of-fail:
  the test is red against `main`, where the skip is silent.**
- AC3.2 — Deleting a retro row from `RETROSPECTIVES.md` makes the freshness check red; regenerating
  makes it green.
- AC3.3 — The freshness check is read-only and does not itself write the index.

### FR4 — `B49`'s remainder: the version check covers every file that states a version

`checkVersionConsistency` exists and works — it fired on `.claude-plugin/marketplace.json` during
v0.1.13's own release cut, catching a third version file the bump had missed. It does not cover
`package.json`, which is precisely why `B49` survived while the suite stayed green.

**Acceptance criteria**
- AC4.1 — A `package.json` version disagreeing with `.claude-plugin/plugin.json` fails the check
  with both paths named. **Proof-of-fail against `main`.**
- AC4.2 — The set of files the check covers is enumerated in one place, so a fourth version file is
  an edit rather than a rediscovery.

### FR5 — Ledger and capture hygiene

- **FR5.1** The claim-integrity class gets a ledger identity — **`B50`** — so future retros count
  sightings instead of rediscovering the class.
- **FR5.2** `ISSUES-INBOX.md:1660` currently carries a heading and *"**Status:** Logged 2026-07-28
  via `/sig:add`"* and **no body**. The seven entries above it all carry content on that same line,
  so this is an authoring miss, not a `/sig:add` defect. The entry gets its body and a pointer to
  the analysis.

**Both discharged at DISCUSS (2026-07-28), not queued** — per *document in the moment*: the stub was
a live falsehood in the corpus, and leaving it for EXECUTE would have meant the record stayed wrong
for the length of an Epic. PLAN should treat FR5 as **verification**, not authoring.

**Acceptance criteria**
- AC5.1 — `B50` exists in `BUGS.md` with the class named, its instance count, and a pointer to
  `analysis/CLAIM-INTEGRITY-ANALYSIS.md`. ✅ *done at DISCUSS*
- AC5.2 — No heading in `ISSUES-INBOX.md` carries a `Status: Logged` line with an empty body.
  ✅ *done at DISCUSS for the known instance; the general check remains for PLAN to scope — a
  one-off correction is not a guard, which is this Epic's entire subject.*

### FR6 — The five fired triggers each get a decision

M5.E8 landing satisfied the trigger condition on five parked items. Per `B39`, nothing walks them;
leaving them untouched is the class's fourth instance in the same Epic meant to fix it. Each is
**promoted** or **re-parked with a new written condition and a date** (D-M5E13-6). Silence is not a
permitted outcome.

**Acceptance criteria**
- AC6.1 — All five carry a dated decision in `BACKLOG.md`. A reader can tell a checked-and-declined
  condition from an unchecked one — which is `B39`'s own second half.

## Non-functional requirements

Signal is a CLI plugin, not a service. The FULL-tier NFR prompt's web-service items — health probes,
graceful shutdown, security headers, rate limiting — are **N/A by architecture**, not deferred.
What translates:

- **NFR1 — Offline and deterministic.** Every new check runs without network and returns the same
  result on the same input. Signal's guards are deliberately offline; nothing here changes that.
- **NFR2 — Read-only checks stay read-only.** The retro-index freshness check and the guard-caller
  test inspect and report; they do not repair. (`/sig:sweep`'s discipline.)
- **NFR3 — Fail-open on advisory paths, fail-closed on gates.** A freshness check that cannot read a
  file reports that it could not, and does not block. A release gate that cannot evaluate says so
  loudly — the `B36` failure mode is precisely a gate failing *quietly*.
- **NFR4 — Atomic writes and lock discipline preserved.** FR2.2's one-time stamp pass goes through
  the existing write path; it does not hand-edit around `atomicWrite` or the state lock.
- **NFR5 — Proof-of-fail is mandatory.** Every fix ships with a test demonstrated red before the fix
  (D-M5E13-8). This is M5.E10's standard, adopted here rather than waiting for it.

## Not doing (and why)

- **`B38`** — reclassifying the anti-rationalization tables. It belongs to M5.E10, where
  `CLAIM-INTEGRITY-ANALYSIS.md` §6 item 6 gives it an actual purpose (the provenance rule as a
  positive recipe). Doing it here would be writing work without that context.
- **A cross-shape mechanism for the guard class.** Covering the document-shaped instances needs a
  declared registry of obligations — new schema, new authoring, and it overlaps the tracker Epic.
  Deliberately not attempted; the gap is labeled instead (FR2.3).
- **Any status-tracking machinery for `B46`.** See FR2.2. Signal has been incrementally rebuilding
  an issue tracker out of markdown; this Epic does not add to it.
- **`B47`** — `/sig:resume` reading `0/7 phases done` after a linear ship. Cosmetic, and the honest
  fix teaches `resume.js` to read `STATE-HISTORY.md`, which is a new capability rather than a repair.
- **The tracker integration itself.** Decided in direction, needs its own Epic (D-M5E13-7).
- **Lanes.** Proposal committed at `e61f614`, sequenced behind this Epic by its own §10.

## Assumptions to validate during EXECUTE

1. **`resolveArtifactPath` is sufficient for FR1.2.** Assumed it can answer "does this phase's
   artifact exist" for all six phases in both linear and Epic mode. If a phase has no artifact by
   design, FR1.2 needs an explicit exemption list rather than a blanket rule — AC1.3 exists to
   force that discovery early.
2. **The 45 dispositions map cleanly onto inbox entries.** `M5.E7-DISPOSITIONS.md` carries 76 table
   rows against 47 drain candidates; the mapping may not be 1:1. If it isn't, FR2.2 stamps only what
   maps unambiguously and reports the remainder rather than guessing.
3. **`B39`'s fix is a real choice, not a formality.** FR2.1 offers two branches (implement the walk,
   or correct the standing entry). PLAN picks one with a stated reason; executing neither is the
   current bug.
