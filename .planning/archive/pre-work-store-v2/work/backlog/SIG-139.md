## The suite is flaky under local parallel load — a different test times out each run

**Status:** needs-triage. Found 2026-09-08 during the `B118` fix lane, on a Mac Studio.

**Two distinct tests hit vitest's 15 s `testTimeout` across five consecutive full runs, each passing
comfortably alone**, and one of them did it **twice, in non-consecutive runs**: `tests/cross-project-scan.test.js >
returns structured buckets, not text` (**9.56 s** alone; runs 1 and 5) and `D-ID → home map +
resolveDecisionId (t5) — AC3.3 > every D-… resolves to a file that DEFINES it` (**5.04 s** alone; run
3). One of the five runs was **fully green** at 3347/3347, so it is not a fixed set — it is whichever
heavy test loses the race. ⚠ **This paragraph said "three" until the PR reviewer counted the list and
found two.** The number came from *three runs having failed*, not from enumerating distinct tests —
`analysis/CLAIM-INTEGRITY-ANALYSIS.md`'s count-asserted-rather-than-derived shape, written into an
entry about a check that misfires. Recorded rather than quietly corrected, because the instance is
worth more than the tidy version.

Every one is a **timeout, not an assertion failure**, and the slow ones share a shape: they build
real git fixtures or walk the whole `.planning/` corpus. Full-run wall clock is ~21 s against ~290 s
of summed test time, so the pool is heavily oversubscribed.

**Why it is worth triaging rather than shrugging at.** CI passes this suite in 47–59 s, so the defect
is local-only *today* — but *"the suite is green"* is the gate every lane in `CLAUDE.md` depends on,
and a suite that fails differently each run trains people to re-run until green instead of reading
the failure. Same reasoning the doc-budget rule uses for ledgers: a check that misfires teaches
people to ignore checks.

**Not diagnosed, and two readings fit:** raise `testTimeout` for the git-fixture files (cheap, hides
a real slowness signal), or cap pool concurrency (slower wall clock, honest). Choosing needs a
measurement of which tests actually contend.

⚠ **A second finding, and it is why this entry is here rather than in `ISSUES-INBOX.md`.**
`tests/drain-standing.test.js:128` — *"AC2.2c — THIS repo: the inbox reports 0 live candidates and 1
standing"* — asserts a **snapshot of live data**, so **filing any genuinely new, undrained inbox
entry turns the suite red.** Reproduced here: this note was written to `ISSUES-INBOX.md` first and
the assertion failed with `expected [ { …(7) } ] to have a length of +0`. The entry was correct and
the check fired on correct behaviour, which is the exact failure the doc-budget rule names for
ledgers — *"a check that fires on correct behaviour teaches people to ignore checks"* — and
`ISSUES-INBOX.md` is on that rule's own `exempt` list for being a capture inbox. The test's intent is
sound (it demonstrates the standing-marker mechanism reaching 0 on real data, which it could not do
before `M6.E4`); pinning it to **live** data is what makes it a trap. Fix shape, not applied here
because changing a test to accommodate one's own data is the wrong instinct: assert against a
fixture, or assert `standing ≥ 1` and drop the live-candidate pin.
