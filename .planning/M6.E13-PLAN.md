# M6.E13 — Plan: work items as records

**Goal:** every work item becomes a JSON record at a fixed path, with its status folded from
recorded events. One library writes the records, a hook blocks hand edits, and every store-on
reader goes through the library. Signal's own store is migrated in one verified cutover, and
projects without a store do not change by a byte.

- Requirements: [`M6.E13-REQUIREMENTS.md`](M6.E13-REQUIREMENTS.md).
- Research: [`M6.E13-RESEARCH.md`](M6.E13-RESEARCH.md). Its count corrections supersede the
  REQUIREMENTS "Measured" figures: 26 readers, 12 commands, about 40 tests.
- Node 22+ assumed; the dev machine runs 22.13. No new runtime dependency.

## How the branch stays green: v2 beside v1, one switch at cutover

This repository keeps its v1 store for the whole of EXECUTE, and the installed `v0.1.47` plugin
keeps writing v1 items during the run. So **the v2 code is built beside the v1 code, not over it.**

- **New modules:**
  - `work-record.js`: schema, serialiser, fold.
  - `work-convert.js`: v1 → v2, pure.
  - `work-records.js`: the v2 read and write library.
  - `work-views.js`: v2 views.
  - `legacy-lists.js`: one home for every Markdown list parser. Their old modules re-export them
    statically, so nothing synchronous changes. Under a test-only flag every export throws when
    called (Decision 12).
- **The v1 modules stay untouched and live until S7:** `work-ops.js`, `work-store.js`,
  `work-item.js`, `work-generate.js`. This keeps `folderFor`, `walkFiles`, the v1 `generateAll`, and
  every live-repo test that reads the v1 views (`work-generated-fresh`, `bugs-tally:214`,
  `drain-standing:98`) green.
- **Callers switch to `work-records.js` slice by slice, and each switch rewrites its own tests in
  the same task** (pass 2, finding 2). Those tests use v2 fixtures. On the live v1 store, a v2
  *read* goes through the converter (Decision 1), and a v2 *write* refuses.
- **⚠ The split this causes, stated:** from S4 until S7, the branch's capture and promote refuse on
  any v1 store, while `/sig:item` on the branch still writes v1. Only this repository has a v1
  store, and the session's own tooling is the installed plugin, so nothing running is affected.
  The branch is not released in that state.
- **S7's cutover commit is the one switch:** data migrated, `schema_version: 2`, the live-repo
  tests flipped to v2. After it, the v1 modules are narrowed to what the converter needs, or
  removed.

## Decisions made here (plumbing altitude, reversible, adopted)

1. **AC4.2, how it is read:** v2 reads a v1 store through the migration's pure converter, and v2
   writes refuse.
   - "Reads nothing silently wrong" holds because the converter is checked against every real item
     in t1.5, and again against the store as it stands at cutover (t7.1).
   - Tests that only pass on v2 (the live AC5.2 test, the SIG-n-only view assertions) are gated on
     `schema_version: 2` with a stated skip reason.
2. **An `edited` event, recorded as `D-M6E13-19`.** It amends the event list fixed by `D-M6E13-4`
   and AC1.4. AC2.1 counts "edit fields" as a mutation that must append an event, and AC1.4 had no
   event for it.
   - It carries `changes: {field: {from, to}}` and never changes status.
   - `checkEvents` asserts that every edited field's current value equals its last `to`, so the
     record and its history cannot disagree.
3. **The transition table.** Status is derived. `closing` is its own derived value, never a letter.

   | Event | Legal from | → | Required | Epic (derived) |
   |---|---|---|---|---|
   | `created` | first event, exactly once | N | — | none |
   | `triaged` | N, Q, P | T | — | cleared |
   | `queued` | T, Q, P | Q | `epic` | set |
   | `started` | T, Q | P | `epic` | set |
   | `close_requested` | N, T, Q, P | closing | `reason: fixed`, `proof` = commit token | kept |
   | `closed` (confirm) | closing | C | written by `confirmCloses`, copying reason and proof | kept |
   | `closed` (direct) | N, T, Q, P, closing | C | `reason` ∈ stale/wontdo/rejected with non-empty `proof` text; or `dup` with `dup_of` | kept |
   | `closed` (legacy) | migration only | C | `legacy: true`, the original reason; `proof` text optional and never admissible | kept |
   | `reopened` | C, closing | T | `reason`; refused when the item's Epic is archived | cleared |
   | `edited` | any | unchanged | `changes` | unchanged |

   - `fixed` only closes through a confirmed request, or as a legacy close.
   - A *closing* item may still close as wontdo or dup without a reopen.
   - The status letter `Q` and the item type `Q` are never compared.
   - `dup_of` existence and no-cycle are store-level checks, done at write and in `checkStore`.
4. **Epic is derived from the events, never stored** (B4). There is no top-level `epic` key.
   `epicOf(record)` folds it. This is `D-M6E13-5` taken literally, and it follows the reason
   `D-M6E13-4` gives for refusing a stored status.
5. **View window (AC6.2, as amended):** "recent closes" means the 30 days before the **newest event
   in the store**, not before today. Committed views would otherwise churn daily with no write, and
   AC5.2 could not be deterministic.
6. **Older closes** go in `.planning/work/history/YYYY.md`, by the year of the `closed` event. These
   files are views: generated, committed, and blocked by the hook.
7. **Schema file:** `plugin/references/work-item.schema.json`. `WORK.md` carries
   `schema_version: 2`; records carry no `$schema`. The validator is hand-rolled over a declared
   keyword subset, because `plugin/` ships exactly one dependency.
8. **Key order:** `id, type, title, theme, priority, source, source_ref, legacy_id, keep_because,
   migration_note, events`. Inside an event: `type, at, by`, then that event's own fields in a
   fixed list.
9. **Lock:**
   - `file-lock.js` is not modified.
   - In `work-records.js`, only public entry points take the `work` lock; internal functions
     receive a handle.
   - The inventory test fails when one lock-taking export calls another.
   - The existing state → work nesting (`checkpoint.js:326`, `archive-tree.js:594`) is out of scope
     and listed as a reviewed exemption. It is two different locks in a fixed order, not a
     re-entry.
10. **The migration tool is a maintainer script, not a command** (B3). This follows the v1
    precedent: `tools/work-migrate.mjs`, repo-root, not shipped (`docs-migrate.md:37`).
    - The logic is `migrateWorkStoreV2` in `plugin/tools/lib/work-migrate-v2.js`.
    - The entry point is `node tools/work-migrate-v2.mjs [--apply]`, which the v1 refusal message
      names.
    - **`/sig:docs-migrate` is untouched, including by t6.2.** Its list instructions describe
      store-off migration, and moving other projects is a later Epic.
11. **Mapping for v1 closes that are not legacy** (B2, measured: 12):
    - `rejected` (2) and `dup` (1) map directly.
    - **The 6 `fixed` closes whose proof carries a commit hash** (SIG-118, 121, 122, 127, 135, 254):
      - The **converter**, which stays pure, emits `close_requested` with the bare hash, using the
        v1 close's own `at` and `by`.
      - The rest of the proof text goes in `migration_note`.
      - In the t1.5 scratch run they read *closing*, which is deterministic.
      - The **migration script** then runs `confirmCloses`, which writes `closed` as it would for
        any request. The manifest records both steps.
    - **The 3 with no commit (SIG-123, SIG-142, SIG-161): ⚠ held for Brett (pass 2, finding 5).**
      Making them legacy closes would raise the legacy count from the 142 that `D-M6E13-14` covers
      to 145. That is his call, asked at the end of this phase. Until it is answered, the converter
      reports them as *unmapped* and t1.5 counts them as such.
    - The manifest lists each of the 12 and the form it took.
12. **AC3.2, how it is enforced** (pass 2, finding 1). "Imports or calls" is enforced at the two
    levels where it can hold:
    - **Calls (runtime):** under a test-only flag, every `legacy-lists.js` export throws when called.
      Every AC3.1 reader runs over a store-on fixture with the flag set.
    - **Imports (static):** no v2 module (`work-record`, `work-records`, `work-views`, and the
      readers' store-on helpers) may reach `legacy-lists.js` in its import graph.
    - **Why not a static ban on the mixed reader modules:** modules like `add.js` hold both a
      synchronous store-off path (`rewriteBugTally`, published as sync in `add.md:28`) and a
      store-on path. Banning the import there would force async on store-off code and break AC4.1.
    - Each inline parser becomes a named `legacy-lists.js` function, so the runtime flag catches it
      too.

## What this Epic does for the first time — wave 1

**Folding status from events over real data.** 268 items, 142 legacy closes, 12 non-legacy closes in
three shapes, 14 bodies that contradict their status, and 42 relative links at two depths have never
been put through an event model. **So S1 ends with a read-only conversion of the live store into a
scratch directory, with a manifest**, before any library exists. Every record must validate and
fold, and every v1 field must be accounted for. **Limit, stated:** `.planning/work/epics/` is
empty today, so the real data has no `queued` or `started` items, and those shapes are covered by
fixtures only.

The store-off golden capture is also in wave 1. M6.E11 broke "store off is unchanged" twice (retro
A3), so the pin has to exist before any reader is touched.
