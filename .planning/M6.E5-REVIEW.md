## Critical Issues

### C1 — A proposed `deny` rule was silently dropped when the user had already **allowed** it

**`plugin/tools/lib/permissions-report.js` (`buildProposal`) → `permissions-state.js`
(`proposalDelta`).**

Deny proposals were routed through `proposalDelta`, which suppresses a rule found in `state.granted`
— **the allow set**. So a user who had already allowed `curl` silently lost the proposal to deny it,
and the loss was counted as *"already granted"*.

**Reproduced before fixing:**

```
settings.json: { permissions: { allow: ["Bash(curl:*)"] } }
deny proposed: ["Bash(sudo:*)", "Bash(rm -rf:*)", "Bash(git push --force:*)", "Read(./.env)"]
Bash(curl:*) proposed as deny?  false
```

**Why Critical rather than Important.** The protective half shrank **precisely in the case it exists
for**, and said nothing while doing it. `D-M6E5-5`'s whole argument is that *"yes, and don't ask
again"* only ever teaches the system to say yes, so the deny half cannot fill itself — and this made
the one mechanism that fills it get *quieter* the more the allow list had grown.

**Fixed in-phase.** A new `denyDelta` compares proposed denies against the existing **deny** set. A
collision with an existing **allow** is not a suppression — it is a **conflict**, and it now renders
as its own line:

```
⚠ CONFLICT: Bash(curl:*) is proposed as a deny AND is already in your allow list.
    Deny wins outright, so installing this silently overrides that allow. Decide deliberately.
```

That is the most useful thing the report can say to that user: deny-first precedence means
installing it would override an allow they set on purpose.

**Coverage written for the defect (6 new tests, all green):** existing deny rules collect into their
own set; an allow does **not** suppress the matching deny; an existing deny **does**; the collision
is reported as a conflict; the conflict renders as a visible line; the deny proposal survives.
