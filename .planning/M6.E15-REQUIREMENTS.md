## Why now, and what the lists look like

Only Signal has a store. The segmenters that moved Signal's lists (`plugin/tools/lib/work-migrate.js`)
read Signal's formats and refuse others. Two corpus projects, read 2026-10-08, write their lists as:

| Shape | Seen in |
|---|---|
| Bug table with `B1` IDs, then `##` bug headings with no ID, some with a `**Status:**` line, some without | corpus project 1 |
| Backlog rows `### #99 — title · **tag** · size`, finished rows struck through with `**DONE — …**` | corpus project 1 |
| Open questions under section headings `## Currently blocking` / `## Resolved during v2.6`, with `### R3 —`, `### Issue #45 —`, `### NFR-04 —` | corpus project 1 |
| Bugs as `##` write-ups with no ID; status in bold prose | corpus project 2 |

| Inbox (217 lines) and open questions (383 lines) as long `##` write-ups; finished ones struck through with `RESOLVED <date>` | corpus project 2 |

## Functional requirements

Every FR starts with a test that fails on `main` before the change (FULL, strict TDD).

### FR1 — `/sig:docs-migrate --work-store` (`D-M6E15-5`, `-6`)
- AC1.1 Without `--work-store`, `/sig:docs-migrate` reads and writes no list and no `.planning/work/`
  file (existing behaviour, pinned).
- AC1.2 With it, a dry run (default) prints: the key, per-file counts (items open / closed / flagged,
  non-item regions), every item's new ID, old ID, title and status, and writes nothing.
- AC1.3 `--apply` keeps the command's contract: refuses a dirty tree without `--force`, creates the
  pre-apply tag, leaves changes staged and not committed, prints the tag and the undo line.
- AC1.4 A project with none of the four lists: apply writes `WORK.md` (`schema_version: 2`, the key)
  and generated empty views, after which `/sig:item new` succeeds (`SIG-274`).
- AC1.5 A project that already has a store (any `WORK.md`) is refused: "already on the store", nothing
  written (`D-M6E11-21`).
- AC1.6 A project below `docs_layout_version: 3` is refused with the command to run first
  (`D-M6E15-8`).

### FR2 — The key (`D-M6E15-7`)
- AC2.1 The dry run proposes a key from the repository folder name, valid against `STORE_KEY_RE`.
- AC2.2 `--key ABC` overrides it; an invalid key is refused with the rule stated.
- AC2.3 No `'SIG'` default on the new migration path: `planListsToRecords` throws without a key, and
  the path never reaches `planMigrationFromTexts`, whose `'SIG'` default stays for Signal's own tooling
  (amended at VERIFY; PLAN t3.1).

### FR3 — Splitting lists into items (`D-M6E15-1`, `-11`)
- AC3.1 Each corpus project 1 shape in the table above splits into the expected items, by fixture.
  Corpus project 2's shapes are recorded for a follow-up, not built here (`D-M6E15-17`).
- AC3.2 Signal's own archived lists (`.planning/archive/pre-work-store/`) still split as before
  (existing round-trip tests stay green).
- AC3.3 Types by source file: BUGS → `BUG`, BACKLOG by tag (`**roadmap**`/untagged → `FEAT`,
  `**hygiene**` → `CHORE`, `D-M6E15-22`), OPEN-QUESTIONS → `Q` (open ones at T with a
  `migration_note`); ISSUES-INBOX → `NEW` at N (amended at VERIFY).
- AC3.4 Nothing the splitter cannot classify throws for a non-Signal shape. It becomes a flagged item
  or a named non-item region.

### FR4 — Finished entries (`D-M6E15-3`, `-10`)
- AC4.1 Each finished-marker in `D-M6E15-10` closes the item with `legacy: true` and the original
  wording as its reason; one fixture per marker.
- AC4.2 An entry with no marker, or an unclear one, is open and flagged. Never closed by inference.

### FR5 — IDs (`D-M6E15-2`, `-12`)
- AC5.1 Items are numbered `KEY-1` upward in file order: BUGS, BACKLOG, ISSUES-INBOX, OPEN-QUESTIONS.
- AC5.2 Any old ID (`B1`, `#99`, `R3`, `NFR-04`) is kept in `legacy_id` and on the first line of the
  body.
- AC5.3 `/sig:item show #99` and `list` resolve an old ID; two items with the same old ID are reported,
  not guessed between.

### FR6 — No text lost, checked before writing (`D-M6E15-9`)
- AC6.1 Originals copied byte-for-byte to `.planning/archive/pre-work-store/` with a manifest
  (counts, per-item source line ranges, verification result).
- AC6.2 Every byte of each source list lands in exactly one item body or one named non-item region;
  a failure refuses the whole apply and writes nothing.
- AC6.3 Non-item text beyond structure (a title, blank lines, `---`, a bug-table header, section
  headings, a `*Last updated:*` footer) becomes one flagged item per file (amended at VERIFY).
- AC6.4 The apply's input-hash guard covers the four lists: a list changed between dry run and apply
  aborts before any write.

### FR7 — No Signal-only assumptions (`D-M6E15-13`)
- AC7.1 Bug IDs other than `B\d+`, or none, are accepted.
- AC7.2 `NO_COMMIT_LEGACY_IDS` (Signal data) no longer applies outside Signal.
- AC7.3 The `WORK.md` written for another project describes that project's migration, not Signal's.

### FR8 — `SIG-286`: archive moves need a closed unit (`D-M6E15-4`)
- AC8.1 `/sig:docs-migrate` moves a unit's files only when the closure check `/sig:docs-archive` uses
  says closed. A filled-in retrospective alone is not enough, and the current unit never moves.
- AC8.2 With STATE.md unreadable, no archive move is planned (as `/sig:docs-archive`).
- AC8.3 The dry run's move list and its "could not evaluate" lines can no longer disagree about one
  unit (fixture: the observed case).
- AC8.4 The verdict reader is unchanged. A `## Verdict` heading with `**PASS …**` on the next line is
  unreadable on purpose (`plugin/tools/lib/verdict.js:87-91`, M5.E18 FR2: the body is not guessed at),
  so under AC8.1 such a unit is not moved, and the dry run says why.

## Non-functional requirements (FULL prompt, answered)

- Health probe, graceful shutdown, request logging, security headers, rate limiting: **N/A**. Local CLI
  plugin, no server, no network call added.
- **Integrity:** the apply is all-or-nothing (FR6), reversible by git (AC1.3), and never runs on a
  dirty tree by default. No existing refusal is weakened.
- **Security:** list text from another repository is data. M6.E12's hostile-repository rules apply:
  no path in list text is followed outside the repository; record bodies are scrubbed for secrets as
  `newItem` does, with a hit stopping the apply for a person's decision.
- **Performance:** a dry run on a 400-line list completes in under 5 s.

## Blast radius

- **Code:** `work-migrate.js` (segmenters), `work-migrate-v2.js` / a new record-writing path,
  `work-convert.js`, `work-store.js` (on-switch), `work-records.js` (old-ID lookup),
  `migrate-memory.js` and `archive-tree.js` (`SIG-286`), `commands/docs-migrate.md`, `commands/item.md`.
- **Stored data:** Signal's own store is not migrated again (refused by AC1.5). Record format unchanged;
  `legacy_id` already exists.
- **Users tracking `main`:** plain `/sig:docs-migrate` changes only in `SIG-286` (fewer, correct
  archive moves). The store path is new and opt-in.
- **Docs:** edits to `commands/*.md` can move the directive ceiling; `ADHERENCE-LOG.md` may need
  regenerating, merged with `--merge`.
- **Not touched:** the corpus projects (Brett applies, `D-M6E15-15`), STATE.md, Epic artifacts.

## Outcome

- **Leading:** a dry run on a scratch copy of corpus project 1 finishes with a verified manifest (zero
  bytes unaccounted) and no refusal.
- **Lagging (the real outcome):** when Brett applies it to corpus project 1, it ends on the store with
  `/sig:docs-sweep` clean and `/sig:item new` working, and his triage pass finds no item whose status
  the migration got wrong (closed that was open, or the reverse). Each wrong one is filed and traced.
