## What EXECUTE found that VERIFY has to calibrate

**The command was run end-to-end on this repository**, which is the check `/sig:drive` is still
missing and the reason it is the gate on further loop work. It read 50 live rows, recommended 5,
declined 45, resolved 51 citations, and wrote exactly one file:
[`BACKLOG-REVIEW-2026-09-05.md`](BACKLOG-REVIEW-2026-09-05.md). That artifact is kept as the run
record rather than deleted.

⚠ **Two of the five recommendations are not actionable work, and the cause is not the ranking.**
The run's own output:

1. *"Since the re-audit — what `M5.E7` changed (reconciliation, 2026-07-26)"* — a dated historical
   note.
4. *"Parked — the trigger watchlist **(not sprint material)**"* — a row that says in its own
   heading that it is not work.

`parseBacklogRows` treats **any non-container heading** as a row, and Signal's `BACKLOG.md` carries
prose section headings at row depth. So the input to the ranking contains non-rows, and no ordering
of the four specified inputs can fix that — it is a corpus-shape problem arriving as a
recommendation-quality problem.

**Not fixed here, deliberately.** `t3.1` enumerates four ranking inputs and a fifth ("is this row
actually work") is a design change, not an implementation detail. Adding it silently is precisely
what this phase's anti-rationalization table forbids: *"The plan says X but I think Y is better —
update the plan first. Don't silently diverge."*

`M6.E7-REQUIREMENTS.md` pre-committed to reporting a low calibration score honestly rather than
rationalising it. **This is that report, written from the run rather than from the shape of the
work** — 3 of 5 recommendations are real, 2 are not. VERIFY decides whether that clears the bar,
and the options are a fifth ranking input, a `HELD_OPEN_RE`-style declaration in the row vocabulary
(the mechanism already exists in `backlog.js` for this exact purpose), or accepting it and saying so.
