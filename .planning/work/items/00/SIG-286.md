Seen 2026-10-08 on a corpus project (layout v2→v3 dry run). The dry run put all 7 files of an Epic on the archive-tree move list, and the closure explanation beneath the same count said it could not evaluate that Epic because its VERIFICATION.md had no verdict it could read. The verdict was there, under "## Verdict": "**PASS with one documented pending item.**" A sibling Epic with "**PASS with documented limits.**" evaluated fine.

Two things, not yet separated:
1. The move list (`archive.moves`) and the closure explanation (`resolveClosures` → `explainArchiveOutcome`) are computed independently in `plugin/tools/lib/migrate-memory.js` (~1950–1990), so the dry run can contradict itself. Check whether archive-tree moves are closure-gated at all in docs-migrate the way /sig:docs-archive is ("only units that are genuinely closed move"). If not, an unfinished Epic's files could move.
2. The verdict reader does not accept "PASS with one documented pending item".

Harmless in the observed case (both Epics had shipped). Needs root cause before the work-store migration Epic reuses this path.
**Root cause (M6.E15 DISCUSS, 2026-10-08).** `senseArchiveTree` (`plugin/tools/lib/archive-tree.js:475-526`)
treats as closed the union of (a) Epics with a non-stub retrospective and (b) units `resolveClosures`
marks closed. Path (a) has no current-unit check and no verdict check, so a filled-in retrospective
alone moves an Epic's files. `renderDryRun` calls `resolveClosures` separately, only to explain the
count (`plugin/tools/lib/migrate-memory.js` ~1985-1999), which is why the dry run contradicts itself.
`/sig:docs-archive` also refuses all moves when STATE.md is unreadable (`archive-command.js:93-105`);
docs-migrate does not. The "could not evaluate" itself is the verdict reader working as designed:
a `## Verdict` heading with `**PASS …**` on the next line is unreadable on purpose
(`plugin/tools/lib/verdict.js:87-91`). Fix scoped in M6.E15 FR8.
