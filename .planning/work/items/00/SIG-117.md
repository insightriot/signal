**The Epic lane keeps getting squashed because GitHub's merge button remembers the last method used REPO-WIDE — third instance, and the first with a confirmed cause.** PR #239 (`M6.E7`, Epic lane) was merged with the green button on 2026-09-06 and squashed all **35** commits into one. Two published anchors then named commits unreachable from `main` — `STATE.md`'s `last_updated_commit` and `ADHERENCE-LOG.md:56`'s ceiling commit — and `tests/adherence-anchor-reachability.test.js` went **red on `main`**. Repaired by PR #240. ⚠ **`B?`/#236's row recorded the root cause as *"still open pending one question about how #236 was merged"*. That question is answered: the button.** The mechanism is that the fix lane **correctly** uses `--squash`, which sets the repository's remembered method, and the very next Epic merge inherits it silently and reports success. So the two lanes' correct behaviours are in direct conflict, and the conflict is invisible at the moment of clicking. **Not a discipline problem** — `CLAUDE.md` has documented this trap since `v0.1.19` and it has now fired three times (#211, #236, #239), which is the evidence that documentation is not the fix. ⚠ **A second harm surfaced this time and is not in the earlier rows:** GitHub **deletes the branch on merge**, so the 35 orphaned commits existed on exactly one machine until the branch was pushed back. `CLAUDE.md` says an Epic's commit messages are *"frequently the best surviving account of why a line exists"* — a squash plus branch deletion destroys that account, and only the local clone stood between it and permanent loss. **Fix shapes, none yet chosen:** (a) a repo ruleset allowing only merge-commits, with the fix lane switching to a rebase or accepting merge commits; (b) a `PreToolUse`-style guard is impossible here since the merge happens in a browser; (c) auto-merge configured per-PR from the CLI at `/sig:ship` time so the button is never the mechanism. **(a) is the only one that removes the trap rather than routing around it**, and it costs the fix lane its squash — a real trade that needs a decision, which is why this is filed rather than fixed. **→ FIXED 2026-09-08 — shape (a) is APPLIED.** `main`'s ruleset (`main-requires-pr-and-green-ci`, id `20199646`) carries `allowed_merge_methods: ["merge"]`; verified against the API rather than inferred, and the date is the ruleset's own `updated_at` (`2026-09-08T17:45:24-04:00`) rather than the day someone noticed. ⚠ **The trade is applied but NOT recorded** — `DECISIONS.md` holds zero mentions of `allowed_merge_methods`, so the fix lane lost its squash with no dated entry saying who decided it or why. This row and `CLAUDE.md` are currently the only account. The button now has one option, so the sticky repo-wide state can no longer arm an Epic merge, and the trade this row called for was taken as predicted — the fix lane loses its squash. ⚠ **Repo-level settings still allow all three** (`allow_squash_merge=true`): the restriction is scoped to `main`, which is precisely the *"do not instead disable squash repo-wide"* caveat, honoured. ⚠ **Found by the setting REFUSING a merge, not by anyone recording it.** A fix-lane `gh pr merge --squash` on `#248` came back *"Squash merges are not allowed on this repository"* while `CLAUDE.md` still read **"Not yet applied; it needs repository-admin rights this session did not have"** and its two-lane table still instructed the fix lane to squash. So the guard was correct and every document describing it was wrong — **a right guard with a stale instruction fails the same way a wrong guard does**, because whoever follows the file hits an error the file says cannot happen. Both corrected in the same PR that found it.
