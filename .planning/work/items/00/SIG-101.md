**`diffRequirementCoverage` clears a requirement group from `unattributableGroups` when the report merely *names* the group — including in a sentence saying the group was not checked.** Found 2026-08-17 while running VERIFY on `M6.E1`, by watching the value change after an edit that verified nothing. Against the draft report the check returned `unattributableGroups: ["NFR-1","NFR-2","NFR-3","NFR-4"]`. A bullet was then added *disclosing* those four groups, and the value became **`[]`** — no requirement was verified in between; the only change was that the four strings now appear in the document. **Reproduced deliberately, and the reproduction is the severity:** a verification text reading `"NFR-1, NFR-2, NFR-3 and NFR-4 were not checked at all"` also returns `[]`. **A sentence declaring the groups unchecked satisfies the check whose job is to surface unchecked groups.** This is the exact limit `AC0.1` / `D-M5E10-1` states in the abstract — *everything shipped compares **tokens*** — reproduced on a live artifact rather than argued, and it is worse than the abstract statement suggests, because the satisfying sentence can assert the opposite of coverage. **Sibling to `B100`**, found in the same run on the same tool: `B100` is a denominator that silently omits ids, this is an exclusion list that empties itself on mention. Both make a **reassuring** word (`covered`, `[]`) out of an absence. *Fix shape (not attempted):* attribution should require evidence adjacency — a group counts as attributed only when its ids or an evidence marker appear, not when the group label appears anywhere in the file. The deeper fix is `AC0.1`'s semantic half, which is deliberately unbuilt and has a live `BACKLOG.md` row. **Do not fix by widening the token match** — that recreates the defect one layer out, which is the lesson `B85`'s test recorded.
