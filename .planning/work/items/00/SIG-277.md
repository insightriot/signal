Deferred from M6.E13 REVIEW pass 1 (.planning/M6.E13-REVIEW.md, "Deferred, with reasons").

`promoteInStore` (plugin/tools/lib/backlog.js) dedupes a promoted inbox block by looking for a record whose
`source_ref` is the block's sha1 key, and only then calls `newItem`. The lookup runs OUTSIDE the `work`
lock and the write runs inside it, so two promotes of the same block started at once can both find no
twin and both write one: two records for one block.

The fix is to dedupe inside the lock (look up `source_ref` under the same lock that allocates the ID and
writes), which changes `newItems`' contract — it would need to accept a dedupe key, or return an existing
record. v1 had the same hole. Not taken in REVIEW loop 1 for that reason.

Not reachable today (checked by reading the code on 2026-10-04): the only caller of
`promoteToBacklog`/`promoteToBugs` is `drain.js` `promoteDrainEntryCore`, and `promoteDrainEntry`
refuses with the store on (`refuseWhenStoreOn`). It becomes reachable when a store-on caller is added.
