**A drain disposition stamp is only recognised when the reason's LAST word is `drain`.** `STATUS_DISPOSED_RE` (`drain.js:65`) is `\(\[^)\\n]*\\bdrain\\b\)` — the word must sit immediately before the closing paren, not merely somewhere inside it. So `(inbox drain — shipped in M4.5.E2)` reads **live** to the code while reading **disposed** to a human, and the entry resurfaces at every future drain; `(delivered by M4.5.E2 — inbox drain)` disposes. Measured both ways 2026-08-10 during the 52-entry inbox drain, on an in-memory copy before any write. **This is `B4`'s shape** (a stamp format the detector could not see, so promoted entries resurfaced) and the exact hazard `drain.js:60-64` warns about for the verb list — stated there for *which verbs* are recognised, and silent about *where in the reason* the keyword must fall. Nothing in the reason's own contract says it: `applyDisposition`'s JSDoc calls `reason` a free-text "stamp context, e.g. 'M4.5.E2 drain'", and the example happens to comply. **Caught only because the run asserted the candidate count dropped by the batch size**; a visual read of the file would have passed. **Fix candidates:** relax the regex to `\\bdrain\\b[^)\\n]*` so the keyword may fall anywhere in the reason, or validate the reason at write time in `transformBlock` and throw — silently writing an unrecognised stamp is the failure mode. **Second, smaller defect in the same pass:** `transformBlock` appends to the first physical `**Status:**` line, so on a hard-wrapped Status paragraph the stamp lands mid-sentence (hit 1 of 12 entries; repaired by hand).
