Found in M6.E16 S9 while correcting `ship.md` §5.5. Read from the code and the two command files; not run end to end.

Before unit records, an Epic-close SHIP evicted the Epic's narrative from `STATE.md` (§5.5, `evictEpicNarrative` in `plugin/tools/lib/evict.js`): the retrospective existed, so the Epic read closed.

With unit records the Epic's record decides, and at SHIP it reads open — §6.8 (`closeEpic`) only requests the close, and it runs after §5.5. So §5.5 returns `{evicted: false, reason: 'not-closed'}`. The record reads closed once the close's commit is on the default branch and `/sig:docs-sweep` or a later SHIP confirms it.

The only other caller in the flow is `/sig:checkpoint` step 3, which calls `evictEpicNarrative(baseDir, state.current_epic)` — the current Epic only. In the usual order (ship, merge, then `/sig:discuss --epic` for the next Epic) `current_epic` has already moved on by the time the close is confirmed, so nothing evicts the finished Epic's narrative. It stays in `STATE.md`.

This is a change from v0.1.50 for a project with unit records. It fails safe: nothing is lost, the narrative is kept. `ship.md` §5.5 now states the condition (M6.E16 t9.1); no code changed.

Options, none chosen: (a) the step that confirms a unit close (`confirmCloses`, in the sweep and at SHIP) evicts that unit's narrative, or says it is ready; (b) `/sig:checkpoint` evicts every closed unit that still has a narrative section, not only the current one; (c) SHIP evicts on the close request and puts the narrative back if the request is reopened.
