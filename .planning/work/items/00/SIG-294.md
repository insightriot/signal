Found during M6.E16 EXECUTE (S4), confirmed by reading the code in S9. Not fixed in M6.E16.

`shipFR1Check` (`plugin/tools/lib/retrospective.js`) is the check `/sig:ship` runs first (§0.5). It validates the retrospective with `validateRetroContent`, whose own comment says `[FILL IN]` markers do not fail it: the headings must be there, no section empty, and the file long enough. So a retrospective that still holds a placeholder line passes §0.5.

On a project with unit records, `closeEpic` (`plugin/tools/lib/work-ops.js`, SHIP §6.8) refuses that same file: it requires `retroStatusFromContent` to read `complete`, and one `[FILL IN]` makes it a stub (CONFLICT, nothing written).

Result: SHIP passes its first gate, runs the steps in between (the state transition, the retro index, the inbox drain, the backlog discharge), and then halts at §6.8. Nothing is lost — finish the retrospective and re-run — but the halt comes late, after files have been written, when §0.5 exists to say it first.
