## Two mutually-blind milestone Epic-row parsers, and the one feeding the SHIP gate cannot read Milestone 6 at all

**Status:** confirmed

There are two module-private regexes for "which table line is an Epic status row", they match **disjoint** formats, and neither is exported. Found 2026-09-05 during `M6.E7` PLAN research and verified by running both over the real files:

| Parser | Location | MILESTONE-4.5 | MILESTONE-5 | MILESTONE-6 |
|---|---|---|---|---|
| `findEpicStatusRow` | `plugin/tools/lib/retrospective.js:1008` | 11 rows | 16 rows | **0 rows** |
| `EPIC_ROW` | `plugin/tools/lib/published-facts.js:277` | 0 rows | 0 rows | **6 rows** |

`MILESTONE-5.md` writes rows as `| **E1** | … |`; `MILESTONE-6.md` writes them as `` | `M6.E1` | … | ``. Each parser sees exactly one shape. Both formats predate this session (`git show ba5d1c3:.planning/MILESTONE-6.md`), so this is not edit-induced.

**The consequence is not cosmetic, because `findEpicStatusRow` is load-bearing.** It feeds `isEpicCloseShip` (`retrospective.js:407`), which returns `false` the moment the lookup is `null` (`:408`). Its own docblock (`:451`) states the design: callers gate on **milestone-ROW ABSENCE**, *"NOT a pure OR, so a maintained `pending` / `in flight` row still wins for a legit per-slice ship (`D-E9-5`)."*

For every Epic in Milestone 6 the row can never be seen, so **the maintained row can never win** and `isEpicCloseByState` decides alone. `D-E9-5`'s override has been inert across `M6.E1`, `E2`, `E4`, `E5` and `E6` — five Epic ships. This also explains, at a level below what was recorded at the time, why `M6.E6`'s SHIP returned a clean `isEpicClose: true` rather than the `stale-milestone-row` warning: that branch was unreachable, not merely unmatched.

**Direction of failure is toward MORE gating, not less** — an Epic-close retro is demanded where a maintained row might have said per-slice — so nothing shipped unguarded. That is why this is `confirmed` rather than higher: the damage is a decision mechanism silently not existing, which is `B36`'s and `B75`'s shape (documented end to end, enforced nowhere), not an escaped defect.

**Fix shape.** Export ONE reader covering both formats and re-point both call sites at it. Writing a third private parser is the `B82` shape this repo already names — and `bugs-tally.js:109` carries the standing warning in its own docblock (*"writing the walk twice is `B82`'s shape"*). ⚠ Note `MILESTONE-6.md:29` already carries a self-documented instance of the neighbouring defect (its Epic-status table sat two rows long while six Epics existed), so the table's *contents* and the table's *parser* have now both been found wrong within two days.
