| B56 | `confirmed` | P3 | **⟨STALENESS RE-CHECK 2026-08-09 — numbers stale, structural gap fully live.⟩** The headline figure is three corrections old (`facts.md` now reads **2389**, set by `cut-release.js` from the gating vitest run). The defect is untouched: `cross-file-consistency.test.js` still compares docs to `facts.md` and **never to the suite**, and `cut-release.js` is referenced only from `tests/` — never from CI, never from a command — so *"nothing requires the script to be used"* remains exactly true. **`B77`'s fix is the pattern to copy here:** derive the number and pin it with a test that fails on disagreement; that is now shipped for `BUGS.md`'s tally and is the same shape this row needs for the test count. Original: **`references/facts.md` publishes a test count that is wrong by 912, and the cross-file guard over that exact file cannot see it — it pins two documents to each other, never to the thing they describe.** `references/facts.md:22` reads `**Test count:** 894`; the suite is at **1806**. `tests/cross-file-consistency.test.js` is the guard: it extracts `TEST_COUNT` via `extractFact('Test count')`, asserts `expect(TEST_COUNT).toBeTruthy()` (:46), and asserts that any doc mentioning "N tests" **matches facts.md** (:65 — `` `${doc} mentions "${hit} tests" but facts.md says ${TEST_COUNT}` ``). **It never compares facts.md's number to the actual test count.** So facts.md and README.md agree with each other, drift together from reality, and the suite stays green — a published, currently-wrong number with a passing guard over it. Its own file header calls facts.md the "source-of-truth," which is the assumption that makes the gap invisible: a source of truth is only true if something checks it against the source. **Found 2026-07-31 at M5.E17 PLAN**, incidentally, while establishing the Epic's test baseline — *not* by any mechanism, which is the M5.E13 retro sentence again. **Same class as `B39`/`B48`** (a guard that does not guard) with a data shape rather than a document shape, and it is a **fourth** location for it. **Not folded into M5.E17** — it traces to none of FR1–FR4 and absorbing it would be the scope creep the Epic's "Not doing" section forbids. **Fix shape:** have the test derive the real count (collect the vitest totals, or count `it(`/`test(` across `tests/`) and assert facts.md matches, so the guard compares the document to the world rather than to its own echo. → homed at **M5.E16** (the data-shaped detector); a one-line correction of the 894 → 1806 string is *not* the fix and would leave the guard exactly as blind. **UPDATE 2026-08-03 — the prediction in that last sentence has now been confirmed twice, by two more one-line corrections.** v0.1.16 corrected the number to **1938**; v0.1.17 corrected it again to **1954** (it was found stale by 16 while cutting that release). **M5.E16 shipped without taking this on**, so each release has repeated the same one-line fix and left the guard untouched — the number is right at each tag and wrong again by the next. This is no longer a predicted recurrence; it is a measured one, three instances deep. **Sharpening the fix shape, because half of the original suggestion does not work:** counting `it(`/`test(` across `tests/` **undercounts**, since several suites generate cases in a loop — `tests/status.test.js` builds its `nextActionForPhase` cases with `for (const [phase, skipped, expected] of cases) { it(...) }`, and `tests/noncanonical-phase.test.js` iterates `PHASES`. Static counting cannot see runtime-generated tests. **The workable half is the other one:** have the suite emit its own total (a vitest reporter, or a post-`npm test` step writing the count to a generated file) and pin `facts.md` to that artifact. Small tooling, not a one-line assertion — which is the honest reason this keeps getting deferred, and worth stating so the next person does not re-derive it. **Second, independent weakness in the same test, unfixed:** AC3 is vacuous by construction — *"only enforce if a doc actually mentions a count"* (`cross-file-consistency.test.js:59-60`) — so removing the count from README makes the assertion pass trivially rather than fail. Any fix should close both. **Still P3**: the published number is wrong between releases, which misleads a reader but breaks nothing. **UPDATE 2026-08-03 (second pass, same day) — the reason three corrections have not stuck is that the field has no defined semantic, and that must be decided before any guard can be written.** Nobody has ever said whether `facts.md`'s count means *"tests in the last shipped release"* or *"tests at HEAD."* The two readings disagree constantly and give opposite verdicts **right now**: the file reads **1954**, which is exactly what v0.1.17 shipped (correct under the release reading), while HEAD carries **1965** after the `B32` work (wrong under the HEAD reading). Its own header sentence — *"Updated at the v0.1.6 release"* — implies the release reading; this row's original framing (*"the suite is at 1806"*) assumes the HEAD reading. **Under the HEAD reading the number is unmaintainable by hand** — every test-adding PR invalidates it, which is precisely the churn that produced three throwaway corrections. **Under the release reading it is maintainable and is already part of the release checklist.** Recommendation: **adopt the release reading**, then the guard is not *"count the suite"* at all — it is *"`facts.md`'s count matches the count recorded at the current `plugin.json` version,"* which is a comparison between two artifacts that both change only at a tag. That is a far smaller mechanism than the vitest-reporter route sketched above, and it is why **`facts.md` was deliberately left at 1954 in this pass** rather than corrected a fourth time. **UPDATE 2026-08-03 (third pass) — the release reading is now implemented, and this bug stays `confirmed` anyway.** `tools/cut-release.js` sets the count from **the same `vitest --reporter=json` run that gates the release**, so a tagged release can no longer publish a stale number, and the hand-correction loop is broken. **Two reasons that is not a fix.** (1) **Nothing requires the script to be used** — a release cut by hand skips it entirely, which is exactly `B71`'s shape one file over: a mechanism that works, reachable only through a path nobody is obliged to take. (2) **The guard is unchanged.** `cross-file-consistency.test.js` still compares `facts.md` to `README`/`SECURITY.md` and never to the suite, so a hand-edit between releases is still invisible, and AC3 is still vacuous when no doc mentions a count. **What would actually close it:** record the suite count at tag time in a committed artifact the script writes, then assert `facts.md` matches *that* — a comparison between two artifacts that both change only at a tag, which is the mechanism sketched in the previous update. Until then this is a **process** where a **guard** is wanted. **Claim corrected the same day:** `CHANGELOG.md` and the `cut-release.js` commit message both originally said the script *"closes `B56`"*.
