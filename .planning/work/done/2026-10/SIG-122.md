| B122 | `confirmed` | P2 | **The `<details>` counter in `parseBacklogRows` is fence-unaware and code-span-unaware, so any MENTION of `<details` silently drops every row after it.** `inFence` gates `headingRe` but the depth counter accumulates on every line, including inside fenced blocks and inline code spans. Measured: a fenced ```` ```\n<details>\n``` ```` block and an inline `` `<details>` `` mention each mark the FOLLOWING live row `inDetails: true`; `readCorpus` filters those rows out of `live` with **no `cannotCheck`**, so they appear in neither the recommended nor the declined list — while the artifact states the declined pool is *"complete rather than curated"*. Also blinds `backlogDischargeStatus` to those rows and makes `dischargeBacklogRows` report `not-found` for a row that exists. **Zero such mentions on this repository today**, so it is latent here and live for any project whose backlog discusses `<details>`. Found by the `M6.E8` REVIEW pass-3 security audit, reproduced. Fix: skip the counting inside fences and strip code spans first, or anchor on `^\s*<details` / `^\s*</details>` as block openers. |
