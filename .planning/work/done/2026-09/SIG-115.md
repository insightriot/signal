| B115 | `fixed` | P2 | **FIXED 2026-09-04, same day as filing — `/sig:drive` never checked whether it was running the installed Signal, and it is the command where that matters most.** `readBindingBanner` (`B52`, `v0.1.20`) is called by `/sig:status` and `/sig:resume` and by **no other command**. `/sig:drive` is the one that *acts*, repeatedly, on instructions it read once — so a stale binding means an entire autonomous run executes a retired release's rules, and the longer the run the more it does before anyone notices. ⚠ **Found by RUNNING the command, not by reading it.** The first live `/sig:drive` invocation (2026-09-04, this repository) loaded **`v0.1.34`'s** copy of `drive.md` while **`v0.1.36`** was installed and recorded in `installed_plugins.json`. The front end — `0a` propose / `0b` confirm / `0c` preflight, shipped in `v0.1.35` and `v0.1.36` — **was not in the file the run executed**, and the run reported no anomaly because it had no way to see one. Verified precisely: the `0.1.34` cached copy has zero occurrences of the front-end headings, the `0.1.35`/`0.1.36` copies have them, and `readBindingBanner` invoked **from the bound `0.1.34` copy** renders the correct RETIRED-code banner naming both paths. **The mechanism was not broken — nothing called it.** `B52`'s own design note says the command path *"re-reads both files at the moment of use, which is the only moment that can observe it"*; that reasoning applies with more force here and the wiring simply stopped at the two briefings. **Fix:** `drive.md` step 0 calls it **before the front end** and **halts** rather than reporting — the distinction is the finding, not a preference. A briefing's reader is present and deciding; this command is not. Three tests: it is called, it stops, and it stops *first*. ⚠ **The run that found this also could not have exercised `M6.E6`'s queue wiring** — that work merged to `main` unreleased, so no cached copy carries it. Same class as the `v0.1.35` gap: unbumped work on `main` is unreachable by any session. |
