| B42 | `fixed` | **P1** | **A linear-mode project cannot run `/sig:ship` at all — the FR1 retro gate hard-halts on `current_epic: null`, and there is no bypass.** `shipFR1Check` (`retrospective.js:751-762`) returns `{halt:true, code:'NO_CURRENT_EPIC'}` whenever `!state.current_epic`, *before* any Epic-close/per-slice reasoning. `ship.md:27` runs that check **"before any other Workflow step, regardless of `gate_strictness`"** and `ship.md:41` states **"No bypass"** — no flag, no env var, no extra-args trick. `ship.md:34` compounds it: Step 0.5's milestone-file derivation parses `state.current_epic` and halts if the derived `MILESTONE-{n}.md` is missing, which is also unsatisfiable with no Epic. **Linear mode is first-class everywhere else** — `new-project.md:35` (*"Without `--epic`, the project starts in linear mode"*), and the identical Epic-mode/linear-mode profile+artifact-naming preamble in `discuss.md:13`, `plan.md:13`, `execute.md:13`, `verify.md:13`, `review.md:13`, **`ship.md:13` itself**, plus `status.md:115` / `resume.md:143`. So six phase commands support a mode the seventh refuses to run. **Not an untested gap — the halt is asserted:** `tests/ship-fr1.test.js:125` (*"halts with NO_CURRENT_EPIC when state.current_epic is empty (AC1-extended)"*) and `:138`; `M4.5.E9-VERIFICATION.md` records AC1-extended as PASS. Fixing this means **rescoping an AC**, not just editing a branch: the M4.5.E9 author read empty `current_epic` as *"state is broken"*, not *"this project has no Epics."* **Landed `3d41159` (2026-05-26, M4.5.E9.S1.t6), shipped in v0.1.3 (2026-05-31) — live across nine releases (v0.1.3 → v0.1.11), invisible because Signal-on-Signal has run Epic-mode since M4.5.E11.** **Reported live 2026-07-26** from `eval-project-A`, which has run linear (`current_epic` always null) its whole life: FR1 halted `/sig:ship` on step zero; the close was completed by hand. **Fix shape — and it is a rescope, not a three-liner. Three separate gates each assume an Epic, and fixing only the first leaves ship still blocked:** (1) `shipFR1Check`'s early halt (`retrospective.js:755`) → return `{halt:false, skipped:true, reason:'linear mode'}`; (2) **`ship.md:34`, which runs *before* it** — Step 0.5 derives the milestone file by parsing `state.current_epic` and halts on its own when the derived `MILESTONE-{n}.md` is missing, so a linear project halts one step earlier regardless; (3) `isEpicCloseByState` (`retrospective.js:412`) returns `false` on `!state.current_epic`, so the entire B26/B30 Epic-close machinery — `aboutToClose`, the synthesized post-SHIP state, the row-absence fallback — is **dead code in linear mode**. Decide what the close unit even *is* for a linear project before touching any of them (`resume.js:129` already says *"in linear mode the retro is milestone-scoped"* — the intent existed and no gate implemented it). **Sharpest evidence the halt was never a deliberate reading:** the layers disagree on the same condition. Layer 1 fails **closed** (hard halt, no bypass); **Layer 2 fails open** — `checkProposedStateWrite` returns `{block:false}` on a null/absent `current_epic` (`retrospective.js:500-502`). One missing Epic, a hard block in one layer and a silent pass in the other. **P1 rather than P2:** this is not degraded behavior, it is a documented mode blocked end-to-end with the escape hatch explicitly designed out. **→ Status reconciled 2026-08-02** (fix lane, BUGS.md status-vs-code sweep): fixed in **M5.E9 (D-M5E9-1)** and never flipped — all three gates, which is what the fix shape above demanded. (1) `shipFR1Check` returns `{halt:false, skipped:true, reason:"linear mode …"}` on `detectMode(state) === "linear"` (`tools/lib/retrospective.js:764-790`). (2) `ship.md:34` Step 0.5 is now **Epic mode only** and passes `milestoneContent: null` in linear mode, naming this entry as its reason. (3) `isEpicCloseByState` returning `false` in linear mode is now correct by scope, not dead code — the gate is Epic-only by ratified decision.
