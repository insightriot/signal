## `detectProjectKind` calls every non-git directory `greenfield`, so a real codebase is told to start fresh

**Status:** needs-triage

**Status: verified by execution WITH A CONTROL ARM, 2026-08-27.** `detectProjectKind`
returns `greenfield` for **any** directory without a `.git`, however much source it contains — so
`/sig:add`'s missing-`.planning/` error tells the operator of a full codebase to *"start fresh"*
when *"scan the existing code"* is the correct advice.

**The deciding line** (`tools/lib/add.js:192`):

```js
export function detectProjectKind(baseDir) {
  if (!existsSync(join(baseDir, '.git'))) return 'greenfield';   // <-- returns here
  ...
  const hasSource = entries.some(...)                             // <-- dead for non-git dirs
  return hasSource ? 'brownfield' : 'greenfield';
}
```

**Measured, with the control arm that makes it a finding rather than one odd row:**

| Directory | Returns | Message composed |
|---|---|---|
| this repo (`.git` + source) | `brownfield` | run `/sig:init` — correct |
| `examples/url-shortener` (real Node project, no own `.git`) | **`greenfield`** | run `/sig:new-project` — **wrong** |
| scratch: full codebase, **no `.git`** (`package.json` + `src/` + `README.md`) | **`greenfield`** | run `/sig:new-project` — **wrong** |
| scratch: **truly empty** dir, no `.git` | `greenfield` | run `/sig:new-project` — correct |

**Rows 3 and 4 are indistinguishable.** A full codebase and an empty directory produce the same
verdict and the same advice. The `hasSource` scan that exists precisely to tell them apart is
unreachable for either, because neither has a `.git`.

**The consequence, in the user's terms.** `buildMissingPlanningError` exists to route someone to the
right onboarding command. For a non-git codebase it routes them to `/sig:new-project` (*"start
fresh"*) instead of `/sig:init` (*"scan it"*). Following that advice onboards a real project as a
blank one.

**How common is a codebase with no `.git`?** More common than it sounds: an unpacked archive, a
vendored or downloaded project being evaluated, a subdirectory of a larger repo (which is what
`examples/url-shortener` is — the case that surfaced this), or someone who simply has not run
`git init` yet. The last is also the case where the advice matters most, because they have the most
existing code and the least scaffolding.

**Priority P3, not P2:** the failure is a wrong *message* on an error path, not data loss or a wrong
write. Nobody is broken by inaction — only by taking the advice, which is `B102`'s shape at much
lower stakes.

**Fix shape (candidate, not decided).** Do the `hasSource` scan **first** and let `.git` be one
signal among several rather than a gate. ⚠ **Not obviously free:** `.git` is currently doing double
duty as a cheap "is this a project root at all" guard, so removing it as a precondition means
deciding what an empty non-git directory should return, and `NON_SOURCE_ENTRIES` becomes
load-bearing where today it is unreachable for this case. Worth pairing with a test that asserts the
two scratch directories above return **different** verdicts — the assertion that currently cannot
pass.

**Found 2026-08-27** at `M6.E5` EXECUTE, by the wave-1 first-execution probe (`S1.t0`) that the
plan scheduled specifically to run existing machinery before building on it. The probe's stated
purpose was to check whether `detectProjectKind` was usable for `FR5.3`; the answer was no, and the
reason turned out to be a live defect on a different command's path.
