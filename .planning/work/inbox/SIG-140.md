## `claude-review` CI fails before reviewing: claude binary missing on the runner

**Status:** needs-triage

**The `claude-review` CI workflow fails before reviewing anything: the Claude CLI is not on the runner.** Exact error, twice on PR #246 (initial run and an explicit `--failed` re-run): `Action failed with error: Failed to add marketplace 'https://github.com/anthropics/claude-code.git': ENOENT: no such file or directory, posix_spawn '/home/runner/.local/bin/claude'`. The job ends in ~20-30s having posted **zero** findings and logging *"No buffered inline comments"* — so a green-looking PR page with a red `claude-review` is indistinguishable at a glance from a reviewer that ran and found nothing.

**Not transient, and not caused by the diff.** The same workflow passed earlier the same day on PR #243 (10m19s), #244 (9m44s) and #245 (49s), then failed twice consecutively on #246. Only the release cut sits between them (`plugin.json`/`package.json` version bump, CHANGELOG, `docs/map/index.html`, `facts.md`, `tools/cut-release.js`) — none of which the review action reads. **Cause not established**; the installer step is the place to look, not the repo. **→ Third consecutive failure 2026-09-08, and it narrows the cause:** PR `#247` — whose entire diff is *this bug entry* in `BUGS.md` — failed identically (20s, same `ENOENT`). So the release cut is **ruled out**: the reasoning above ('only the release cut sits between them') was the best available inference from two data points and is now superseded by a third. The failure is diff-independent and reproduces on any PR opened after roughly 23:20 UTC. Whatever changed is in the action's own environment, not this repository. **→ RECOVERED 2026-09-08, and the recovery is itself the evidence.** PR `#248` ran `claude-review` to **success in 9m50s** and posted a real inline finding. So the failure was **transient and has cleared**, and this entry's own sentence — *"reproduces on any PR opened after roughly 23:20 UTC"* — is now falsified: it was the best available inference from three data points and the fourth broke it. ⚠ **That is this row's second superseded inference in two days** (the first was *"only the release cut sits between them"*), which is the pattern worth keeping rather than either conclusion. **Nothing was fixed here**; the cause was never established and nothing rules out a recurrence, so the two questions below stand unchanged — in particular that a job failing in the *"looks fine"* direction is still indistinguishable in the PR UI from one that reviewed cleanly.

⚠ **The consequence is the one this repo cares about most.** `v0.1.39` merged and published **without a passing external review pass**, on the very release that wired the fresh-context reviewer as a required REVIEW step because two review passes had found six issues an in-session review missed. The required status check is `test` alone, so the ruleset permitted the merge; that is the ruleset working as configured, and it also means **a broken reviewer does not block anything.**

**Two things worth deciding, not assumed:** whether `claude-review` should be a required check (it would have blocked this release, which may or may not be wanted for an infrastructure failure), and whether a review job that posts zero findings *because it never ran* should be distinguishable in the PR UI from one that reviewed cleanly. The second is the more valuable of the two — a check that fails silently in the direction of "looks fine" is the never-called-guard class.
