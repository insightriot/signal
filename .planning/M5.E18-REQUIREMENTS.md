# M5.E18 — The archive half, for the projects Epic-gating does not reach

**Epic:** M5.E18 · **Tier:** FULL (project default — no Epic-scoped override)
**Opened:** 2026-08-03 · **Target release:** v0.1.18 *(v0.1.17 was cut for `B70` alone — D-M5E18-5)*

---

## Why this Epic

**Signal's archive paths reach 4 of 12 readable projects.** Both are Epic-gated *by construction*,
not by omission:

- `planArchiveMoves` filters its input through `EPIC_ID_STRICT_RE` and only matches
  `.planning/{epicId}-{suffix}.md` (`archive-tree.js:96-110`).
- `extractEpicSection` rejects any non-strict ID (`evict.js:175`); `deriveEpicArchiveDir`
  **throws** on one (`evict.js:243`).

So the de-prose, stamp, `BACKLOG`-create and v3-rename halves of `/sig:migrate-memory` work
everywhere, and **the halves that actually stop `.planning/` from growing forever reach a third of
the corpus.** That is why nextpass still runs Curator — reported 2026-08-02, citations checked:
*"`reconcile --apply`'s move half has no Signal equivalent for linear slices."* Their conclusion is
correct.

**This is `B42`'s shape one layer over** — a documented mode that a whole subsystem silently does not
serve, invisible because Signal-on-Signal has been Epic-mode since M4.5.E11.

### What DISCUSS measured, and how it changed the Epic

Three real trees were walked during DISCUSS rather than quoted from the backlog. Two findings
reshaped the scope:

**1. There is no single "prefix" to read.** `BACKLOG.md` framed the problem as *"the prefix is not in
`current_epic`'s contract."* Measured, it is worse: **nextpass has no single prefix at all** — 10+
unit names, some beginning with the word `PLAN`, so `PLAN-GATE-A.md` is ambiguous on its own. A
declared-prefix field cannot express that shape. (→ **D-M5E18-2**)

**2. The retro requirement, not the prefix, is the harder blocker.** **None of the three projects has
a single retrospective file.** Closure today is *"a retro exists"*, so even with grouping fixed the
planner would move **zero files** on all three. (→ **D-M5E18-3**)

| Project | `current_epic` | Mode | Naming | Retros | Verdict readable |
|---|---|---|---|---|---|
| `agent-tools-sync` | `M1` | linear | one prefix (`M1-*`) | 0 | prose only |
| `traction-engine` | `PHASE12` | linear | nested (`PHASE10-S4-*`) | 0 | yes (`Verdict: PASS`) |
| `nextpass` | `null` | linear | 10+ unit names | 0 | no |

**Both projects carrying a usable unit name sit in `linear` mode** — `EPIC_ID_STRICT_RE` rejects
`PHASE12` and `M1` alike. Any guard that asks *"which unit is current"* through a strict-gated path
receives `null` and silently never fires. (→ **D-M5E18-4**)

## Functional Requirements

### FR1 — Units are derived from filenames

The archive planner groups `.planning/*.md` into units by matching **known artifact suffixes from
the right-hand end** of each filename. The suffix list is **declared in one place** and is the same
list the rest of the doc-runtime already uses for scaffold suffixes.

**Acceptance criteria**

- **AC1.1** — `PHASE10-S4-PLAN.md` → unit `PHASE10-S4` (nested units survive; the match is
  right-anchored, not first-hyphen).
- **AC1.2** — `PLAN-GATE-A-RESEARCH.md` → unit `PLAN-GATE-A` (a unit name that begins with an
  artifact word is not mis-split).
- **AC1.3** — `M1-PLAN.md` → unit `M1`; `M5.E16-PLAN.md` → unit `M5.E16` (Epic IDs keep working —
  this replaces nothing that works today).
- **AC1.4** — Run against `traction-engine`'s real tree, the derived unit set is exactly
  `{PHASE7, PHASE8, PHASE9, PHASE10, PHASE10-S4, PHASE10-S5, PHASE11, PHASE12}` and
  `CONTEXT.md` / `DECISIONS.md` / `INDEX.md` / `LANDSCAPE.md` / `OPEN-QUESTIONS.md` /
  `FUTURE-IDEAS.md` are **not** members of any unit.
- **AC1.5** — Files with no recognised suffix are returned in a named **`ungrouped`** collection.
  A test asserts `NEXTPASS-STACK-DECISION.md`, `BUGHUNT-2026-06-12.md` and `PLAN-SLICE-VOICE1.md`
  land there. **An empty `ungrouped` must be distinguishable from an unreported one** — the
  dry-run prints the count unconditionally, including when it is zero.

### FR2 — Closure has three outcomes

A unit resolves to exactly one of **`closed`**, **`open`**, or **`cannotDetermine`**.

`closed` requires all three: (a) the unit has a `VERIFICATION` or `SHIP` artifact; (b) the unit is
**not** the current unit; (c) where a verdict line is readable, it passed.

**Acceptance criteria**

- **AC2.1** — `cannotDetermine` is a value in the returned data structure, not a rendering
  decision. A caller can count the three statuses without re-reading any file.
- **AC2.2** — A unit with a terminal artifact whose verdict line is **absent or unparseable**
  resolves `cannotDetermine`, **never** `closed` and never `open`. Fixture: nextpass's
  `PLAN-SLICE-SSO-VERIFICATION.md` (no verdict line) and `agent-tools-sync`'s `M1-VERIFICATION.md`
  (prose *"Verdict remains"*).
- **AC2.3** — `traction-engine`'s `PHASE8` resolves `closed` (`Verdict: PASS`, not current).
- **AC2.4** — **The regression guard.** `agent-tools-sync`'s `M1` has a `VERIFICATION` artifact and
  **is** the current unit → resolves `open`, and appears in **no** proposed move. This is the test
  that pins the not-current clause, which carries the whole guard (D-M5E18-3).
- **AC2.5** — A unit whose readable verdict is **FAIL** resolves `open`, not `closed`.

### FR3 — The current-unit guard reads the raw field

The not-current check sources its value from the **raw `current_epic` string** on STATE, plus the
unit names derived in FR1. It does **not** route through `EPIC_ID_STRICT_RE`, `detectMode`,
`isEpicDone`, or any helper that fails open to `null` on a non-strict value.

**Acceptance criteria**

- **AC3.1** — With `current_epic: PHASE12` (non-strict, `detectMode` → `linear`), unit `PHASE12`
  resolves `open` and is excluded from every proposed move. **RED-first**: this test must fail
  against a strict-gated implementation.
- **AC3.2** — With `current_epic: null` (nextpass), no unit is excluded on current-unit grounds,
  and the planner still resolves the other two clauses. A `null` current unit must not be treated
  as *"every unit is current"* or *"no unit is current"* by accident — the behaviour is asserted.
- **AC3.3** — A test asserts the guard's value is byte-equal to `readState().current_epic` for a
  non-strict input, pinning that no normalisation silently drops it.

### FR4 — The dry-run reports four statuses (`B63`)

M5.E16's four-status model is ported into `/sig:migrate-memory`'s dry-run so `0` stops meaning both
*could not look* and *checked and clean*.

**Acceptance criteria**

- **AC4.1** — The dry-run output distinguishes **checked-and-clean** from **could-not-check** for
  every unit, and reports the `cannotDetermine` count as its own line.
- **AC4.2** — A project where every unit is `cannotDetermine` produces output that **cannot be read
  as "nothing to archive"** — a test asserts the rendered text differs from the all-clean case.
- **AC4.3** — Run against Signal's own `.planning/`, the dry-run proposes moves only for Epics whose
  retro is real (see FR5) and reports the rest by status.

### FR5 — A stub retro is not closure (`B64`)

`senseArchiveTree` currently does `closedEpicIds = retros.map(r => r.epicId)` (`archive-tree.js:357`)
with **no `isStub` filter**, though `retro-index.js` already computes one.

**Acceptance criteria**

- **AC5.1** — A stub retro yields `cannotDetermine` for its unit, not `closed`.
- **AC5.2** — Against Signal's own tree, `M4.5.E1`, `M4.5.E3`, `M4.5.E6` and `M4.5.E7` — the four
  stubs measured at DISCUSS — are **not** proposed for archive. **RED-first**: this fails today.
- **AC5.3** — `isEpicDone` (`retrospective.js:168`), currently `existsSync(retroPath)`, either
  gains the same non-stub condition or its callers do. Whichever is chosen, a test asserts a stub
  retro does not report the Epic done. *(`isEpicDone` also backs `/sig:discuss`'s done-Epic guard —
  PLAN decides whether tightening it there is in scope or a separate change, and records why.)*

### FR6 — The linear-`RETROSPECTIVE.md` applicability gap

M5.E16 REVIEW-2 `S3`: check `(c)`'s applicability probe keys on a strict filename and misses the
unprefixed `RETROSPECTIVE.md` that linear projects write (`M5.E16-REVIEW-2.md:70-84`). Left alone
there because it fails **safe** (`not-applicable`, never a false clean). Folded in here because this
Epic re-measures the same corpus.

**Acceptance criteria**

- **AC6.1** — A linear project with an unprefixed `RETROSPECTIVE.md` is evaluated by check `(c)`
  rather than reported `not-applicable`.
- **AC6.2** — The fail-safe direction is preserved: no input that previously produced
  `not-applicable` now produces a false `clean`.

## Non-Functional Requirements

- **NFR1 — Read-only until `--apply`.** Dry-run is the default and writes nothing, matching
  `/sig:migrate-memory`'s existing contract. Relocate-never-delete; every move is git-reversible.
- **NFR2 — Offline and deterministic.** No network. Same inputs → same proposed moves, so a dry-run
  can be diffed against the subsequent apply.
- **NFR3 — Fail-open on unreadable input.** A malformed STATE, an unreadable artifact, or a
  permission error yields `cannotDetermine` for the affected unit and never aborts the run — the
  status exists precisely so failure has somewhere truthful to go.
- **NFR4 — Path confinement.** Derived unit names reach the filesystem as path components and are
  attacker-influenced in principle; they route through `path-confine.js` as existing archive paths
  do. A unit name containing `..` or a separator must not escape `.planning/archive/`.
- **NFR5 — No silent caps.** If the planner bounds what it proposes, the dropped set is reported by
  count and reason.

### FULL-tier NFR checklist — dispositioned, not skipped

Signal is a CLI plugin with no served surface. Each item is marked with its reason rather than
passed over:

| Item | Disposition |
|---|---|
| Health / liveness probe | **N/A** — no long-running process; commands are invoked and exit. |
| Graceful shutdown / signal handling | **N/A** — no daemon. Atomic writes + `file-lock.js` already cover interrupt-mid-write, which is the real analogue and is unchanged by this Epic. |
| Structured request logging | **N/A** — no requests. The dry-run report *is* the audit trail, and FR4 governs it. |
| Security headers (CSP / HSTS / X-Content-Type-Options) | **N/A** — nothing is served over HTTP. |
| Rate limiting | **N/A** — not publicly exposed; no network calls (NFR2). |
| Input validation at boundaries | **IN SCOPE** — NFR4. Derived unit names are the untrusted input this Epic introduces. |

## Open questions for PLAN

1. **Where does unit derivation live?** `archive-tree.js` already owns `planArchiveMoves`, but
   `evict.js` and `retro-index.js` each carry their own strict-ID assumptions. PLAN decides whether
   FR1 is a new module the three call, or a widening of `archive-tree.js`. **Two implementations of
   one rule is the shape M5.E13 REVIEW flagged** — one home, or an explicit reason for two.
2. **What is the archive directory for a non-Epic unit?** `deriveEpicArchiveDir` yields
   `.planning/archive/{M}/E{n}` from a strict ID and **throws** otherwise. `PHASE10-S4` and
   `PLAN-GATE-A` have no milestone to key on. PLAN proposes the layout; it must be stable across
   runs so a second dry-run proposes no moves.
3. **Does `isEpicDone`'s tightening (AC5.3) reach `/sig:discuss`'s done-Epic guard in this Epic?**
   Tightening it means an Epic with a stub retro no longer blocks re-entry — which may be correct
   or may surprise. Decide and record.

   **Answered in advance by `B71` (filed 2026-08-03): yes, in scope.** `isEpicDone` is
   `existsSync(retroPath)`, so `isEpicDone('M5.E17')` is **`false`** — that Epic shipped as v0.1.15
   with no retrospective, so the done-Epic guard would not halt on it and
   `M5.E17-REQUIREMENTS.md` is clobberable by anyone who sets `current_epic` back to it. The
   failure is live, not hypothetical, and it is the **same weak signal** FR2/FR5 are already
   rewriting: *a file existing* standing in for *work being finished*. Three mechanisms read it
   (archive planning, the `/sig:ship` retro gate, the `/sig:discuss` guard) and fixing it in one
   place while leaving the others is how this Epic would re-create its own defect class. PLAN
   confirms the decision and records it; the question is no longer open in the sense of
   *undecided*, only of *unratified*.

4. **Does FR2's closure rule need a third detector for Signal's own repo (`B71`)?**
   `B71`'s fix shape is *"a world-check keyed on something outside `.planning/` — a tag, a
   `plugin.json` bump, a release commit — so 'a release happened for this Epic' is answerable
   without the phase ledger's cooperation."* That is FR2's question (*what proves a unit is
   closed*) pointed **inward** at Signal rather than outward at a user project. PLAN decides
   whether it is a fourth clause on FR2 or a separate slice — and, if deferred, says so in writing
   rather than by omission.
