## Functional requirements

Every FR starts with a test that fails on `main` before the fix (FULL, strict TDD).

### FR1 — Promote dedupe inside the lock (`SIG-277`, `D-M6E14-1`)
- **AC1.1** `newItems` accepts a dedupe key and, under the same `work` lock that allocates the ID,
  returns the existing record when one carries that `source_ref`, writing nothing.
- **AC1.2** `promoteInStore` uses it; the unlocked pre-check is removed or is only an early exit.
- **AC1.3** A test runs two promotes of the same block concurrently (two processes) and asserts
  exactly one record exists afterwards, **and** that the two calls actually overlapped.

### FR2 — Discharge never says done while a broken record could match (`SIG-278`, `D-M6E14-2`)
- **AC2.1** With any broken record present and exactly one readable open match, the row reports
  `unreadable`, naming the broken records, and nothing is closed.
- **AC2.2** With no broken records, behaviour is unchanged (one match → `discharged`).

### FR3 — A linked `.planning/` inside the repo works (`SIG-279`, `D-M6E14-3`)
- **AC3.1** With `.planning` a symbolic link to a folder inside the repository, `/sig:item` changes
  succeed and the views regenerate.
- **AC3.2** A link below `.planning/` (a linked view or record) is still refused, as now.
- **AC3.3** A `.planning` link that resolves outside the repository is still refused.
- **AC3.4** The v1→v2 migration refuses a linked `.planning` up front with a plain `CONFIG` message,
  not an IO error from the copy step.

### FR4 — Record writes either fully land or refuse up front (`SIG-280` (6), `D-M6E14-4`)
- **AC4.1** Before writing a record, every writer checks that the views can be regenerated (no
  hand-kept view, no linked `WATCHLIST.md`, readable archived Epic README YAML); if not, it refuses
  with the reason and writes nothing.
- **AC4.2** If regeneration still fails after a write, the error says the record **was** written and
  names the command that rebuilds the views. It never reads as "nothing changed".

### FR5 — `SIG-280` residue (`D-M6E14-5`)
- **AC5.1** The remedy for a broken record in `ship.md` §6.8 and `docs-sweep.md` names
  `git checkout --ours/--theirs <path>` for a conflicted record, and says plain `git checkout --`
  only helps when `HEAD` holds a good copy.
- **AC5.2** `refuseBroken` called from a read-only path (`probeCloses`) does not claim anything was
  or was not written.
- **AC5.3** `/sig:docs-sweep` reports a broken record once.
- **AC5.4** `confirmCloses`' `@throws` lists `NOT_FOUND`.

### FR6 — A proof hash must name one commit (`SIG-276`, `D-M6E14-6`)
- **AC6.1** A proof that matches more than one commit is refused at request time and at confirm time
  as ambiguous, naming the fix (use a longer hash).
- **AC6.2** The `ancestryFailure` comment in `work-records.js` matches the behaviour.

### FR7 — Lock messages and the stat race (`SIG-251`, `SIG-252`, `D-M6E14-7`)
- **AC7.1** When the holder is a live pid on this host, the held message states the real worst-case
  wait (10 × ttl).
- **AC7.2** A missing stat during acquisition is retried like a missing read, never treated as
  mtime 0.

## Non-functional requirements (FULL prompt, answered)

- Health probe, graceful shutdown, request logging, security headers, rate limiting: **N/A**. This is
  a local CLI plugin with no server, and this Epic adds no network call (FR6 uses local git only).
- **Integrity:** no change may weaken an existing refusal. FR3 narrows a symlink check, so AC3.2 and
  AC3.3 must hold, with tests.
- **Security:** M6.E12's hostile-repository rules still apply. A linked `.planning` is accepted only
  when its real path is inside the repository (`assertRealInsidePlanning`).
- **Performance:** the pre-write view check (FR4) must not read every record a second time on each
  write. Measured at PLAN.

## Blast radius

What this touches and does not change:
- **Code:** `work-records.js` (`newItems`, `requestCloses`, `confirmCloses`), `backlog.js` (promote,
  discharge), `path-confine.js`, `work-views.js`, `work-migrate-v2.js`, `file-lock.js`, `sweep.js`.
  `file-lock.js` is shared by `state.js`, `add.js` and `archive-tree.js`, so its tests run in full.
- **Stored data:** no record format change. `newItems` gains an option; existing calls are unchanged.
- **Docs:** `ship.md` and `docs-sweep.md` wording (FR5). Edits to `commands/*.md` can move the
  directive ceiling, so `ADHERENCE-LOG.md` may need regenerating; the merge uses `--merge` either way.
- **Users tracking `main`:** only Signal has a store today. A project with a linked `.planning` starts
  working instead of refusing.
- **Not touched:** the record schema, generated view formats, `STATE.md`, Epic artifacts.

## Outcome

- **Leading:** each of the eight defects has a test that fails on `main` before its fix and passes
  after. This is a completion check, stated here because it is what a reviewer will check first.
- **Lagging (the real outcome):** when priority 2 moves the first other project onto the store, none
  of these failure classes (twin records, a false discharge, a linked-`.planning` refusal, a written
  record with stale views, an ambiguous proof, a lock misjudged as stale) is filed against it.
  One such filing means the hardening missed a route, and it is traced before priority 2 continues.

## Out of scope, stated so it is a decision

- Turning the store on for new projects (`SIG-274`) and moving other projects onto it: priority 2.
- Folder-aware readers outside the store (`deriveRetroPath`, `published-facts.js`, …): M6.E11 retro,
  a later Epic.
- The PID-namespace limit of the dead-pid shortcut (M6.E11 retro): known limit, not changed.
