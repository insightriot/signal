## Important Issues

### I1 — `listDrainCandidatesWithRecovery` did not exclude standing entries · `drain.js:393` · **FIXED IN-PHASE**

The two candidate filters must agree, and only one was updated:

| Line | Filter | State at review |
|---|---|---|
| 315 | `listDrainCandidates` | `!dispositioned && !standing` ✓ |
| 393 | `listDrainCandidatesWithRecovery` | `!dispositioned` **only** ✗ |

So a standing entry sitting **below a dangling fence** would be recovered straight back into the
live candidate set — **S2's bug reintroduced by the one code path that exists to handle malformed
inboxes.** Narrow trigger (needs both an unclosed fence and a standing entry beneath it), real
consequence: the drain silently returns to reporting a permanent entry as live work.

**Same shape as `B107` and `B82`** — two implementations of one predicate, one updated, free to
disagree. Signal's own inbox would not have hit it today, because its standing entry sits above any
fence. Nothing would have caught it but a reader.

**Fix:** `!e.dispositioned && !e.standing && !seenStarts.has(...)`, with the reason recorded at the
line so the next reader does not "simplify" it back.

**Coverage written in-phase, and mutation-verified:** three tests in `tests/drain-standing.test.js`
— the fence is detected, a recovered **standing** entry stays out, and a recovered **non-standing**
entry still surfaces (so the fix is not a blanket drop). **Reverting the one-line fix turns exactly
the middle test red and nothing else; restoring it turns it green.** The test catches the defect
rather than merely accompanying it.

### I2 — `parseEntries`' JSDoc was detached from its function and its `@returns` was stale · `drain.js:128` · **FIXED IN-PHASE**

S2 inserted `STANDING_MARKER_RE` **between the JSDoc's closing `*/` and `export function
parseEntries`**, so the doc block no longer documented the function. The same block's `@returns`
still listed the pre-`standing` shape — a documented return type contradicting the actual one, in a
repo whose standing rule is that stale docs are a defect rather than cosmetic.

**Fix:** const moved above the doc block (reattaching it), `standing: boolean` added to `@returns`.

### I3 — `plan-checker.md`'s reach numbers were hand-typed, duplicating `REACH` · **FIXED IN-PHASE**

`published-facts.js` states that `describeReach` is *"the one place a reach figure becomes prose…
nothing types the numbers."* `plan-checker.md` is a **prompt** — static text that cannot call a
function at render time — so its *"10 of 13 projects evaluable"* sentence is necessarily
hand-written. That makes it a **published fact duplicated from `REACH` and free to drift**: exactly
`M6.E2`'s defect class, committed inside the Epic that reviews for it.

**The prompt cannot be made dynamic, so the fix is `M6.E2`'s own mechanism** — derive, then compare.
A test reads `REACH['plan-internal-consistency']` and asserts the file contains `{evaluable} of
{total}`. Editing `REACH` without editing the prompt now turns the suite red.

## Suggestions

- **S1 — `QUANTITY_RE`'s `s` and `x` unit alternatives are broad.** `\b\d+\s*(?:…|s|×|x)\b` will
  match a bare *"2 s"*. Checked against false-positive shapes: *"2 slices"* does **not** match (no
  word boundary after `s`). Left as-is deliberately — the detector optimises recall, and a stray
  flag costs one paragraph of reviewer attention. Recorded so the next reader knows it was
  considered rather than missed.
- **S2 — `REACH` now carries a key with no corresponding check in `PUBLISHED_FACT_CHECKS`.**
  Intentional and commented at the line: this detector runs at PLAN, not at sweep, but its reach
  belongs in the one table that holds reach. No test iterates `REACH` keys, so the orphan is inert.
  Worth revisiting only if a key↔check invariant is ever added.
