## What this could not establish

- **No other project has used any of this.** Every test builds a temporary store; the only real store
  is Signal's own, which has no linked `.planning`, no conflicted record and no concurrent promote.
  The Outcome's lagging measure — none of these failure classes filed against the first project moved
  onto the store in priority 2 — cannot be checked until that happens.
- **The twin-record race is shown in one process, by a seam.** `acquireLock` never waits, so two real
  processes produce one record and one LOCKED; the deterministic interleave stands in for a race the
  real scheduler would produce rarely. No store-on caller of `promoteToBacklog`/`promoteToBugs` exists
  yet (the drain refuses with the store on), so the path is reachable only through tests today.
- **Performance is one machine.** The 272 ms figure is a Mac Studio with a warm filesystem cache; a
  slower disk or a cold cache was not measured.
- **A failure the write itself creates is not checked beforehand** — e.g. a new `history/` year file
  that turns out hand-kept. `regenerateAfter` reports it ("the change stands … make any item change").
- **The ambiguous-proof check at request time asks the repository git finds from `baseDir`**, an
  enclosing one included — the same one the confirm-time checks ask. A project nested in an unrelated
  repository would be checked against that repository; this is existing behaviour of every proof
  check, not new to this Epic, and was not changed.
- **`diffRequirementCoverage` reads ids and tokens, not meaning** (`B116`, `B126`): a requirement can
  read as covered because the report names it. The per-AC evidence above is what carries the claim.
