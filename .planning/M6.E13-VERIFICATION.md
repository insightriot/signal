### VERIFY pass 2 (2026-10-04, at `dded23f`, after loop 1)

**PASS with documented limits. 28 of 28 acceptance criteria PASS; 3 of 3 testable NFRs PASS.** Pass 1
found AC7.2 and AC3.2 PARTIAL (kept below as the record of what pass 1 found). Loop 1 fixed them in
`64dc0bd` (AC7.2), `17cde58` (AC3.2) and `543e5de` (hook wording). Pass 2 did not just re-run the fix
tests; it probed each fix in scratch copies and temp git repos:

- **AC7.2, 19 hostile cases through all three callers** (`probeCloses`, `confirmCloses`,
  `closeEpicCheck`), each in a fresh clone. No false confirm. A branch named with the full 40-hex SHA
  of an off-main commit, pointed at `origin/main`, gives `not-on-default-branch` (git reads a full SHA
  as an object id first). A 40-hex name of no object gives `unknown-commit`. 41-hex and 64-hex ref
  names, a short prefix of a real off-main commit reused as a branch name, a `.git/<hex>` pseudo-ref
  file, and an annotated tag object (full and short id) all give `proof-names-a-ref`. A blob and a tree
  give `unknown-commit`. A commit on local `main` but not on `origin/main` gives
  `not-on-default-branch`. The Epic gate counts it, because D-M6E13-22 checks `HEAD`, as designed.
  With `origin/HEAD` deleted, the `main` fallback confirms a real commit. With `origin/HEAD` pointed
  at a local branch, the result is `no-default-branch`. An uppercase proof and the suffixes
  `^{tree}`, `~1`, `@{-1}` and `^0` are refused by `requestClose` (SCHEMA). If a record is edited by
  hand to carry one, `serializeRecord`/`listRecords` marks the record broken, so it never reaches git
  and `closeEpicCheck` throws SCHEMA. Across all 204 recorded git calls, no argument began with `-`
  apart from the code's own fixed flags.
- **AC3.2, a swallowed call planted in each of the 28 reader entry points** (one at a time, in a
  scratch copy, as `try { parseBacklogRows('## a\n') } catch {}` at the top of the entry function).
  Every plant failed `list-parser-ban.test.js` with "the throw was swallowed", on both the v1 and v2
  twins. The failure stayed with the planted reader and the readers that call it (for example,
  `runAdvise` alone: 2 failures; `readCorpus`: 10, its callers included). So the count resets between
  readers. `forbiddenCallCount` and `resetForbiddenCalls` are referenced only in `legacy-lists.js`
  (where they are defined) and in two test files. No production code reads them.

**One new low-severity finding (not blocking):** an *ambiguous* short id still confirms when a ref
with the same name points at one of the colliding commits. Repro: two commits sharing a 7-hex prefix
`P`, one of them (`a`) on `origin/main`. With no ref, `probeCloses` gives `unknown-commit`. After
`git branch P a`, it gives `confirmable: ["SIG-1"]`. The confirmed commit does start with the proof
and is on the default branch, so this is not a false confirm of a non-commit. But it contradicts the
`ancestryFailure` comment ("An ambiguous short id makes `rev-parse` fail"). It needs a planted
7-hex collision plus a local ref, so it is recorded as a limit, not a PARTIAL.

### VERIFY pass 1 (2026-10-04, at `0774820`)

**PASS with documented limits.** All 28 acceptance criteria and the 3 testable NFRs were checked
against code, tests, and the live repository. 26 PASS and 2 PARTIAL. No requirement is missing, the
full suite is green, and `checkRecords` finds 0 problems on this repository.

The two PARTIALs are real defects I found by probing, not gaps in paperwork:

- **AC7.2: a hex-named branch or tag confirms a close.** `ancestryFailure`
  (`plugin/tools/lib/work-records.js:1363`) passes `${proof}^{commit}` to `git merge-base`.
  `${proof}` resolves as a ref name before it resolves as an abbreviated hash. In a temp clone with a
  branch `deadbee` and a tag `cafebab` on `origin/main`'s commit, `requestClose` with those proofs
  followed by `confirmCloses` returned `confirmed: ["SIG-1","SIG-2"]`. Neither proof is a commit. That
  is a false confirm, which is the one outcome AC7.2 says never happens. The same helper is the
  D-M6E13-22 Epic-close gate (`work-records.js:1309`), so `closeEpic` is affected too. **This should be
  fixed before SHIP.** Suggested fix: `git rev-parse --verify --quiet <proof>^{commit}`, then require
  the resolved full SHA to start with the proof.
- **AC3.2: a parser call inside an empty `catch {}` passes the ban.** I added
  `try { parseBacklogRows('## a'); } catch {}` to drive's store-on branch in a scratch copy, and
  `list-parser-ban`, `legacy-lists` and `drive-store-on` all passed (160/160). The header of
  `tests/list-parser-ban.test.js` says the check covers try/catch. It only covers a catch that copies
  the ban's message into the result. The uncaught call was detected (2 tests failed). Suggested fix:
  `guard()` in `legacy-lists.js` counts calls while the flag is set, and the test asserts the count is
  0 after each reader.

## What this could not establish

- **Live history views:** `history/*.md` has never been produced on this repository. Every live
  `closed` event is dated 2026-09-29 or later, and the newest event is 2026-10-04, so the 30-day
  window has not opened. AC6.2's history path is proven by unit test only. Around 2026-10-29, the 154
  closes now listed in the views move out to history together.
- **Writes outside the hook:** the hook sees only Edit, Write and MultiEdit. A record changed through
  Bash (`sed`, `echo >`) or by another tool is not blocked. `checkRecords`/AC5.2 would report such an
  edit afterwards, but would not stop it.
- **Hook message wording:** pass 1 found that the message for a record file said the record "is
  generated from the work records". Fixed in `543e5de`: it now says records are written only through
  `/sig:item`.
- **AC3.2 coverage in practice (pass 1; the hole is fixed, see pass 2):** I did not search the existing store-on readers for a parser call
  already inside a swallowing catch. The hole is demonstrated, but whether live code uses it is not
  established.
- **AC7.2, ambiguous id plus a same-named ref (pass 2):** see the Verdict. Its scope is narrow
  because it needs a deliberate 7-hex collision and a local ref, and the commit it confirms does
  start with the proof. Recommend correcting the `ancestryFailure` comment, or refusing the proof when
  `rev-parse --disambiguate` lists more than one commit.
- **Replace refs and grafts (pass 2, not probed):** `git merge-base` follows `refs/replace/` and
  grafts, so someone with write access to the local repository could make a commit look like an
  ancestor. That person could also edit the records directly, so it is outside AC7.2's threat model.
- **AC7.2 in practice (pass 1):** the false confirm needs a local ref whose name is hex. I did not check
  whether any ref like that exists on this repository or its remote. The six live confirms named real
  commits on `origin/main` (`413cc5e`, per `a01d464`), but I did not independently re-run their
  ancestry.
- **AC4.1 scope:** "every command behaves byte-identically" is pinned for the 25 AC3.1 reader entry
  points and the store-off capture writers in the golden. Command Markdown changed in 12 files.
  Whether an agent following the edited store-off wording does exactly what it did at `v0.1.47` is not
  machine-checked.
- **AC4.2 read equality:** it was compared in a scratch repository with a fresh git history, so
  `created`/`triaged` dates from git fallback differ by construction. Date equality under the real
  history rests on `work-convert-live.test.js` and the MANIFEST.
