## 0. Headline

**Cross-model adversarial review is portable for a solo dev without new infrastructure — but not without a second vendor's AI coding CLI.** There is no API key, no daemon, no server, and nothing this skill asks you to configure. The mechanism is a shell-out to a *second AI coding CLI already installed and logged in on the same machine*. On a Claude Code host, same-family exclusion rules out the `claude` target, so the default lands on `codex`, with `grok` and `cursor-agent` as the other routes. Whatever each vendor charges for that CLI's own login is a product question outside this tree and **could not be verified here**; what the tree establishes is that the skill supplies no credentials of its own and inherits whatever auth the second CLI already has.

Two further findings shape what the capability is worth:

1. **Cross-model buys exactly two mechanical things** — a one-notch confidence promotion on agreement, and permission to skip a validator. It adds **no new detection path**: the peer is adversarial-only, gets the *same* persona brief, and is *mutually exclusive* with the in-process adversarial reviewer. It replaces a lens; it does not add one.
2. **Could not verify any measured cross-model-vs-same-model comparison.** The repo's one rigorous eval (150 runs, blind judge) compares models *within* the peer slot and states independence is "not a variable here." The effectiveness premise is carried by one practitioner report, and the repo records the correlated-blind-spot caveat against itself.

The thing in this repo that most directly addresses Signal's v0.1.9 failure class is **not** the cross-model mechanism. It is technique 5 of the adversarial persona brief — §1.8.

## 1. Cross-model adversarial review

### 1.1 The shape, stated narrowly

`skills/ce-code-review/references/cross-model-review.md` (143 lines) is the orchestration contract; `scripts/cross-model-adversarial-review.sh` (814 lines) is the worker; `scripts/peer-job-runner.py` (1,844 lines) is the detached-job supervisor.

Four scope facts, all quotable, that together make the capability narrower than its name suggests:

| Fact | Where |
|---|---|
| **Adversarial-only.** "No other persona gets a cross-model twin, and there is no whole-diff generalist peer." | `cross-model-review.md:5` |
| **Same brief.** The peer gets "the **same** `references/personas/adversarial-reviewer.md` brief the in-process reviewer uses" and returns the same schema shape. | `:3` |
| **Mutually exclusive with the fallback.** The in-process `adversarial-reviewer` persona is spawned **only when the peer cannot start**. | `persona-catalog.md:38` (recorded by t6a §5.3) |
| **Gated twice.** Runs only when (a) `adversarial-reviewer` was already selected in Stage 3 — "don't run a costly external CLI on a trivial diff" — and (b) scope is `local-aligned` or standalone. Skipped in `pr-remote` / `branch-remote` because "the peer reviews the local tree, which is not the PR/branch head." | `:11-12` |

So the design bets on **model diversity within a single fixed lens**, not on a different model re-running the panel. Note the sibling `ce-doc-review` made the opposite call — it gives three lenses a cross-model twin *and* adds a whole-document generalist sweep (`docs/plans/2026-07-09-003-feat-doc-review-cross-model-plan.md:28`), with the reason recorded at `:32`: doc-review's "value is spread across several judgment lenses rather than concentrated in one, so a faithful adversarial-only mirror would leave most of the cross-model upside unclaimed." The adversarial-only shape is a code-review-specific choice, not a house style.

### 1.2 What spawns the peer

**Not a subagent.** The worker is a CLI shell-out started as a **detached, supervised job** through `peer-job-runner.py`, at the Stage 3d routing boundary, before the local reviewer wave. The stated reason (`:60`):

> **Never hold a tool call open for the peer's runtime** — some harnesses kill long tool calls, which silently vanishes the pass.

The literal start command (`:87`) is one short Bash call that returns a job id in under ~2s:

```
"$PY" "$SKILL_DIR/scripts/peer-job-runner.py" start --skill ce-code-review --run-id "<run-id>" --label adversarial \
  -- env CROSS_MODEL_HOST_HARNESS="<host-harness>" CROSS_MODEL_FIXED_ROUTE="<fixed-route>" \
  bash "$SKILL_DIR/scripts/cross-model-adversarial-review.sh" "<host-serving-family>" "<target>" "<base-ref>" "<run-dir>"
```

Because it is a shell-out rather than a subagent, "it doesn't consume the subagent concurrency budget" (`:60`) — the peer overlaps the local reviewers for free. Job state lives under `<run-dir>/jobs/<job-id>/` and is deleted after fold-in because "its log and result are review content and must not outlive their use" (`:130`).

Before `start`, the orchestrator writes `<run-dir>/adversarial-review-brief.md` — capped at 32 KiB, carrying the Stage 2 intent summary and "2-8 material risk divisions chosen from the current file inventory and diff" (`:62-67`). This is explicitly agent judgment, and the division of labor is stated: the worker's large-diff preflight "only measures and stages the exact diff outside the prompt; it never cuts semantic shards or chooses or rewrites the orchestrator's divisions" (`:69`).

### 1.3 How a different model is selected and configured

**Step 1 — the host attests its own identity.** A shell snippet sniffs environment variables to name the host harness *and*, separately, its serving family (`:21-24`): `CLAUDECODE=1` → `claude`/`claude`; any `CODEX_*` → `codex`/`codex`; any `CURSOR_*` → harness `cursor` but family **`unknown`**, because "Never infer serving family from the Cursor brand" (`:27`). An un-attestable host family **skips the pass entirely** — the worker hard-exits at `cross-model-adversarial-review.sh:290`.

**Step 2 — same-family exclusion.** The worker drops any candidate whose serving family equals the host's, in one line (`:340`):

```bash
[ "$HOST_PROVIDER" != "unknown" ] && [ "$(target_serving_family "$p")" = "$HOST_PROVIDER" ] && continue
```

**Step 3 — preference resolution**, in this order (`cross-model-review.md:29-34`): a preference the user states in conversation → `cross_model_peer:` in `.compound-engineering/config.local.yaml` ("the only file the script/skill reads for this") → a preference already in the active project instructions, consumed from context and "**never** read from a named file" → default order `codex → claude → grok → composer`.

**Step 4 — one fixed route, resolved before egress.** The host must resolve exactly one concrete route and pass it as `CROSS_MODEL_FIXED_ROUTE`; the worker refuses to send anything without it (`:691`: *"host must resolve one fixed route before egress; skipping"*) and "A failed route returns no artifact and never changes provider or intermediary internally" (`cross-model-review.md:36`). `CROSS_MODEL_PEERS` is an optional allowlist restricting which providers may receive content (`:38`).

**Step 5 — the model is the script's call, not the user's.** Model IDs and reasoning tiers are one hardcoded mapping (`cross-model-adversarial-review.sh:73-77`):

```
M_CODEX="gpt-5.6-luna"                # codex CLI            (-c model_reasoning_effort="xhigh")
M_CLAUDE="opus"                       # claude CLI, Opus 4.8 (--effort high)
M_GROK="grok-4.5"                     # grok CLI             (--effort high)
M_GROK_CURSOR="cursor-grok-4.5-high"  # fixed cursor-agent Grok route
M_COMPOSER="composer-2.5-fast"        # cursor-agent composer (no high tier; -fast is the ceiling)
```

The stated principle (`cross-model-review.md:44`): *"Users choose the peer target, not an arbitrary model/effort matrix. Never inherit a harness-configured default model. A lower tier is adopted only after a discriminating effectiveness eval, never from cost alone."* A host-observed unavailable/obsolete model may be replaced only within the same target and family, bound by `CROSS_MODEL_MODEL_OVERRIDE_TARGET` + `CROSS_MODEL_MODEL_OVERRIDE` (`:40`).

**Step 6 — disclosure before dispatch.** `:52-56` requires a prominent standalone line naming the model, the reasoning level, and — for cursor-agent routes, since two models can arrive over the same CLI — the route as well, plus a statement that reviewed code egresses to that provider. Announce wording must follow the receipt: on receiptless routes, say *"requested `<model>` at `<effort>`; serving model/effort unverified on this route."* In `mode:agent` no user prose is emitted, but the worker still writes a one-line stderr audit record per send "so the third-party data egress is auditable."

### 1.4 How findings come back

Done-detection is **presence-keyed**: the worker publishes `<run-dir>/adversarial-<provider>.json` only after normalization (`:96`). The orchestrator captures the epoch time after `start`, does **not** poll while local reviewers run, then reads status exactly once (`:102-108`); if still running and the shared 610s deadline allows, it issues one bounded `wait` capped at 480s — the cap is justified because "Luna xhigh runs can legitimately take up to ~419s, so a lower cap can end before a healthy peer returns" (`:96`). The worker self-bounds at idle 480s / hard 600s (`cross-model-adversarial-review.sh:440-441`).

Normalization is a single `jq` program (`:706-737`) that forces `reviewer` to `adversarial-<provider>`, downgrades any peer `safe_auto` → `gated_auto`, and backfills `first_evidence` from `evidence[0]` when absent. Fold-in is then ordinary Stage 5 dedup, with the promotion rule below.

**`independence_verified` is computed by the script itself** (`:713-716`):

```bash
_independent=false
[ "$HOST_PROVIDER" != "unknown" ] && [ "$_target_family" != "unknown" ] && [ "$HOST_PROVIDER" != "$_target_family" ] && _independent=true
```

It attests **a different serving family, not a verified served model**. The contract says so plainly (`cross-model-review.md:122`): *"`independence_verified` attests a different serving family; it does not claim the exact served model was verified. `receipt_supported`, `model_actual`, and `effort_actual` carry that separate identity evidence."* Cursor-default artifacts default to `false`.

### 1.5 What cross-model mechanically buys — exactly two things

**(a) One-notch promotion on agreement.** In `scripts/findings-mechanics.py:75-80`:

```python
def independent_reviewer(name, source):
    if name == "fast-pass":
        return False
    if name.startswith("adversarial-"):
        return source.get("independence_verified") is True
    return True
```

Promotion is `{50: 75, 75: 100, 100: 100}` and fires only when `len(independent) >= 2 and has_first_evidence` (`:83-84`, `:124-125`). Since suppression drops anything below anchor 75 that is not a P0 (`:197-209`), a promotion 50→75 is the difference between a finding surfacing and being buried.

**(b) Permission to skip a validator.** `references/finish-review.md:49`:

> Skip a validator only when the finding has `first_evidence` and both an ordinary reviewer plus an `adversarial-<provider>` reviewer whose artifact records `independence_verified:true`. **Same-model corroboration never licenses this shortcut.** Record the skip count in Coverage.

That is the complete list. Cross-model does not add a lens, does not widen coverage, and does not change what the reviewer looks for. It makes *agreement mean more*, and it buys a cost saving on validation.

### 1.6 `findings-schema.json` — required fields, and whether the contract is enforced

**What the schema requires.** `skills/ce-code-review/references/findings-schema.json`, 101 lines, JSON Schema draft-07. Top level requires `reviewer`, `findings`, `residual_risks`, `testing_gaps`. Each finding requires **eleven** fields: `title`, `severity`, `file`, `line`, `why_it_matters`, `autofix_class`, `owner`, `requires_verification`, `confidence`, `evidence`, `pre_existing`. (t6a §7.1 records the field semantics — the `[0, 25, 50, 75, 100]` confidence anchors and the quote-the-line evidence gate. Not restated.)

**Is it mechanically validated? Yes — but by a hand-maintained duplicate, and only partly at the peer boundary.** Three enforcement points, none of which is the schema file validating itself:

| Layer | What actually happens | Where |
|---|---|---|
| **At the peer CLI** | Enforced as structured output on **2 of 6 routes only**. `claude` and `grok-cli` receive `--json-schema "$SCHEMA_REF"` (the schema file's full text). `codex`, `grok-cursor`, `cursor`, `composer` receive **no schema flag** — only `-o <file>` or `--output-format json`. | `adapter_argv`, `:196-235` (`:207`, `:216` carry the flag) |
| **Post-hoc recovery** | For the unconstrained routes, shape is *recovered*, not required: `parse_structured` tries `.structured_output`, then `.result`, then `recover_findings_json`, which scans raw stdout with a `raw_decode` loop and keeps the last object with a `findings` array. | `:600-645` |
| **At normalization** | A shape check only: `jq -e '(.reviewer\|type=="string") and (.findings\|type=="array") and (.residual_risks\|type=="array") and (.testing_gaps\|type=="array")'`. Anything else → "produced no usable schema-shaped output; skipping fold-in." | `:750` |
| **At merge** | Real field + enum validation — but against **its own hardcoded copy** of the contract. | `findings-mechanics.py:14-64` |

`findings-mechanics.py` **never reads `findings-schema.json`.** It declares `SEVERITIES`, `CONFIDENCES`, `AUTOFIX_CLASSES` (`:14`), `OWNERS` (`:15`), `REQUIRED_TOP` (`:16`), and `REQUIRED_FINDING` (`:22`) as Python literals, and `valid_finding` (`:45-64`) checks types, the four enums, and a positive-int-or-nonempty-string `line`. Malformed items are **counted and dropped, not repaired**, with `malformed_returns` / `malformed_findings` in the output so the loss is visible.

Two consequences worth recording:

- **The two field sets differ.** The schema requires 11 fields per finding; `REQUIRED_FINDING` requires 9. `evidence` is deliberately absent — the two-tier return (t6a §7.1) moves `evidence` to the on-disk artifact and promotes only `first_evidence` inline, and the merge does gate on that (`:121-123`: `if confidence >= 75 and not has_first_evidence: confidence = 50`). But **`why_it_matters` is required by the schema and unguarded at merge**; it is pinned only in prose (`finish-review.md`, asserted by `tests/review-skill-contract.test.ts:285`).
- **No parity test binds the two.** `tests/review-skill-contract.test.ts:236-274` pins the *schema's* enums against literals written in the test file; `findings-mechanics.py` carries a second, independent set of literals. They agree at this commit, but nothing asserts they must. This matters because t6a §1.4 established that this repo *does* use byte-parity tests for genuinely shared assets (seven of them) — so the absence here is a real gap in a repo that knows the pattern, not an oversight anyone would expect them to have missed.

**Fair summary:** the contract is enforced, at merge, deterministically — but the schema file is the *reviewer-facing prompt contract* and the Python is the *merge-time gate*, and they are two hand-synchronized copies of one idea.

### 1.7 Infrastructure requirements — the portability answer

**No API key. No paid second API account beyond a CLI's own login. No daemon. No server.** The peer is a subprocess of a second AI coding CLI already on `PATH` and already authenticated. The literal argv per route (`adapter_argv:193-238`):

| Target | Command | Isolation |
|---|---|---|
| `codex` | `codex exec - -C <repo> --skip-git-repo-check -s read-only --json -o <out> -m gpt-5.6-luna -c model_reasoning_effort="xhigh"` | `-s read-only`, may run `git diff` itself |
| `claude` | `claude -p --model opus --effort high --permission-mode dontAsk --disallowedTools Edit Write NotebookEdit Bash Task WebFetch WebSearch Skill 'mcp__*' --max-turns 15 --no-session-persistence --json-schema <schema> --output-format json` | Read allowed for context; diff embedded because Bash is denied |
| `grok` | `grok --prompt-file <f> --model grok-4.5 --effort high --cwd <repo> --permission-mode dontAsk --deny Edit --deny Write --deny Bash --deny Task --deny 'mcp__*' --disable-web-search --no-subagents --max-turns 15 --json-schema <schema> --output-format json` | Read allowed; writes/shell/subagents/web denied |
| `cursor` / `composer` / `grok-cursor` | `cursor-agent -p [--model <id>] --mode ask --trust --sandbox enabled --workspace <repo> --output-format json` | ask mode + sandbox |

**The default route on a Claude Code host is also the weakest-contract route.** Cross-referencing §1.6: `codex` is the one target that receives neither `--json-schema` nor any structured-output constraint, so its findings shape is not enforced at the peer at all — it is recovered post-hoc by `recover_findings_json` scanning raw stdout. Since same-family exclusion makes `codex` the default target for a Claude Code host (below), the most likely configuration is the one with the least contract enforcement at the boundary.

Availability is a bare `command -v` per target (`:325-329`). **Authentication is whatever that CLI already has** — nothing is configured by this skill. A login failure surfaces as peer output text that the orchestrator classifies at fold-in, and the contract carries a specific caution against misreading it (`cross-model-review.md:129`): a sandboxed host denying spawned commands network or keychain access "produces the identical signal to a genuine account logout," so it must be classified as a cross-model execution-context failure and "never report it as the user's account being logged out."

**Hard requirements, verified by reading the preflight** — each of these `skip`s the pass rather than failing the review:

| Requirement | Hard? | Where |
|---|---|---|
| A second, different-family AI coding CLI, installed **and** logged in | **Yes** — `:350` skips with *"no different-provider peer reachable"* | `:325-329`, `:340`, `:350` |
| `jq` | **Yes** | `:278` |
| Running inside a git repository | **Yes** | `:302` |
| Python 3 (for `peer-job-runner.py`, and for `recover_findings_json`) | **Yes** | `:604-606`; `cross-model-review.md:81` |
| bash | Yes (the worker is bash) | — |
| Host can attest its own serving family | **Yes** — `unknown` skips automatic dispatch | `:290` |
| `timeout` / `gtimeout` | **No** — falls back to `perl -e 'alarm shift; exec @ARGV'` | `:583` |

`jq`, git, Python 3, bash and perl are all standard or trivially available on macOS and Linux. **The only non-trivial dependency is the second CLI.**

**What this costs a solo dev on Claude Code specifically.** Host family attests as `claude` (`cross-model-review.md:21`). Same-family exclusion (`:340`) therefore removes the `claude` target. The default preference order `codex → claude → grok → composer` lands on **`codex`**. So the concrete requirement is a working, logged-in `codex` CLI — or `grok`, or `cursor-agent` — held *in addition to* Claude Code. What each of those costs is a vendor question this tree does not answer and I did not verify; the tree's own contribution is only that the skill adds no credential or account of its own. The requirement is a second vendor's CLI, not an infrastructure build.

One further portability note in the source's favor: the entire trust boundary is disclosure, not mutation. Every route is read-only against the working tree, and `:143` states the impact is "bounded to disclosure, not repo mutation."

### 1.8 Is there stated evidence it outperforms same-model review?

**Could not verify a measured cross-model-vs-same-model comparison. The premise is asserted, not benchmarked.** Three artifacts bear on this, and it is worth being precise about what each does and does not establish.

**(a) The rigorous eval exists — and measures a different question.** `docs/plans/2026-07-17-001-eval-cross-model-peer-model-config.md` (431 lines) is a genuinely serious piece of work: pre-registered decision rule, non-inferiority framing, 3 arms × 10 reversed-real-bug diffs × n=5 = **150 runs, zero failures**, graded by a 3-vote blind Opus judge with arms shuffled and unlabeled, plus a cross-language spot-check on Python and Go. Its result: Sol-medium ties Sol-high within noise (detection 92% vs 94%) at ~31% fewer tokens; Terra-high is the weakest detector (78%, 11/50 missed).

But **all three arms are the same serving family**. The doc says so as an explicit design principle (`:78-80`):

> **Independence is unaffected.** Terra and Sol are both gpt-5.6 / OpenAI family, so swapping between them does not touch the "different serving family from the Claude host" property. **Not a variable here.**

So this measures *which model and reasoning tier should occupy the peer slot* — it takes the value of the peer slot as given. (Side observation: its recommendation was `gpt-5.6-sol` at `medium`; the shipped mapping at this commit is `M_CODEX="gpt-5.6-luna"` at `xhigh` (`:73`), so a later model swap has moved past the eval's conclusion.)

**(b) The file named `cross-model-eval.md` is a conformance spec, not an effectiveness eval.** All nine of its cases (`:12-68`) test activation gating, host attestation, route fixing, disclosure honesty, fold-in promotion mechanics, failure non-blocking, lifecycle bounding, and large-diff transport. **Zero cases test whether the peer finds anything the in-process reviewer missed.** Its pass criteria (`:70-75`) are entirely about routing behavior.

**(c) The one stated effectiveness claim is a practitioner report, about documents.** `docs/plans/2026-07-09-003-feat-doc-review-cross-model-plan.md:32`:

> ce-code-review already closes this gap for its adversarial lens by running a second, different-family model and treating cross-model agreement as its strongest promotion signal. **Running the same review through another model manually on documents has reliably surfaced issues the single-model pass missed — the same motivation, confirmed in practice.**

No numbers, no corpus, no control. And the repo records the counter-caveat against itself in two places — `docs/plans/2026-07-14-002-feat-ce-pov-cross-model-panel-plan.md:32`: *"peers can share a **correlated** blind spot, so concurrence raises confidence without guaranteeing independence"*; and `skills/ce-pov/references/cross-model-panel.md:327`, which states a cross-model panel *"does not eliminate correlated-model blind spots."*

**Verdict for the record:** the cross-model architecture is built on a reasonable and honestly-caveated assumption, backed by one practitioner report. It is not backed by a head-to-head measurement, and the repo's own measurement apparatus — which is demonstrably capable of running one — has never been pointed at this question.

### 1.9 The adversarial persona brief — the part that matches Signal's actual failure

Recorded here because it would be missed by anyone evaluating "cross-model" as the capability. `skills/ce-code-review/references/personas/adversarial-reviewer.md` (110 lines) is the brief **both** the peer and the in-process fallback receive. It defines five hunting techniques: assumption violation, composition failures, cascade construction, abuse cases, and — technique 5 (`:64-66`):

> **Silent-pass verification-mechanism fidelity.** When the change *is* a guard that stands in for the real thing — a CI/CD gate, merge-blocking check, build/deploy step, coverage/lint gate, or test harness/mock — its risk is not blast radius, it is fidelity: **it can go green while production is red.** Construct the scenario where the guard passes but the thing it protects fails. Verify it reproduces the same context, inputs, and steps as the real thing […] not merely that it runs. A guard that exercises a different context than production, **mocks away the code path that actually breaks, or asserts on a proxy rather than the real output** is the green-while-red failure.

It carries a depth override that outranks the size heuristic (`:15`): *"Never pick Quick for it regardless of changed-line count, and run the fidelity lens (technique 5) even when it is the only reason you were selected. […] a small CI/config diff still gets the full green-while-red attack."*

This is a supply fact, not a recommendation: the lens whose stated target is "the guard passed while the thing it protects fails" lives in a **persona brief**, and is model-independent. It runs identically on the in-process fallback. Whether it addresses Signal's v0.1.9 case is S3's call.

### 1.10 Effort to port into Signal's REVIEW phase: **L**

**Integration point:** `signal:commands/review.md` §§1–4 (the four review passes) plus the three specialist agents in `signal:agents/specialists/` (`code-reviewer`, `security-auditor`, `test-engineer`).

**Why L, and why the 814-line shell script is the wrong thing to size.** The peer is the last piece, not the hard piece. It plugs into four upstream mechanisms Signal does not have. Each verified absent:

| Upstream mechanism the peer requires | Signal today |
|---|---|
| A structured reviewer return (JSON findings) | **Absent.** `signal:commands/review.md:83-107` writes markdown prose sections — Critical / Important / Suggestion, plus Security / Performance / Simplification findings. No machine-readable return. |
| A confidence-anchor system decoupled from severity | **Absent.** Categories are severity-only. |
| A per-run artifact directory reviewers write to | **Absent.** Reviewers produce prose into one report file. |
| A deterministic merge/dedup/promotion step | **Absent.** No `findings-mechanics.py` equivalent; synthesis is prose. |
| The `independence_verified` concept | **Absent.** |

A repo-wide grep for `findings-schema`, `independence_verified`, `confidence_anchor` in this repository matches only the M5.E7 planning documents — i.e. these supply notes themselves — and nothing in `commands/`, `agents/`, `skills/`, or `tools/`.

**Decomposition, if S3 wants one:**

- **M** — the prerequisites: a findings JSON schema, anchored confidence with the quote-the-line gate, a run-dir artifact convention, and a deterministic merge script. This is the bulk of the work and is **independently valuable without any cross-model peer** — the promotion, suppression, and independence machinery all operate on same-model reviewers too (`findings-mechanics.py` bars the orchestrator's own `fast-pass` from counting as corroboration regardless of any peer).
- **S–M** — the peer shell-out itself, once the above exists: route resolution, one CLI adapter, detached job supervision, normalization. Signal could ship a single-target version (Codex only) and skip the five-route matrix, the Cursor/Composer distinction, and the receipt machinery.

**One gate that happens to fit:** the pass requires scope `local-aligned` or standalone (`cross-model-review.md:12`). Signal's REVIEW runs on the local branch before SHIP, where the working tree *is* the reviewed head — so this constraint is satisfied rather than blocking.

## 2. `ce-retune` — measurement-first corpus retuning

`skills/ce-retune/SKILL.md` (97 lines) + six conditionally-loaded references (670 lines total) + `docs/skills/ce-retune.md` (100 lines). Landed 2026-07-24 — days before this pin.

### 2.1 What it measures, against what baseline, and what it changes

**Measures — two metrics, never collapsed.** *"Followed the process"* and *"did the job"* are tracked separately, "because a run can complete the task while skipping the workflow entirely. Collapsed into one number, that reads as success" (`docs/skills/ce-retune.md:55`; SKILL `:37`). The per-run extraction table (`references/baseline-mining.md`) pulls `run_id`/`model`/`settings`, `session_id` plus the child id on every dispatch, `phase_trace` (which corpus phases fired, "in ordered list"), `marker_present`, `output_tokens`, `wall_clock_min`, `helper_dispatches`, `max_parallel_dispatch`, and `final_message` verbatim and untruncated ("halt language lives here and nowhere else").

`phase_trace` is derived **from artifacts, not claims** — a phase counts as fired only if the trace shows its side effect (a reference file read, a helper dispatched, a file written): *"A run asserting 'Phase 3 complete' in prose is not evidence — the defect class you are hunting is exactly runs that report success without doing the work."* A phase with no observable marker is recorded as **unobservable**, not assumed fired, and that list is carried forward to Phase 5's unmeasured-paths report.

The headline derived metric is **tokens per minute** (`output_tokens / wall_clock_min`), checked for bimodality before anything else: *"healthy cells ran 10-12k tokens/min; every failing cell sat at 1.5-3.8k. A run burning hours at 2k tok/min is not thinking hard, it is waiting — the prose told it a second party would respond. Duration alone cannot show this: a long successful run and a long stalled run look identical until you divide."*

**Baseline — two, in order.** (a) **Mine the existing run archive** (Phase 1, zero model cost — "Do not run the harness in this phase"); in the source engagement 745 archived runs were on disk, 458 with usable traces. (b) **An A/A noise floor** (Phase 2): two byte-identical checkouts of the corpus at the same commit, hash-asserted equal before the first run, labelled by path not intent, **interleaved A,B,A,B** rather than batched (because API load and time-of-day "are indistinguishable after the fact from a real difference between builds"), ≥12 runs. The reported floor from the source engagement is the argument for the entire method:

> 12 runs across two identical builds gave workflow adherence 7 of 12 and output tokens from 21,872 to 155,682, **a 7.12x spread on identical code**. It retired every small-sample claim in flight, including an outside analyst's "2 of 8 improved to 5 of 8", which sits entirely inside the envelope of doing nothing.

The bar is registered **in writing before any change exists** (SKILL `:45`): *"A bar chosen after seeing results is not a bar."*

**Changes — prose cuts, in surgical passes.** Phase 3 audits adversarially: one agent per skill proposes cuts, a second agent **defends the existing prose** using the project's own documented learnings, tests and git blame. *"'A weaker model might need it' is not grounds for keeping; only citable provenance is"* (`docs/skills/ce-retune.md:63`), and a defended keep is off the list and not relitigated (SKILL `:57`). Phase 4 cuts with one problem per agent and disjoint file ownership. Guardrails that survive: *"Field names, enums, greppable markers and security guards are data. They stay. What goes is the justification clause around them that teaches the model a separate consumer is waiting"* (`:71`); *"Not every stop is the enemy"* (`:72`); *"Never edit tests to make a suite green. A removed string a test pins is a finding to report, not a test to weaken"* (`:73`). Phase 5 reads **where** a run failed, not just whether — "A failure that moves to a later phase is progress and names the next target." One commit per pass (`:89`).

**Non-goal, stated twice:** word reduction. *"Leanness and performance are separate programs that happen to share a corpus, and only one of them is the result"* (`:16`).

### 2.2 Repeatable harness, or one-off procedure?

**A repeatable procedure that ships no harness — and hard-refuses without one.** This is the decisive fact. Phase 0 (SKILL `:18-28`) demands three things the *project* must already possess:

1. **A run archive or a harness that produces one** — per-run logs carrying the tool-call trace, a terminal marker, token counts, and the final message.
2. **A build selector** — the harness can point a run at a specific source checkout of the corpus (a `--plugin-dir`-style override, a configurable skills path, an env var), so two builds are comparable under one runner.
3. **A repeatable task** the corpus actually executes end to end.

> If any is missing, **stop and say so**, naming what to build. Do not fall back to a static audit and present it as retuning: an audit can say what looks cuttable and can never say whether cutting helped, which is the error this skill exists to prevent.

`references/noise-floor.md` adds a fourth practical requirement — the harness must **record which build produced each row in a durable post-completion field**. The source engagement's first scorer read a field the harness clears on completion, so "every finished row had an empty build column and the arms were unverifiable from the scored data. The runs were fine; the measurement was worthless until re-scored." The generalized rule: *"read the durable post-completion field first, fall back to the transient in-flight one."*

It is user-invoked only — `disable-model-invocation: true` (SKILL frontmatter `:4`), with the reason at `docs/skills/ce-retune.md:100`: *"It spends many paid runs and refuses without a harness, so model-routing it would let a cheap request escalate into an expensive measurement program."*

### 2.3 Could it run against a corpus like Signal's?

**Addressable: yes. Runnable today: no — Phase 0 would refuse.**

The corpus path is parameterized: `argument-hint` (`:5`) is `"[target model or symptom] [path to the corpus, defaults to ./skills] [bar:<n> consecutive clean runs]"`, and `docs/skills/ce-retune.md:27` shows `/ce-retune ./agents bar:12`. So `signal:skills/`, `signal:agents/`, and `signal:commands/` are addressable targets in principle, and nothing in the method is specific to `ce-*` naming.

What blocks it is the Phase 0 gate, on all three counts:

- **No run archive.** Signal keeps no per-run trace of its own phase-command executions — no tool-call traces, token counts, or final messages from `/sig:execute` runs.
- **No build selector.** Nothing points a Signal workflow run at a specific checkout of `skills/`+`agents/`+`commands/` for A/B comparison.
- **No scripted repeatable end-to-end task** that exercises the corpus.

Signal's 1,561 tests do not substitute, and the skill names that exact confusion in its own "Done" criterion (`:14`): *"A green test suite is not done: it proves nothing broke, not that behavior improved."* Signal's tests exercise `tools/` — they are not behavioral runs of the 21 skills and 26 agent prompts.

Two parts of the method **would** apply to Signal without a harness, and the skill is explicit that they are a *different request*: the adversarial corpus audit (Phase 3) and the "audit what the instrument cannot reach" step (`:83`) — list the phases a probe never enters, read those files directly, and weight what you find equally with what the runs found. But the skill insists an audit be asked for as an audit: *"You want a corpus audit, not a retune. Ask for the audit directly; it is cheaper and honest about what it can conclude"* (`docs/skills/ce-retune.md:84`).

## 3. `ce-pov` — structured point of view (brief, per task priority)

`skills/ce-pov/SKILL.md` (146 lines) + 8 references + 4 agent briefs + `references/pov-schema.json` + its own `scripts/cross-model-pov.sh`. Documented at `docs/skills/ce-pov.md` (238 lines).

**What it is.** A decisive, project-grounded verdict delivered "in the subject's own shape" — a graded adoption verdict (Adopt/Reject/Hold/Trial), a holistic take on a document, or a position on a user-supplied approach set (frontmatter `:3`). Default output is a compact chat block, not a document (`:47`). Read-only while forming (`:14`).

**The stated moat** (`:16`) — the one line that characterizes it:

> **Do not issue a POV you did not earn against the project's own context.** Generic web research already covers "tell me about X"; the differentiator is never "research the web" — it is the refusal to answer in the abstract.

Every subject must clear a "project floor" defined in `references/method.md`; an external-adoption verdict must additionally clear a full external floor, and *"Neither the conversation nor the user's own assertions substitute for grounding."*

**The four role prompts** (`references/agents/`), tiered by task shape rather than model name (`:36-42` — extraction / generation / ceiling, with a degradation rule when the platform can't select per-agent models):

- **`project-grounding-scout`** (extraction) — the project floor.
- **`precedent-activity-scout`** (extraction) — *"what the team has **already decided or attempted**"*: closed issues, PR descriptions and review threads, "especially a PR that was **closed without merging** — 'tried X, backed it out'", `<root>/solutions/`, ADRs — plus incumbent pain from open issues and in-flight PRs. Local decision record first (file access only, so it always runs); tracker search is optional and *"a missing tracker is a capability gap, not an error."* Its stated highest value: *"it stops the caller re-litigating a settled question."*
- **`external-evidence-researcher`** (generation) — *"gather **verified external evidence** … not to recommend. You gather and verify; the caller decides."* Hard precondition on reachable web search + fetch; if neither is reachable it reports "external research unavailable" and stops, which the caller converts into a "Hold" — *"do not pretend to have evidence you could not fetch."*
- **`pov-peer`** — forms an *independent* POV grounded in the shared working tree, and explicitly *"Do not require or infer a host-curated project summary."* Carries a data-egress rule: public subject-level terms only, never repository-derived fragments, paths, identifiers, or secrets.

A separate `references/cross-model-panel.md` runs multi-model debate through the same `peer-job-runner.py` machinery as §1, with the honest caveat at `:327` that it *"does not eliminate correlated-model blind spots."*

**Overlap with Signal's existing agents.** Recorded factually; matching is S3's.

| Upstream | Signal's nearest | Overlap |
|---|---|---|
| `external-evidence-researcher` | `signal:agents/researchers/advisor-researcher.md` (49 lines) — "Researches gray-area decisions and returns structured comparison tables"; process is *identify 2-4 viable options → research against consistent criteria → comparison table → recommendation*; has `WebSearch`/`WebFetch` | **Substantial.** Both do external option research for a decision. Two differences: Signal's ends in a recommendation, upstream's explicitly refuses to recommend ("the caller decides"); upstream hard-stops when web tools are unreachable rather than degrading. |
| `precedent-activity-scout` | **No Signal equivalent.** | **None.** Signal has no agent that mines prior decisions and abandoned attempts (closed-unmerged PRs, decision records) before forming a view. Signal's own `DECISIONS.md` / `RETROSPECTIVES.md` are exactly the corpus such a scout would read. |
| `pov-peer` / the project floor | `signal:agents/researchers/assumptions-analyzer.md` (45 lines) — "Surfaces Claude's implicit assumptions about a phase approach"; reads PROJECT.md, CONTEXT.md, `{phase}-RESEARCH.md`; lists technical/scope/other assumptions | **Partial and oblique.** Both push back on unexamined reasoning, but from opposite directions: `assumptions-analyzer` makes the *host's own* premises explicit; `pov-peer` forms a *separate, independently grounded* position. Neither produces the other's output. |

Net: `ce-pov`'s adoption-verdict and external-research surface substantially duplicates `advisor-researcher`. Its genuinely non-overlapping piece is the **precedent scout** — the "has this already been decided or tried and backed out?" pass, which Signal has no agent for.

## 4. Where the three land, as supply

| Capability | Substance | Notable constraint |
|---|---|---|
| **Cross-model adversarial review** | Real, carefully built, heavily disclosure-conscious. Genuinely portable mechanism: no infra, no keys, no daemon. | Adversarial-only, same brief, mutually exclusive with the in-process lens. Buys promotion + a validator skip, not new detection. Requires a second vendor's logged-in CLI. No head-to-head effectiveness evidence. |
| **`ce-retune`** | The most transferable *method* of the three, and the only one addressing a problem Signal has no answer to. The A/A noise-floor discipline and the two-metrics rule are portable ideas independent of the skill. | Ships **no harness** and hard-refuses without one. Signal fails all three Phase 0 gates today. |
| **`ce-pov`** | Coherent, well-scoped; the "refuse to answer in the abstract" floor is its whole differentiator. | Its research surface substantially overlaps Signal's `advisor-researcher`. The non-overlapping value is concentrated in the precedent scout. |

**Two things a matcher should not miss:**

1. The mechanism in this repo most directly aimed at "the guard went green while the real thing is red" is **technique 5 of the adversarial persona brief** (§1.9) — a prompt asset, model-independent, that runs on the in-process fallback identically. It is not the cross-model feature.
2. The four prerequisites the cross-model peer plugs into — structured findings, anchored confidence, run-dir artifacts, deterministic merge — **operate on same-model reviewers too**. `findings-mechanics.py` applies its promotion, suppression, and quote-the-line gates to every reviewer, and bars the orchestrator's own `fast-pass` from corroborating, regardless of whether any peer ran (§1.5). Cross-model adds one qualifying condition to that machinery rather than being what the machinery is for.
