## Four findings (checked by hand)

1. **Nothing writes a milestone's Epic-status row.** No code writes one and no command says to. It is
   a hand edit, and three readers depend on it. (`M6.E15`'s row was missing after its SHIP; added by
   hand in PR #298.)
2. **Three row parsers, each reading a different format.** `findEpicStatusRow`
   (`lib/retrospective.js:1008`, feeds the SHIP gate) matches `| **E1** |` only, so it returns null
   on `MILESTONE-6.md` and the gate falls back to `STATE.md`. `EPIC_ROW` (`lib/published-facts.js:395`)
   matches full IDs only. `parseEpicStatusRows` (`lib/milestones.js:154`) matches both, and only
   `/sig:advise` calls it. This is `SIG-132`.
3. **Two archive layouts exist side by side.** `archive/epics/<ID>/` (used by `closeEpic`,
   `isEpicArchived`, `readEpicFolders`, `epicFolderRel`, `work-convert`) holds only `M6.E11`.
   `archive/<M>/E<n>/` (used by `deriveEpicArchiveDir`, `deriveUnitArchiveDir`, `unitArchiveDirFor`)
   holds `M6/E1…E15` except `E5`, `E9` and `E10`.
4. **`.planning/work/epics/` does not exist, so `closeEpic` records nothing.** Nothing creates Epic
   folders on a v2 store (`lib/work-ops.js:309-312`). `closeEpic` returns `no-folder` for every Epic
   since `M6.E11`, so `M6.E11` is the only Epic with a close record. `EPICS.md` prints
   *"M6.E14 — no Epic folder"* and *"M6.E15 — no Epic folder"* for two shipped Epics.

## How an item names its Epic today

No stored field. `epic` rides on `queued` and `started` events
(`plugin/references/work-item.schema.json:77-93`), must match `^M\d+(\.\d+)*\.E\d+$` (`:21`), and is
folded by `epicOf`. **The pattern admits only strict Epic IDs**, so an item in a project whose units
are not Epic IDs cannot name its unit.
