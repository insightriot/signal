## What changed mid-flight

- **The `BUGS.md` half changed from a code rule to a Jev check** (`D-M6E3-15`). `t3.2` measured the subject-position rule at 7 flags for 1 real, and fix commits at 0 real. The honest result was *"nothing precise enough to refuse on"*. The refusal path therefore shipped wired and tested, but **nothing can feed it yet**. `ship.md` says so, and so does the live-gate test header (after REVIEW caught it claiming otherwise).
- **`S4` was dropped** (`D-M6E3-16`). Brett, verbatim: *"feels like we need to revisit this whole architecture vs. keep applying band-aids."* Inferring "done" after the fact had just been measured failing for bugs, and questions would have been the same inference again. The redesign, which records done at the source, is the next Epic.
- **`AC4.1`/`AC4.2` were revised at VERIFY, not built** (`D-M6E3-17`). The criteria still promised docs-sweep receipts after `D-M6E3-15` had removed the only check that could produce them. That decision was never written back into the requirements, and VERIFY caught it.
- **REVIEW added a real security surface** that DISCUSS and PLAN never considered: reading the key from a project `.env` (`D-M6E3-14`, an EXECUTE convenience) turned a cloned repo into a way to spend the author's key on the cloner's files. See *surprised*.

## What assumptions broke

- **A1 — "a receipt at a real line is a receipt."** Two receipts cited real lines that did not carry the claim.
  - The `STATE.md` check **composed** its evidence text (`version: 0.1.40`) and cited it at a line that reads `"version": "0.1.40"`.
  - The bug check cited B102's **headline**, which never says "fixed". Jev had judged the whole section.
  - A test pinned the composed string. **This is `M6.E7`'s failure shape, inside the Epic built against it, for the second time running.**
- **A2 — "the project `.env` is the user's key."** It is whoever put the file there. REVIEW measured four distinct ways that belief was wrong:
  - a committed `.env`;
  - a committed `.ENV` on a case-insensitive disk;
  - git failing and the check failing open;
  - a template copied by the user (recorded as a limit).
- **A3 — "model findings never refuse" holds by writing `judgedBy`.** It held by each check remembering to. Now it holds by declaration (`judged: 'model'` on `defineCheck`), with a structural test.
- **A4 — "40 live criteria."** Written at VERIFY loop 1 without being derived; the real count is 44. It went into the report, into VALIDATION and into a commit message before a script recount caught it. The same shape as A1, in the verification of it.
- **A5 — "the coverage tool says covered."** It counts an id as verified when the report *mentions* it, so a criterion marked FAIL read as covered (`B126`).

## What surprised us

- **Fresh-context review found what the author could not, three rounds running, including in the author's own fixes.**
  - My in-session REVIEW pass found none of pass 1's 13 Important issues.
  - Pass 2 found that **two of my pass-1 fixes introduced new defects**: a `TypeError` when the id is only in a heading, and a long line still dropping the id. It also found a **High**: the `.env` fix was defeated by filename case on macOS, which the auditor reproduced.
  - This is `#243`'s measurement again, at larger scale. The step that caught it (§ 4.5) is the one wired in `M6.E9`.
- **The accidental find: `B127`.** `/sig:advise` could not see M6.E3 while it was in flight, because the backlog heading said *"EXECUTE done"* and the done-marker rule ignores case. It surfaced only because rewording the heading moved a pinned count from 2 to 3. That is the false-**done** direction of this Epic's own class, in the tool that ranks what to work on next.
- **The live numbers held after REVIEW changed the input.** For multi-section bugs the input changed: at most 3 sections are sent, each cut to a window around the id. The re-measurement was advised as a check, and it held: 4 of 4 with 0/26, and B102 at p 0.63, lower than the 0.69–0.76 seen before, within the stated run-to-run variation.

## What we'd do differently

- **Run the fresh-context reviewers on EXECUTE's output before VERIFY**, at least the security auditor on any Epic that adds a network call or reads a secret. The `.env` risk was introduced at EXECUTE (`D-M6E3-14`) and lived through VERIFY unexamined.
- **When a decision changes scope, write it back into REQUIREMENTS the same day.** `D-M6E3-15` changed what `FR2`/`FR4` meant, and five criteria kept the old wording until VERIFY failed on one of them.
- **Measure a REVIEW fix before writing it**, not after. Pass 2's fixes were written expecting to fit under 50 LOC and came to 133. The rule then required a FAIL, correctly, and an extra pass.
- **Derive every denominator by script at the moment it is written.** A4 happened inside a report whose template exists to stop it.

## What to feed back into Signal

- **`review.md` § 4.5 should say that fix-on-fix needs its own fresh pass.** Measured here: pass 2 found defects that pass 1's fixes introduced. The PASS-WITH-FIXES path assumes an in-phase fix is safe if it is small. The size test caught this one; the assumption would not have.
- **`verify.md` should compute the denominator with a tool that reads verdicts, not mentions** (`B126`). Until then, the template should tell the author to count by script and never by hand.
- **`backlog.js` `DONE_WORD_RE` should not match a phase word** (`B127`). Better, as the redesign proposes, "done" should be recorded where the work happens, not inferred from prose.
- **A new-network-call checklist item for PLAN:** where the key comes from, who else could put a key there, and what text leaves the machine. Every item REVIEW found on the key path was answerable at PLAN.

## Anti-rationalization moment

- **At REVIEW pass 2, the fixes were already written and green**, and the natural move was to call it PASS-WITH-FIXES. Every finding was real, closed, and tested. The measurement said 133 LOC against a 50-LOC cap, so it was recorded as a **FAIL** and put in front of Brett. The pass it forced (pass 3) was the first in which **no reviewer found anything Important**. Had the fixes been waved through, the case-bypass fix and the fail-closed git check would have shipped with no independent read.
- **A second one, smaller:** at pass 3 the security auditor's Medium (a copied `.env.example` template) was fixable in ~10 lines. It was **recorded as a limit and filed instead**, because a change after the last fresh read ships code no reviewer has seen. Passes 1 and 2 had just measured what my fixes do when nobody re-reads them.
