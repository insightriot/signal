# M5.E19 — Plan: `/sig:archive`

**Goal (one sentence):** give archiving a command of its own, so filing away finished work does not
require running a document-layout reorganizer and reading past half its output.

**Tier:** FEATURE (`M5.E19-PROFILE.md`) · `plan_validation_dims: core` · `nyquist_enforcement:
strict` · `gate_strictness: light`.

**Scope corrected at research.** `B82` shipped separately (v0.1.21) and the closure gate already
exists. See `M5.E19-RESEARCH.md` and `D-M5E19-6`. What is left is genuinely a command.

---

## What this Epic does for the FIRST TIME (M5.E17 FR1) — and it is wave 1

**`examples/sandbox/` gets used for its real purpose.** It was built earlier today (#100) and has
only ever been exercised by the test that asserts it is well-formed. **No Signal command has ever
been pointed at it.** That is the "shipped but never run" shape this instruction exists to catch,
and it is precisely why the sandbox was built — so `/sig:archive` never needs a real project.

**Second first: `applyArchiveTree` has never run outside `/sig:migrate-memory`'s apply path.** It
has always executed under that command's single coarse lock, with `v3Rename` set from the migrate's
own sense. `/sig:archive` will be its **second caller ever**, and the first with no layout migration
in flight. Lock composition and the `v3Rename: false` path are therefore wave-1 concerns, not
wave-2 ones.

**Therefore S1 is wave 1:** run the *existing* machinery against the sandbox and write down what it
actually prints, before writing any new rendering. If the current output is already adequate, that
is a finding worth having early — it would shrink S2 to a thin wrapper.

## Slices

### S1 — Point the existing machinery at the sandbox and record the truth · **wave 1** · S

No new code. Run `senseArchiveTree` + `resolveClosures` against `examples/sandbox`, capture the
real output, and answer two questions **in writing** in `M5.E19-PROGRESS.md`:

1. What does a user actually see today if they archive via `/sig:migrate-memory`?
2. Which of FR2/FR5/FR6's reporting requirements are **already met** by
   `explainArchiveOutcome` + `renderMoveBreakdown`?

**AC-S1.1** — the captured output is in `M5.E19-PROGRESS.md` verbatim, not summarized.
**AC-S1.2** — every FR2/FR5/FR6 line item is marked *already met* / *partially* / *missing*, with
the function named. An unmarked item fails this slice.

**Why first:** writing a renderer before reading the existing one is how a second implementation of
one rule gets born. That is `B82`, one week later, in a different module.

### S2 — `buildArchiveReport` — one structured answer · **wave 2** · M

`tools/lib/archive-command.js`. Pure-ish (takes `baseDir`, reads, returns data — no writes, no
rendering decisions baked in).

Returns `{ plan, refusals, ungrouped, dropped, stateReadable, reason }` where `refusals` carries
every unit **not** archiving **with the reason `resolveClosures` already produced.**

**AC-S2.1** — `open` and `cannotDetermine` units appear in `refusals`, never in `plan` (FR2.1/2.2).
**AC-S2.2** — each refusal carries a non-empty `reason` (FR2.4).
**AC-S2.3** — a stub-retro unit is refused even though closure calls it `closed` (FR2.5, `B64`).
The sandbox's `M1.E2` is the fixture.
**AC-S2.4** — `ungrouped` is always present, **including when empty** (FR5.1, `B39`).
**AC-S2.5** — `stateReadable: false` yields zero plan entries and one top-level reason, not one
repeated per unit (FR6.2).

### S3 — `renderArchiveReport` — "checked and clean" ≠ "could not check" · **wave 2** · S

**AC-S3.1** — a run with nothing to archive says *which* — no closed units, versus could not
evaluate (FR6.1).
**AC-S3.2** — the ungrouped count renders unconditionally (FR5.2).
**AC-S3.3** — dropped unsafe names render with their reason (AC-N1.1).

### S4 — `commands/archive.md` · **wave 3** · S

Dry-run by default; `--apply` writes. States its taxonomy group (`references/command-taxonomy.md`)
and that it is not phase-gated.

**AC-S4.1** — no write flag ⇒ zero bytes change under `.planning/`, asserted by a before/after
content snapshot (FR4.1).
**AC-S4.2** — `--apply` moves the planned files and only those.
**AC-S4.3** — a second `--apply` is a no-op (NFR2.1).
**AC-S4.4** — registered in the roster; `install-contract` / command-count checks updated.

### S5 — Wire it and prove it end-to-end against the sandbox · **wave 3** · S

**AC-S5.1** — `/sig:archive --apply` on the sandbox archives `M1.E1` (4 files) and `SLICE-AUTH`
(5 files, **whole**), and moves nothing else.
**AC-S5.2** — `M1.E2`, `M1.E3`, `SLICE-BILLING`, `GATE-B` are each refused **with their reason
shown**.
**AC-S5.3** — `applyArchiveTree` invoked outside a migrate (`v3Rename: false`, no coarse lock held)
behaves — the second-caller-ever risk named above.

## Dependencies

S1 → S2 → S3 → S4 → S5. Genuinely serial: S1's finding can shrink S2/S3, and S4 documents what S2/S3
do. No parallel waves worth the coordination at this size.

## Test strategy

Unit tests for `buildArchiveReport` (fixtures + the sandbox), integration for the apply path against
a **temp copy** of the sandbox so the committed fixture stays pristine. Strict Nyquist: every AC
above maps to a test in `M5.E19-VALIDATION.md`.

**No test touches a project outside this repo.** The sandbox exists exactly so that rule costs
nothing.
