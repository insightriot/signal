# M6.E12 — `/sig:advise` proposes big-picture priorities and asks

**Brett, 2026-10-01:** *"priority shouldn't be based on age — it should a) review docs to get big
picture b) propose 3-5 big picture priorities c) ask user to choose."*

Answers backlog row `SIG-142`. Decisions: `D-M6E12-1` … `D-M6E12-12` in [`DECISIONS.md`](DECISIONS.md).

## Measured, before designing anything

- **`/sig:advise` ranks 44 of 46 live rows on age alone** (`SIG-142`, measured 2026-09-07): the
  inputs that discriminate fire on 2 (blocked), 2 (trigger-met) and drop 4. The rest sort by how long
  they have sat there, then by line number.
- **The metadata cannot carry the big picture.** Of 111 open work items (2026-10-01), **33 carry a
  priority and 2 carry a theme.** Grouping by fields would group almost nothing.
- **`/sig:drive` has the same shape without age:** `rankBacklogRow` scores a row's heading
  conventions and ties break on line number, which in an append-mostly file is close to oldest-first.
- **Nothing parses an advisory's contents.** `backlog.js`, `drain.js` and `migrate-memory.js` match
  `BACKLOG-REVIEW-*.md` by file name only, so the format can change.

## The design

The command becomes three steps: **gather → propose → ask.** Code gathers a cited digest of the
project's own documents. The agent running the command reads it, opens the cited files where it needs
more, and proposes 3–5 big-picture priorities, each with the evidence behind it. Code validates the
proposal against the contract and the citation gate, writes the advisory, and the user picks. The
pick is recorded and Signal offers to start it.

The row-by-row list stays as an appendix, no longer ranked: rows sit under the priority that covers
them, the rest follow in file order.

## Functional requirements

### FR1 — The digest (`gatherBigPicture`)
Reads, per `D-M6E12-5`: `PROJECT.md` vision; the current milestone file (theme lines and Epic-status
table); open Epics, local and other-branch (`findWorkOnOtherBranches`); open bugs grouped by priority;
live backlog rows with tags; the newest three retrospectives' *What to feed back into Signal* and
*What we'd do differently* sections; open questions; the inbox's untriaged count.
- **AC1.1** Every digest entry carries a `path:line` that resolves on disk.
- **AC1.2** Each source is `checked` or `cannotCheck`, never both and never neither; absent and
  unreadable carry different reasons. `checked.length + cannotCheck.length` equals the source count.
- **AC1.3** A project with none of these files gets a digest of cannot-checks, not a throw.
- **AC1.4** The digest is bounded: retrospective sections and row bodies are excerpted (a stated
  character cap), so a large corpus cannot exhaust the agent's context.

### FR2 — The priorities contract (`validatePriorities`)
- **AC2.1** 3 to 5 priorities; fewer or more is refused, naming the count.
- **AC2.2** Each has a non-empty `title`, a `why` of at most three sentences, a non-empty `covers`, and
  one or more `evidence` citations.
- **AC2.3** Every citation resolves (path exists, line within it when a line is given — a whole
  file is accepted as evidence), every covered backlog row is **live** in the appendix, and every
  covered row's and bug's citation points at the line it is on (the stale-read check). *(Amended at
  REVIEW pass 1: liveness was implied and not checked; whole-file evidence was allowed by the code and
  the command doc and not by this wording.)*
- **AC2.4** The gate asserts a **count**, exactly: resolved citations = every evidence token +
  every cited covered row and bug + every appendix row. One too few or one too many refuses; zero
  never passes. *(Amended at REVIEW pass 2: the first wording, "≥ priorities + covered rows", counted
  per priority against a per-token total and left slack.)*
- **AC2.5** A refused proposal writes no file and returns every reason, not just the first — except
  a proposal of the wrong SIZE (not 3–5), which is refused on that alone, at once. *(Amended at
  REVIEW pass 1: the rest of the work scales with the proposal's size, and model output is untrusted.)*

### FR3 — The advisory artifact
- **AC3.1** Sections in order: header and status line; corpus read (checked / cannot-check);
  open on other branches (when any); citation rule; **Priorities** (numbered, each with why,
  covers, evidence); **Appendix — every live row** (`D-M6E12-10`). *(Amended at EXECUTE: the
  citation rule precedes the claims it governs, as it did before this Epic; the first wording put
  it after the priorities.)*
- **AC3.2** The header states that the priorities are a judgment and can differ between runs.
- **AC3.3** The appendix carries no age-based ordering or reason. The words "oldest" and "days old"
  do not appear as a ranking reason.
- **AC3.4** Every live row appears exactly once in the appendix: under its covering priority, or in
  the file-order list. Dropped rows appear in a dropped list with their reason.

### FR4 — Asking and recording (`recordChoice`)
- **AC4.1** The command asks with `AskUserQuestion` for 3–4 priorities, and a numbered plain prompt
  for 5 (`D-M6E12-7`).
- **AC4.2** `recordChoice(baseDir, artifactPath, {pick, by, words})` appends a *Chosen* section
  naming the priority (or the user's verbatim words for *Other*) and the date. It writes nothing else.
- **AC4.3** A same-day re-run never overwrites an advisory that holds a choice; it writes the next
  `-N` suffix (`D-M6E12-8`).
- **AC4.4** After recording, the command offers: start with `/sig:drive`, open an Epic with
  `/sig:discuss --epic`, or not now. Nothing starts without a yes.

### FR5 — `/sig:drive` takes the same flow (`D-M6E12-3`, `D-M6E12-11`)
- **AC5.1** An open Epic (local or other-branch) is still proposed first.
- **AC5.2** With no open Epic chosen, `drive.md` step 0a runs gather → propose → ask using the same
  functions, and the picked priority becomes the run's work.
- **AC5.3** The backlog rows stay reachable behind "something else", in `proposeEpicCandidates`'
  existing order (unit-id and tag rows lifted, ties on line number), described accurately in
  `drive.md`. *(Amended at REVIEW pass 1: "in file order" did not describe the code.)*

### FR6 — Age is gone
- **AC6.1** `rankRows` has no age input; `RECOMMENDATION_LIMIT` is removed.
- **AC6.2** The remaining row inputs (blocked, trigger-met, discharge, not-live, fold, bug-discharge)
  still compute and appear as appendix annotations or drop reasons.

## Non-functional requirements (FULL prompt, answered)

- Health probe, graceful shutdown, request logging, security headers, rate limiting: **N/A** — a
  local CLI command with no server or network surface. The one network-adjacent read is `git` for
  other branches, already bounded by timeouts in `branch-work.js`.
- **Context budget:** the digest is capped (AC1.4) so a large `.planning/` cannot crowd out the work.
- **Read-only:** the only file written is the dated advisory, now including its *Chosen* section.

## Blast radius

What this touches and does not change: `plugin/tools/lib/advise.js`, `advise-corpus.js` and a new
digest module; `plugin/commands/advise.md` and `drive.md` step 0a; `tests/advise*.test.js` (rewritten
where they pin the ranked-five shape). Existing `BACKLOG-REVIEW-*.md` files are left as written. The
filename-only consumers (`backlog.js`, `drain.js`, `migrate-memory.js`) are unaffected.
`advise-live-measurement.test.js` pins counts of the discriminating inputs, which this keeps. The
`M6.E8` outcome procedure (diff the next advisory against `BACKLOG-REVIEW-2026-09-13.md`) stops being
comparable, because the format changes. That is stated here rather than discovered.

## Outcome

In the first three real runs of the new `/sig:advise` or `/sig:drive` pick step, the user picks one of
the proposed priorities rather than *Other*. Two *Other*s in three runs means the synthesis is
missing what matters, and the digest's sources are revisited first (`D-M6E12-12`).

## Out of scope, stated so it is a decision

- Judging the priorities with Jev or any second model. The user is the judge, by picking.
- Writing priorities back into `BACKLOG.md` or work items. The advisory stays the only output.
- Step 5 of the work-item store (`/sig:docs-migrate` moving other projects over). Next in the queue.
