# `M6.E6` — Wire the decision queue

**Plain: the loop can park a question and keep working, instead of stopping dead.**

**Opened:** 2026-09-03 · **Tier:** FEATURE (see `M6.E6-PROFILE.md`) · **Phase:** DISCUSS

---

## The trigger, stated as a fact rather than a plan

`queueDecision`, `readQueue`, `formatQueuedDecision` and `DECISION-QUEUE.md`'s header all shipped
in **`v0.1.31`**. Measured 2026-09-03: **every caller outside `tests/` is zero.** `readQueueAdvisory`
(`status.js`) reads the file for `/sig:status` and `/sig:resume`, and `drive.md` §2 reports it — so
the *read* half has consumers and the *write* half has none.

That is this repository's named defect class — built-and-unreached — and
`LOOP-GOAL-DIRECTION.md` §6 puts it second in the agreed order, phrased as an either/or:
**wire it to at least one phase command, or delete it.**

**Delete is now off the table, and by evidence rather than preference.** Two real `/sig:drive`
runs (2026-09-03, an external project) established that drive is reached and useful; the halt in
both cases was structural, not a sign the command is a dead end. A queue serving a command nobody
runs would be worth deleting. This one serves a command that now runs.

## What the gap costs, concretely

`/sig:drive`'s own description promises: *"Queues what it can defer."* It cannot. Today an
unattended run that meets a gray-area question mid-phase has exactly one move — **halt**.

So the experience the `attention` dial was built to buy — *asked me once up front, then ran* —
holds only until the first unanticipated question. `collectPreflight` (v0.1.35) moved the
**foreseeable** questions to the front; every question that could not be foreseen is still a full
stop. The queue is the mechanism for the second category, and it is the difference between a run
that pauses and a run that ends.

## Functional requirements

### FR1 — DISCUSS writes to the queue when it defers

`commands/discuss.md` §4 is the first consumer. When a gray-area decision is deferred rather than
asked, the entry is written with `queueDecision`, carrying the recommendation that would have been
offered.

⚠ **The recommendation is not optional and the module already says so** —
`formatQueuedDecision` renders a defect notice when one is absent, because every gray-area question
in Signal is required to carry one and hiding it is *"failing to use the model's signal."*

### FR2 — Routing: what may be adopted vs. what must be queued

The rule is **not** new vocabulary. `LOOP-ENGINEERING-ANALYSIS.md` §"routing rule" reuses
calibration's own reversibility terms per decision:

| Reversibility of the decision | Behaviour |
|---|---|
| `trivial` / `moderate` | adopt the recommendation, mark it **provisional**, continue |
| `painful` / `irreversible` | **queue**, and block only if downstream work depends on it |

⚠ **A queued decision the next step silently assumed an answer to is worse than a blocked run**,
because it looks like progress. `drive.md` already states this rule in prose; FR2 is what makes it
executable.

### FR3 — Answers are read forward

An answered entry must reach the next pass. `readQueue` already parses `answered`; what does not
exist is any consumer that *acts* on an answer — so today a person answering an entry changes
nothing.

### FR4 — A provisional decision is visibly provisional

An adopted-but-unconfirmed decision is recorded as **provisional** in `CONTEXT.md` / `DECISIONS.md`,
distinguishable from one a person made. A provisional decision that reads like a settled one is a
published fact nothing derived — `M6.E2`'s class.

### FR5 — The advisory keeps telling the truth after wiring

`readQueueAdvisory` currently carries: *"⚠ This is the read half only. Nothing writes to the queue
outside tests yet, so `all answered` is honest about the file and says nothing about whether
deferral is happening."* That sentence becomes **false** the moment FR1 lands and must be removed
in the same change. A caveat that outlives its cause is `M5.E17`'s class.

## Non-functional

- **NFR1 — the queue is a measurement, not a backlog.** Entries accumulating faster than they are
  answered means the attention setting is wrong for the project, and the tooling says so in those
  words. Already implemented in the file header and `readQueueAdvisory`; must survive.
- **NFR2 — no new dial.** Reversibility is per-decision and comes from calibration's existing
  vocabulary. A fourth unenforced knob beside `tier` / `gate_strictness` / `attention` is `B75`.

## Open at DISCUSS — decide before PLAN

### D1. DISCUSS at `unattended` already auto-adopts. What does queueing add? ⚠ **Answer first**

`discuss.md` §4 today: `unattended` → *"select the recommended option for every gray area without
invoking `AskUserQuestion`… then ask once at the end for batch approval."* That is auto-adopt for
**every** gray area regardless of reversibility, and it already exists.

So FR1+FR2 do not add deferral to DISCUSS — they **narrow** what it currently adopts silently, by
carving the irreversible decisions out into the queue. That is a defensible change and it is a
different change from the one the backlog row describes. It needs saying out loud before building,
because a requirement that misdescribes its own effect is how the wrong thing ships correctly.

### D2. Is DISCUSS the right first consumer at all?

The alternative is `/sig:drive` itself: it is the command whose description already promises
queueing, and the only one where a halt is the current behaviour. DISCUSS is where gray areas are
*named*; drive is where deferral has a caller and a cost.

### D3. How does a decision get its reversibility tag?

Calibration's vocabulary is per-**project**. FR2 needs it per-**decision**, and nothing currently
produces that. Options: the asking command tags it as it forms the question; a default of
`moderate` with explicit escalation; or infer from the question's own options. This is the piece
with no existing mechanism behind it.

### D4. What "reads answers forward" actually means (FR3)

Re-running the phase that asked, applying the answer to a waiting task, or only surfacing it for a
person to act on. The third is honest and nearly free; the first two are the ones that make the
queue a loop rather than a noticeboard.

## Decided at DISCUSS (2026-09-03)

All four open questions are answered; `D-M6E6-1`…`D-M6E6-5` in [`DECISIONS.md`](DECISIONS.md) carry
the reasoning.

| | Answer |
|---|---|
| `D1`/`D2` — first consumer | **`/sig:drive`**, not `discuss.md` — reverses the backlog row's framing, on a fact found while writing FR1 |
| `D3` — reversibility tag | **the asking command tags it**, a convention reusing calibration's vocabulary; no new dial |
| `D3a` — untagged decision | **queues**; never adopted by default |
| `D4` — read-forward | **surfaced**; a person acts. A noticeboard, not a loop — said plainly |

⚠ **`FR1` is superseded by `D-M6E6-2`:** the first writer is `/sig:drive`, and `discuss.md`'s
existing auto-adopt behaviour is untouched by this Epic. The requirement is kept unedited above
because it records what was believed at the time; the decision records why it changed.

## How we will know it worked — the outcome oracle

**The completion oracle is the acceptance criteria.** This is the separate question DISCUSS asks at
FEATURE and FULL: what observable thing tells us the *outcome* landed, not merely that the work did?

**Metric: a `/sig:drive` run that meets an unforeseen gray-area question CONTINUES, and the question
is answerable afterwards from `DECISION-QUEUE.md` alone.** Today that run halts. The measurement is
a single real run and a file read — not a suite, which cannot distinguish "queue written" from
"queue written *instead of halting*".

**The counter-metric, because the failure mode has a direction.** Queue depth after that run must be
**small** and every entry must carry a recommendation. A run that continues by parking twenty
decisions has not succeeded at anything except deferring — `drive.md`'s own anti-rationalization
table says so — and `readQueueAdvisory` is already built to report exactly that.

⚠ **What this oracle cannot tell us**, said now rather than discovered at VERIFY: whether the
*routing* is right. A run producing zero queued entries is consistent with "everything was
genuinely reversible" and with "nothing was tagged and the fail-closed default never fired." Only
reading the entries distinguishes those, and that is a person's read, not a check.

## What this Epic explicitly does not do

- **No automatic trigger and no automatic Epic selection.** Both were recommended against on
  measurement (`LOOP-GOAL-DIRECTION.md` §2, §3) and neither is in scope here.
- **No auto-merge.** Unchanged and not negotiable.
- **`B75`'s enforcement half stays open.** Wiring the queue does not make `attention` enforced;
  that remains reported-not-enforced by a decision recorded 2026-08-22.
