# M6.E2 — The facts Signal publishes about itself · PLAN

**Phase goal:** make every published fact in scope either derived-and-compared by a check a user's
command actually runs, or recorded as excluded with a reason — and make each check's reach visible
where a reader will see it.

Requirements: `M6.E2-REQUIREMENTS.md` (26 criteria). Decisions: `D-M6E2-1` … `D-M6E2-7`.
Research: `M6.E2-RESEARCH.md`. Reach evidence: `M6.E2-CORPUS-MEASUREMENT.md`.
Tier: **FULL / strict** — `nyquist_enforcement: strict`, `plan_validation_dims: all`.

## What this Epic does for the FIRST TIME — and it is wave 1

Not the things it builds. The things it **runs**.

1. **`compareBugTally` used for its real purpose.** It has existed since `B77`, derives correctly, and
   has **never once run outside vitest**. Wiring it to a command is its first real execution.
2. **`defineCheck` used from a module that is not `state-drift.js`.** The harness's generality is a
   property of its contract that has never been *exercised* — all 8 registered checks live in the file
   that defines it.
3. **`formatTallySegment` writing into a file.** Today it renders a string inside a test-failure
   message. Nothing has ever used its output as content.

**Therefore S1 is wave 1** — one check, end to end, through the real runner and out of a real
command, before the other four are written. If the harness does not compose from outside its own
file, that breaks against one check rather than five.

**This step has already paid, before any code was written.** Asking what runs for the first time is
what sent us to read `insertAboveFooter` against the real `BUGS.md` — and it does not match
(`RESEARCH` §3). FR1's assumed implementation was wrong in the requirements. Found at PLAN, not
EXECUTE.

## Slices

### S1 — One check, end to end · wave 1 · **M**

The tally check, from `defineCheck` through `runDriftChecks` to `/sig:sweep` and `/sig:resume`.

| Task | What |
|---|---|
| S1.t1 | `plugin/tools/lib/published-facts.js` — a frozen registry exporting **one** check (`published-tally`), built with the imported `defineCheck`. Heal category declared. **Applicability is three-valued, and the middle value is the one that matters** (see below). |
| S1.t2 | Compose at both call sites: `sweep.js:542` and `resume.md`'s step 1e. `runDriftChecks` already takes the registry as an argument; no runner change. |
| S1.t3 | Reach labels **derived**, not transcribed — the check's `describe` reports its evaluable count from `tools/measure-published-facts.js`'s output shape, so a hardcoded `1 of 12` cannot rot (`AC4.3`). |

> **⚠ Applicability, corrected at PLAN review — the first draft got this wrong in the Epic's own
> failure mode.** It read *"`NA` when the project has no `BUGS.md` and `NA` when it has one with no
> tally."* The second branch flattens an honest refusal into a clean-looking verdict:
>
> - **no `BUGS.md` at all** → `NA`. The check does not apply here.
> - **has a `BUGS.md`, publishes no tally** → **`CANNOT_EVALUATE`**, never `NA`. There is a file that
>   *could* carry a claim and does not; that is an unknown, not an exemption. `compareBugTally`
>   already returns `ok: false, reason: 'no-tally'` for exactly this, on the stated grounds that
>   *silence must not read as clean* — mapping it to `NA` would take a correct refusal and undo it.
> - **has a tally** → `EVAL`, then `FINDINGS` or `CLEAN`.
>
> **This is not hypothetical: it is the only non-Signal case the check can see.** All three
> non-Signal corpus projects with a `BUGS.md` publish no tally. Under the first draft, the check
> reported nothing about all three and looked fine doing it.

**Acceptance:** `AC2.1`, `AC2.2`, `AC2.3`, `AC2.4`, `AC3.1`, `AC4.3`, `AC5.1`.
**Test strategy (TDD, RED first):** unit tests over the check's `applicability` and `run` against
fixtures for all four `STATUS` values; an integration test that runs `runDriftChecks` with the
composed registry and asserts the tally check appears in the result; a **proof-of-fail** test that
the check reports findings against the historical `BUGS.md` fixtures `bugs-tally.test.js` already
carries; and `AC5.1`'s test must **distinguish all three applicability outcomes by fixture** —
no-file, file-without-tally, file-with-tally — because a test that only asserts "some status was
returned" passes on the wrong mapping, which is how the first draft would have shipped.

**`AC2.4` is asserted behaviourally, not by grep.** "A non-test caller exists" tested as a grep is
`B81`'s shape — a population-of-one assertion that cannot tell one governed thing from all of them,
and it passes the day someone imports the symbol without calling it. The real property is that
running the composed registry through `runDriftChecks` against a fixture whose tally is wrong
**surfaces the finding**, which can only happen if the caller exists and works. `AC2.4` points at
S1's `AC2.3` integration test.

### Non-functional coverage

`NFR1` (read-only/offline/deterministic) and `NFR3` (no new dependency) are properties of every
slice, asserted once in S1's integration test and re-asserted by the network-call audit already in
`tools/`. `NFR2` (per-check fail-open) is S1.t1's own test — a check that throws must degrade to
`cannot-evaluate`, not take down the briefing (`B70`). `NFR4` (the `/sig:add` path stays instant) is
S2's: no confirmation step is added, asserted by the absence of any prompt in the capture path.

> **Enumerated, not ranged — and this was caught rather than remembered.** The first draft wrote
> S2's acceptance as `AC1.1 … AC1.5` and S3's as `AC3.2 … AC3.5`. `diffRequirementCoverage` returned
> **three missing** (`AC1.2`, `AC1.3`, `AC1.4`) because an id existing only inside an en-dash range
> is invisible to it. That is `M5.E10`'s exact finding — its own VERIFICATION claimed *"56 of 56"*
> and the check returned six missing, every one inside a range. Written down here because the Epic
> reproduced it at PLAN while writing the requirements about published facts being wrong.
