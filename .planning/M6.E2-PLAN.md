# M6.E2 — The facts Signal publishes about itself · PLAN

**Phase goal:** make every published fact in scope either derived-and-compared by a check a user's
command actually runs, or recorded as excluded with a reason — and make each check's reach visible
where a reader will see it.

Requirements: `M6.E2-REQUIREMENTS.md` (26 criteria). Decisions: `D-M6E2-1` … `D-M6E2-7`.
Research: `M6.E2-RESEARCH.md`. Reach evidence: `M6.E2-CORPUS-MEASUREMENT.md`.
Tier: **FULL / strict** — `nyquist_enforcement: strict`, `plan_validation_dims: all`.

## What this Epic does for the FIRST TIME — and it is wave 1

Not the things it builds. The things it **runs**.

1. **`compareBugTally` used for its real purpose.** It has existed since `B77`, derives correctly, and
   has **never once run outside vitest**. Wiring it to a command is its first real execution.
2. **`defineCheck` used from a module that is not `state-drift.js`.** The harness's generality is a
   property of its contract that has never been *exercised* — all 8 registered checks live in the file
   that defines it.
3. **`formatTallySegment` writing into a file.** Today it renders a string inside a test-failure
   message. Nothing has ever used its output as content.

**Therefore S1 is wave 1** — one check, end to end, through the real runner and out of a real
command, before the other four are written. If the harness does not compose from outside its own
file, that breaks against one check rather than five.

**This step has already paid, before any code was written.** Asking what runs for the first time is
what sent us to read `insertAboveFooter` against the real `BUGS.md` — and it does not match
(`RESEARCH` §3). FR1's assumed implementation was wrong in the requirements. Found at PLAN, not
EXECUTE.

### S3 — The remaining four checks · **L** · depends on S1

`AC3.2` (status cell), `AC3.3` (`[Unreleased]`), `AC3.4` (milestone row), `AC3.5` (`facts.md`).

**`AC3.3` is the one general check** (4 of 11 non-Signal projects). It gets its own test against a
fixture derived from a corpus shape, not from Signal's `CHANGELOG`.

### Non-functional coverage

`NFR1` (read-only/offline/deterministic) and `NFR3` (no new dependency) are properties of every
slice, asserted once in S1's integration test and re-asserted by the network-call audit already in
`tools/`. `NFR2` (per-check fail-open) is S1.t1's own test — a check that throws must degrade to
`cannot-evaluate`, not take down the briefing (`B70`). `NFR4` (the `/sig:add` path stays instant) is
S2's: no confirmation step is added, asserted by the absence of any prompt in the capture path.

> **Enumerated, not ranged — and this was caught rather than remembered.** The first draft wrote
> S2's acceptance as `AC1.1 … AC1.5` and S3's as `AC3.2 … AC3.5`. `diffRequirementCoverage` returned
> **three missing** (`AC1.2`, `AC1.3`, `AC1.4`) because an id existing only inside an en-dash range
> is invisible to it. That is `M5.E10`'s exact finding — its own VERIFICATION claimed *"56 of 56"*
> and the check returned six missing, every one inside a range. Written down here because the Epic
> reproduced it at PLAN while writing the requirements about published facts being wrong.
