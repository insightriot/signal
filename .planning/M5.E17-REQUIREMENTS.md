# M5.E17 — Papercuts: instructions that contradict other instructions

**Epic:** M5.E17 · **Tier:** FEATURE (Epic-scoped override — see [`M5.E17-PROFILE.md`](M5.E17-PROFILE.md))
**Opened:** 2026-07-31 · **Target release:** v0.1.15

---

## Why this Epic

Four small items, three of which share a shape: **a Signal instruction that disagrees with
another Signal instruction.** None is a subsystem. All were found *by doing the work* rather
than by looking for them — three of them during M5.E13's own run.

That shape matters more than the size. M5.E13 shipped `B48`, `B51`, and REVIEW's own Critical
for the same underlying reason: **nothing compares one instruction against another**, so two
documents can give an agent conflicting orders indefinitely and only a live run reveals it.

**This is deliberately the small release.** It clears the papercuts before M5.E15 (`B55`) and
M5.E16, both of which are real design work. Nothing here blocks those; this is debt-clearing.

---

## FR1 — `/sig:plan` names what the Epic will do for the first time

**Problem.** `B55` — M5.E13's largest finding — surfaced on that Epic's **very last task**,
because that is when the adherence harness was first used for its real purpose rather than to
prove itself. Had it surfaced in Wave 1, FR1.1's single-shared-wording requirement would have
been recognised as *in direct tension with the measurement* before it was built.

The wider evidence (M5.E13 retro, "What surprised us"): **every significant find of the last
three Epics came from a first execution** — `B54` (first read of that file), `B39`'s two fired
triggers (first walk of the watchlist), `B42`/`B53` (first outside contact), `B48` (first read of
a transcript). *"Shipped but never run"* is the best defect predictor Signal has, and nothing
schedules the running.

**FR1.1** `commands/plan.md` instructs the planner to **name the thing this Epic will do for the
first time** — a tool used for its real purpose, a document executed rather than read, a code
path taken by a project shape not previously tried — and to **schedule it in the first wave.**

**Acceptance criteria**
- **AC1.1** — `plan.md` carries the instruction, and it is specific about *first wave*, not merely
  "consider first-use". A test greps for it.
- **AC1.2** — The instruction names at least one worked example, so a reader knows what counts.

## FR2 — `review.md`'s verdict table stops contradicting ratified practice

**Problem.** `commands/review.md:131` reads *"FAIL | Any Critical, OR Important fix > 50 LOC…"*.
But **two Epics have now shipped PASS-WITH-FIXES with a Critical closed inside REVIEW** — M5.E9
(recorded in `CLAUDE.md` as precedent) and M5.E13. The table and the practice disagree, and at
M5.E13's REVIEW I followed the precedent and *flagged the conflict rather than quietly picking
the convenient reading.* That flag is this requirement.

**The distinction the table misses:** a Critical **discovered and closed inside REVIEW**, with a
small diff and green tests, is not the same event as a Critical discovered at ship or one needing
re-planning. The existing PASS-WITH-FIXES guidance already draws exactly this line for Important
issues (≤ 50 LOC, tests green, no design impact); it simply was never extended to Critical.

**FR2.1** The verdict table is corrected so a Critical **fixed in-phase** under the existing
PASS-WITH-FIXES conditions is PASS-WITH-FIXES, and a Critical that is **not** fixed in-phase — or
whose fix breaks those conditions — remains FAIL.

**⚠ Open question for PLAN, and it is a real one.** The alternative reading is that the *table*
is right and *practice* has been drifting — that a Critical should always force a loop back to
EXECUTE, and the two prior Epics took a shortcut. **PLAN must choose with a written reason, not
assume the code-matches-practice direction.** If the answer is "practice was wrong", FR2 becomes
a process correction rather than a doc fix, and the Epic escalates.

**Acceptance criteria**
- **AC2.1** — The table and the PASS-WITH-FIXES guidance paragraph agree with each other, and a
  test asserts they do.
- **AC2.2** — Whichever direction is chosen, the rationale is written into `DECISIONS.md` — this
  is a rule about how Signal judges its own work, not a typo.

## FR3 — `ship.md`'s `markFresh` ordering stops defeating the freshness check

**Problem — found live during M5.E13's own ship, 2026-07-30.** `plan.md:173` states the rule
plainly: *"Run it **after** the commit — passing a pre-commit HEAD records a stale sha and
silently defeats the freshness check (AC3.4)."* But `ship.md` § 5 lists `markFresh` as step
**5.3**, before the commit that step 5 describes. I followed `ship.md`'s order, and
`isStateStale` immediately reported the release commit as unreflected work.

Two instructions, opposite orders, and only a live run surfaced it — the Epic's whole shape.

**FR3.1** `ship.md` § 5 is corrected so `markFresh` runs **after** the SHIP commit, matching
`plan.md`'s stated rule, or states explicitly why SHIP differs.
**FR3.2** The same ordering is checked across **every** command that calls `markFresh` —
`verify.md`, `review.md`, `discuss.md` — and the audit is recorded with its finding either way.
*"Checked, nothing to change" is a result, not a skip* (the AC1.5 convention from M5.E13).

**Acceptance criteria**
- **AC3.1** — No command instructs `markFresh` before the commit it is meant to stamp.
  A test asserts the ordering.
- **AC3.2** — The cross-command audit is recorded.

## FR4 — The 48-entry inbox backlog gets decided, not deferred again

**Problem.** `listDrainCandidatesWithRecovery` reports **48 undecided candidates** — 1 from April,
16 from May, 5 from June, 26 from July. Every `/sig:plan` drain shows the same wall, so the
rational move is to skip it, which is what has happened for months.

**The constraint, which is not the 48.** The drain has exactly **two** states: *undecided* (shows
every time, forever) or *dispositioned* (never shows again — `defer` included; verified against
`listDrainCandidates`, which filters on `!e.dispositioned`). **There is no "parked, remind me."**
So the pile is either permanent noise or permanently buried. The trigger watchlist already solved
this — every row carries a condition and a review-by date — and the inbox never got the same
treatment.

**FR4.1** The 48 are triaged into real dispositions.
**FR4.2 — HARD GATE, non-negotiable.** Signal does **not** decide these unilaterally. The entries
are Brett's captured ideas; killing them is a product call. The mechanical work — grouping,
age-banding, flagging entries superseded by shipped work — is done first, then **presented as one
batched decision**, not 48 prompts and not a blanket verb.
**FR4.3** Whether to add the missing third state (*parked-with-review-date*, the watchlist
pattern) is **decided but not necessarily built** in this Epic. If it is built, it is a small
addition to the existing disposition vocabulary, not a schema.

**Acceptance criteria**
- **AC4.1** — Candidate count before and after is recorded. No entry is dispositioned without
  explicit approval of the batch it belongs to.
- **AC4.2** — Entries superseded by already-shipped work are identified **mechanically** (by
  cross-referencing `CHANGELOG.md` / `BUGS.md` status), not by recollection — the `B50` discipline.
- **AC4.3** — The third-state decision is recorded in `DECISIONS.md` either way.

## Non-functional

- **NFR1 — Instruction agreement is testable.** FR1–FR3 each ship with a test that pins one
  instruction against another. This is the Epic's whole point: the class exists because nothing
  compares documents, and three fixes without tests would rebuild the class.
- **NFR2 — No new schema.** FR4 is a data pass. If it needs a schema change, escalate (see PROFILE).
- **NFR3 — Reversible.** Every change here is a `git revert` away from undone.
