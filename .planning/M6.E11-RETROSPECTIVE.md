## What changed mid-flight

- **Epic folders entered step 1** (DISCUSS). Without them "what is in this Epic?" would have been a
  metadata field — the stay-put pattern Brett rejected.
- **Closed Epic items stay in their folder** (`D-M6E11-29`, EXECUTE). The first build moved every
  closed item to `done/`, so an archived Epic held documents and no items.
- **Reopen** was added at VERIFY (`D-M6E11-31`), on Brett's answer.
- **An Epic's documents move into its folder when the folder is created** (`D-M6E11-33`), with the
  retrospective and profile exempt (their readers look only at the root), and **only for live Epics**
  (pass 3: moving a closed Epic's artifacts blinded `closure.js`).
- **Nothing is ever deleted** reversed the backlog's "retention policy is not optional" (`-12`).

## What assumptions broke

- **A1 — DISCUSS counts.** 127 bugs, 91 rows, "flags 2 rows" were all written from memory or from a
  describe string; research measured 140, 92 and 1. **The claim-integrity class again, in the Epic
  that exists to end it — caught this time by the PLAN step that measures.**
- **A2 — "folder and metadata can't disagree because one command moves them."** True for items; the
  **generated lists** could still go stale behind a later edit, and did, in the Epic's own last
  EXECUTE commit. Only a test that regenerates and diffs made it impossible.
- **A3 — "store off means unchanged."** Two separate changes altered behaviour for projects without
  the store (S5's `isStateStale` pathspecs; the shared `compareEpicIds`' tie order). The golden
  captured from pre-Epic code caught the first; the second was judged order-only.
- **A4 — "the lock is a detail."** Four of the Important findings across REVIEW were in
  `file-lock.js`, which every Signal command shares. Pass 2's fix for a takeover race introduced a
  new two-holder bug (empty lock read as stale), found only by pass 3.

## What surprised us

- **The migration's riskiest step was the least eventful.** 378 KB of hand-written bugs, multi-line
  rows, pipes inside code spans, 13 un-numbered entries — segmented losslessly on the first real
  run, because wave 1 ran it read-only against the real files before anything else was built.
- **The reviewers kept finding the fix, not the feature.** Pass 2's worst finding was in pass 1's
  fixes; pass 3's worst was in pass 2's. `M6.E3`'s lesson — *fix-on-fix needs its own fresh read* —
  held three times over.
- **The half-met outcome.** Backlog status guessed from wording: **92 → 0**. Bug half **not met**:
  `bug-status-vs-changelog` still judges 33 confirmed bugs, because "did a release fix it?" stays an
  inference until a fix records its item (`Fixes: SIG-n`, step 3). Recorded, not rounded up.

## What we'd do differently

- **Name the store's shared infrastructure (the lock) as a first-class slice.** It was treated as
  plumbing and absorbed four rounds of findings.
- **Write "the committed generated files equal a regeneration" test in S2, not at VERIFY.** It is
  the invariant the whole design rests on.
- **Ask Brett the lifecycle questions (reopen, Epic docs) at DISCUSS.** Both surfaced mid-build.

## Anti-rationalization moment

At REVIEW pass 3, at the loop ceiling, with 4237 green tests, the easy call was "PASS — the rest are
edges". The fixes were instead held to the ≤ 50 LOC in-phase rule, measured at exactly 50, and the
50 lines got their own fresh reader, which found one more real gap (`/sig:item reopen` had no abort
path). "The suite is green" was not the question; "who has read this code who didn't write it?" was.
