## The two findings that change the plan

### R1 — `FR3` (remove the dedupe) **breaks a user-visible renderer** unless `FR5` lands with it

`resume.js:272-275` renders the resume banner's progress line from the raw array length:

```js
const completed = (state.completed_phases ?? state.completedPhases ?? []).length;
const total = PHASES.length - skipped;
lines.push(`Phase:   ${state.phase}  (${completed}/${total} phases done)`);
```

The `/7` denominator assumes the list is **one run's worth**. That assumption held only
because the dedupe capped it. Remove the dedupe with no trim and a real project renders
**`53/7 phases done`** — a number that is not wrong so much as meaningless, in the one
surface `/sig:resume` exists to make trustworthy (the whole point of M4.5.E10).

### R2 — the same change can make **Epic-close detection fire on stale entries**

`completedContainsPhase` (`retrospective.js:382-386`) tests the array with `.some()`, and
`isEpicCloseByState` (`:410-420`) calls it once per tier-required pre-SHIP phase. With a
multi-run log, **a previous run's `REVIEW` entry satisfies the current run's coverage test.**
`coversPreShip` goes true early, and the FR1 retro gate — the thing M4.5.E9/B26/B30 spent
three Epics making fire correctly — starts firing at the wrong moment.

The same `.some()` shape is duplicated in the Layer-2 hook (`checkProposedStateWrite`,
`:494-498`), so both enforcement layers inherit it.

### What R1 + R2 mean for sequencing

**`FR3` and `FR5` are one change, not two.** The trim rule is not hygiene bolted onto the log
decision — it is what keeps the live list scoped to the current run, which is the invariant
`resume.js` and `isEpicCloseByState` **already silently depend on**. Shipping the log without
the trim would trade a silent data bug for a silent counting bug and a mis-firing gate.

*This is the same defect class the Epic is fixing, one level up: an invariant that two
consumers rely on and no writer states. It gets written into
`references/state-schema.md` (AC3.2), not just implemented.*

## What already exists and can be reused

### R3 — `/sig:migrate-memory` already has a `completed_phases` repair vector

Vector-1 de-prose (`migrate-memory.js:314-336`) was built for **the acute eval-project-A/cmmc
case** — the comment says so by name. It locates offending `completed_phases` entries and
relocates their content into the STATE body verbatim, leaving a short scalar. B12 already
ensures the residue is a *meaningful* scalar, never a generic placeholder.

**The gap is narrow and exactly `B45`-shaped.** Vector-1's predicate is *"prose"* —
multi-line, or over `COMPLETED_PHASES_MAX = 150` chars. The live junk entry
`"**▶ Active: Slice SEC1"` is **24 characters and single-line**, so it passes every existing
check while being structurally invalid. **FR4/FR7 is a predicate extension** — from
*too long / multi-line* to *does not match `PHASE (YYYY-MM-DD)` for a `PHASES` member* —
reusing the locator/transform/gate machinery whole. Materially cheaper than assumed at
DISCUSS.

### R4 — vector-2 is the working precedent for FR5's linear trim

Vector-2 (`migrate-memory.js:615-712`) already relocates an oversized STATE body to
**`STATE-HISTORY.md`**, behind a `migrate-memory:vector-2` marker and a dated pointer line.
FR5's linear trim has the same shape, the same destination file, and can mirror its
marker/pointer convention rather than inventing one.

### R5 — Epic-close eviction operates on the **body**, never the frontmatter

`evict.js:296` and `extractEpicSection` (`:174`) work on the markdown below the frontmatter.
This is *why* D-M5E9-7 exists: the phase list has never been in the eviction path, so an Epic
roll deletes it with no copy. FR5's Epic half adds the frontmatter list to that path.

## Risks and non-risks

| | Finding |
|---|---|
| **Risk — regression** | `tests/state.test.js:116-126` **asserts the dedupe** (*"dedupes by phase name when transitioning to a phase already completed"*). Same class as `tests/ship-fr1.test.js`'s two `NO_CURRENT_EPIC` cases: a shipped test asserting behavior we are deliberately reversing. **Rewrite, never delete** — a deleted test and a fixed bug look identical in the suite count. |
| **Risk — recovery** | The dedupe's stated purpose was *"recovery re-transitions don't accumulate duplicates."* Removing it means a re-run appends a second `PLAN (date)`. Under log semantics that is **correct** (it did happen twice) — but it must be a stated consequence in `state-schema.md`, not a discovered surprise. |
| **Non-risk — write-guard** | `checkStateFrontmatterShape` budgets are **per entry** (`COMPLETED_PHASES_MAX = 150`), not per list. A long list of clean scalars does not trip the B8 guard. |
| **Non-risk — checkpoint** | `checkpoint.js:104/127` treats `completedPhases` as a camelCase meta alias it deletes before writing. Unaffected. |
| **Risk — ordering** | `FR6` (B41) wires four more callers to `transitionPhase`. Landing it before the ledger fix multiplies the sites where a bad write happens. Already locked by D-M5E9-3; restated here because it is the plan's hardest constraint. |
