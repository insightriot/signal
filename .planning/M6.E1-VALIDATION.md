### The completeness gap, stated rather than smoothed

**`AC3.4` (the failed dependency install) has no automated test and cannot easily have one.** Its
subject is a user with no registry access at install time — a condition that requires network
isolation to reproduce. `S3.t4` makes the *symptom* legible (a named error at the two import sites)
and **that** is testable by simulating an absent `yaml`. What is not tested is the end-to-end
restricted-network install. **Recorded here as a known limit of this plan**, not discovered later in
VERIFY.

### Coverage summary — derived, and the first draft of it was wrong

> **⚠ This section's first draft claimed "23 of 23 ACs." That number was written from the shape of
> the work and it was false.** `diffRequirementCoverage` — the check `M5.E10` shipped for exactly this
> — was run against this file and returned a denominator of **22**. A grep returns **24**. The claim
> matched **neither**, while its own sub-counts below summed to 24.
>
> **The refutation ships instead of being tidied away**, because it is the most useful thing in this
> document: the check earned its place on its first real use in a new Epic, on the artifact of the
> author who had just written the requirements.

**The true numbers, each with its provenance:**

- **24 acceptance criteria** exist (`grep -oE '\*\*AC[0-9]+\.[0-9]+[a-z]?'`, deduped). **All 24 are
  mapped** in the table above — **0 unmapped**.
- **`diffRequirementCoverage` reads only 22 of them**, returning `covered` with `missing: 0`. It is
  **blind to `AC1.2a` and `AC1.2b`** — the letter-suffixed ids added at DISCUSS. A clean verdict from
  a check that cannot see two of the criteria is not the same as coverage, and this file says so
  rather than quoting the tool's `covered`. **Filed as `B100`.**
- **19 automated** (unit / integration / suite / meta-test) · **3 E2E-or-measurement**
  (`AC3.2`, `AC4.4`, `AC5.1`) · **1 partial** (`AC3.4`) · **1 decision record** (`AC3.5`). Sums to 24.

**Also reported and not suppressed:** the four NFRs come back as `unattributableGroups`
(`NFR-1 … NFR-4`) — they carry no per-criterion ids to attribute, which is a property of how they
were written, not a coverage failure. And `checkValidationConsistency` returned **`cannot-evaluate`**
(*"the completeness dimension names no requirement ids this check can read"*) — a **could-not-check,
rendered as could-not-check**, which is the contract working.

**What this mapping cannot establish.** It maps criteria to *intended* tests. It does not prove those
tests discriminate — that is VERIFY's job under `nyquist_enforcement: strict`, where a test must be
shown to fail before it passes. **A row in this table is a plan, not evidence.**
