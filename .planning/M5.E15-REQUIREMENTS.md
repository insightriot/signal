# M5.E15 — The control arm, made real (`B55`)

**Epic:** M5.E15 · **Tier:** FULL (project default — no Epic-scoped override)
**Opened:** 2026-08-04 · **Target release:** v0.1.19
**Decisions:** `D-M5E15-1 … D-M5E15-7`

---

## Why this Epic

**Signal's flagship adherence result was never isolated.** `tools/adherence-run.js:374` mutates
exactly one file — `join(plugin.root, 'commands', ${canary.command}.md)` — and the guard that is
supposed to prove the mutation worked reads `mutated.includes(residue)` (`:383-384`): it inspects
**the one string it just edited**. A file it never opened cannot fail it.

Meanwhile `createPluginCopy` copies the whole plugin. So a control-arm agent running `/sig:execute`
with the instruction deleted from `execute.md` opens `plan.md` and finds a **byte-identical** copy of
it — and that is not incidental, it is required: M5.E13's FR1.1 mandated one shared wording across
the four middle commands precisely so they cannot drift. **The requirement and the measurement are
in direct tension, and nothing said so.**

Measured consequence, already on the record: re-running `B41-phase-entry` against the reworded
instruction returned **treatment 3/3, control 1/3 → `INDETERMINATE`**, replacing M5.E8's `OBEYED`
(3/3 vs 0/3). The earlier verdict is **not falsified** — 0/3 means no leak was observed in those
three runs — but it was **unisolated**: it could never have distinguished *"the instruction works"*
from *"the agent found it elsewhere."* Every future verdict inherits that defect until this lands, so
the harness cannot support the claims it was built to support.

### What DISCUSS measured, and how it changed the Epic

`B55` prescribes the fix as *"delete the instruction corpus-wide across the copied plugin."* Walking
the copied tree instead of quoting the bug found that this is **not a coherent operation**.
`PLUGIN_COPY_DIRS` (`adherence-harness.js:50-62`) copies `.claude-plugin`, `commands`, `skills`,
`agents`, `references`, `hooks`, `tools`, `state`. `transitionPhase` occurs in **13 files** there, in
**five different kinds of statement**:

| Kind | Files (mentions) | Deletable? |
|---|---|---|
| **Orders the call** | `execute.md` (4, the target) · `plan.md` (4) · `verify.md` (4) · `review.md` (4) · `ship.md:98` (1) | **Yes — this is the instruction** |
| Teaches the rule without ordering it | `discuss.md:158` (*"do NOT set `phase` here — the **incoming** command advances it"*) · `index.md:11` · `calibrate.md:251` | No |
| Documents the semantics | `references/state-schema.md` (6) | No |
| The experiment itself | `references/adherence-canaries.json` (4) — the measured sentence **verbatim** | Excluded from the copy (FR4) |
| The capability | `tools/lib/state.js` (3) — the function | **Never** |

**The finding that reshaped the Epic: there are two ways to be wrong, and `B55` names only one.**

- **Under-delete** (today) → the instruction leaks → the recorded defect.
- **Over-delete** → a *different* invalidity. A control agent stripped of `state-schema.md` is not an
  *uninstructed* agent, it is a *differently-informed* one, and its 0/3 is equally unreadable. The
  extreme case makes it plain: delete `transitionPhase` from `tools/lib/state.js` and a control arm
  that does not transition means **"could not"**, not **"was not told."**

So the claim was fixed first and the mutation derived from it (**D-M5E15-1**): *this rule, as
instructed anywhere a command tells an agent to act on it, does work.* Not *"this line does work"*
(too weak to be worth six live runs) and not *"this rule, wherever stated"* (a claim the mutation
cannot support).

**Second finding — a declared list of deletion sites would re-create `B55` exactly.** The current
anchor was already widened once, line → section, and **stopped one scope short**. A per-canary list
of files is correct the day it is written and silently stops matching the corpus when a sixth command
names the function. That is why FR2 separates *deleting* from *deciding the tree is clean*, and why
the check fails closed on anything it does not recognise.

## Scope

**In:** the registry schema for directive anchors; the independent leak walk; refusal on directive
residue and reporting of descriptive residue; excluding the canary registry from the plugin copy;
registering the leak check with the `guard-callers` mechanism; the live re-run of `B41-phase-entry`
under the fixed arm; amending the existing log records.

**Out:** widening the harness to new canaries (the registry holds exactly one and this Epic does not
add another); the adherence **ceiling** and its classifier (untouched); `B41`'s own conflict with the
phase-log integrity rules (`B48`, already recorded as a `QUALIFIED` caveat and unresolved by design).

## Functional Requirements

### FR1 — A canary declares its directive sites per file, and its isolation scope on its face

The registry entry replaces the single `deleteSection` anchor with a **list** of per-file deletion
targets, plus an explicit declared scope. Declared **before any run**, same rule as AC3.3 — an anchor
chosen after seeing a result is a rationalization.

**Acceptance criteria**

- **AC1.1** — A canary declares `isolation: "directive"` and a `deletions: [{file, section}]` list;
  loading a canary that declares neither **throws**, naming the canary id. A canary that silently
  falls back to one-file behavior is the defect this Epic is fixing.
- **AC1.2** — `B41-phase-entry` declares its five directive sites (`execute.md`, `plan.md`,
  `verify.md`, `review.md`, `ship.md`), each with the section anchor that removes it.
- **AC1.3** — Every declared anchor is asserted to occur **exactly once** in its real file, by a test
  that reads the live corpus — the existing `deleteLine`-occurs-once discipline, widened to the list.
  A drifted anchor deletes nothing, makes both arms identical, and reads as `INERT`.
- **AC1.4** — `applySectionDeletion` is applied per declared file; a section anchor that is absent
  **throws** rather than skipping that file (unchanged behavior, now per-entry).

### FR2 — The leak check walks the whole copied tree independently, and fails closed

The check never consults the canary's deletion list to decide whether the tree is clean. It greps
every copied file for the residue token (`canary.trace.functionName`) and classifies what survives
against an **allowlist of known-descriptive sites**. Anything not on the allowlist is **directive**.

**Acceptance criteria**

- **AC2.1** — Given a mutated tree where one declared directive site was *not* deleted, the check
  fails and names the **file and line**. A test constructs this case by dropping one entry from the
  deletions list.
- **AC2.2** — Given a fixture tree containing a **new** file that names the residue token and is not
  on the descriptive allowlist, the check fails. This is the anti-regression criterion: a sixth
  command naming `transitionPhase` breaks the harness loudly instead of leaking into a verdict.
- **AC2.3** — The descriptive allowlist is pinned by a test enumerating exactly
  `discuss.md`, `index.md`, `calibrate.md`, `references/state-schema.md`, `tools/lib/state.js`,
  `tools/lib/directive-classifier.js`, `tools/lib/adherence-verdict.js`. Adding a file to the
  allowlist is therefore a visible, reviewed edit, never a side effect.
- **AC2.4** — `tools/lib/state.js` is on the allowlist **as the capability, not as a leak**, and a
  comment at that entry states why deleting it would convert *"was not told"* into *"could not."*
- **AC2.5** — The walk covers every directory in `PLUGIN_COPY_DIRS`, not just `commands/`. A test
  plants the token in `skills/`, `agents/`, `hooks/` and `state/` and asserts each is found.

### FR3 — Directive residue refuses the run; descriptive residue rides on the verdict record

**Acceptance criteria**

- **AC3.1** — Surviving directive residue throws before any agent is invoked, so **no verdict is
  emitted** — the same discipline as the existing seam precondition (`adherence-verdict.js:20-26`).
- **AC3.2** — Descriptive residue never blocks a run; under FR1's directive scope it is **non-empty
  by construction** on every run.
- **AC3.3** — The descriptive residue and the declared isolation scope both appear on the rendered
  record, via `renderRunRecord`'s existing `caveats` mechanism ("Scope of this verdict"). A reader
  who sees `OBEYED` sees, in the same table, what the control arm could still reach.
- **AC3.4** — A record rendered without an isolation scope fails a test. A verdict whose scope is
  implicit is the overclaiming this Epic exists to end.

### FR4 — The canary registry is excluded from the plugin copy

`references/adherence-canaries.json` states the measured instruction verbatim in `instruction` and
names the section being removed — the sharpest of the five leaks, and the measuring apparatus leaking
into its own measurement.

**Acceptance criteria**

- **AC4.1** — After `createPluginCopy`, `references/adherence-canaries.json` does not exist in the
  copy; the rest of `references/` does.
- **AC4.2** — The harness still resolves the registry, because `loadCanaryRegistry(ROOT)`
  (`adherence-run.js:446`, `:495`, `:559`) reads from the real repo root. A test asserts a full run
  plans correctly with the file absent from the copy.
- **AC4.3** — What the plugin **ships** is unchanged: `references/adherence-canaries.json` is still
  in the installed plugin. A test pins that this is a copy-time exclusion, not a packaging change.

### FR5 — The leak check has a caller by construction

**Acceptance criteria**

- **AC5.1** — The leak check is registered in `tests/guard-callers.test.js` (M5.E13 S3.t3 / FR2.3,
  the `I2` mechanism) and the test fails if it loses its caller.
- **AC5.2** — That file's stated scope-limit header is updated to name this instance. It currently
  declares it covers **2 of 4** known instances of the never-called-guard class; a new covered
  instance that leaves the header saying otherwise is a claim the artifact contradicts.

### FR6 — `B41-phase-entry` is re-run under the fixed arm, and the result is published

**Acceptance criteria**

- **AC6.1** — A run of ≥ 3 per arm completes under the directive-scoped arm with the seam precondition
  passing, and its record is appended by `appendRunRecord`.
- **AC6.2** — The record carries `isolation: directive` and the descriptive residue (AC3.3).
- **AC6.3** — **Whatever the verdict is, it is published.** `INERT` would mean M5.E9's phase-entry
  instruction — four command files and FR1.1's shared wording — changes nothing. Pre-committed at
  DISCUSS (**D-M5E15-6**); a result publishable only when it flatters the project is not a
  measurement.
- **AC6.4** — The Epic does not close on a re-run that was planned but not executed. A run that
  cannot complete (agent CLI unreachable, seam failure) blocks the close and is recorded as such —
  `AgentUnreachableError` already exists so *"could not measure"* is never confused with
  *"measured zero."*

### FR7 — The existing log records are amended in place, never rewritten

**Acceptance criteria**

- **AC7.1** — M5.E8's `OBEYED` record gains an annotation recording that it was **unisolated**,
  appended beneath the record with the record left byte-identical.
- **AC7.2** — It is **not** retracted. The annotation states that 0/3 means no leak was observed in
  those three runs, and that unisolated is not falsified — the log has to be able to say the
  difference.
- **AC7.3** — `NOTICE_KINDS` supports the kind used. It currently holds only `INVALIDATED` and
  `QUALIFIED`, while the file already carries a hand-written `DIAGNOSED` block on the `INDETERMINATE`
  record — see **`B80`**. Whichever kind FR7 uses must exist in code, or the annotation is another
  hand-edit to an append-only log.

## Non-Functional Requirements

- **NFR1 — No verdict without proof.** Every existing refusal path is preserved: seam precondition,
  the ≥ 2-runs-per-arm rule in `summarizeArm`, and `AgentUnreachableError`. FR2's check is added to
  that set, not substituted for any of it.
- **NFR2 — The real corpus is never mutated.** Deletions apply to the plugin **copy** only;
  `assertIsolatedFixture` guarantees remain unchanged. A test asserts the real `commands/*.md` are
  byte-identical after a full run.
- **NFR3 — Fail closed, not open.** Unlike the read-only briefing commands, an unrecognised residue
  site **stops** the run. A measurement that fails open produces a plausible number, which is this
  harness's documented worst outcome.
- **NFR4 — Deterministic where it can be.** Everything except the live agent runs is offline and
  deterministic: same tree in → same classification out, so the leak check is testable by fixture.
- **NFR5 — No silent caps.** If the walk skips anything (binary files, size limits), the skipped set
  is reported by count and reason.

### FULL-tier NFR checklist — dispositioned, not skipped

| Item | Disposition |
|---|---|
| Health / liveness probe | **N/A** — no long-running process; the harness is invoked and exits. |
| Graceful shutdown / signal handling | **IN SCOPE, existing** — runs already spawn a subprocess with a timeout and SIGKILL, and temp fixtures are removed in a `finally`. Unchanged here; noted because an aborted run must not leave a mutated copy behind. |
| Structured request logging | **IN SCOPE, existing** — per-run transcripts are retained for **every** run, not only failures, because `absent` is the verdict that most needs a reason. Unchanged. |
| Security headers | **N/A** — nothing is served over HTTP. |
| Rate limiting | **N/A** — not publicly exposed. The live runs call the local `claude` CLI. |
| Input validation at boundaries | **IN SCOPE** — FR1 anchors and FR2 allowlist entries become file paths against the copy root; they route through the existing path-confinement discipline. |

## Open questions for PLAN

1. **Where does the leak check live?** `adherence-verdict.js` owns the deletion helpers and the
   refusal discipline; `adherence-harness.js` owns the copy and the isolation assertions. The check
   spans both. One home, or an explicit reason for two — **two implementations of one rule is the
   shape M5.E13 REVIEW flagged.**
2. **How is a directive site distinguished from a descriptive one — allowlist alone, or allowlist
   plus a shape rule?** AC2.3 pins an allowlist, which is simple and fails closed. A shape rule
   (imperative verb, code-fence, `await`) would generalise to future canaries but adds a classifier
   whose errors are silent. PLAN decides; the bias should be toward the boring one, since the
   classifier next door (`directive-classifier.js`) already carries a documented split rule people
   argue with.
3. **Does `ship.md:98` belong in the directive set?** It orders `transitionPhase(baseDir, 'SHIP')` —
   the same rule, a different phase, in a command the canary does not run. Including it is the
   consistent reading of D-M5E15-1; excluding it is defensible because `/sig:ship` is not reachable
   from the fixture. **Decide and record** — this is exactly the "one scope short" judgment that
   produced `B55`.
4. **Does the re-run happen inside EXECUTE or at VERIFY?** FR6 is the Epic's own proof, and a live
   6-run measurement is not a normal EXECUTE task: it is slow, non-deterministic, and its result is
   a published artifact rather than code. PLAN places it and states what happens to the wave if the
   verdict comes back `INERT`.
