## R1 — `commands/verify.md` confirms the diagnosis, at the line

`verify.md:54` — *"For each task in `{phase}-PLAN.md`"* — is the **whole** coverage loop. The file
never names `REQUIREMENTS.md`. A requirement that never became a PLAN task acceptance criterion is
**structurally outside** VERIFY's enumeration; it is not missed by carelessness, it is out of scope by
construction.

`verify.md:100` — *"All acceptance criteria verified with evidence"* — is a **self-attested checkbox
over a self-enumerated set**. Both halves matter: the checker chooses the population *and* attests to
it.

**Consequence for FR1:** AC1.4 is not a docs tweak. Adding the REQUIREMENTS read changes what VERIFY
*enumerates*, which is the actual fix; the diff is what makes the enumeration honest.

## R2 — `state-drift.js` is the right host, and it already enforces the three-outcome rule

The check registry (`state-drift.js:101-146`) requires each check to declare
`{id, healCategory, applicability, run, healMechanism, describe}` and **validates the declaration at
registration** — a check claiming a heal category it cannot deliver throws at load, not at use.

`applicability` returning `{status, reason}` is exactly `NFR4`'s three-outcome contract, already
built and already tested. **FR8 should register here rather than invent a parallel mechanism**, and
FR1/FR2/FR7 should copy its shape even where they live elsewhere.

**This also answers a PLAN open question:** FR8 lives in `state-drift.js`. Not a new module.

## R3 — ID extraction already exists; do not write a second one

`tools/lib/evict.js:51-53` already carries:

```js
const FR_ID_RE = /\bFR\d+[a-z]?\b/g;
const AC_ID_RE = /\bAC\d+(?:\.\d+)?\b/g;
```

**FR1 must reuse these, not re-derive them.** A second implementation of *"what counts as a
requirement ID"* is `B82`'s exact shape — that bug was two implementations of *"which files belong to
this unit"* disagreeing, and it shipped a half-archived unit. Extract to a shared module and have
both call it; if the two are allowed to drift, the coverage diff will one day disagree with the
evictor about what a requirement even is.

Note the regexes cover `FR` and `AC` but **not `NFR`** — and `\bFR\d+\b` does not match `NFR1`
(word boundary fails mid-token). `M5.E10-REQUIREMENTS.md` declares five NFRs. **This is a live gap,
not a hypothetical:** shipping FR1 against these regexes unchanged would produce a coverage report
that silently ignores every non-functional requirement while reporting itself complete — the Epic's
own defect class, in the Epic's first deliverable.

## R5 — There is no VERIFICATION template, and the precedent for making one is strong

`references/` holds no verification template. The precedent is
`references/retrospective-template.md`, and it is worth copying **structurally**, because it solved
the same enforcement problem:

- per-tier template blocks between `<!-- TEMPLATE: {TIER} -->` markers
- **exact-string-locked headings**, matched by `validateRetroContent` against
  `getRequiredSections(tier)`
- a **byte threshold** so *"a heading with an empty body fails as hard as a missing heading"*

**That last rule is precisely `AC3.4`.** FR3's risk is shipping a heading that everyone fills with
one word; the retro validator already faced and solved it. Reuse the mechanism, not just the idea.

## R6 — The `AC1.5` fixture does not exist, and the obvious source is off-limits

**Checked, not assumed.** `PHASE11` does appear in `tests/` — but it is the **non-strict Epic-ID**
case (`resolve-artifact.test.js:171`, *"non-strict token (traction-engine's live value)"*), which is
`B53`'s territory. **The Phase 11 REQUIREMENTS/VERIFICATION artifact pair is not in this repo.**

AC1.5 asks for the **field case, not a synthetic one** — deliberately, because a synthetic fixture
proves only that the check catches what its author imagined.

**Constraint:** traction-engine is a live project and Signal's standing rule is that production repos
are not test beds. **Reading it is fine; running against it is not.**

**Resolution for PLAN:** *import*, don't *point at*. Copy the two artifacts into
`tests/fixtures/claim-integrity/` as a **frozen** fixture with provenance recorded in a README —
a one-time read-only copy, after which the test touches only the repo. This satisfies AC1.5's "field
case" and violates nothing.

**Second home, deliberately:** `examples/sandbox/` already carries REQUIREMENTS/VERIFICATION pairs
(`M1.E1-REQUIREMENTS.md`, `M1.E1-VERIFICATION.md`, …). It exists so no command need be pointed at a
real project, and its README says shapes get added as the commands needing them get worked on. The
**command-level** path should exercise the sandbox; the **field-case** assertion uses the frozen
import. Two fixtures, two different jobs — not duplication.
