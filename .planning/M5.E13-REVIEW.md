## Critical

### C1 — The new phase guard made SKETCH-tier projects unshippable ✅ FIXED

**`tools/lib/state.js`** — `PHASE_ARTIFACT_EXEMPT`

`commands/execute.md:96` explicitly permits skipping the PROGRESS artifact:

> *"Optional for single-task plans. When the plan has only one task (**typical at SKETCH tier**),
> `{phase}-PROGRESS.md` is informational and the commit log substitutes for it. **Skip without
> ceremony** — the SKETCH dogfood (T3 Task 3) confirmed this works cleanly."*

S2.t2's guard demanded it unconditionally. Since `/sig:ship`'s transition **leaves EXECUTE**, a
SKETCH project that skipped PROGRESS — as the docs invite — **could not ship at all.**

Reproduced before the fix:

```
transitionPhase(sketchProject, 'SHIP')
  → Refusing to record EXECUTE as complete: no PROGRESS artifact found
```

**This is `B42`'s exact shape** — a gate refusing a supported mode, invisible because
Signal-on-Signal never runs at SKETCH. `B42` was a **P1 that survived nine releases** for the
same reason.

**And the irony is the finding.** This Epic exists because `B48` was an **unconditional
instruction**. FR1.1 fixed the instruction; FR1.2 replaced it with an **unconditional guard**.
The failure mode was re-created one layer down, by the work that was removing it.

**Fix:** `EXECUTE` added to `PHASE_ARTIFACT_EXEMPT`, with the `execute.md` citation inline.

**Costs `B48` nothing — verified, not assumed.** `B48`'s case is `/sig:execute` against a project
with no PLAN artifact. That transition *leaves PLAN*, so `PLAN`'s artifact is what gets checked,
and it is still refused. The exemption relaxes only the *leaving-EXECUTE* check — a different
event (the ship), on an artifact the docs already call optional. Both paths now pinned by tests.

**Why REVIEW caught it and VERIFY did not:** VERIFY checked the acceptance criteria, and **every
one passed** — AC1.3 asked that legitimately artifact-less phases not be blocked, and I
enumerated `CALIBRATE` and `SHIP` from the plan, which is where I looked. **The criterion was met
and the code was still wrong**, because the enumeration came from the plan rather than from the
command docs. `execute.md:96` had said so in writing since v0.1.3.

## Important

### I1 — A duplicated literal, under a comment claiming it wasn't duplicated ✅ FIXED

**`tools/lib/retrospective.js`** — `synthIfClosing` / `synthState`

S4.t1 introduced `synthIfClosing` and left `synthState` as a **byte-identical** object literal —
ten duplicated lines. The comment directly above read:

> *"Deriving it here rather than re-deriving it in the skip branch keeps one definition of 'what
> STATE would say,' which is the divergence `B53` was about."*

The comment states the principle; the code beneath it does the opposite. `aboutToClose` implies
`atLastPreShip`, so the second literal was always exactly the first.

**Fix:** `const synthState = aboutToClose ? synthIfClosing : null;` — 10 lines → 1, behaviour
identical, tests unchanged and green.

Two implementations of one rule is `B53`'s own shape. Worth recording that a **comment asserting
a property is not evidence the code has it** — the same class as a doc describing a guard nothing
calls.
