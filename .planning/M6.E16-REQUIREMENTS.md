# M6.E16 — Requirements: Epics and units become records

**Label:** *"Epics and units as records"*. Priority 1 of
[`BACKLOG-REVIEW-2026-10-10.md`](BACKLOG-REVIEW-2026-10-10.md), picked by Brett. Stage 1 after work
items in [`analysis/STORAGE-ARCHITECTURE-PROPOSAL.md`](../analysis/STORAGE-ARCHITECTURE-PROPOSAL.md)
§4. Covers `SIG-132`, `SIG-255`, `SIG-288`, `SIG-289`. Tier: project FULL (no per-Epic profile),
`attention: checkpointed`. Decisions `D-M6E16-1` … `D-M6E16-20` in [`DECISIONS.md`](DECISIONS.md).
The list of code this Epic touches is [`M6.E16-INVENTORY.md`](M6.E16-INVENTORY.md).

## Why now

Work items are records; Epics and units are still worked out from filenames, a hand-kept table and
which folder a file sits in. Measured on this repository, 2026-10-11:

- `closeEpic` looks for `.planning/work/epics/<ID>/`, which nothing creates. It has recorded no close
  since `M6.E11`. `EPICS.md` prints "no Epic folder" for `M6.E14` and `M6.E15`, both shipped.
- No code writes a milestone's Epic row. `M6.E15`'s was missing after its SHIP.
- Three parsers read that table in three formats; the one feeding the SHIP gate reads none of
  `MILESTONE-6.md` (`SIG-132`).
- "Is this unit closed?" is answered from a retrospective existing, a verdict line, a milestone row, or
  `STATE.md`, depending on the caller (`SIG-288`, `SIG-289`).
- No project is on the store yet besides Signal, so changing the design now costs one migration.

## Functional requirements

Every FR starts with a test that fails on `main` before the change (FULL, strict TDD).

### FR1 — The unit record (`D-M6E16-1`, `-5`)
- AC1.1 A unit is one JSON record at a path fixed by its ID, never moved, validated against a schema
  that ships with the plugin.
- AC1.2 The record stores no status. Open, closing, closed and held are folded from its events.
- AC1.3 A unit ID is either an Epic ID (`M6.E16`) or the project's own unit name; an ID that could
  escape the store folder or collide with another unit is refused. Collisions, named at PLAN: two
  names differing only by case; a name shaped like one of the project's own item IDs; a name equal
  to a phase name.
- AC1.4 An item's `queued` and `started` events accept any existing unit ID, and refuse one with no
  record.
- AC1.5 A record that fails the schema is reported by `/sig:docs-sweep` by ID and path, as item
  records are.
- AC1.6 A project has unit records when `.planning/work/units/` exists, even empty (`D-M6E16-16`,
  added at EXECUTE); without it every reader and writer behaves as on `v0.1.50`, as AC6.4 defines
  that — the kinds of difference it names included (the edit hook, the migration's dry run and the
  100-character limit on a unit name apply with or without the folder).

### FR2 — One write path (`D-M6E16-9`)
- AC2.1 Every change to a unit record goes through one library and records an event. One writer
  records two: asking again to close with a newer commit records `reopened` then `close_requested`
  (amended at EXECUTE).
- AC2.2 The edit hook blocks `Edit` and `Write` to unit records, as it does for item records.
- AC2.3 The write-path inventory test covers unit writers: an exported function that changes a unit
  record without recording an event fails the suite unless listed with a reason.

### FR3 — Opening a unit
- AC3.1 `/sig:discuss --epic` and `/sig:new-project --epic` create the unit record when they set
  `current_epic`. These commands open Epic IDs only; other unit names are created by the migration
  (`D-M6E16-13`, amended at PLAN).
- AC3.2 The next Epic ID is derived from the unit records, including closed ones; filenames only
  raise it, never lower it (`D-M6E16-18`, amended at EXECUTE).
- AC3.3 Opening a unit whose record is closed is refused with its close line; it is reopened only when
  the person confirms after seeing that (`D-M6E16-17`, amended at EXECUTE).

### FR4 — Closing a unit (`D-M6E16-2`)
- AC4.1 SHIP records a close request on the unit with a commit as proof. The unit reads *closing*.
  With no commit passed the proof is HEAD, and the request is refused, with nothing written, when
  the project has uncommitted or untracked changes and either HEAD is already on the default
  branch or the default branch is not recorded in the clone (`origin/HEAD` not set), so nothing
  can say whether it is (`D-M6E16-21`; the second case amended at REVIEW pass 4, `D-M6E16-28`).
- AC4.2 It reads *closed* only when that commit is on the default branch; the same confirm step that
  confirms item closes confirms unit closes. The default branch is the one `origin/HEAD` names in
  the clone, and is never guessed: with `origin/HEAD` not set, no close is confirmed — an item's or
  a unit's — each stays *closing* with the reason `no-default-branch`, and the confirm step's line
  says to run `git remote set-head origin -a` (`D-M6E16-27`, added at the REVIEW loop ceiling).
- AC4.3 The close is refused when the unit's retrospective is missing or still holds placeholders, and
  when any of its items is open.
- AC4.4 The close no longer depends on an Epic folder existing: closing `M6.E16` itself at SHIP
  records a close.
- AC4.6 With unit records, whether a SHIP closes the Epic is read from `STATE.md` alone; no milestone
  row is read (`D-M6E16-10`, added at PLAN).
- AC4.5 A closed unit can be reopened with a recorded event and a reason.
- AC4.7 When a unit's close is confirmed, the step that confirms it evicts that unit's narrative from
  `STATE.md` (the existing `evictEpicNarrative`, with its gate) and reports the result beside the
  confirmation: moved, nothing to move, or kept and why. A refusal or a failure there never undoes or
  fails the confirmation, and a run that confirms no unit evicts nothing (`SIG-295`, `D-M6E16-19`;
  amended at EXECUTE, S10).

### FR5 — Hold (`D-M6E16-7`)
- AC5.1 A hold is a recorded event with a reason; releasing it is another event.
- AC5.2 `/sig:docs-archive` and the archive step of `/sig:docs-migrate` refuse to move a held unit's
  files and print the reason (`SIG-255`).

### FR6 — Readers switch to the records (`D-M6E16-1`, `-2`)
- AC6.1 Every function in [`M6.E16-INVENTORY.md`](M6.E16-INVENTORY.md) § *Readers and derivers* is
  listed in the plan as **switches** or **stays**, with a reason for each that stays. The list, not a
  count, is the denominator.
- AC6.2 With unit records present, a unit that **has** a record is decided by its record alone: no
  switched reader decides its closure from a retrospective existing, a verdict line, a milestone row,
  or a file's folder (`SIG-288`, `SIG-289`). A unit with **no** record is still judged from its
  files, and `/sig:docs-sweep` reports it by name with the fix (`unit-without-record`).
  A unit whose record is closed reads closed even while it is `current_epic`, but none of its files
  is moved while it is current: the archive names it "closed; still the current unit, so its files
  stay until the next Epic opens" (`D-M6E16-25`, added at REVIEW pass 2).
  (Amended at REVIEW, pass 1, `D-M6E16-23`: as first worded the criterion allowed no exception, and a
  test pinned one — a unit that has no record, on a project that has unit records, is closed by its
  retrospective and verdict. That is intended: nothing else is known about such a unit, and reading
  it as open would stop every unit from before the records from archiving. What was missing is that
  nobody was told; the sweep now says so.)
- AC6.3 Phase-progress readers (`phase`, `completed_phases`) keep reading `STATE.md` and behave as
  before; existing tests for them stay green unchanged.
- AC6.4 A project with no unit records gets what it gets on `v0.1.50`, said by kind, not as a list
  of functions.
  **Identical to `v0.1.50`:** every closure answer; every file move; every item write and read of a
  record `v0.1.50` accepted, except one naming a unit over 100 characters; every refusal `v0.1.50`
  gave for a call `v0.1.50` had, with the same code; every printed report except the one corrected
  sentence. (Pinned by the existing suites for linear and non-store projects, unchanged.)
  **Different, by kind** (each is an exception to the list above, and nothing else is):
  (a) *what this Epic adds* — the edit hook guards `work/units/` paths whether or not the folder
  exists (AC2.2), and reads a path under every `.planning` folder it names, not only the innermost,
  so an item record under a folder called `.planning` inside `work/items/` is refused where
  `v0.1.50` let it through (added at REVIEW pass 2); `/sig:docs-migrate --work-store`'s dry run on a project already on the store
  proposes unit records where it used to refuse (AC9.2); return values gain keys that are empty
  without unit records (`settled`, `counts.settled`, `held`); the first-time
  `/sig:docs-migrate --work-store` migration of a project with no store proposes unit records and
  legacy closes in its dry run — which also says, of a milestone file with no Epic-table markers,
  that it is left as it is (AC7.2) — and its apply creates `work/units/` (AC9.1), so a project
  migrated on this version has unit records on; that same first-time apply no longer fails its own check on
  a project that has `.planning/archive/epics/<ID>/`, where `v0.1.50` threw `SCHEMA` ("the
  migrated store did not verify: … view-stale: .planning/work/EPICS.md") and wrote nothing; the
  `WORK.md` body a migration writes names `units/`, and words its `epics/` line to match; and the
  migrate command reads `--also`, which `v0.1.50` passed over. (The last four amended after VERIFY
  loop 3.)
  And the item library has one new call, `rerequestCloses`: it asks again, with a commit that
  landed, for the close of an item still *closing* on a commit that never reached the branch (a
  squash or rebase merge); it works with or without the folder, and changes no answer of a call
  `v0.1.50` had (`D-M6E16-24`, added at REVIEW pass 2). The Epic close never makes that call on
  its own: on the default branch after the merge it lists each such item and writes nothing, and
  asks again only for the ones a person names as part of the merged pull request; an item that was
  not named stays open and refuses the close (`D-M6E16-26`, added at the REVIEW loop ceiling).
  (b) *the unit-name rule* — the item schema accepts any safe unit name where it accepted only an
  Epic ID; without unit records the writers and the readers still refuse a name that is not an Epic
  ID, as `v0.1.50` did; and a name over 100 characters is refused everywhere, where `v0.1.50`
  accepted one shaped like an Epic ID. The limit is kept on purpose: no real ID is that long, and a
  name without a bound is hostile input.
  (c) *wording* — the text of a refusal or a finding (never its code), and the one false sentence of
  `/sig:docs-migrate`'s dry run corrected in t10.3 (`SIG-289`).
  (d) *the default branch is not guessed* — in a clone where `origin/HEAD` is not set, `v0.1.50`
  confirmed an item's close against whichever one of `origin/main` / `origin/master` existed; now
  it is not confirmed until `git remote set-head origin -a` is run (AC4.2, `D-M6E16-27`; none of the
  94 captured answers asks this, and `tests/unit-close-git-edges.test.js` pins it).
  `tests/unit-records-off-parity.test.js` compares 94 answers (80 library calls, 6 listings of the
  files on disk, 3 `git status` listings and 5 readings of a `WORK.md` the library wrote) with
  literals taken from `main`, takes out only these kinds, and fails on any other difference. A
  message `main` words the same way is compared word for word; one worded differently must still
  say every number, ID, path and quoted name `main`'s said (one exception, pinned: a writer
  refusing a unit name now names the item where `v0.1.50` named the event's place, `events[2]`).
  (Amended at VERIFY, loop 1 and loop 2, `D-M6E16-20`: "exactly" was measured against `main` twice.
  Loop 1 named four differences as a closed list; loop 2 found five more in functions that list's
  test did not call, so the criterion now says what is identical and what differs by kind. One of
  the five was removed in code instead: the readers refuse a record naming a unit that is not an
  Epic ID again. No closure answer or file move differed in either loop.
  Amended after VERIFY loop 3: four differences fitted kind (a) by its label and not by the three
  things it listed — the first-time migration, the refusal it no longer gives, `WORK.md`'s text and
  `--also`. Kind (a) now names them, and the parity test calls the paths they are on. Calling them
  showed one more line, the dry run's note on a milestone file without markers; it is named above
  with the dry run it belongs to.)

### FR7 — Generated views (`D-M6E16-4`)
- AC7.1 `EPICS.md` lists every unit with its folded status; a shipped Epic reads closed, with its
  date, PR and release when recorded. "no Epic folder" no longer appears.
- AC7.2 The Epic rows of the live milestone file are written by code inside a marked region; text
  outside the markers is byte-identical before and after. Closed milestones' files are not touched
  (`D-M6E16-12`, amended at PLAN).
- AC7.3 With unit records, no code reads the milestone rows: every call of `findEpicStatusRow`,
  `isEpicCloseShip`, `EPIC_ROW` and `parseEpicStatusRows` sits behind the no-unit-records branch, and a
  test lists the allowed call sites (`SIG-132`). The parsers stay for projects without unit records
  (AC6.4). (Amended at EXECUTE: "gone" contradicted AC6.4.)
- AC7.4 A view that does not match its records fails the suite, as the item views do.

### FR8 — Signal's own units (`D-M6E16-3`, `-6`)
- AC8.1 Every Epic that shipped before this one gets a record closed as `legacy`, carrying what the
  milestone tables say (date, PR, release) as recorded text.
- AC8.2 A `legacy` close is refused as proof wherever a close is used as evidence: the migration's
  evidence index does not count a `legacy`- or `dropped`-closed unit (`D-M6E16-15`, amended at PLAN —
  no code refused this before; the test `M6.E13`'s verification cited does not exist).
  (Added at REVIEW, pass 1: the rule holds today because no reachable path uses a unit close as
  evidence — the index is built only by the first-time migration, which runs before a project has
  unit records, and the run that adds unit records to a store closes no item. The branch that
  refuses a `legacy` or `dropped` unit stays, tested on its own, for the day a path does.)
- AC8.4 Epics that never ran (`M5.E11`, `M5.E12`, `M5.E14`, `M5.E20`) get a record closed as `dropped`
  with a sentence; `v0.1.6` gets a legacy record (`D-M6E16-11`, `-13`, added at PLAN).
- AC8.3 The cutover is one commit, with a written diff of what the tables said against what the
  records say, reviewed before the commit. Existing archive folders are not moved or deleted.

### FR9 — Other projects (`D-M6E16-8`)
- AC9.1 `/sig:docs-migrate --work-store` proposes unit records for a project's existing units, in the
  dry run, by name; legacy closes are proposed and need the person's yes. A milestone row's words
  propose a close only when its status cell begins with "shipped" (decoration aside) and names
  nothing still to do; a cell that says it further on is proposed open, flagged `row-unclear`, and
  quoted in the dry run. Evidence that is not the row's words — a complete retrospective, today's
  closure check — counts as before (amended at REVIEW pass 4, `D-M6E16-29`).
- AC9.2 A project already on the store with no unit records can add them with the same command, and
  nothing else in its store changes.
- AC9.3 Tested on fixtures and the sandbox only; no run against a live project.

## Non-functional requirements (FULL prompt, answered)

- **Health probe, graceful shutdown, request logging, security headers, rate limiting:** N/A — a
  command-line plugin with no server.
- **Input safety:** unit names from other projects reach paths; AC1.3 covers traversal and collision.
  No unit name reaches a shell argument list.
- **Performance:** reading and folding unit records grows in proportion to their number — 16× the
  records in under 64× the time, best of five — and 500 units fold in under 1 s, with the measured
  figure logged. (Amended at PLAN: a bare 100 ms limit fails from timing noise in CI, as `SIG-293`
  showed.)
- **Failure:** a refused write leaves the record and the views unchanged.

## Blast radius

- **Command files change** (`ship.md`, `discuss.md`, `new-project.md`, `docs-archive.md`,
  `docs-migrate.md`, `item.md`, and — found at PLAN — `checkpoint.md`, `drive.md`, `resume.md`). That moves the instruction-line ceiling, so
  [`ADHERENCE-LOG.md`](ADHERENCE-LOG.md) is regenerated in this Epic. Planned as a task, not found at
  SHIP.
- **Stored data:** the item schema's unit-ID rule widens; existing records stay valid, with one
  exception stated here: a record naming a unit over 100 characters, which `v0.1.50` accepted when
  it was shaped like an Epic ID, no longer validates (no real ID is that long). It widens for
  every project, with or without unit records: the schema alone no longer refuses an item event
  naming a unit such as `phase-11`. Without unit records the writers (`queueItem`, `startItem`) and
  the readers (`listRecords`, `getRecord`, `checkRecords`) still refuse it (AC6.4, kind b; amended
  at VERIFY, loop 2).
- **Published files:** `EPICS.md` and the Epic tables in `MILESTONE-*.md` become generated.
- **Other projects:** none are on the store yet. A project without unit records gets the same
  answers, refusals and moves as before, with the kinds of difference AC6.4 names (amended at
  VERIFY, loop 1: "untouched" was not true of them; loop 2: by kind, not a list of four).
  A project moved onto the store with this version does not stay without unit records: the same
  apply creates `work/units/` (AC9.1). And a project that has `.planning/archive/epics/<ID>/` can
  now be moved onto the store; on `v0.1.50` that apply failed its own check and wrote nothing
  (amended after VERIFY loop 3).
- **Rollback:** revert the merge commit; the cutover commit is separate and reverts on its own.

## Outcome

- `M6.E16` is the first Epic closed through its own record: after its SHIP merges, its unit reads
  closed with the commit its close was requested with as proof — the branch commit SHIP recorded,
  which the merge brings onto the default branch — and nobody edited a table. (Reworded at REVIEW
  pass 2: it said "the merge's commit", which is not what the code or its end-to-end test records.)
- `EPICS.md` shows every shipped Epic as closed.
- The `M6.E16` row in `MILESTONE-6.md` was written by code.
