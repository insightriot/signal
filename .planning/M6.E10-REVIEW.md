# M6.E10 — Review

**Verdict: PASS-WITH-FIXES.** Three fresh-context specialists, 2 Important + 1 Medium security + 4
Important code + 2 Important test findings, all fixed in-phase. **0 Critical.**

## The finding that matters most

**FR3 says *"no setting may be documented with behaviour that has no code path."* This Epic replaced
one such description with another, and shipped it into three documents.**

`drive.md`, `profile-schema.md` and a source comment all stated that `checkpointed` **asks** on a
gray-area decision while `unattended` **queues**. `queueDecision` gated on `attended` alone —
**`checkpointed` and `unattended` were byte-identical.** So a user choosing *"Drive it — ask when it
matters"* would have had product-altitude decisions **silently parked** in a file this Epic's own
out-of-scope section says nothing drains.

Found by the fresh-context `code-reviewer`. **Fixed**: `queueDecision` now refuses at `checkpointed`.
A test in `drive-router.test.js` had pinned the old behaviour shut — *"queues at unattended and
checkpointed — what the dial buys"* — and is rewritten with the old assertion quoted in place.

**That is the second test this Epic that held a defect shut**, after `drive.test.js`'s
`checkpointed stops at the phase boundary`.

## Medium (security) — FR2's guarantee lived in the wrong function

`always: true` was consulted **only** inside `resolveFloors`, which `canProceedUnattended` never
calls. `hasFloor` is nullish-coalesced, so an explicit `false` **replaces** the static fallback:

```
canProceedUnattended('SHIP', unattended, { hasFloor: false }) -> proceed: true
```

**A caller passing `false` proceeded past the pull-request and no-bypass-retrospective floors** —
the two gates FR2 exists to protect, defeated by the parameter FR1 introduced. Before this Epic no
caller passed `hasFloor` at all, so the safe fallback always ran; FR1 moved that enforcement into an
arithmetic expression an agent executes from markdown.

⚠ **The FR2 test could not catch it**: it derived `hasFloor` from `resolveFloors` first, asserting
the happy-path *composition* and never the function's *invariant*. **Correct at the unit, vacuous at
the gate** — the `verifyCitations` lesson, repeated. Fixed, with the invariant asserted directly.

## Important — the floor condition and `/sig:plan` used different parsers

`inboxHasDrainableEntries` called `listDrainCandidates`; `/sig:plan` § 1b calls
`listDrainCandidatesWithRecovery`. On an inbox whose only live entry sits below an unclosed code
fence the bare form returns **0** and the recovery form returns **1** — so the driver declared both
drain floors dormant and advanced into a PLAN whose drain had real work. `drain.js` already carries a
comment about this exact shape: *"Two filters that must agree; only one had been updated."*

## Important — two fail-closed branches had zero coverage, and the test's name said otherwise

`test-engineer` proved it by mutation: flipping **both** fail-closed branches to fail-**open** left
the entire suite green. The test named *"a floor with neither `always` nor a condition is treated as
LIVE and reported"* **never called `resolveFloors`** — it compared `FLOORS` ids against a hand-typed
literal, which two further mutations showed drifts silently from the real table.

**So the behaviour `drive.md` advertises to users was untested.** Fixed by making the branches
reachable (`conditions` is now injectable, `FLOOR_CONDITIONS` exported) and testing them directly:
a throwing condition, a rejecting async condition, and an unclassified floor.

## ⚠ A test I wrote for a reviewer finding was itself vacuous

The guard for the parser disagreement asserted `live.length > 0` against a fixture carrying a live
entry **above** the fence as well — so both parsers returned non-zero and reverting to the bare one
produced **zero red**. Caught by running the proof, not by reading it. The fixture now puts the only
live entry below the fence (bare: **0**, recovery: **1**), and the mutation reds it.

**Third instance of this class in two Epics.** The rule holds and needs restating: *a proof must
assert the specific outcome, not that the suite passes.*
