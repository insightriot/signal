## What surprised us

**The backlog row's two proposals did not survive being measured.** *"A row naming an open
`confirmed` bug should rank above one that does not"* fired on **0** headings and 7 bodies — and 4 of
those 7 named `B75`, which the backlog calls the *entry price* for autonomy work. Those rows are
stuck *behind* the bug; the input as worded would have promoted them. It was built inverted
(`D-M6E8-2`). *"A row whose Epic reads closed should drop out"* turned out, at PLAN, to be ranking
input 3 already (`D-M6E8-8`) — nothing new was built. And the widening of `BLOCKED_RE` that was
supposed to be the Epic's live effect hit **one** row, the gate row itself (`D-M6E8-7`).

**The shipped *Consulted by the ranking* line was wrong in the opposite direction from `M6.E7`'s.**
`M6.E7` REVIEW fixed an over-claim; the line then said *"`BACKLOG.md` only"* while the discharge input
had read `BUGS.md` and unit closure on every run. An under-claim is the same defect (`D-M6E8-9`). It
is now derived from what `rankRows` was given, never written as a literal.

**Three REVIEW rounds running, the previous round's fix carried the next round's defect** — pass 1's
regex widening was quadratic (5.9 s at 60k chars); pass 2's decline reason still named inputs the row
had won, and two of its fixes had no test; the pass-3 audit resend found that `\b` is satisfied by a
hyphen, so `B9: discharged-batch queue` read as closing `B9`. **The discharge predicate was narrowed
three times in one review.** And the one Critical was in the Epic's own test design: population pins
that fired on any ordinary backlog edit — `B120`'s shape, which this Epic's own requirements had
warned against in DISCUSS.

## What we'd do differently

**Measure a vocabulary adversarially before choosing it, not only for hits.** Every live count in
this Epic was taken — the counts were right — but nobody fed each pattern hostile shapes (hyphenated
compounds, 60k-character headings, corpus text containing Markdown structure) until a reviewer did.
A short fixed battery of adversarial inputs per regex, run at the moment the pattern is written,
would have caught the quadratic widening, the hyphen false positives and the structure injection
before REVIEW rather than across three passes.

**Write the test for a REVIEW fix in the same commit as the fix.** Two of pass 2's fixes shipped with
no test, and pass 3 existed partly to find that. A fix without a failing-first test is the pattern
that let each round carry the next round's defect.

**Pin acceptance criteria to named rows, never to counts** — DISCUSS said this in so many words and
the Critical was a count pin anyway.

## What to feed back into Signal

**The in-phase fix budget counts the wrong thing.** Each REVIEW pass exceeded 50 LOC (59, 90, 95),
but functional lines were 12, 15 and 29 — all inside. The rest was findings written into the source,
which is this repository's own norm. A raw-line ceiling penalises the documentation the project
asks for. Changing the rule was deliberately not done here; it is a follow-up candidate for
`review.md`'s budget definition.

**`verifyCitations`-style checks need a content check, not a range check** — carried from `M6.E7`,
and this Epic's advisory still has no commit anchor (`B119`).

**Filed, not fixed, and each touches this Epic:** `B116` (the coverage check under-counts its
denominator), `B118` (`/sig:drive` and `/sig:advise` read one branch's corpus — which is why nothing
reminded anyone this Epic was waiting at SHIP for ten days), `B119`, `B121` and `B122` (two
pre-existing `parseBacklogRows` reader defects), `B123` (`today` unvalidated before it becomes a
filename; the author's re-probe was inconclusive, recorded at that confidence).

**The ranking is still not shown to be better.** For most live rows it is still age. Stated in the
requirements in advance and still true; filed to `ISSUES-INBOX.md` (`D-M6E8-6`) rather than absorbed.
