## How the read was done

so git-dependent paths see the same history and origin refs in all three.

- **off:** `WORK.md` is removed. The store-off code parses the v1 generated views. This is what the
  lists say today.
- **v1:** the store as it is now. The branch's store-on readers read it through the converter.
- **v2:** `.planning/` is replaced by the project that `migrateWorkStoreV2` builds aside. This is the
  state just before `confirmCloses` runs.

## Recommendations — the t7.1b carry items, and what this read found

**R1. The BUGS.md summary rule (carry item).** Measured: 10 rows differ, in two directions.
- **SIG-52 and SIG-99:** their bodies have more than one paragraph, so v2 shows the truncated bold
  title. The v1 view showed the whole migrated row, 12.5 KB and 3.4 KB.
- **8 bugs filed in the v1 store** (SIG-249, 251, 252, 264–268): their body is one paragraph, so v2
  shows the body where v1 showed the bold title.
- *Recommend:* change "a one-paragraph body is the summary" to **"the body's first paragraph, else
  the title"**.
  - SIG-52 and SIG-99 get their row back, and no row loses text.
  - The other choice is the title for every row. That is shorter and uniform, but about 140 migrated
    rows would change to their truncated titles.

**R2. Inbox count meaning (carry item).** Measured: the 6 status-N records are all type `NEW`.
- There is no N bug and no N question today, so the two meanings agree (6 and 6).
- The 7 in the store-off digest comes from **SIG-271**: it counts the watchlist heading.
- *Recommend:* the count is **every status-N record** (the readers' meaning, and what the v1
  `work/inbox/` file count measured). The views keep their partition, so N bugs stay in `BUGS.md`.
  ISSUES-INBOX.md gets one line naming any N bugs or questions listed elsewhere, so the view and the
  count can never disagree.

**R3. Dangling references (carry item).** The v2 sweep reports:
- `B300`, `SIG-300`, `SIG-412` and `SIG-1000`: examples in `DECISIONS.md`, and the PROGRESS note
  quoting them;
- one new one, `D-M6E19-6`. It is a historical mention of a typo that was fixed, in **SIG-157**'s
  body. SIG-157 is a recent close, which the v2 `BACKLOG.md` now prints (AC6.2).

*Recommend:* add all five to `DANGLING_REF_EXEMPTIONS`, each with its reason, rather than rewording an
append-only ledger or a closed item's history. ⚠ This report names them too, so once it is committed
the sweep counts one more file for each.

**R4. The two bug checks, v1 reading against record reading (carry item).**
- The tally is clean in both.
- bug-vs-changelog gives the same one flag, with the ID form changed and the cited file changed from
  `BUGS.md` to the record.
- As predicted: ID form only. *Recommend:* no change.

**R5. Found here: `/sig:drive`'s candidate order changes (rows 5).** `rankBacklogRow` gives +5 for "an
explicit unit id". On records that ID is every record's own `SIG-n` (t4.3), so the bonus no longer
singles anything out. The view's ` · SIG-n` suffix also no longer adds +2 to every row.
- The rows titled by an Epic fall: **M5.E20, M5.E12 and M5.E14 move from #2–4 to #24, #26 and #27**.
- The tagged roadmap rows rise to #2.
- *Recommend:* on records, compute the +5 from a unit ID **leading the title**, as the view heading
  gave it, not from the record ID. Small, and it can go in t7.3 or a follow-up. It is Brett's call
  because it changes what the driver proposes first.

**R6. 11 `created` dates (row 18).** The v1 read path asks git only when an item has no date at all,
so it dates `created` by the close. The migration dates it by the file's first commit, 2026-09-29,
the same as the t1.5 run. No action: the v1 read path retires at cutover. One comment is wrong:
`work-records.js`'s `firstAddedDates` says the v1 read "gives the same created date the t1.5 run
validated", which is false for these 11. Fix it in t7.4.

**R7. For t7.3.**
- **`WORK.md`:** `--apply` sets `schema_version: 2` in the frontmatter only, as specified. Its body
  still describes status folders.
- **The apply manifest:** `--out` is refused inside the repository, at apply too. So the cutover's
  `manifest.json`, the only record of what `confirmCloses` confirmed, lands in a temp directory.
  t7.3 should copy it into `.planning/`, or the refusal should be loosened at apply.
- **Empty folders:** `--apply` moves item files only. It leaves `work/inbox/`, `work/backlog/` and
  `work/done/*/` empty on disk. Git ignores empty folders, so this is harmless.
- **BACKLOG.md and OPEN-QUESTIONS.md:** they now list 46 recent closes (rows 16 and 24). That is by
  design, but it doubles BACKLOG.md (82 KB → 182 KB) until the 30-day window moves them to
  `work/history/2026.md`.
