# `M6.E7` — Retrospective

*The Roadmap Advisor: a read-only `/sig:advise` that reads this project's own `.planning/` corpus and
recommends what to work on next, where every claim carries a citation that mechanically resolves.*

## Timeline

DISCUSS 2026-09-05 → PLAN 2026-09-05 (2 parallel researchers; plan validation returned **FAIL** and
the plan was revised) → EXECUTE 2026-09-05 (three slices, S1 first) → VERIFY 2026-09-05 (PASS with
limits) → REVIEW 2026-09-05 (**FAIL** on the 50-LOC cap) → **loop 1**: EXECUTE / VERIFY / REVIEW
2026-09-06 (PASS) → SHIP 2026-09-06.

Two days wall-clock, one continuous session. **24 commits**, 2979 → **3300 tests** (+321). Loop
counts at close: VERIFY 1 of 3, REVIEW 1 of 3 — neither near the ceiling.

## What surprised us

**Five times, measuring contradicted something already written down — and that is the Epic's real
finding, in the Epic about claims that resolve.** Listed together because the pattern is the finding
and five separate apologies would hide it:

1. **The citation grammar.** The plan's first draft claimed to recognise *"the grammar the known-good
   artifact actually uses."* Enumerating the frozen review showed bare-line `:219` is its
   **second-largest** class (×32) and was missed entirely. Caught at PLAN.
2. **The 2-of-5 cause.** I attributed two bad recommendations to corpus shape and wrote it into a
   commit. Printing the ranking inputs said otherwise: `TRIGGER_MET_RE` reads a row's whole body, so a
   watchlist row was promoted by a trigger belonging to **a different item**.
3. **The reach of the fix.** I told Brett the `HELD_OPEN_RE` mechanism would fix one of the two rows.
   Scanning the vocabulary found `reconciliation` ×2 — which was the **#1** recommendation. It fixed
   both.
4. **Unreachability.** I measured `assertRealInsidePlanning` as unreachable through `runAdvise` and
   put it in the VERIFY artifact. Sound reasoning that **presumed at least one citation exists**; an
   empty backlog produces none. The reviewer found it, I reproduced it, the artifact was corrected.
5. **A fix that did not happen.** `PROGRESS.md` said a nit was *"computed once"*. It was not — the
   call had only moved lower inside a per-citation function. Caught at REVIEW pass 2 by reading my
   own note back against the source.

**A fresh-context reviewer found five of the six REVIEW Importants, including the sharpest one.** The
artifact printed `Read: BACKLOG.md · BUGS.md · retrospectives · STATE/closure · milestone rows` above
a ranked list that consulted **one**. That is
[`CLAIM-INTEGRITY-ANALYSIS.md`](../analysis/CLAIM-INTEGRITY-ANALYSIS.md)'s class, inside the command
built to stop it.

**Three tests passed while covering the wrong thing.** Ranking input 5 shipped with five green
predicate tests and **no test that it was wired** — deleting the wiring left all 3279 green. A
cannot-check test used ENOTDIR and missed ENOENT. A declined-reason test matched the first line
mentioning a row, which for the contrast row is a different section. **Each was found by mutation or
by a reviewer, never by the suite going red on its own.**

**A fix I wrote, tested, and deleted.** The guard against the zero-claims vacuity was unreachable —
`rankRows` partitions — and my own new test told me by failing against the old message. It would have
been dead code shipped to look like rigour.

## What we'd do differently

**Run the command before writing the write-up.** Surprises 2 and 3 both came from describing behaviour
I had not printed. The run took seconds; the wrong claim reached a commit both times. **Print the
inputs, then write the sentence.**

**Write the wiring test with the predicate test, not after.** Input 5's gap was structural, not an
oversight: a predicate is easy to test and a *use* is not, so the easy half gets written and reads as
done. A predicate test and a wiring test are two different claims.

**Spawn the fresh-context reviewer earlier — at EXECUTE close, not REVIEW.** It found five Importants,
two of which (the injection through `projectName`, the contradicting count) were in code I had already
verified and shipped a VERIFY verdict against. Five of its findings would have cost nothing to fix
during EXECUTE and instead consumed the entire REVIEW LOC budget.

**Count the cap before declaring the verdict, not after.** I wrote PASS-WITH-FIXES, then did the
arithmetic: 62 against a 50 cap. The rule caught it, but only because I checked afterwards.

## What to feed back into Signal

**The 50-LOC cap has no check, and it decided this Epic's verdict.** `review.md` states it in prose
and nothing computes it — I measured it by hand and could as easily have not. It is a *number*, in a
document that already fails the suite over roster counts. **This is the promote-an-advisory-to-a-check
trigger, met**: the rule changed a verdict, so it has earned enforcement.

⚠ **And the counting method is undecided**, which the check would have to settle: insertions plus
deletions (the rule's words, making a modified line count twice) gave 62; insertions only gives less
and would have produced PASS-WITH-FIXES. I took the stricter reading and said so.

**`diffRequirementCoverage` drops a real requirement on 21 of 22 artifacts in this repo** — filed as
`B116` during this Epic's VERIFY, found by *using* it. `AC{N}.{M}` is treated as `FR{N}`'s child,
correct for `M5.E10`'s convention and wrong for nearly every other Epic's. `missing` cannot report
what is not in the denominator, so it is a **false clean in the check built to stop unfalsifiable
coverage claims.**

**A fresh-context reviewer should be a phase step, not a judgement call.** It was the highest-yield
action in the Epic and nothing in `review.md` asks for one. `review_depth: quality-only` describes
*what* to review and says nothing about *who*.

**`transitionPhase` regenerating `INDEX.md` at phase entry has a consequence worth naming.** It
auto-resolved the orphan `t3.7` had designated a one-time human SHIP step. Harmless here; it means a
phase transition silently performs work another document assigns to a person.
