# M6.E2 — The facts Signal publishes about itself · REQUIREMENTS

**Tier: FULL / `gate_strictness: strict`** (project PROFILE; no Epic PROFILE — `D-M6E2-6`).
Decisions: `DECISIONS.md` § *2026-08-18 — M6.E2 DISCUSS* (`D-M6E2-1` … `D-M6E2-7`).
Scope evidence: `M6.E2-CORPUS-MEASUREMENT.md`, run **before** scope was locked.

**The class.** A document publishes a fact about the project — a count, a status, a version, a phase
— and nothing derives that fact from the artifact it summarises. The two drift apart silently and
only a person reading both ever notices.

> **AC ids here are numeric only — no letter suffixes.** `B100`: `diffRequirementCoverage` cannot see
> a letter-suffixed acceptance-criterion id and reports `covered` while blind to it. `M6.E1` used
> `AC1.2a`/`AC1.2b` and its own VALIDATION read 22 of 24 criteria as a result. Not repeating that in
> the Epic about published facts being wrong.

## Functional requirements

### FR1 — `/sig:add --bug` cannot leave `BUGS.md` publishing a count its own contents contradict

`captureToBugs` inserts with `insertAtEnd` on the stated belief that `BUGS.md` has no footer.
`BUGS.md` **does** have one: the italic tally line that is the file's last line. Two consequences
follow from the one wrong belief — captures land physically below the file's own summary, and the
tally is never rewritten. `captureToFutureIdeas`, in the same file, already solves this with
`insertAboveFooter` + `rewriteFooter` + the `repaired` drift announce.

- **AC1.1** — A `/sig:add --bug` capture into a `BUGS.md` carrying a footer is inserted **above** the
  footer, not appended after it.
- **AC1.2** — After the capture, the published tally is **re-derived from the file's contents**, never
  incremented. `bugs-tally.js` already derives; the write path calls it.
- **AC1.3** — A `BUGS.md` with **no** footer keeps today's end-of-file behaviour. The fix must not
  require a footer to exist — 3 of 11 non-Signal corpus projects have a `BUGS.md` and none publishes a
  tally.
- **AC1.4** — Entries already stranded below the footer by the old behaviour are reported when the
  capture normalises the file, in the same shape the inbox path uses (`result.repaired`). Silent
  repair of a user's file is not acceptable; neither is leaving it broken.
- **AC1.5** — `commands/add.md` no longer states that `BUGS.md` has "no footer to rewrite". The
  documented belief and the code agree, verified by a test that reads both.

### FR2 — A published-fact check is a registrable shape, in its own home

- **AC2.1** — Checks live in `plugin/tools/lib/published-facts.js` and export their own frozen
  registry. They are **not** appended to `STATE_DRIFT_CHECKS` (`D-M6E2-3` — single home).
- **AC2.2** — Each check is built with the existing `defineCheck` from `state-drift.js`, declaring a
  heal category and an applicability function. No second harness is written.
- **AC2.3** — The two call sites that already run drift checks — `/sig:sweep` (`sweep.js`) and
  `/sig:resume` (`resume.md`) — run the composed set. A check that reaches neither command is not
  shipped; that is the defect this Epic is named after.
- **AC2.4** — `compareBugTally` gains a caller that is not a test. Today its only caller is
  `tests/bugs-tally.test.js`, so it fires only in this repository, only under vitest, and only after
  the write.

> **One id is deliberately not written literally in this file.** `M5.E10`'s unbuilt semantic
> criterion is cited as `D-M5E10-1` throughout. Written in its `AC`-id form it lands in *this*
> Epic's coverage denominator — `diffRequirementCoverage` parses the token, not its owner — and
> VERIFY would then demand evidence for another Epic's deliberately-unbuilt criterion. Caught by
> running the tool against this file at DISCUSS rather than discovering it at VERIFY.

### FR3 — Five checks, one per named instance

The population is these five and the registrable shape — **not** a derived corpus sweep
(`D-M6E2-2`).

- **AC3.1** — `BUGS.md` published tally vs. its own entries.
- **AC3.2** — A bug's `Status` cell vs. whether its fix shipped (evidence: `CHANGELOG.md`).
- **AC3.3** — A dated `[Unreleased]` CHANGELOG heading vs. the released version. Note doc-hygiene
  **deliberately skips** `[Unreleased]` today, so this check must not be added to the guard that is
  aimed away from it.
- **AC3.4** — A milestone file's Epic-status row vs. `STATE.md`.
- **AC3.5** — `facts.md` headline figures vs. the artifact (`B56`).

### FR4 — Every check publishes its own measured reach

`D-M6E2-1`. Narrow reach is permitted here; **claiming generality you do not have is not**.

- **AC4.1** — Each check declares its measured reach (evaluable / total, from
  `M6.E2-CORPUS-MEASUREMENT.md`) somewhere a reader encounters it — not only in a planning document.
- **AC4.2** — The three Signal-only checks (`AC3.1`, `AC3.4`, `AC3.5`) are identifiable as such. A
  reader must not come away thinking a 1-of-12 check is general.
- **AC4.3** — The reach figures are **re-derivable** by running
  `tools/measure-published-facts.js`, not transcribed from prose. A hardcoded number in a comment is
  this Epic's own defect committed inside it.

### FR5 — "Checked and clean" is distinguishable from "could not check"

- **AC5.1** — Every check returns one of the four `STATUS` values the harness already defines;
  `cannot-evaluate` is a value on the record, never rendered as clean (`B39`).
- **AC5.2** — On the 11 corpus projects where `AC3.1` and `AC3.4` cannot evaluate, the report says so
  rather than printing nothing.
- **AC5.3** — Adding five checks does not turn `/sig:resume`'s briefing into noise for a project none
  of them evaluate. Not-applicable checks are summarised, not enumerated one line each.

### FR6 — The two evidence items are folded in, not fixed around

- **AC6.1** — `B102`'s status row is corrected **by** the `AC3.2` check finding it, and the run that
  found it is recorded. It is deliberately left wrong until then (`D-M6E2-5`) — fixing the evidence
  first is how a detector ships untested against the only real instance available.
- **AC6.2** — The `[Unreleased]` defect stops being filed in two places (`BUGS.md:186` and
  `OPEN-QUESTIONS.md:74`). One home, the other cross-references.

## Non-functional requirements

- **NFR1 — Read-only, offline, deterministic.** No check writes, and none touches the network.
- **NFR2 — Fail-open, per check.** A check that throws degrades to `cannot-evaluate` with a reason
  and never takes down `/sig:sweep` or `/sig:resume`. `B70` is the precedent: one unguarded call
  inside `renderResumeBriefing`'s argument list killed the entire briefing.
- **NFR3 — No new dependency.**
- **NFR4 — The `/sig:add` write path stays instant.** Re-deriving a tally is a single pass over a
  file already read; no confirmation step is added (`add.md` Decision 4).

**FULL-tier NFR prompt, answered rather than skipped.** Health/liveness probe, graceful-shutdown
signal handling, structured request logging, security headers, rate limiting: **all N/A** — this is a
CLI plugin with no service surface, no listener, and no request path. Input validation **is** in
scope at the check boundary (NFR2 covers a malformed document reaching a check).

## Blast radius — what this touches that we are not changing

- **Every project's `BUGS.md` that `/sig:add --bug` writes to.** FR1 changes where an entry lands.
  Files already carrying stranded entries below a footer are the migration case; `AC1.4` covers
  reporting it, and git is the rollback.
- **`/sig:sweep` and `/sig:resume` output in every project**, including the 11 corpus projects where
  two checks can never evaluate. `AC5.3` exists because the blast radius is *reader attention*, which
  is the resource this repo has already spent on `B39`-shaped noise.
- **`bugs-tally.js`'s contract**, once a non-test caller exists. Its current shape was free to change;
  after `AC2.4` it is not.
- **Nothing downstream consumes these documents programmatically** outside Signal itself — checked:
  no published artifact, no API, no other tool reads `BUGS.md` or `facts.md`.

## Out of scope, stated so it is not absorbed

- **Semantic faithfulness** (`D-M5E10-1` — `M5.E10`'s deliberately-unbuilt backstop; its criterion id
  is cited by decision rather than written literally, see the note below) — whether a report's prose is faithful to the
  evidence it cites. Everything here compares derived values against published values; a document
  internally consistent and simply wrong about what its evidence means passes all five checks.
- **A derived corpus sweep** for published facts beyond the five named (`D-M6E2-2`). Excluded on
  evidence, not overlooked.
- **Whether `.planning/` should be public** — unrelated, still deferred (`B99`).

## Done when

Every instance in scope is either derived-and-compared by a registered check or recorded as excluded
with a reason; the checks run from a command a user actually invokes rather than only from vitest;
`/sig:add --bug` cannot falsify `BUGS.md`'s own count; each check's reach is published and
re-derivable; and the report distinguishes *checked and clean* from *could not check*.
