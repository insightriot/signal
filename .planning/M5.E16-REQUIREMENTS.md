# M5.E16 — STATE-vs-world drift detection

**Epic:** M5.E16 · **Tier:** FEATURE (Epic-scoped override — see [`M5.E16-PROFILE.md`](M5.E16-PROFILE.md))
**Opened:** 2026-08-01 · **Target release:** v0.1.16

---

## Why this Epic

**20 of the 56 entries in `BUGS.md` are STATE.md-related — 36%, the largest cluster in the catalog
by a wide margin.** One sub-class accounts for six of them on its own (`B41`, `B43`, `B44`, `B45`,
`B47`, `B51` — the phase ledger asserting something that did not happen).

Nothing checks STATE.md against the world it describes. `isStateStale` compares one field
(`last_updated_commit`) to git. Every other field — `phase`, `current_epic`, `completed_phases`,
`blockers` — is **asserted and never verified against the artifacts on disk that would prove or
disprove it.**

### The live instance, from this Epic's own opening session (2026-07-31)

`STATE.md` frontmatter read `current_epic: M5.E17`, `phase: DISCUSS`.

`STATE.md`'s body, under *"Next candidates, in the order the evidence argues for"*, listed
**M5.E15, M5.E16, M5.E10** — and **M5.E17 was not in it.** The frontmatter advanced when M5.E17
opened; the prose saying what comes next was written before M5.E17 existed and was never updated.

**`/sig:resume` read both halves and reported neither the conflict nor the omission.** The briefing
quoted the frontmatter for the phase line and the body for the narrative, and the two disagreed in
the file it had just called authoritative. A human caught it from memory, hours later.

That is the whole Epic in one file: *the data moved, the prose did not, and the command whose job is
orientation read straight past it.*

---

## The reframe — this ships as a capability, not as Signal hygiene

M5.E16 previously meant *"the guard class's document-shaped and data-shaped detectors"* — Signal
checking Signal. **That framing is retired here** (both of its original homes moved: `B39` was fixed
in M5.E13, `B46`'s remedy went to M5.E14, so the slot was vacant).

**These checks run on the invoking project.** Signal's own repo is one consumer among several. The
motivating complaint is that Signal-managed projects accumulate documentation that drifts, and the
drift-correction is manual and constant. This Epic is the first one aimed at that directly.

---

## FR1 — `/sig:sweep` gains STATE-vs-world checks

**All deterministic. No LLM, no network, no heuristics that need tuning.** Each check is a file-existence
or string comparison between what STATE.md asserts and what is on disk or in git.

**FR1.1** The following classes of contradiction are detected. PLAN picks the final set and may drop
any that cannot reach the precision bar in **FR2** — *dropping one with a written reason is a
result, not a skip*:

| # | STATE asserts | Contradicted by | Existing coverage |
|---|---|---|---|
| a | `phase: {P}` | An artifact for a **later** phase of `current_epic` exists on disk | none |
| b | `current_epic: {E}` | The body never mentions `{E}` anywhere | none |
| c | `completed_phases` contains `SHIP` | No retrospective / ship artifact for that Epic exists | none |
| d | `last_updated_commit` | Not an ancestor of `HEAD` | partial — `isStateStale` |
| e | `current_tasks[]` | No matching commit, task older than the orphan window | partial — `detectOrphans` |
| f | `blockers[]` | References an Epic or bug already closed | none |

**FR1.2** Findings render in the existing sweep report under a **new group**, distinct from
`structural` and `advisory`. Naming is PLAN's call; the requirement is that a STATE contradiction is
not silently folded into the same bucket as a dead link — it is a different kind of wrong.

**FR1.3** Every check is **read-only, offline, and deterministic**, preserving `/sig:sweep`'s stated
contract (`sweep.md` §2: *"two runs on unchanged input are byte-identical"*). A check that cannot
meet this does not ship here.

**Acceptance criteria**
- **AC1.1** — Each shipped check has a fixture proving it goes **red on real drift**.
- **AC1.2** — Each shipped check has a fixture proving it stays **silent on a clean project**.
- **AC1.3** — Two consecutive sweeps on unchanged input produce byte-identical output.
- **AC1.4** — Any check from FR1.1 that is **not** shipped is recorded with the reason it was dropped.

## FR2 — Precision is the deliverable; a muted detector is worse than none

**The failure mode is not a missed contradiction. It is a false one.** A checker that cries wolf gets
muted within a week, and a muted checker looks like coverage while providing none. This is the same
shape as the M5.E9 REVIEW Critical that told *every healthy project* its history had been destroyed —
**removed rather than re-tuned**, because the honest fix was admitting undetectability.

**FR2.1** Every check runs against **at least one real project outside Signal's own repo** before it
ships. A check validated only against Signal is validated against the one project shape that is
hand-maintained, Epic-mode, and FULL-tier — the configuration `B42` and `B53` proved is unlike every
other consumer.

**FR2.2** A check that produces a false positive on a healthy real project is **removed or narrowed,
not tuned into silence with a threshold.**

**Acceptance criteria**
- **AC2.1** — Sweep runs clean (zero STATE findings) on at least one healthy non-Signal project.
- **AC2.2** — The projects used and their results are recorded — **including any check killed by
  this gate**, which is a success of the gate, not a failure of the Epic.

## FR3 — The checks must be reachable where the confusion happens

`/sig:sweep` is opt-in: it only helps someone who runs it. The live instance above happened at
`/sig:resume`, which people run constantly and which **already** renders drift banners.

**FR3.1** PLAN decides — **with a written reason** — whether these findings also surface at
`/sig:resume`, and if so which. This is a real question with a real cost on both sides: resume's
banner budget is finite and the briefing is capped at 50 lines, but a detector nobody runs is the
`B39` failure (an instruction nothing executed) in a new costume.

**Acceptance criteria**
- **AC3.1** — The decision is recorded in `DECISIONS.md` either way.

## FR4 — Every check declares a heal path (added 2026-08-01)

**The load-bearing requirement, and the reason the Epic exists in this form.** As originally
scoped, M5.E16 was detect-and-report — which means **every finding it produces becomes a manual
chore.** That is the habit this project is trying to get out of, rebuilt one layer up.

**The measurement that forced this.** `/sig:sweep` was run against four real non-Signal projects
(eval-project-C, eval-project-A, conversor, eval-project-D) on 2026-08-01. It produced **16 structural
findings**:

| Category | Count | Should it have reached a human? |
|---|---|---|
| False alarms (walked a frozen migrate backup) | 11 | **No** — `B57`, fixed same day |
| Self-healing (malformed `completed_phases`) | 3 | **No** — `transitionPhase` quarantines them on next use |
| Regenerable by one command (stale `INDEX.md`) | 1 | **No** — see FR5 |
| Genuinely needed a person | 1 | Yes |

**15 of 16 findings should never have reached a person.** A detector that cannot say which of
those four buckets a finding sits in is a chore generator.

**FR4.1** Every check ships declaring exactly one heal category:

1. **Self-healing** — normal use fixes it. Report as *reassurance* ("this clears next time you run
   a phase command here"), never as a defect demanding action.
2. **Command-healable** — a safe, deterministic regeneration exists. **Signal runs it**; it does not
   tell the user to go run it.
3. **Needs a person** — genuinely ambiguous, e.g. two documents disagree and only the user knows
   which is right. **This is the only category permitted to interrupt.**

**FR4.2** A check that cannot state its category **does not ship**. There is no default bucket.

**Acceptance criteria**
- **AC4.1** — Every shipped check declares a category, asserted by a test over the check registry.
- **AC4.2** — Category-1 and category-2 findings are visibly distinct from category-3 in the report;
  a test pins the distinction.
- **AC4.3** — The 16-finding baseline above is re-measured after the work. **The number that matters
  is how many findings still reach a person**, and it is recorded whether it improved or not.

## FR5 — `INDEX.md` refreshes at every phase transition (added 2026-08-01)

**Decided by Brett 2026-08-01** after the options were laid out; record the rationale in
`DECISIONS.md` at PLAN.

**Problem.** `regeneratePlanningIndex` is called by `/sig:ship` §8 and by `/sig:index` — nowhere
else. So the docs map is correct at exactly the moment an Epic *finishes*, and drifts through the
entire span of work when someone is actually re-orienting from it. All four projects surveyed had a
stale, missing, or foreign `INDEX.md`. `CLAUDE.md` tells every reader to *"read it first."*

**FR5.1** The index regenerates at **every phase transition**, not only at SHIP. The call is
compare-before-write and idempotent, so an unchanged doc set produces no diff and no git noise.

**Rejected, with reason:** regenerating on **session start** (freshest, and it would also cover a
dormant project returned to after months) was rejected because **no Signal hook writes anything
today** — all four are warn-only. A hook that edits files before the user has asked for anything
crosses a trust line the current design holds deliberately. A user who returns to a dormant project
refreshes it the moment they run any phase command.

**Acceptance criteria**
- **AC5.1** — Index regeneration fires on phase transition; a test asserts it.
- **AC5.2** — An unchanged doc set still produces no write (`{written: false}`) — the guarantee that
  makes the added frequency free.
- **AC5.3** — No hook gains write capability. The warn-only posture is asserted by a test.

## FR6 — `/sig:update` (added 2026-08-01)

**Problem, in the user's words:** there is *"ambiguity between new version and new features."*
`/plugin` reports that a number changed. It cannot tell you **what you would be getting**, so
deciding whether to update means leaving the tool and reading a changelog — and menu-diving for a
thing that should be one command.

**This requirement exists because of `B58`.** The user could not receive v0.1.14 or v0.1.15 at all,
found it by chance while menu-diving, and Signal — the tool whose entire premise is noticing drift —
had nothing to say about its own.

**Feasibility confirmed 2026-08-01**, not assumed. A `claude plugin` CLI exists:
`claude plugin update <plugin>` (*"restart required to apply"*), `claude plugin marketplace update`,
`claude plugin list`. No poking at Claude Code internals is required.

**FR6.1** `/sig:update` reports **installed version vs. available version**.
**FR6.2** When newer, it shows **the CHANGELOG entries between the two** — the half `/plugin` cannot
do, and the half the user actually asked for.
**FR6.3** On confirmation it runs the update, then **states plainly that a restart is required**.
This is `B52` — a session binds to one plugin version for its whole life — and it is a real
constraint, not a rough edge to paper over. **The user explicitly wants the restart surfaced so the
timing is theirs to choose.**
**FR6.4** Read-only and fail-open when offline: no network, no update, one honest line saying so.

**Acceptance criteria**
- **AC6.1** — Reports both versions; a test covers the up-to-date, behind, and offline cases.
- **AC6.2** — When behind, the changelog delta between the two versions is shown.
- **AC6.3** — The restart requirement is stated on every successful update; a test pins the wording.
- **AC6.4** — Roster count moves 18 → 19 across `README`, `CLAUDE.md`, `/sig:index` and the validator
  — the roster-drift check already covers this and must stay green.

**Noted while confirming feasibility:** `claude plugin tag` *"validates that plugin.json and any
enclosing marketplace entry agree"* — a built-in that checks **exactly the drift class that was
`B58`**, and which has existed the whole time. PLAN should decide whether release bookkeeping adopts
it. Signal hand-rolled that check next to a tool built for it.

## Scope note (2026-08-01)

FR4–FR6 roughly double this Epic. That is deliberate — FR4 is what makes FR1 worth shipping, and
FR6 is the direct remedy for the P1 found the same day — but it should be **sliced to ship
incrementally** rather than as one block. FR6 is fully separable and has no dependency on FR1–FR5.

The Epic's through-line holds: **Signal notices things, tells you plainly, and heals what it can.**
FR6 is that sentence applied to Signal's own version. If PLAN finds the scope does not slice
cleanly, split FR6 into its own Epic rather than dropping requirements.

## Non-functional

- **NFR1 — No schema change.** Every check reads fields that already exist. If a check needs a new
  field, it is out of scope (see PROFILE escalate-if).
- **NFR2 — No writes, no network.** `/sig:sweep` is detect-and-report; that holds.
- **NFR3 — Sweep stays fast.** A sweep that noticeably slows down is a sweep nobody runs. PLAN sets a
  budget and VERIFY measures against it. This is a floor, not a profiling pass.
- **NFR4 — Reversible.** `git revert` restores.

---

## Not doing

- **Auto-fixing category-3 findings.** FR4 lets Signal heal categories 1 and 2. A finding where two
  documents disagree and only the user knows which is right is **never** resolved automatically.
- **Semantic / LLM-judged contradiction detection.** The deterministic checks cover the largest
  cluster at zero cost and with no false-positive tuning problem. The judge-based version —
  claims-vs-artifacts, the `analysis/CLAIM-INTEGRITY-ANALYSIS.md` class with its eval-project-C
  Phase 11 evidence — is **real and still wanted**, but it goes after this, not with it.
- **Fixing the drift.** `/sig:sweep` is read-only by design (`sweep.md` AD1). Detect and report.
- **`B55` / M5.E15.** Unaffected, still queued.
- **The 48-entry inbox triage.** M5.E14, per `D-M5E17-3`.
