### Findings 5 and 6 — both found by RUNNING the report, neither by a test

`S4` finished with 25 green tests. Then the report was rendered against this repo, and it was wrong
in two ways at once.

**`Bash(git:*)` was proposed** — alongside the specific `Bash(git log:*)`, `Bash(git add:*)` and the
rest. A bare `git` rule grants `git reset`, `git rebase` and `git push --force`, which is exactly
what `AC1.2b` exists to withhold. ⚠ **`classify('git reset')` was correct the entire time.** The
defect lives *between* a correct classification and the rule rendered from it, so no test of
`classify` could ever have caught it. Fixed by refusing a bare-binary rule whenever the table holds
any non-`propose-allow` key beneath that binary.

**The flow half proposed `cargo build`, `go test`, `bundle exec`, `jest run`, `yarn test` and
`npx prisma` — for a Node project.** Every one arrived from `plugin/agents`, where command files
*describe other people's stacks*. This is precisely the over-proposal `D-M6E5-3` and probe 2 warned
about, and the plan amendment had already said provenance must be a classification input — **it
simply was not, until the render made it visible.** Fixed by a rule that gives the flow/stack split
real work: an ecosystem-specific binary can never be proposed by the flow half, only by the stack
half, which is derived from the host's actual manifests.

**Both are now pinned by tests that fail if either returns.** The lesson is the Epic's own wave-1
rule arriving a second time: shipped-but-never-run is the best defect predictor, and 25 green tests
did not substitute for looking at the output once.

### Finding 3 — the extractor rule, measured rather than assumed

Requiring an argument was not enough. It admits **74 distinct "binaries" over 224 occurrences**, and
the overwhelming majority are prose: code identifiers (`result.wrote`, `state.phase`,
`findings.length`), enum values (`trivial`, `familiar`, `off`), and English inside backticks
(`documentation lives in …`, `tests co-located with source`). A structural extractor cannot tell
`npm test` from `plain markdown` — both are a lowercase word followed by another word.

**The rule that works: a known binary OR a flag-shaped argument.** Measured: **74 distinct → 21**,
every dropped span genuinely prose. The flag clause is what preserves the point — `frobnicate
--hard` is unknown, flagged, detected, and reported unclassified, so a **new** binary is still
visible. A bare allowlist would have destroyed that.

⚠ **Published residual:** an unknown binary written as `binary subcommand` with no flag is not
detected. Measured 2026-08-27: **zero such instances in this corpus.**

### Finding 4 — `gh` is never prescribed in the payload

The only `gh` in `plugin/` is the bare word inside prose (`ship.md:271` — *"no `gh`, no auth, no
network"*). The real guidance — `gh pr create --fill`, `gh pr merge --squash` — lives in the
**repo-root `CLAUDE.md`**, which is not part of the shipped payload and is therefore not scanned.

**So a flow-derived proposal offers no `gh` rules, while the hand-cleaned project settings carry
three** (`gh auth`, `gh repo`, `gh api`). That is a genuine under-proposal, pinned by a test rather
than patched away, and it is the first real data point for `S5.t3`'s outcome metric — which exists
to publish exactly this direction of miss.

# `S5.t3` — Outcome measurement, 2026-08-27

**The metric from REQUIREMENTS:** run the generator against this repository and compare its
proposal to the **43 hand-cleaned rules** — a human-curated ground truth for what this flow needs
(`D-BR0826-1` finding 2: cleaning by hand *wrote the generator's target output by hand*).

⚠ **Published, not targeted.** A generator tuned until it matches 43/43 has been fitted to one
machine's history, which is the opposite of the point. Both directions are itemised below and
**nothing was tuned to improve the number.**

## Headline

| | |
|---|---|
| Hand-cleaned rules | **43** |
| Generated rules | **36** |
| Agreement (binary+subcommand) | **15 of 36** |
| Under-proposed | **33 of 43** |
| Over-proposed | **21 of 36** |

⚠ **These are the RE-MEASURED figures, taken after the PR #211 review fixes.** The first run
reported 29 / 14 / 34 / 15 and was taken with a scanner carrying two defects — the code layer
discarded captured subcommands, and the prose layer could not read inside fenced code blocks. Both
are fixed and pinned; the scan went from ~130 to **200** entries.

⚠ **The first run of this measurement was wrong, and the tool was mine.** It reported 41 under and
22 over, because the two pattern dialects — the hand rules use `Bash(git add *)`, the generator
emits `Bash(git add:*)` — were normalised to different keys, so identical rules counted as
disagreements. **A comparison that treats those as different rules measures its own normaliser.**
Caught by reading the output rather than by a test on it.

## Under-proposed (34) — and most of it is the generator being RIGHT

The 34 split into four causes, and only one is a defect:

**(a) Not `Bash()` rules at all — 7. A real design limit.**
`Read(...)`, `Skill(update-config)`, `WebSearch`, three `WebFetch(domain:...)`, two `mcp__…`.
**The generator only ever emits `Bash()` rules.** The flow genuinely fetches documentation and uses
skills, so this is a gap in what it can express — stated as a limitation, not fixed here.

**(b) Machine-specific tools belonging to OTHER projects — ~12. Correctly missed.**
`graphify` ×3, `vercel --prod`, `source ~/.zshrc`, `ssh`, `ssh-add`, `brew list`, `pip show`,
`which python3`, `mcp__airscale…`, `WebFetch(domain:docs.airscale.io)`. **These are the strongest
evidence the generator works.** They are exactly what accretes into a settings file over months, and
a proposal that reproduced them would have reproduced the mess `D-BR0826-1` was written about.

**(c) `gh` — 3 rules.** Already pinned by a test. `gh` is prescribed nowhere in the payload; the
real guidance lives in the repo-root `CLAUDE.md`, which is not shipped and not scanned.

**(d) Genuinely missed flow commands — ~12.** `git clone`, `git config`, `git remote`,
`git commit -m`, `git --version`, `claude --version`, `npm install`, `npm ls`, `npm view`,
`node --input-type=module -e`, `cat pyproject.toml`, `chmod`.

### ⚠ RETRACTED: "`git commit` is prescribed nowhere in the payload"

**This section previously reported that `git commit` appears zero times as a runnable command string
anywhere in `plugin/`, and called it the honest headline of the measurement. It was false.**

The cause was a defect in this Epic's own scanner. `SPAWN_RE` matched `execFileSync('git', ['commit',
…])`, **captured the subcommand, and then discarded it** — so
`plugin/tools/lib/adherence-harness.js:278` was recorded as `git`, not `git commit`. A second defect
compounded it: `INVOCATION_RE` is anchored on inline backticks and its character class excludes
newlines, so every command inside a fenced code block was invisible.

**Both fixed and pinned.** The scan went from ~130 entries to **200**, and `Bash(git commit:*)` is
now proposed. Found by the independent PR #211 reviewer, not by the 31 tests in this feature's own
suite.

**What survives, smaller and still true:** `gh` genuinely is prescribed nowhere in the payload — the
`gh pr create --fill` guidance lives in the repo-root `CLAUDE.md`, which is not shipped and not
scanned. And the generator emits only `Bash()` rules.

**The lesson is sharper than the retracted version.** A measurement taken with a broken instrument
does not read as a broken instrument — it reads as a finding about the world, and it is *more*
persuasive the more it explains. This one was published in five documents.

## Over-proposed (15) — breadth, not error

`git branch`, `git diff`, `git for-each-ref`, `git grep`, `git init`, `git log`, `git ls-files`,
`git mv`, `git rev-parse`, `git symbolic-ref`, `cat`, `grep`, `ps`, `wc`, `claude plugin`.

**Thirteen of fifteen are read-only** and genuinely used by the flow — the human simply never
accumulated a rule for them, which is what you would expect of a list that grows from prompts
somebody actually saw.

⚠ **Two are worth a second look and are named rather than averaged away:** `git init` (odd to
propose inside a repo that exists) and `git mv` (mutating, and `mv` itself is classified
`never-propose` — so the bare tool is refused while the git subcommand is allowed). Neither is
wrong, both are arguable, and `AC4.1b`'s logic applies in reverse: an allow rule slightly too wide
is not a work stoppage, but it is still a grant nobody asked for.

## What this measurement could not establish

- **It compares one machine's history.** `n = 1`, and that machine belongs to the person who
  designed the flow.
- **Matching is at binary+subcommand granularity**, so `Bash(git add *)` and `Bash(git add:*)` count
  as agreement. Whether the *patterns* are equivalent in Claude Code's matcher was not tested.
- **Nothing here tests that an installed rule behaves as expected.** That is the platform's, and
  outside what this Epic can assert.
