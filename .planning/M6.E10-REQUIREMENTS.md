# M6.E10 — `/sig:drive` asks how to run, and floors fire on conditions

**Brett, 2026-09-09:** *"ALL I want right now is for `sig:drive` to actually do what it's designed to
— take a decent size swath of work, determine what 'done' looks like for each piece, then take over
the driver's seat and loop until it's all done."*

**It cannot currently take one step.**

## Measured, before designing anything

Traced through `canProceedUnattended` with this repository's real `PROFILE.md`:

```
checkpointed   CALIBRATE=stop  DISCUSS=stop  PLAN=stop  EXECUTE=stop  VERIFY=stop  REVIEW=stop  SHIP=stop
unattended     CALIBRATE=GO    DISCUSS=GO    PLAN=stop  EXECUTE=GO    VERIFY=GO    REVIEW=GO    SHIP=stop
attended       everything stops
```

**`PROFILE.md` sets `attention: checkpointed`, so `proceed` is false at every phase.** The loop
physically never advances. That is the whole of *"it doesn't work"* — not a tuning problem.

### Defect 1 — `checkpointed` is documented as something it cannot do

`drive.md` says it *"runs free **inside** a phase; stops at each phase boundary."* **The "runs free"
half has no code path.** `canProceedUnattended` is only ever called at phase granularity — `drive.md`
§ 3 calls it once per pass, keyed on `state.phase` — so the only question ever asked is a boundary
question, and `checkpointed` answers `phase-boundary` to all of them. The middle setting of a
three-position dial is a dead stop.

### Defect 2 — floors fire on the phase's NAME, not on their condition

`const floors = hasFloor ?? floorsFor(phase).length > 0` — and `floorsFor` is
`FLOORS.filter(f => f.at === phase)`, purely a name match. The two PLAN floors exist to protect the
idea-inbox drain: preview the diff, confirm deletions. **With an empty inbox there is no diff to
preview and nothing to delete — and PLAN halts anyway.** So even at `unattended` every run is
DISCUSS → dead stop at PLAN.

⚠ **The hook to fix this already exists and no caller uses it.** `canProceedUnattended` accepts
`hasFloor`; `drive.md` § 3 passes only `{ loopStatus }`, so it always falls back to the static check.

### Defect 3 — the dial is invisible, and that is documented as having already caused harm

`D-BR0908-1`: this project had no `attention`, silently derived `attended` from
`gate_strictness: strict`, and **four consecutive Epics (`M6.E4`–`M6.E7`) each wrote a throwaway
per-Epic `PROFILE.md` at `light` to escape it** rather than setting the dial — because `attention`
was missing from `references/profile-schema.md`, the document every phase command points at.

**Nobody disagreed with the setting. Nobody could find it.** A dial nobody can find is worse than a
question everybody is asked.

## The design

**Ask at the start of the run instead of inferring from a file the user has never opened.** The
profile supplies the **default**; the question makes it visible and overridable at the one moment it
matters. Config as a default, not as a hidden gate.

**One `AskUserQuestion` call, two questions** — `AskUserQuestion` takes up to four, so choosing the
work and choosing the cadence are one interaction rather than two round-trips (today's `0a` then
`0b`).

| Mode | Behaviour |
|---|---|
| **Step me through it** | Confirm at every phase boundary. Today's real behaviour, honestly labelled. |
| **Drive it — ask when it matters** | Run DISCUSS→REVIEW. Stop for product/scope decisions and **live** gates. Stop at the PR. |
| **Drive it — queue everything** | Never stop mid-run; park decisions in `DECISION-QUEUE.md` and keep going. Stop at the PR. |

## Functional requirements

**FR1 — A floor fires only when its condition is live.** `floorsFor` stays (it answers *"what floors
exist at this phase"*); a new resolver answers *"which of them apply right now"*. The PLAN drain
floors are live only when the inbox holds drainable entries.

**FR2 — SHIP's floors are unconditional and stay that way.** The pull request and the Epic-close
retrospective are tier-independent decisions (`D-M5E17-5`, `D-E9-3`). FR1 must not become a route to
re-litigating them by omission.

**FR3 — `checkpointed` either earns its description or loses it.** No setting may be documented with
behaviour that has no code path.

**FR4 — `/sig:drive` asks how to run, in the same interaction that picks the work.** One
`AskUserQuestion` call carrying both questions.

**FR5 — The profile pre-selects the default mode**, so `attention` still means something and an
existing profile's behaviour is unchanged unless the user chooses otherwise in the question.

**FR6 — The chosen mode is reported and recorded**, so a run's cadence is legible afterwards rather
than inferred.

**FR7 — `attention` is documented in `references/profile-schema.md`** — the omission `D-BR0908-1`
names as the cause of four Epics' worth of workarounds. An open bug row already exists for it.

**FR8 — A test proves the loop can actually advance.** The trace above, as an assertion: for each
mode, the phases it advances through and the ones it stops at. This Epic's own defect is that nothing
checked whether `proceed` was ever true.

## Out of scope, stated so it is a decision

- **Sub-phase granularity.** FR3 is satisfied by making `checkpointed`'s description true, not by
  building a finer-grained loop. Wave-level or task-level driving is a separate build.
- **Draining the decision queue.** Mode 3 fills it; nothing here empties it. `drive.md` already warns
  that a queue nobody drains is the failure this command most easily creates — that stays true and
  stays flagged.
- **`B118`** (drive and advise read one branch) — filed, unfixed, not this Epic.
