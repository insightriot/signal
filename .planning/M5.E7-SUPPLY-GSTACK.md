## 2. THE MANIFEST / CARVE PATTERN — evaluated separately from `/cso`'s content

This is the item with the most downstream leverage, and the finding is **more nuanced than
"gstack solved skill token cost in code."**

### 2.1 What the manifest actually is

`cso/sections/manifest.json` — its own `note` field says it plainly:

> *"**PASSIVE registry** (v2 plan T9 / CM2). id/file/title/trigger text ONLY. Mode dispatch
> (`## Arguments`, `## Mode Resolution`), always-run phases (0,1), and FP-filtering exceptions
> (Phase 12) stay in the always-loaded skeleton; only the scope-dependent audit phases are on demand."*

`office-hours/sections/manifest.json` is more explicit still:

> *"Fields are IDs, file paths, human titles, and human-readable trigger text ONLY. **The skeleton's
> decision-tree prose is the ONLY place that decides WHEN to read a section. No machine predicate
> here.**"*

Each entry is exactly four fields: `id`, `file`, `title`, `trigger`. **`/cso`'s manifest has exactly
one entry** bundling all ten scope-dependent phases (2-11) into a single `audit-phases.md`. It is a
**two-tier split — always-loaded skeleton + one deferred bundle — not a per-phase lazy-load registry.**

### 2.2 Who reads it — build time, not runtime

**No runtime path reads `manifest.json` at all.** The only non-test reader is
`scripts/resolvers/sections.ts` (96 lines), which runs at **skill-generation time**. Two test files
also read section manifests (`test/section-manifest-consistency.test.ts`,
`test/helpers/carve-guard-checks.ts`) — that is the guard suite in §2.3, not a loader.
*(A repo-wide `grep -rln "manifest.json"` also hits `browse/`, `bin/gstack-extension`, and
`open-gstack-browser/` — those are `extension/manifest.json`, a browser-extension manifest,
unrelated to section carving.)*

Two template resolvers:

- **`{{SECTION:id}}`** (`sections.ts:52-73`) — host-aware:
  - On **Claude**, emits a prose pointer into the generated skeleton:
    ```
    > **STOP.** Before {trigger}, Read `{skillRoot}/{skill}/sections/{file}` and execute it
    > in full. Do not work from memory — that section is the source of truth for this step.
    ```
    (rendered instance: `cso/SKILL.md:957`)
  - On **every other host**, it **inlines the section template's full content**, so non-Claude hosts
    ship the original monolith. `sections.ts:9-13`: *"the SAME template ships to every host, so
    these resolvers make the carve host-aware."*
- **`{{SECTION_INDEX:skill}}`** (`sections.ts:75-96`) — renders a situation→section markdown table
  from the manifest, Claude-only. Rendered instance: `cso/SKILL.md:822-829`.

**At runtime the deferral is enforced by an instruction to the model — a `STOP` directive it is
expected to obey — not by a loader that meters or withholds tokens.** No process reads the manifest
while a skill is executing. This qualifies `M5.E7-RESEARCH.md:237-239`'s framing: gstack solved the
*authoring and shipping* half of skill token cost mechanically, and left the *obedience* half to the
model. That is a materially different port than "gstack has a lazy loader."

### 2.3 What IS mechanical — and it is substantial

The pattern is not merely a convention. It is pinned by a **five-test guard suite** driven from one
registry:

`test/helpers/carve-guards.ts` (336 lines) — *"Canonical carved-skill guard registry — the single
source of truth for which skills are carved and what each carve must guarantee"* (`:1-4`). A pure
leaf data module, `import type` only. Consumers, per its own header (`:14-21`):

| Test | Tier | What it enforces |
|---|---|---|
| `carve-section-ordering.test.ts` | gate | `staticInvariants` — skeleton shape |
| `carve-section-loading.test.ts` | **periodic** | `requiredReads` + `scenario` — **a live-model behavioral test that asserts the agent actually Read the section** (see below) |
| `carve-guard-completeness.test.ts` | gate | filesystem carved set **==** `CARVE_GUARDS` set, bidirectionally |
| `carve-guards-negative.test.ts` | gate | injects a broken fixture and asserts the guards fail |
| `section-manifest-consistency.test.ts` | — | manifest ↔ filesystem orphan classification |

**The behavioral test drives a real model — confirmed, not assumed.**
`carve-section-loading.test.ts:23` imports `captureSectionReads` from `test/helpers/auq-sdk-capture.ts`,
whose header (`:1-13`) describes *"the `claude -p` SDK path"*. `captureSectionReads` (`:219-232`)
takes a `model` and `maxTurns`, returns `{readSections, reportProduced, toolCalls, output}`, and
builds a prompt (`:235-244`) that pins the skill to one absolute path and states the assertion
target verbatim: *"When the skill gives a STOP-Read directive… you MUST actually Read that
sections/ file with the Read tool BEFORE doing the work it covers. Do not work from memory."*
It is gated to `EVALS=1 && EVALS_TIER=periodic` (`:26`) — a paid, non-PR tier.

**This settles §10's open item 5 and firms up the §2.5 ranking:** the guard that converts a prose
`STOP` into a checked claim requires a live-model eval harness (SDK runner, run IDs, per-test
timeouts, a paid periodic tier). That is why it sits at #4 — most valuable, least cheap.

Four static invariants per carve (`carve-guards.ts:28-52`):

- **`mustStayInSkeleton`** — substrings that must remain always-loaded.
- **`mustPrecedeStop`** — substrings that must appear **before the first STOP-Read**. The comment
  names why, for `/cso` specifically: *"mode-dispatch directives (`## Arguments`, `## Mode
  Resolution`) must be resolved before any section is read — a dispatch directive stranded after the
  STOP can't govern which sections to read."*
- **`mustMoveToSection`** — substrings that must be in the union but **must NOT** be in the skeleton
  (proves the carve actually relocated the heavy body).
- **`gateAfterStop`** — a marker that must appear **after** the last STOP-Read (e.g. the EXIT PLAN
  MODE GATE that fires once section work returns).

`section-manifest-consistency.test.ts:1-19` adds a three-tier orphan classification: generated
orphan (`X.md` with no `X.md.tmpl`) → **FAIL**; hand-edited generated file (missing the
AUTO-GENERATED header) → **FAIL**; manifest orphan (`X.md.tmpl` unlisted) → WARN. It also **pins
the passive-manifest contract**: entries carry only `id/file/title/trigger`, *"no machine predicate
(`applies_when`/`required_for`)."*

And a size-budget layer on top (`test/skill-size-budget.test.ts`, 235 lines +
`test/helpers/parity-harness.ts`):

- Per-skill regression ratio, default **1.50** (`:48-49`), overridable only via
  `GSTACK_SIZE_BUDGET_OVERRIDE_REASON` — *"allow and audit-log"* (`:105`).
- Whole-corpus growth ratio against a pinned baseline fixture.
- A **floor** at 0.80 of baseline to catch mass-deletion (`:162`), because *"the existing
  skill-coverage-floor enforces body ≥ 200 bytes… 250 bytes passes that check despite losing 99.75%
  of content"* (`:139-141`).
- The carved-skill semantics are exactly right and worth copying (`parity-harness.ts:38-52`):
  content and `minBytes`/`maxSizeRatio` checks run against the **union** (skeleton + all sections),
  so a carve cannot be used to smuggle a content deletion; **`maxSkeletonBytes` separately asserts
  the always-loaded half actually shrank.** *"Without this, lowering minBytes to fit a 65KB skeleton
  would make the size floor toothless."*

### 2.5 Portability against Signal's loader — *labelled Signal comparison (AC2.4)*

Signal's `tools/lib/skill-loader.js` is **73 lines** and does one thing: read
`config.skills.phase_bindings[phase]`, then `readFile` each bound `SKILL.md` whole and return
`{name, content}`. There is no partial read, no section concept, no deferral, and no size assertion.
Its own header comment (`:6-12`) already records the design decision:

> *"Skills are markdown files with YAML frontmatter — they get injected into the agent's context
> as-is. **No summarization or chunking needed** (confirmed: worst-case REVIEW phase is ~12,700
> tokens, well within budget)."*

`tools/lib/context-monitor.js` (109 lines) supplies `estimateTokens` (`length / 4` — the same
heuristic gstack uses), `checkContextBudget` against 35% warn / 25% critical, and
`estimatePhaseSkillCost(pluginRoot, phase, phaseBindings)`.

`tools/measure-phase-costs.js`, run 2026-07-25 against the current tree:

```
Phase      Skills      Total  % of 200K  Verdict
discuss         2       3881       1.9%  ok
plan            3       6537       3.3%  ok
execute         5      12761       6.4%  ok
verify          2       3616       1.8%  ok
review          4      10435       5.2%  ok
ship            5      12234       6.1%  ok
```

Signal's skill corpus is **21 `SKILL.md` files totalling 199,711 bytes** (counted on disk
2026-07-25; the phase table above sums to 21 loads but some skills are cross-bound to two phases —
`context-monitor.js:56-60` — so the two 21s coincide rather than being the same count). Its largest
single skill is `skills/build/test-driven-development/SKILL.md` at **14,041 bytes**. gstack's
*smallest* carved skill is budgeted at a **56,000-byte skeleton**, and gstack's `ship` skill alone
is **~87% of Signal's whole corpus** — *that 174,407 B figure is from the v1.57.7.0 baseline
fixture, not a current disk measurement, so treat the ratio as an order-of-magnitude point, not a
precise one.*

**Assessment, offer-side:** the carve mechanism is portable in principle — it is host-agnostic
markdown plus a build-time resolver plus a test registry — but it is **built for a corpus one order
of magnitude larger than Signal's**. Signal has no template-generation step to hang
`{{SECTION:id}}` on; adding one is the precondition, and that is the bulk of the port.

**The genuinely transferable pieces, ranked by independence from the rest:**

1. **`maxSkeletonBytes` + union-vs-skeleton measurement discipline** — portable *today*, with no
   carve at all. Signal already has `estimatePhaseSkillCost` and `tests/state-size.test.js` as a
   precedent for a size-assertion test; it does not currently assert a ceiling on skill load.
2. **The size-budget regression harness** — baseline fixture + ratio + explicit audit-logged
   override + an anti-mass-deletion floor. Independent of carving entirely.
3. **The passive-registry contract** — *"no machine predicate; the prose decides when"* — a design
   rule Signal could adopt if it ever splits a skill.
4. **The behavioral test that asserts the agent actually read the deferred file** — the only thing
   that converts a prose `STOP` into a checked claim, and the hardest piece to build.
5. **The carve itself** — least transferable; needs the generator, and Signal has no skill large
   enough to justify it.

| 1 | **SCOPE EXPANSION** | *"You are building a cathedral… Push scope UP. Ask 'what would make this 10x better for 2x the effort?'"* |
| 2 | **SELECTIVE EXPANSION** | *"A rigorous reviewer who also has taste."* Hold scope as baseline, surface every expansion **individually** for cherry-picking, **neutral** recommendation posture |
| 3 | **HOLD SCOPE** | *"Maximum rigor… Do not silently reduce OR expand."* |
| 4 | **SCOPE REDUCTION** | *"You are a surgeon. Find the minimum viable version… Cut everything else."* |

Each mode has its own analysis block at `:1256-1279` (0D. Mode-Specific Analysis) — EXPANSION runs
10x check + platonic ideal + delight opportunities + an opt-in ceremony; SELECTIVE EXPANSION runs
the HOLD SCOPE analysis **first**, then a candidate scan and a cherry-pick ceremony; HOLD SCOPE runs
a complexity check (>8 files or >2 new classes/services = a smell) + a minimum-set question;
SCOPE REDUCTION runs a ruthless cut + a must-ship-together separation.

**Defaults by change type** (`:1419-1424`): feature enhancement → SELECTIVE EXPANSION · bug fix or
hotfix → HOLD SCOPE · refactor → HOLD SCOPE · *"hold scope but tempt me" / "show me options" /
"cherry-pick"* → SELECTIVE EXPANSION, **no question asked**.

**The commit rule is the load-bearing part** (`:879`): *"Once the user selects a mode, COMMIT to it.
Do not silently drift toward a different mode. If EXPANSION is selected, do not argue for less work
during later sections… If REDUCTION is selected, do not sneak scope back in. Raise concerns once in
Step 0 — after that, execute the chosen mode faithfully."* Plus: *"In ALL modes, the user is 100% in
control. Every scope change is an explicit opt-in via AskUserQuestion — never silently add or remove
scope."*

**Step 0 is a six-part gauntlet that runs BEFORE mode selection**, which is more than the four modes
Signal knew about:

| Step | What |
|---|---|
| 0A | **Premise Challenge** (`:1192`) — right problem? actual outcome vs. proxy? what if we did nothing? |
| 0B | **Existing Code Leverage** (`:1197`) — *"Map every sub-problem to existing code… Is this plan rebuilding anything that already exists?"* |
| 0C | **Dream State Mapping** (`:1201`) — CURRENT → THIS PLAN → 12-MONTH IDEAL ascii diagram |
| 0C-bis | **Implementation Alternatives (MANDATORY)** (`:1208`) — 2-3 approaches, each with Effort/Risk/Pros/Cons/Reuses; **one must be "minimal viable", one must be "ideal architecture", and `:1235` insists they have equal weight** — *"If the right answer is a rewrite, say so."* Blocking: *"Do NOT proceed to Step 0D or 0F until the user responds"* (`:1241`) |
| 0D | Mode-specific analysis (above) + 0D-prelude expansion framing + 0D-POST persist |
| 0E | **Temporal Interrogation** (`:1393`) — EXPANSION, SELECTIVE EXPANSION, and HOLD modes |
| 0F | Mode Selection |

**0D-POST** (`:1280-1309`) persists the CEO plan to
`~/.gstack/projects/$SLUG/ceo-plans/{date}-{feature-slug}.md` with `status: ACTIVE` frontmatter, and

## 5. `/retro` + `/learn` — the memory loop, concretely

This is a **closed loop with a real reader**, and it is **not** the thing `/retro` does.
The two are separate mechanisms that happen to share a skill directory namespace.

### 5.1 The write path — `## Capture Learnings`, in 12 skills

Not a `/learn` feature. **Twelve skills carry a `## Capture Learnings` block**: `cso`,
`design-consultation`, `design-review`, `devex-review`, `investigate`, `office-hours`, `qa`,
`qa-only`, `retro`, `review`, `scrape`, `skillify`.

Each emits one call (verbatim from `cso/SKILL.md:1240`):

```bash
~/.claude/skills/gstack/bin/gstack-learnings-log '{"skill":"cso","type":"TYPE","key":"SHORT_KEY",
  "insight":"DESCRIPTION","confidence":N,"source":"SOURCE","files":["path/to/relevant/file"]}'
```

The prose defines the vocabulary (`cso/SKILL.md:1242-1256`):
- **Types:** `pattern` · `pitfall` · `preference` · `architecture` · `tool` · `operational`
  (the binary also accepts `investigation`).
- **Sources:** `observed` · `user-stated` · `inferred` · **`cross-model` (both Claude and Codex agree)**.
- **Confidence 1-10, with calibration anchors:** *"An observed pattern you verified in the code is
  8-9. An inference you're not sure about is 4-5. A user preference they explicitly stated is 10."*
- **`files`** enables staleness detection — *"if those files are later deleted, the learning can be
  flagged."*
- Gate: *"Only log genuine discoveries… A good test: would this insight save time in a future
  session? If yes, log it."*

### 5.2 The storage — `bin/gstack-learnings-log` (91 lines)

Append-only JSONL at **`~/.gstack/projects/$SLUG/learnings.jsonl`** (`:87`). `$SLUG` comes from
`bin/gstack-slug` — **the store is per-repo, outside the repo.**

Validation before append (a `bun -e` block, `:27-77`): type must be in the allowlist · **key must
match `/^[a-zA-Z0-9_-]+$/`** (*"no injection surface"*) · confidence must be an integer 1-10 ·
source must be in the allowlist · `insight` runs through a shared `hasInjection()` from
`lib/jsonl-store.ts` (*"one audited list across learnings + decisions, no drift"*) and is **rejected**
if it *"contains suspicious instruction-like content"* · `ts` injected if absent · and
**`j.trusted = j.source === 'user-stated'`** — a trust bit stamped at write time.

Header comment (`:6-7`): *"Append-only storage. Duplicates (same key+type) are resolved at read time
by `gstack-learnings-search` ('latest winner' per key+type)."* Last line enqueues the file for
cross-machine gbrain sync, backgrounded and no-op'd if sync is off (`:90`).

### 5.3 The read-back path — `## Prior Learnings`, in 10 skills

**Ten skills open with a `## Prior Learnings` block**: `cso`, `design-consultation`, `design-review`,
`investigate`, `office-hours`, `plan-ceo-review`, `qa`, `qa-only`, `retro`, `review`. Each runs
(`cso/SKILL.md:883-894`):

```bash
_CROSS_PROJ=$(bin/gstack-config get cross_project_learnings || echo "unset")
if [ "$_CROSS_PROJ" = "true" ]; then bin/gstack-learnings-search --limit 10 --cross-project
else bin/gstack-learnings-search --limit 10; fi
```

On first run it asks a one-time consent question (`cso/SKILL.md:897-910`) — *"gstack can search
learnings from your other projects on this machine… This stays local (no data leaves your machine).
Recommended for solo developers. Skip if you work on multiple client codebases where
cross-contamination would be a concern"* — and persists the answer via `bin/gstack-config set`.

**The compounding is made visible on purpose** (`cso/SKILL.md:912-918`):

> *"When a review finding matches a past learning, display: **'Prior learning applied: [key]
> (confidence N/10, from [date])'**… The user should see that gstack is getting smarter on their
> codebase over time."*

### 5.4 The reader — `bin/gstack-learnings-search` (162 lines)

Four behaviors that make this more than a `grep`:

1. **Confidence decay** (`:79-85`): `observed` and `inferred` entries lose **1 point per 30 days**
   — `conf = max(0, conf - floor(days/30))`. `user-stated` and `cross-model` do **not** decay.
2. **Latest-winner dedup** (`:108-116`) per `key|type`, resolved at read time (which is why the
   store can stay append-only).
3. **Cross-project trust gate** (`:93-102`) — an **allowlist**, with the bug it fixes recorded in the
   comment: *"#1745: this is an ALLOWLIST, not a denylist. The old equals-false check admitted any
   row where `trusted` is missing/undefined (legacy rows written before the field existed,
   hand-edited rows, rows from other tools). Require `trusted` to be exactly `true`."* Rationale:
   *"This prevents prompt injection from one project's AI-generated learnings silently influencing
   reviews in another project."* Cross-project reads cap at **5 other projects**.
4. **Token-OR query filter** over key + insight + file paths, then sort by **effective** (decayed)
   confidence, then recency, then `--limit`.

Output is a formatted digest grouped by type, each row carrying key, decayed confidence, source,
date, a `[cross-project]` tag where applicable, and the referenced files.

**This is a genuinely closed loop:** 12 skills write → validated append-only JSONL → 10 skills read
back with decay, dedup, and a trust gate → the match is surfaced to the user by name.

### 5.5 `/learn` — a management CLI over that store, not the loop itself

`learn/SKILL.md` (953 lines; ~46 KB / ~11,500 est tokens at the v1.57 baseline). Its command surface:
**Detect command** (`:793`) · **Show recent** (default, `:806`) · **Search** (`:821`) ·
**Prune** (`:832`) · **Export** (`:862`) · **Project Learnings** (`:874`) · **Stats** (`:894`) ·
**Manual add** (`:940`).

**What `/learn` adds is curation and inspection over a store that other skills populate and consume.**
Remove `/learn` entirely and the loop still runs; remove the `Capture Learnings` / `Prior Learnings`
blocks and `/learn` has nothing to manage.

### 5.6 `/retro` — a git-derived weekly engineering retro, **not** a learning-capture mechanism

This is the finding most likely to surprise a reader working from the April characterization.

`retro/SKILL.md` description (`:5`): *"Weekly engineering retrospective."* Its `## When to invoke`
(`:40-45`): *"Analyzes commit history, work patterns, and code quality metrics with persistent
history and trend tracking. **Team-aware:** breaks down per-person contributions with praise and
growth areas."*

Arguments (`:846-853`): `/retro` (7d default) · `24h` · `14d` · `30d` · `compare` (current window vs.
prior same-length window) · `global` (cross-project across all AI coding tools).

**Fifteen numbered steps, and they are metrics steps** (`:927-1367`): 0.5 stale-base pre-flight guard
· 1 Gather Raw Data · 2 Compute Metrics · 3 Commit Time Distribution · 4 Work Session Detection ·
5 Commit Type Breakdown · 6 Hotspot Analysis · 7 PR Size Distribution · 8 **Focus Score + Ship of the
Week** · 9 Team Member Analysis · 10 Week-over-Week Trends (window ≥14d) · 11 **Streak Tracking** ·
12 Load History & Compare · 13 Save Retro History · 14 Write the Narrative.

Persistence (`:1301`, `:1746`, `:1804`): a **JSON snapshot** to `.context/retros/{date}-{n}.json`
(repo-local) or `~/.gstack/retros/global-*.json` for global mode. `:1804` is explicit: *"ALL
narrative output goes directly to the user in the conversation. **The ONLY file written is the
`.context/retros/` JSON snapshot.**"* The narrative is not persisted.

Read-back is declarative, via a **`gbrain:` frontmatter block** (`retro/SKILL.md:16-34`) — three
`context_queries` that inject prior context before the skill runs:

```yaml
gbrain:
  schema: 1
  context_queries:
    - id: prior-retros     glob: ~/.gstack/projects/{repo_slug}/retros/*.md  sort: mtime_desc limit: 5
    - id: recent-timeline  glob: ~/.gstack/projects/{repo_slug}/timeline.jsonl  tail: 30
    - id: recent-learnings glob: ~/.gstack/projects/{repo_slug}/learnings.jsonl tail: 10
```

**Six skills carry a `gbrain:` frontmatter block.** This declarative context-injection schema is a
second portable pattern hiding inside the memory loop, distinct from both the carve and the
learnings store.

`/retro` also carries `## Prior Learnings` and `## Capture Learnings`, so it participates in the
learnings loop like any other skill — but its own output is metrics, not learnings.
