# M6.E18 — Requirements: the review loop's signals become trustworthy

**Label:** *"Make the review loop's signals trustworthy, then prove them with a driven Epic"*.
Priority 1 of [`BACKLOG-REVIEW-2026-10-20.md`](BACKLOG-REVIEW-2026-10-20.md), picked by Brett. Covers
`SIG-348`, `SIG-285`, `SIG-349`, `SIG-337`, `SIG-344`, `SIG-335`, `SIG-343`, `SIG-319`, `SIG-342`
(partly, see *Scope*). Tier: project FULL (no per-Epic profile), `attention: checkpointed`, driven by
`/sig:drive`. Decisions `D-M6E18-1` … `D-M6E18-8` in [`DECISIONS.md`](DECISIONS.md).

## Why now

- **The PR reviewer reviews only a PR's first push.** The upstream `/code-review` command's step 1
  reads *"Claude has already commented on this PR … stop and do not proceed."* On PR #304 the first
  push (`e92032de`, run 39316819152) got a real review: 9 turns, $1.44. Each of the nine later pushes,
  which carried every REVIEW fix round, stopped at step 1 in 2–4 turns, and the check stayed green.
  Run 39346376038's own words: *"Claude has already commented on PR #304, so I'm stopping. I did not
  review it"* ([`SIG-348`](work/items/00/SIG-348.md)). M6.E17 built a fresh read of every fix round,
  and the reviewer that runs on the PR never read one.
- **An old PASS can lift the loop ceiling.** `loopStatusFor` cannot tell whether the newest
  `phase_passes` entry was written in the current visit to the phase ([`SIG-349`](work/items/00/SIG-349.md)).
  A visit that ends without `recordPass` leaves an earlier PASS lifting the ceiling at every count.
- M6.E17's retrospective asks for its mechanism to be *"exercised by a driven Epic next"*
  ([`M6.E17-RETROSPECTIVE.md`](M6.E17-RETROSPECTIVE.md) § What to feed back). This Epic is that run,
  and the signals it would rely on are the ones above.

## Functional requirements

Every FR starts with a test that fails on `main` before the change (FULL, strict TDD), proven with
`parent-run.js`.

### FR1 — A real review of the head commit before merge (`D-M6E18-1`; `SIG-348`, `SIG-285`)
- AC1.1 The PR reviewer can be asked for a review of the PR's current head commit on demand, by a
  trigger a person can take from the PR (PLAN picks it: a label, a re-run, or a comment). That run
  reviews even when Claude has already commented on the PR.
- AC1.2 Ordinary pushes keep today's behaviour: the first push is reviewed; later pushes may stop at
  the upstream step 1.
- AC1.3 `readReviewerEffort` tells apart, for the head commit: a real review; a run that stopped at
  the upstream step 1 because Claude had already commented (a **stop**, not a hollow review); a hollow
  run; and cannot-check. It names the newest commit that did get a real review, if any (`SIG-285`).
- AC1.4 At SHIP, when the head commit has no real review, SHIP says so, names the last reviewed commit
  and how many commits came after it, gives the trigger from AC1.1, and does **not** report the PR as
  ready to merge. A real review of the head commit clears it. `cannot-check` is said as cannot-check,
  never as reviewed.
- AC1.5 The workflow's comment explains why the on-demand run exists, citing this Epic's runs, so the
  next reader does not remove it as redundant.
- AC1.6 *(Added at PLAN, `D-M6E18-7`, `-8`.)* The workflow change reaches `main` in its own fix-lane PR
  before this Epic's SHIP. Each reviewer run writes one `REVIEW_OUTCOME=` line to its log, which
  `readReviewerEffort` reads. The job's token permissions are unchanged.

### FR2 — The loop ceiling counts only what this visit recorded (`D-M6E18-3`; `SIG-349`)
- AC2.1 Entering VERIFY or REVIEW (`transitionPhase`) records where the visit began, as a new optional
  `STATE.md` field, added the way M6.E17 added `phase_passes` (no `schema_version` change).
- AC2.2 `loopStatusFor` lifts a phase's ceiling only for a PASS or PASS-WITH-FIXES recorded after the
  current visit's marker. The `SIG-349` probe (`phase_passes: [VERIFY FAIL, VERIFY PASS]`, two later
  VERIFY and REVIEW exits, `phase: VERIFY`, no record this visit) reads held, not lifted.
- AC2.3 A STATE with no marker reads exactly as it does today (older projects, and STATE written before
  this release).
- AC2.4 An Epic roll clears the marker with the other per-Epic fields. A marker that does not parse
  reads as `null`, so `/sig:drive` halts with `loop-unknown`, never as zero.
- AC2.5 `references/state-schema.md` documents the field.

### FR3 — `recordPass` accepts only a pass that can be true (`SIG-337`, `SIG-344`)
- AC3.1 `recordPass(…, phase, …)` refuses when `STATE.md`'s `phase` is not that phase, naming both.
- AC3.2 A pass entry whose date is malformed or after today is not counted on read. It makes the count
  unreadable (`null`), the same answer as any other unreadable record.
- AC3.3 Recording the same pass twice is refused (P3-S8). PLAN defines "the same pass" against the
  visit marker from FR2. *(Amended at EXECUTE: not refused. A visit can hold several real passes —
  passes whose fixes never leave REVIEW are what `phase_passes` exists to count, and M6.E16 ran four —
  so "one record per visit" refused a legitimate second pass, and nothing else identifies a pass. A
  duplicate raises the count, so the ceiling stops sooner, never later. Pinned by a test that records
  three passes in one REVIEW visit and reads the ceiling.)*
- AC3.4 VERIFY's "PASS with documented limits" has a defined `recordPass` value (P4-S6).
- AC3.5 `recordPass` called before `checkFixRounds` on a report that has unchecked fix rounds is refused
  with a reason that names the missing check (P4-S7).
- AC3.6 Tests: `phase_passes` survives a FAIL loop-back; the state-schema row; a `0 of 0` summary
  (P4-S11/S12, P3-S11).

### FR4 — `checkFixRounds` checks what a round claims (`SIG-335`, `SIG-344`)
- AC4.1 A round's **Parent run:** commit is resolved in git and must be the base of that round's
  fresh-read range. An unresolvable or mismatched sha is refused (P3-S3/P4-S2, `SIG-335`).
- AC4.2 Round N+1's range starts where round N's ended, and `review.md` § 4.6 says what the base of a
  round after the first is (`SIG-335`).
- AC4.3 A `### Fix round` heading inside an HTML comment or a code fence is not counted (P3-S4).
- AC4.4 Commits after the newest `## Pass N, at {sha}` that no round accounts for are reported (P4-S5),
  so the check holds even when an agent skipped a `review.md` step.

### FR5 — The flow says where it is at SHIP (`SIG-319`, `SIG-343`)
- AC5.1 At SHIP, `/sig:resume` and `/sig:status` say what is still owed when the current unit's record
  is open or *closing*: the merge of PR #N (when known), then the close confirm. "Next phase: done"
  appears only when the unit's record is closed.
- AC5.2 Re-invoking `/sig:ship` after a linear ship leaves the live `completed_phases` list empty: no
  stray `SHIP (<date>)` entry (`SIG-343`). Pinned with a test that runs `ship.md`'s documented steps in
  order, not `completePhase` alone (M6.E17 retrospective).

### FR6 — SHIP does not write through a symlink (`SIG-342` P4-S1)
- AC6.1 A linear SHIP that finds the REVIEW report is a symlink refuses to append to it (`lstat`) and
  says why.
- AC6.2 `ship.md` stages the appended report with the rest of SHIP's commit.

## Non-functional requirements (FULL prompt, answered)

- Health probe, graceful shutdown, request logging, security headers, rate limiting: **not
  applicable** — Signal is a local CLI plugin; the one network surface is the GitHub workflow, which
  runs on GitHub's runners with the permissions it already declares.
- **Cost:** the on-demand review costs about one real review per Epic (~$1.50 at #304's rate). The
  workflow must not start reviewing every push.
- **Secrets:** the workflow change adds no secret and widens no token permission. Any comment or label
  trigger runs only for people with write access to the repository.
- Errors at the edges: every new refusal names its reason; every "could not look" stays distinct from
  "looked and found nothing".

## Blast radius — what this touches that we are not changing

- **`.github/workflows/claude-code-review.yml`**: a new trigger. The reviewer action refuses to run on
  a PR that edits its own workflow, so the change ships first in its own PR (`D-M6E18-7`) and this
  Epic's PR, once it has merged `main`, can use the trigger on itself.
- **`/sig:drive`**: reads `loopStatusFor`. It may now halt where an old PASS used to let it continue.
  That is intended, and it reaches every project on the next update.
- **`STATE.md` in every project**: one more optional field. Absent means today's behaviour (AC2.3).
- **SHIP's output**: may now decline to call a PR ready to merge. Merging stays a person's act.
- **`commands/*.md`** edits move the adherence directive-line ceiling, so `ADHERENCE-LOG.md` is
  regenerated and the PR merges with `--merge` (the only method on `main`). Planned for at PLAN.
- **Not changed:** the ceiling value (3), the upstream `/code-review` command, the reviewer's model or
  tools, PASS-WITH-FIXES's 50-line rule.

## Outcome

**How we will know it worked:** this Epic, driven by `/sig:drive` at `checkpointed`, reaches SHIP with
every VERIFY and REVIEW pass recorded against a visit marker, `loopStatusFor` reading the count from
those records, and `checkFixRounds` run on every fix round; and this Epic's own PR merges only after a
real review of its head commit, which SHIP confirmed rather than assumed (`D-M6E18-7`). Checked at this
Epic's SHIP and at the next Epic's SHIP, and recorded in this Epic's retrospective.
