prove that independently of what the canary declared, and re-run `B41-phase-entry` under the fixed arm
— publishing whatever verdict comes back.

## What this Epic does for the first time (M5.E17 FR1)

Two shipped code paths have **never run for their real purpose**, and both go in wave 1.

**1. `applyDeletion` — the line-level deleter — is dead code in production.**
`tools/adherence-run.js:378` is the false branch of `canary.deleteSection ? … : …`. The registry holds
one canary and it declares `deleteSection`, so the branch has never executed in a measurement. Its only
exercise is three unit tests. FR1's `ship.md` line anchor is its **first real use** — and it is being
handed the one file in the corpus whose structure defeated the section primitive.

**2. `appendNotice` has no production caller.** Only `tests/adherence-append-only.test.js:140` calls
it, yet `ADHERENCE-LOG.md` carries three annotation blocks — one of which (`DIAGNOSED`) it cannot
produce, because `NOTICE_KINDS` is frozen to two values and it throws on the rest (**`B80`**). FR7 is
the first time an annotation reaches that log **from code**.

**Therefore S1 ‖ S2 are wave 1** — ahead of the leak walk, which is the work that looks more
important. If the line-deletion path or the notice path is broken, it breaks against a unit fixture in
wave 1 rather than against the live measurement in wave 3.

*Neither item is the new code this Epic writes. A newly-authored thing has no history to be wrong
about; the risk lives in machinery that already exists, was built for a purpose, and has never been
run for it. That is the distinction — and it is the distinction that made `B55` itself a last-task
find in M5.E13 instead of a wave-1 one.*

2. **S3 does not depend on S1.** The walk needs only `canary.trace.functionName`, which exists today

3. **`walkResidue` gets its own module** (`tools/lib/adherence-leak.js`), which answers PLAN open
   question 1. Putting it in `adherence-verdict.js` would have collided with S1 inside wave 1, and it
