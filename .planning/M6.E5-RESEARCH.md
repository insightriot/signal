## Angle 1 — Codebase: what this command is modelled on, and what it collides with

### The platform research is 2 days old and is not repeated here

`analysis/PERMISSIONS-SPIKE.md` (2026-08-25) verified the permission API three ways against live
docs. Re-fetching two-day-old, triply-verified research would be theatre. **What was re-checked
instead is the local evidence, which is stronger than the docs for this question:** both settings
files were read on disk during DISCUSS, and the live figure is **43 allow / 0 deny / 0 ask / no
`defaultMode`**.

### The precedent for extracting prescribed commands already exists — and its reach is narrower than we need

`tests/prescribed-cli.test.js` walks backticked CLI strings out of command markdown with a regex
(`INVOCATION = /`claude plugin ([a-z-]+)(?:\s+([^`\s]+))?[^`]*`/g`) and checks the target against an
identity **derived from** two manifests rather than hardcoded. That is the shape `S1` copies.

⚠ **But it reads `plugin/commands` only, and it matches one verb.** Generalising to every binary
across `commands/`, `agents/`, `skills/` and `references/` is a path **nothing has executed**. See
*What this Epic does for the first time*, below.

### Two layers prescribe commands, and they are not equally trustworthy

| Layer | How to read it | Confidence |
|---|---|---|
| Deterministic | `execFileSync` / `exec` call sites in `plugin/tools/`, `plugin/hooks/` | **High** — the binary is in the source |
| Prompt | backticked strings in `commands/`, `agents/`, `skills/`, `references/` | **Lower** — prose that may be describing rather than prescribing |

**Measured 2026-08-26.** Deterministic layer: `git` (9 sites), `ps` (1 site) — that is the entire
set. Prompt layer: **49 distinct binary+subcommand pairs across 130 occurrences.**

**The prompt layer's noise is not incidental, it is structural.** `rm` appears 5 times because
`/sig:doctor --fix` *describes* `rm -rf` on cache directories. `pytest`, `cargo build` and `go test`
appear because command files describe **other people's** stacks. So the two layers must be labelled
separately on the record — a rule traceable to an `execFileSync` site is a stronger claim than one
traceable to prose, and `AC1.1b` requires the report to say which.

### Registration blast radius, measured rather than assumed

Adding the 22nd command is **not** a drop-in. Four places hard-code or reconcile the count:

1. **`tests/roster.test.js`** — four assertions hardcode `21` (`:23`, `:36`, `:37`). **The suite
   fails until updated.** This is a good gate, not an obstacle: it is the whole-population shape,
   already in place for commands.
2. **`docs/map/index.html`** — a `// map-roster:begin COMMANDS` block reconciled against the roster
   by `tests/map-roster-reconcile.test.js`. Also fails until updated.
3. **`plugin/references/command-taxonomy.md`** — every command belongs to **exactly one** of five
   groups, and the file states that a command seeming to belong to two *"is a sign it does two
   things."*
4. **`README.md` / `CLAUDE.md`** — prose command counts and the per-command description list.

⚠ **Taxonomy placement is a real decision, not bookkeeping — and it does not sit cleanly.**
Group 2 (*orientation*) is disqualified by its own contract: *"Writes nothing."* This writes
`.planning/PERMISSIONS.md`. Group 4 (*document upkeep*) is *"acts on `.planning/` as a corpus"* —
this adds one document rather than operating over the tree. **Group 5 (*Signal's own health — acts
on the tool, not your project*) is the closest fit**, because the object is Signal's operating
envelope in this environment rather than your documents. The tension is recorded rather than
smoothed over: the file's own test — *does it do two things?* — is worth asking at REVIEW.

## Angle 2 — Prior art and platform

### Precedence, quoted from the spike rather than re-derived

Deny is **absolute**: *"A broad deny rule like `Bash(aws *)` blocks every matching call, including
calls that also match a narrower allow rule like `Bash(aws s3 ls)`, so a deny rule can't carry
allowlist exceptions."* This is why `S4` is small by design and why `AC4.1b` puts the warning at the
list rather than in a reference file.

### The read is an approximation, and the reasons are enumerable

Five settings scopes exist (managed/enterprise, user, project, local, CLI flags); this command can
read three. Separately, `PreToolUse` hooks can block a call every rule allows. **So the reported set
is not the effective set** — `AC2.2a`/`AC2.2b` require that limit to render whenever the read
renders, not to live in a doc the output points at.

### What the accumulation is, and why a generator beats curation

`D-BR0826-1`: *"Yes, and don't ask again"* is **documented** to save the rule into
`.claude/settings.local.json` at the git root. Those entries are answered prompts, not a curated
list. **Any design assuming operators hand-curate an allowlist is contradicted by the only sample
available.**

⚠ **Re-verified on disk 2026-08-26, and it is worse than "unshared":** `.claude/settings.local.json`
is gitignored at `.gitignore:18`, `.claude/settings.json` does not exist, and
**`git ls-files .claude/` returns nothing.** Nothing in `.claude/` is version-controlled at all.
That is the evidence behind `AC5.2b`'s tracked install target.

## What this Epic does for the first time — and it goes in WAVE 1

**`detectProjectKind` has existed since `M4.5` and has never once been called to let a command
proceed.**

Its only production consumer is `buildMissingPlanningError` (`add.js:217`), which uses it to choose
*which refusal to print* — brownfield repos are told to run `/sig:init`, greenfield ones
`/sig:new-project`. Every one of Signal's 21 commands either requires `.planning/`, creates it, or
is about the install. **`FR5.3` is the first code path that reads this function and then keeps
going.**

That is precisely the instruction's target: *machinery that already exists, was built for a purpose,
and has never been run for that purpose.* A newly-authored function has no history to be wrong
about; this one does.

**Second first, same slice:** the prescribed-CLI extraction has only ever run over `plugin/commands`
for a single verb. Reading `agents/`, `skills/` and `references/` for **every** binary is a path
nothing has executed, and the `rm` finding is already evidence that its output is not what a reader
would predict.

**Therefore `S1.t0` is the first task in wave 1** — execute both paths against real directories and
write down what actually comes back, *before* anything is built on top of them. If the scan's reach
or `detectProjectKind`'s verdict is not what this plan assumes, it fails against a probe rather than
against a finished report.
