## Important Issues

### I1 — A decision tagged on NEITHER axis rendered no tag rows at all

`plugin/tools/lib/drive.js` — `formatQueuedDecision`

The guard read `if (reversibility !== undefined || altitude !== undefined)`. With both absent, both
rows were omitted — and the comment three lines above it says, in its own words:

> An untagged axis renders as `untagged`, never omitted. A missing row would look like a decision
> nobody had to tag, and the whole fail-closed default exists because that is the case worth seeing.

The fully-untagged decision **is** that case. `drive.md` makes the same promise to the user: *"the
entry names which axis you left blank."* For a decision tagged on neither, it named neither.

Not total information loss — the `**Why it is here:**` line still read *"neither axis was tagged"* —
but the structured rows anything parses were gone, in the one case the design exists for.

**The test named for this covered the case that already worked.** `an UNTAGGED axis renders as
untagged, never omitted` passes `altitude: 'plumbing'` and asserts the reversibility row: the
half-tagged path. Same shape as the vacuous-test finding PR #234's reviewer caught in this Epic —
not vacuous this time, but aimed one case to the left of the defect.

**Fixed:** both rows render unconditionally. **New coverage:** a fully-untagged decision asserts both
rows and the router's sentence.

### I2 — A caller-supplied `routeWhy` bypassed the adopt-guard and overrode the router

`plugin/tools/lib/drive.js` — `queueDecision`

The guard read `if (routed.route === 'adopt' && decision?.routeWhy === undefined)`, so passing any
`routeWhy` stood it down. Verified against the shipped module: a `plumbing` + `trivial` decision —
one the router adopts, that nobody has to answer — filed successfully as a parked question reading
**"Why it is here: because I said so"**. That is verbatim the entry the guard's own comment says it
exists to prevent: *"an entry reading 'Adopted: …' sitting unanswered in the queue forever — a
decision nobody has to make, indistinguishable from one that is waiting."*

The same parameter also replaced the router's sentence, via
`routeWhy: decision?.routeWhy ?? routed.why`. `routeWhy` is documented as an **output** of
`routeDecision` (*"the router names the deciding axis, and a second hand-written explanation is how
one rule comes to be described two ways"*), and `drive.md` instructs callers **"Do not write that
sentence yourself."** Honouring it as an input is the code contradicting both.

Latent rather than live — no caller passes it, and no test names it — but it is a hole in a guard,
in an Epic about mechanisms nothing reaches.

**Fixed:** the guard no longer inspects `routeWhy`; the entry always carries `routed.why`.
**New coverage:** the adoptable-with-`routeWhy` case must refuse and write no file; a queued entry
must carry the router's wording and not the caller's.

## Suggestions

### S1 — `ROUTE_REVERSIBILITY` is not frozen, and it is the shared one

`ROUTE_ALTITUDE` is `Object.freeze`d. `ROUTE_REVERSIBILITY = CALIBRATION_ENUMS.reversibility` is a
live reference to calibration's own validation array and is **not** frozen, so mutating it corrupts
profile validation process-wide. Verified: `Object.isFrozen` → `true` / `false`.

Asymmetric hardening, on the riskier of the two. **Not fixed in-phase deliberately** — freezing it
means freezing a `profile.js` structure, which is a ripple into another module, and design impact is
what separates PASS-WITH-FIXES from FAIL. Filed rather than smuggled in.
