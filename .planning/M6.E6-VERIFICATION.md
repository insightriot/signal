## The headline, first

The plan's outcome oracle was: *"a `/sig:drive` run that meets an unforeseen gray-area question
CONTINUES, and the question is answerable afterwards from `DECISION-QUEUE.md` alone."* Its risk row
said, in advance: *"no suite substitutes for it. VERIFY reports the run or reports that it did not
happen — never 'tests pass, therefore it works'."*

**The run happened. It could not exercise the queue, for two reasons that are both findings.**

### 1. The run executed a retired release — `B115`, filed and fixed

`/sig:drive` was invoked for real on 2026-09-04, in this repository. It loaded **`v0.1.34`'s** copy
of `drive.md` while **`v0.1.36`** was installed and recorded in `installed_plugins.json`. The front
end shipped in `v0.1.35`/`v0.1.36` — `0a` propose, `0b` confirm, `0c` preflight — **was not in the
file the run executed.**

Verified precisely rather than inferred. **Method, stated because the numbers are meaningless
without it:** each cell is `grep -c` for one literal marker in that cached copy's
`commands/drive.md` — the string `0a. Choose the work` for the front-end column, and
`routeDecision` for the router column. So the front-end column counts **one sentinel heading, not
all three** (`0a`/`0b`/`0c`); `1` means *the front end is present*, not *one of three headings
exists*. The earlier version of this table gave the counts with no method beside prose describing
three headings, and the two did not reconcile — flagged by the PR #234 reviewer.

| Cached copy | `0a. Choose the work` (front-end sentinel) | `routeDecision` |
|---|---|---|
| `0.1.34` (**bound**) | 0 | 0 |
| `0.1.35` | 1 | 0 |
| `0.1.36` (**installed**) | 1 | 0 |

`readBindingBanner` invoked **from the bound `0.1.34` copy** renders the correct RETIRED-code banner
naming both paths. **The mechanism was never broken — nothing called it.** `readBindingBanner` is
wired into `/sig:status` and `/sig:resume` and into no other command, and `/sig:drive` is the one
that *acts*, repeatedly, on instructions it read once.

**Fixed in this Epic:** `drive.md` step 0 checks it **before** the front end and **halts** rather
than reporting. Three tests. ⚠ The fix ships in the *next* release, so the next run is the one that
can benefit — the same structural lag `B52` documented about its own check.

### 2. The queue wiring is on `main` and unreleased, so no session can reach it

Note the third column above: **zero** cached copies carry `routeDecision`. `M6.E6`'s slices merged
to `main` today; nothing has been released since `v0.1.36`. This is the `v0.1.35` lesson repeating —
version numbers are the only delta `/sig:update` compares, so unbumped work on `main` is unreachable
by any session, including this one.

**So the oracle cannot be met from this repository until a release is cut and the CLI restarted.**
That is a sequencing fact, not a defect in the work, and it is stated here so nothing downstream
cites the module demo as satisfaction.

### What was demonstrated, stated at its true strength

Four decisions through the real modules on a scratch directory: a `plumbing`/`trivial` call
**adopted**, a `product`/`trivial` call **parked**, an `irreversible` call **parked**, an untagged
call **parked** — three entries written, run continued. That is the oracle's **shape** and not the
oracle: the discriminator is whether **`/sig:drive`** parked a question or whether **a script called
the function that parks questions.** The same substitution as `B113`'s *"verified against the module
and the documented call site"*, which two live runs then had to settle.
