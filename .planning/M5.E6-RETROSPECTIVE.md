## What changed mid-flight
- **FR7 collapsed from a build to a close-out.** PLAN research found every RMW path FR7 targeted was already locked by M5.E4 FR5 + M5.E5 B25 — the "unlocked" premise was factually stale, masked by an un-ticked `BACKLOG.md` entry. The scope inverted: instead of building a lock, we marked the delivered lock done and folded in the *one* genuine remaining hole (B31), Brett-approved.
- **AC7.7 met by intent, not letter.** The plan said "add `regeneratePlanningIndex` to `RMW_PATHS`." Execution found that array is coupled to the `_afterRead` `it.each` and `regeneratePlanningIndexCore` has no such seam — literal membership would need a dead test-only seam in prod code. Delivered a standalone lock-symmetry assertion instead (mutation-proven to bite in REVIEW).
- **A concurrent Claude session appeared mid-EXECUTE.** A stray/orphaned executor from a prior session latched onto a leftover task board and picked up Slice 1 — see below.

## What assumptions broke
- **"The milestone row is maintained" (D-E9-5) — broke at our own SHIP.** The FR1 retro-gate trusts a present milestone row (row-absence gates the B26/B30 STATE fallbacks). M5.E6's row was stale (`🔨 DISCUSS`, never advanced), so the gate **silently skipped** at Step 0.5 — the flagship retro enforcement did not fire on a real FULL Epic-close. Had the retro not been written by hand, M5.E6 could have shipped retro-less. → **B36** (P2). Deeply ironic on the Epic that fixed B30, the *other* retro-gate blind spot. Structural corollary: for any row-maintained project, at Step 0.5 the row is never yet "shipped," so `isEpicCloseShip` is always false and the row-absence fallbacks never fire — Layer 1 enforcement is effectively inert unless the row is absent (self-hosted) or already marked shipped.
- **"B29 hardened the prototype-pollution class."** The security panel found `renameFn` — the literal sibling seam of `_afterRead`, same `atomicWrite`-under-lock shape — left bare-destructured. B29's scope was `_afterRead` only; the class was never fully closed. → **B34** (unreachable, same tier B29 was).
- **"Sweep is uniformly crash-safe."** Every check is try-catch-guarded except `checkIndexFreshness`'s managed-index compose/diff. → **B35** (low-reach; stranger-repo contract still holds).

## What surprised us
- **The phantom parallel session.** With no live second session open, an orphaned executor (`exec-s1`, carrying an old `M5.E3.S1` assignment) surfaced via `teammate-message`s and a task board our own `TaskList` couldn't see. It stayed disciplined (verified-not-duplicated, committed nothing on M5.E6), so no corruption — but a T4 collision was one step away. Froze both, confirmed with Brett, retired the stray.
- **The panel's mutations complemented VERIFY's exactly.** The orchestrator mutated one conjunct per gate; the test-integrity auditor independently hit the *others* — between them, both B27 conjuncts and all three B30 conjuncts are mutation-proven. Neither planned the overlap; adversarial redundancy found the full set.
- **A one-time ship-fr1 flake under peak load** (3 review agents running full suites at once) that never reproduced across 16+ runs — a reminder that heavy concurrent dogfooding is itself a load test.

## What we'd do differently
- **Keep the milestone row current** (or have SHIP mark it *before* Step 0.5) so the FR1 gate isn't defeated by staleness. This is the B36 fix surface.
- **Capture flake failure text on first sight** — "it's B17" stayed a hypothesis because the assertion text was never grabbed. Add `--retry=0 --bail=1 --reporter=verbose` when a flake is suspected.
- **Scope security-class hardenings to the whole class up front.** B29 hardened `_afterRead`; had "harden all injectable-fn seams" been the framing, `renameFn` (B34) would have been in scope, not a REVIEW find.
- **Fold the doc reconcile into the release commit, before tagging.** This ship's `v0.1.11` tag → `5062526` predates two follow-ups (the `marketplace.sha` pointer, unavoidably self-referential; and the INDEX regen, which was *not* — it could have run before the release commit). Main HEAD is correct (that's what the install path reads), so the tag was not moved — but next release, run the INDEX regen before the release commit so the tag captures a fully-reconciled snapshot.

**Decision recorded (not a regret):** the two intentional transient-red per-task commits (Slices 6 & 7 — a RED test-task committed before its fix) were **deliberately left un-squashed**. They're pushed to `origin/main`, Brett runs multiple machines (force-pushing to rewrite them would diverge those checkouts for zero real gain), and the per-task RED-first history is itself meaningful evidence for strict-Nyquist. The "optional squash" carried through VERIFY/REVIEW/SHIP carry-ins resolves here as **no**.

## Anti-rationalization moment
The temptation was "VERIFY is green at 1623, REVIEW can just confirm." The advisor named it: a green suite proves pass, not that the tests *pin* the behavior — and this codebase ships false-greens (evict.js in M5.E4, two in v0.1.9). So VERIFY ran independent mutation proof-of-fail on the riskiest gates, and REVIEW ran a 3-specialist adversarial panel whose whole job was to find a false-green. Result: 0. The gate held precisely because we refused to let "tests pass" stand in for "tests bite." The second anti-rationalization: not burying the `renameFn` and stale-row findings as "unreachable / just keep rows current" — both are cataloged with concrete fixes, not waved off.
