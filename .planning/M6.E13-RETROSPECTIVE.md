**Amendments to the requirements:**

**The build layout changed in PLAN.** The first plan rewrote the v1 library in place. The plan
checker showed that would turn the suite red from S2 until S4, so v2 was built beside v1, with a
single switch at cutover. That one change is what kept every commit green against this repository's
own v1 store for the whole of EXECUTE.

## What assumptions broke

- **"A static ban on importing the Markdown parsers enforces AC3.2."**
  - It broke twice in PLAN. First, a synchronous store-off path shares a module with store-on code.
    Second, `work-records.js` reached the parsers through `add.js` by way of the secret scrubber.
  - The working form was three layers: a runtime throw-on-call, a static ban over the v2 modules
    only, and a source-text scan. `scrubSensitive` moved to a leaf module, `scrub.js`.
  - It then broke a third and fourth time in VERIFY and REVIEW. A parser call inside an empty
    `catch {}` was not caught until calls were counted, and the source scan missed common regex
    spellings until it became one general detector.
- **"`fixed` closes all have a commit."** 3 of the 9 had none. The converter reported them as
  unmapped instead of guessing.
- **"The DISCUSS inventory counted the readers."**
  - It said 24 readers and 13 commands, and it was never saved.
  - Rebuilt in PLAN, the real numbers were 26 readers (27 by the end) and 12 commands.
  - The plan's list of tests to rewrite was wrong three times. Each time it was replaced by a grep run
    at the start of the task.
- **"`checkpointed` advances through phases."** It did not. Each phase command still asked at its own
  end (SIG-275, below).

## What surprised us

- **The differential read caught a real regression that every test passed.**
  - Store-on, `/sig:drive` gave its "leads with a unit ID" bonus to every record. That dropped M5.E20,
    M5.E12 and M5.E14 from places 2–4 to places 24–27.
  - All 5,473 tests were green at the time.
  - Comparing old and new reader output over the same data, before cutover, is what found it.
- **A hostile ref name confirmed a close.**
  - A branch named `deadbee` was accepted as proof that a fix was on `main`, because git resolves a
    hex-looking ref name before a short hash.
  - VERIFY's fresh verifier found it with 19 attack cases after the suite was green.
- **REVIEW pass 2 found two regressions caused by pass 1's own fixes:**
  - The "skip a broken record" change turned a clean refusal into a partial write. Its test had
    stubbed out the step that failed.
  - The new SHIP instructions told the reader to repair a broken record with a tool that cannot read
    broken records.

  This is the third Epic in a row where a fix-on-fix needed its own fresh read (M6.E3, M6.E12, now
  M6.E13).
- **Brett reported "it's asking me MORE questions" from another project mid-run, and it was real.**
  `applyRigorOverrides` set the end-of-phase confirm for every attention level except `unattended`.
  M6.E10's fix had removed the loop-level stop and missed this one. This Epic's own PLAN showed the
  symptom (it asked for plan approval) before anyone connected the two. Fixed on its own branch: PR
  #279.
- **What did not surprise us:** the migration itself was the quiet step. It had been dry-run in
  wave 1 and again before cutover, which repeats M6.E11's lesson.

## What we'd do differently

- **Save the DISCUSS inventory as a file.** A count without its list cannot be checked, and every
  number derived from it was wrong.
- **Name test sets by command, not by memory.** Every plan list of "tests that will break" was
  incomplete. Every grep run at the start of a task was correct.
- **Brief subagents against the boundary, not the name.** A brief that named only `insightriot` made
  an agent refuse to push under the correct account. Another agent ran `git stash pop` and applied an
  unrelated stash belonging to Brett. Briefs now say "never git stash" and "anything but
  `brettvtcrowe`".
- **Never let a test stub the step a fix is about.** The pass-1 `confirmCloses` test stubbed
  regeneration, which was exactly the step the fix broke.

## What to feed back into Signal

- **SIG-275 (PR #279):** at `checkpointed`, phase commands must not ask at their end; only
  `attended` does. The tests that pinned the old behaviour were rewritten, as M6.E10 did for the loop.
- **For the store, measured and not yet built:**
  - **SIG-274:** nothing turns the work store on for a new project any more.
  - **SIG-279:** a project whose `.planning` is a symlink to a folder inside the repo is now refused.
  - **SIG-278:** discharge can miss a broken record.
  - **SIG-280:** REVIEW residue.
- **Fixes to fixes get their own fresh reader, by rule.** It has paid off three Epics running. It
  could be a REVIEW step, not a habit.
- **The differential read is a reusable mechanism** for any storage change: the old reader against
  the new reader, over the same data, with every difference classified. The Epics-as-records Epic
  should reuse `tools/work-diff-v2.mjs`'s structure. That tool was retired with v1, but its git
  history keeps it.

## Anti-rationalization moment

- **Considered:** at the end of REVIEW pass 2, six Important findings came in after the suite was
  green and pass 1 had already closed seven. "PASS-WITH-FIXES" was tempting on the strength of fixes
  being "small".
- **Done instead:**
  - The fixes were sized by measurement: exactly **50** non-test lines, at the cap and not over it.
  - Each one needed a test seen failing first.
  - A further narrow fresh read was run on the fixes themselves.

  That read found nothing Important, and its residue was filed (SIG-280) rather than dropped.
- **Earlier, at the cutover:** the before-and-after comparison showed 71 "known contradictions". They
  were not waved through as expected noise. Each one was classified, and the 57-row drive ranking
  regression among them was fixed before asking Brett for the go-ahead.
