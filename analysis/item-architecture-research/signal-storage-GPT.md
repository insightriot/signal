# Signal storage and lifecycle architecture research

## Executive recommendation

Lock Signal onto a **repo-native typed object store**: canonical **JSON per entity**, stable paths by immutable ID, Markdown only for prose bodies, and a disposable SQLite index for queries. Lifecycle state should be **derived deterministically from typed transition events embedded in each lifecycle record**, not inferred from prose, filenames, folders, or artifact existence. Generated Markdown becomes an untracked/read-only projection and is never parsed.

All machine-state writes should go through one Signal library/CLI transaction boundary with JSON Schema validation, typed state machines, referential checks, per-record locking, and optimistic concurrency. This follows the strongest lessons from Beads’ storage rewrite, Backlog.md’s structured task layer, git-bug’s explicit data model, Jira workflows, and the concurrency failures documented by planning-with-files. citeturn4view0turn5view0turn13view2turn21view2

Do **not** adopt a global JSONL log, committed SQLite, or Dolt. They solve harder multi-user problems than Signal has while introducing merge or operational complexity. **[inferred]**

Use LLM judgment only as recorded evidence/proposal; a deterministic policy decides whether that evidence is sufficient. Migrate by normalization, provenance capture, quarantine of unverified legacy closure, verification manifests, and an explicit Git cutover—never automatic startup migration.

Three patterns dominate the useful prior art.

First, the systems with the most robust lifecycle semantics—Jira, GitHub Issues, Beads, git-bug, TaskWarrior—store status and relationships as **machine data**, not as interpretations of prose. citeturn4view0turn16search29turn18view0turn21view0turn21view2

Second, the strongest agent-workflow failure evidence points at **duplicated behavioral rules and shared prose files**: planning-with-files documented silent stale overwrites and guards missing from numerous adapter paths; Agent Skills has had path-selection behavior bypassed when the agent entered the workflow by another route; BMAD has seen naming inconsistency between workflows. citeturn13view2turn13view3turn16search8

Third, Beads' storage rewrite is the most relevant warning against “future-proof” overengineering. Its own design record says extra SQL backends were abandoned because backend-specific migrations, transaction behavior, dialects and operations made the abstraction more expensive than the benefit, while its SQLite→Dolt conformance suite found dozens of defects. citeturn5view0 Signal should copy Beads' **invariants, schema guards, conformance testing and single storage seam**, not its database technology. **[inferred]**

**Event sourcing versus current state.** I would use **event sourcing only for lifecycle state**, and do it **inside each aggregate file rather than through one global event stream**. **[inferred]** A bug's `status` should not be stored as a second fact. Its current state should be a pure deterministic fold over:

```text
created(inbox)
triaged(backlog)
started(in_progress)
blocked(reason=...)
resumed(in_progress)
closed(reason=..., proof=[...])
```

The SQLite cache may materialize `current_state`, but it is explicitly disposable. This removes the “status field says closed while history/body says open” category rather than merely linting it.

For ordinary edits such as title, priority or rationale, Git already provides historical versions; full event-sourcing of every character change would add complexity without solving a demonstrated defect. **[inferred]** Lifecycle events are special because Signal needs semantic answers to “when, why and with what proof did this become closed?”

A **single global JSONL lifecycle stream is the wrong topology** for Signal. It turns unrelated item mutations into shared-file writes. Per-record lifecycle event arrays give the desired append-only semantic history while making different work items independent Git objects. Same-record concurrent edits become intentional conflicts that Signal can detect through an expected-content hash rather than silently merge. **[inferred]**

## Proposed architecture

**Canonical data model**

Use four entity families, not one polymorphic Markdown format.

**Lifecycle entities** represent things that move through work states:

```text
WorkItem:
  bug | backlog_item | capture | question

WorkUnit:
  milestone | epic | slice | task

Run:
  one execution of Signal's CALIBRATE → … → SHIP workflow
```

Every lifecycle entity has:

```json
{
  "$schema": "../schema/work-item.v4.json",
  "schema_version": 4,
  "id": "WI-01K...",
  "kind": "bug",
  "title": "Verification result can drift from STATE",
  "created_at": "2026-10-04T15:24:11Z",
  "priority": "high",
  "theme": "storage",
  "links": [
    {"rel": "member_of", "target": "EP-01K..."},
    {"rel": "blocks", "target": "WI-01J..."}
  ],
  "lifecycle": [
    {
      "event_id": "EV-01K...",
      "type": "created",
      "to": "inbox",
      "at": "2026-10-04T15:24:11Z",
      "actor": {"kind": "agent", "id": "claude-code"}
    }
  ],
  "provenance": []
}
```

There is deliberately **no canonical `status` field**. `status` is the result of `fold(lifecycle)`. **[inferred]** That differs from both the current Signal work-item store and Backlog.md. It sacrifices a little raw-file convenience in exchange for eliminating an entire drift class. The query layer exposes `status` normally, so callers do not pay that complexity.

A terminal event is explicit and complete:

```json
{
  "event_id": "EV-01K...",
  "type": "closed",
  "from": "verifying",
  "to": "closed",
  "reason": "fixed",
  "at": "2026-10-05T02:11:03Z",
  "actor": {"kind": "agent", "id": "claude-code"},
  "proof": [
    {
      "kind": "git",
      "commit": "8d7f...",
      "artifact_id": "VR-01K...",
      "anchor": "proof-tests-pass"
    }
  ]
}
```

There is therefore no separate `closed: true`, no “terminal artifact means closed,” no struck-through title, and no generated table cell whose spelling controls behavior.

The state machines should be typed per family rather than one giant status enum. **[inferred]**

```text
WorkItem:
inbox → triaged → ready → in_progress ↔ blocked → verifying → closed
                           └──────────────────────────────→ closed

WorkUnit:
planned → ready → active ↔ blocked → verifying → closed

Run phase:
calibrate → discuss → plan → execute → verify → review → ship
```

Reopen is an explicit transition from `closed` to a permitted state; it does not erase the old close event. Cancellation, duplication and invalidation are terminal close reasons rather than deletion.

Epic membership is simply an optional typed relation. A work item with no Epic is completely valid. This directly accommodates the eight projects you described that do not use Epic IDs.

**Record entities** are not shoved through the work-item lifecycle. They include:

```text
Decision
RequirementSet
Plan
Verification
Review
Retrospective
Profile
Note / narrative
```

This distinction is supported by ADR practice: adr-tools preserves superseded decisions and creates a new ADR rather than deleting the old one; MADR treats status, rationale, options and consequences as record metadata/content rather than as a task queue. citeturn19view0turn19view1

A Decision might have machine metadata:

```json
{
  "id": "D-M6E11-7",
  "kind": "decision",
  "subject": "Canonical lifecycle representation",
  "disposition": "accepted",
  "decided_at": "2026-10-04T18:00:00Z",
  "supersedes": [],
  "body": "bodies/D-M6E11-7.md",
  "evidence": [...]
}
```

while `bodies/D-M6E11-7.md` contains the rationale, alternatives and narrative. Machine readers never parse headings in that Markdown to discover `disposition`, IDs or relationships.

Verification and Review records likewise have a **typed verdict field** in JSON:

```text
verification.verdict = pass | fail | conditional | unknown
review.verdict       = approved | changes_required | blocked
```

The Markdown body explains why. The explanation never determines the verdict.

This is the central prose/structure rule:

> **Structure answers questions a program can reasonably ask; prose explains the answer.**

State, identity, kind, dates, verdicts, relationship endpoints, readiness criteria, closure reason/proof, phase and policy decisions must be structured. Rationale, analysis, retrospective learning, requirement wording, design explanation and review commentary may remain prose. **[inferred]**

Do not repeat structured facts in prose. A generated human view may render them, but the hand-written body should say “why,” not “status: closed again in English.” This directly addresses the same duplication concern Org mode calls out when it keeps TODO context together rather than maintaining duplicate todo documents, although Signal should use a stronger machine schema than Org's text model. citeturn18view2

**Write path**

There should be exactly one machine-state mutation seam:

```text
Claude command / JS caller
        │
        ▼
signal domain API
        │
        ├─ parse + structural validation
        ├─ load target + expected hash
        ├─ acquire per-record lock
        ├─ evaluate transition/policy
        ├─ validate references/invariants
        ├─ append lifecycle event
        ├─ canonical JSON serialization
        ├─ atomic temp-file → rename
        ├─ re-read + validate
        └─ invalidate/rebuild cache entry
```

Backlog.md already recommends CLI/MCP/Web writes over hand editing because those paths preserve field types and metadata. planning-with-files provides the harder evidence: shared direct Markdown writes produced silent lost updates, and copied adapter logic caused guards to be absent from numerous execution paths. citeturn13view2turn13view3

Accordingly:

- Agents may directly edit **prose body Markdown**.
- Agents must use `signal create`, `signal transition`, `signal link`, `signal decide`, `signal verdict`, etc. for machine facts.
- JavaScript libraries call the **same domain functions**, not a second implementation.
- Hooks are a backstop, not the source of truth: after a tool/file write touching `.planning/data`, Signal validates changed canonical records and blocks workflow progression if an unsupported edit is invalid.
- A pre-commit check can run `signal doctor --changed`, but correctness must not depend on the user having installed a Git hook. **[inferred]**

For concurrency, lock **per entity ID**, not the entire store. Require an optimistic expected hash on every update:

```text
update WI-123
only if SHA256(canonical-record-before) == expected_hash
```

A stale writer gets `E_CONCURRENT_MODIFICATION` and must reread before retrying. Do not nest locks.

Across Git branches, if two branches modify different IDs, normal Git merges cleanly. If they modify the same lifecycle record, Signal's semantic merge driver may union independent event IDs **only if** the resulting transition history has one valid ordering; incompatible transitions remain a visible conflict. **[inferred]** Silently selecting “ours” or “theirs” would be worse than a conflict.

Beads' own storage work reached essentially the same lesson at a database level: mutation and audit data must form one integrity unit, and backend conformance must cover every mutating entry point. Its write-path inventory uses explicit “must mint a version” coverage to prevent new mutation routes from bypassing history. citeturn5view0turn6view0 Signal should add an equivalent meta-test: every exported mutating domain function must either produce the required lifecycle/audit effect or appear in a reviewed exemption list.

**Read path**

Every programmatic read goes through:

```text
signalStore.get(id)
signalStore.query({...})
signalStore.currentState(id)
signalStore.links(id)
signalStore.ready({...})
signalStore.history(id)
signalStore.resolve(ref)
```

No library imports `BUGS.md`. No code searches `STATE.md` headings. No regex recognizes `**SHIPPED**`. No caller knows the physical directory containing an Epic.

The query implementation can initially enumerate a few hundred JSON records; at startup or on demand it can populate `.planning/cache/index.sqlite`. The cache is **never committed, never authoritative, and can be deleted at any time**. **[inferred]**

That is deliberately different from current Beads, where Dolt is canonical and JSONL is only an export/interchange surface. Beads' documentation explicitly warns not to treat JSONL export as sync/SOT and notes that export cannot preserve all database history/branches. citeturn6view1turn6view2 Signal should preserve the same conceptual discipline: exactly one canonical representation.

**Generated human views**

`BUGS.md`, `BACKLOG.md`, roadmaps, current-state summaries and indexes should become deterministic projections:

```text
signal view backlog
signal view state
signal view roadmap
signal view epic EP-...
```

and optionally:

```text
signal views materialize
```

into `.planning/views/`.

They should be gitignored by default. **[inferred]** Committing deterministic views buys little historical information because Git already contains their inputs, while adding merge noise and temptation to hand-edit them.

The generated files should carry a loud header:

```text
GENERATED BY SIGNAL — DO NOT EDIT
Source: .planning/data/
Regenerate: signal views materialize
```

The key invariant is not the warning, however. It is that **zero readers parse those files**.

`STATE.md` should cease to be a half-ledger. There are two clean choices; I recommend the first:

```text
.planning/views/STATE.md       generated current-state view
.planning/bodies/project-notes.md   hand-written narrative
```

No single file should contain both machine facts and editable narrative.

**Gates**

Use a layered deterministic gate:

```text
Schema gate
   ↓
State-machine gate
   ↓
Referential-integrity gate
   ↓
Project policy gate
   ↓
Optional external judgment evidence
   ↓
Deterministic acceptance rule
```

JSON Schema Draft 2020-12 supports structural assertions and conditional subschemas; that is sufficient for many requirements such as “a `closed` event requires `reason`, `actor`, `at` and `proof`.” citeturn20view0turn20view1

CUE is capable of combining constraints and validating data, and OPA/Rego is a mature policy-as-code system. citeturn20view2turn20view3 I would **not add either as a runtime dependency initially**. **[inferred]** Signal's policy surface is small enough that typed JavaScript state machines plus JSON Schema and a declarative `gates.json` are easier to audit and test. Adopt CUE/OPA only if policy composition becomes a product in its own right.

For example:

```json
{
  "gate": "work-item-close",
  "applies_to": ["bug"],
  "requires": [
    "verification.verdict == 'pass'",
    "proof.count >= 1",
    "blocking_links.count == 0"
  ]
}
```

The evaluator must operate on normalized typed objects, never on rendered Markdown.

For membership:

```text
item → Epic
```

the deterministic part can check:

- target exists;
- target `kind == epic`;
- target is not terminal unless policy allows it;
- no cycle is created;
- project/tier constraints are satisfied;
- explicit user assignment wins.

Semantic fit such as “does this bug actually belong to Epic X?” is where Jev or another LLM judge may help. But it should be a **proposer/evidence source, never the state-transition authority**. **[inferred]**

A stored judgment should include:

```json
{
  "judgment_id": "JDG-01K...",
  "criterion": "epic_membership_semantic_fit/v2",
  "subject": "WI-...",
  "candidate": "EP-...",
  "verdict": "yes",
  "confidence": 0.94,
  "provider": "jev",
  "model": "jev-model-version",
  "prompt_template_hash": "sha256:...",
  "inputs": [
    {"ref": "WI-...", "content_hash": "sha256:..."},
    {"ref": "EP-...", "content_hash": "sha256:..."}
  ],
  "raw_response_hash": "sha256:...",
  "at": "..."
}
```

Then deterministic Signal policy decides:

```text
accept relation only if:
  schema valid
  AND deterministic eligibility rules pass
  AND criterion version allowed
  AND judgment input hashes equal current records
  AND verdict == yes
  AND confidence >= configured threshold
```

Otherwise it remains a proposal requiring user resolution.

The right meaning of “reproducible” for an LLM judgment is **reproducible evidence**, not guaranteed identical reruns. **[inferred]** Store the exact inputs, model identifier, rule/template version and returned verdict. Never silently rerun an old judgment with a newer model and call it the same decision.

**References**

Use a hierarchy of reference strength:

| Reference | Survives file move? | Survives line shift? | Survives content edit? | Recommendation |
|---|---:|---:|---:|---|
| `path:line` | No | No | No | Never canonical |
| path + heading | No | Often | Sometimes | Display convenience only |
| text/content snippet | Yes | Yes | No, unless fuzzy | Secondary locator |
| stable record ID | Yes | Yes | Yes | Canonical entity reference |
| explicit anchor ID inside prose | Yes, if resolved through record ID | Yes | Yes if anchor retained | Canonical sub-record reference |
| Git commit + path + line | Historical path fixed | Historical lines fixed | Exact historic version | Good evidence, poor current locator |
| record ID + anchor + commit + content hash | Yes | Yes | Historical evidence remains immutable | Strongest proof package |

Org mode directly demonstrates the key property: its globally unique `ID` can be followed even when the entry moves from one file to another. citeturn18view3

GitHub likewise documents that replacing a branch name with a specific commit ID creates a permanent link to the exact file version; a normal branch URL changes as the branch advances. citeturn21view3

So a Signal citation should look conceptually like:

```json
{
  "kind": "artifact_anchor",
  "record": "VR-01K...",
  "anchor": "tests/regression-suite",
  "commit": "8d7f...",
  "content_hash": "sha256:..."
}
```

The Markdown body can contain stable explicit anchors such as:

```html
<!-- signal:anchor tests/regression-suite -->
```

Line numbers may be generated as a display hint when rendering a report, but they must never be the identity. That would have prevented the shipped report whose citations all drifted five lines.

## Failure-class check

“Impossible” below means **the supported Signal storage/read model has no mechanism by which that defect can produce a valid answer**. A human can always corrupt bytes in a Git repo; malformed raw edits are therefore detected as invalid rather than magically prevented.

| Failure class | Result | Why |
|---|---|---|
| **Status inferred from wording** | **Impossible** | Lifecycle status is a deterministic fold of typed events. No status reader inspects strikethrough, `DONE`, `SHIPPED`, headings, prose or tables. |
| **Markdown structure parsed by regex** | **Impossible for control state** | Machine facts live in JSON. Markdown bodies may be rendered/searched as prose but cannot determine lifecycle, IDs, verdicts or links. |
| **Two derivations of one fact drift apart** | **Impossible for lifecycle state; reduced elsewhere** | There is one canonical lifecycle history. Current status in SQLite/views is explicitly a disposable projection, never a second SOT. Where human prose discusses a fact, readers still ignore it. |
| **Closure inferred from artifact existence** | **Impossible** | Closure exists only when a valid typed `closed` event is present. A VERIFICATION file may exist while the item remains open. |
| **Machine ledger mixed with narrative** | **Impossible** | Machine record JSON and prose body Markdown are separate files with distinct write rules. |
| **Maintainer repo shape encoded as universal rule** | **Reduced strongly** | Canonical schema does not require Epics, particular intake channels or existing IDs. Import adapters normalize heterogeneous layouts and retain source provenance. Adapter bugs remain possible. |
| **Generated files clash with hand-edited files** | **Impossible in the target model** | Views are generated under a dedicated gitignored namespace and are never legitimate edit targets or inputs. |
| **Layout migrations break readers by path/heading** | **Reduced strongly** | Readers resolve entity IDs through a store API/manifest, not folder names. Schema migrations can still contain bugs, so this cannot honestly be called impossible. |
| **Concurrency: many writers, few files, nested locks** | **Reduced strongly** | One record per ID, per-ID non-nested lock, expected-content hash, separate worker artifacts. Same-record concurrent semantic changes become explicit conflicts rather than lost writes. planning-with-files shows why this matters. citeturn13view2turn13view3 |
| **IDs and `path:line` citations drift** | **Reduced strongly** | IDs are location-independent; canonical references use IDs and anchors, with commit/content hashes for evidence. Anchor deletion can still require repair, so not “impossible.” Org's ID model and GitHub commit permalinks support this approach. citeturn18view3turn21view3 |
| **Structured store re-parsed from its rendered Markdown** | **Impossible** | The read API has no dependency on rendered views. Add an architecture test that fails if production readers import any renderer/parser from `.planning/views`. |
| **Decisions, rationale and user choices have no schema/single home** | **Impossible for new records; reduced for imported legacy material** | Decision is a first-class entity with stable ID, disposition, typed links/evidence and one Markdown rationale body. Import ambiguity is retained as provenance rather than silently normalized. ADR prior art strongly supports preserved/superseded decision records. citeturn19view0turn19view1 |

The important point is that the proposal does not try to patch twelve symptoms independently. The first, second, third, fourth, fifth, seventh and eleventh classes all disappear from the supported architecture because **rendered prose is no longer an executable data format**. The remaining hard categories—heterogeneous import, migration and concurrency—become explicit subsystems with testable contracts.

## Migration plan

Signal's deployment model makes migration riskier than a normal library migration: users track plugin `main`, so a storage change can reach repositories the maintainer does not control. The migration therefore must **not run automatically on startup or first write**. Beads' current schema guard similarly refuses unsafe version mismatches and makes migration a deliberate operation rather than silently interpreting a newer database with an older binary. citeturn4view0

The migration should be a sequence of explicit compatibility states, not a flag day.

**Freeze the target invariants before moving data.**

Ship the v4 schema, domain API, read adapters and migration verifier before changing canonical storage. Write architecture tests that forbid:

```text
production reader → generated Markdown parser
production writer → direct fs.writeFile(machine-state path)
closure → artifact existence
state → prose regex
relationship → pathname convention
```

Create a registry of every mutation entry point, analogous to Beads' write-path completeness inventory, so a new command cannot bypass lifecycle event creation. citeturn6view0

**Add a schema/version guard first.**

A plugin encountering:

```text
repo schema < supported schema
```

may read through the legacy adapter but should refuse new-format-only mutations until migration is explicit.

A plugin encountering:

```text
repo schema > supported schema
```

must refuse writes completely.

This is the same basic protection Beads uses when a database schema is ahead of the running binary. citeturn4view0

Because Signal users follow `main`, this guard should land **before** the migration command reaches them. **[inferred]**

**Inventory each repository without mutation.**

Run:

```text
signal migrate inspect
```

The output should classify every discovered source artifact:

```text
recognized canonical item
recognized legacy item
legacy closed claim
decision
epic/work unit
state field
artifact
generated view
unparsed prose
duplicate ID
missing ID
ambiguous relationship
contradiction
```

For every source file, record its Git blob/content hash.

For the maintainer's repository this will expose the known 142 inherited closed verdicts and ten contradictions. For heterogeneous repositories it must discover shape rather than assume it: intake directories, table/list formats, whether Epic IDs exist, and whether IDs are stable.

**Normalize at import; do not support twelve permanent canonical shapes.**

This is the critical heterogeneous-repo decision.

Use:

```text
legacy shape A ─┐
legacy shape B ─┼─ adapter → canonical candidate model → validator → v4
legacy shape C ─┘
```

not:

```text
core runtime understands A + B + C + ... forever
```

**[inferred]** Permanent multi-shape support would preserve exactly the repo-shape conditional logic causing class six and make every future reader carry all historical layout knowledge.

For records with no stable ID, mint one once. Preserve the legacy identity in provenance:

```json
{
  "id": "WI-01K...",
  "provenance": [{
    "kind": "legacy_import",
    "migration": "MIG-...",
    "source_path": "notes/random-intake.md",
    "source_anchor": "...",
    "source_hash": "sha256:...",
    "legacy_identifier": null,
    "channel": "customer-notes"
  }]
}
```

Ten separate intake channels become ten values of `provenance.channel`, not ten entity schemas.

No Epic ID is required. An unclassified item simply has no `member_of` link.

**Preserve source material losslessly.**

Each import candidate gets exactly one disposition:

```text
migrated
preserved-as-prose
duplicate-of <id>
ambiguous
rejected-with-error
```

Nothing simply disappears.

The migration manifest should prove:

```text
source artifact count
= migrated
+ preserved
+ duplicates explicitly mapped
+ ambiguous
+ rejected
```

and every original source blob hash must appear in the manifest or preserved archive. **[inferred]**

git-bug's bridge failures are a useful warning here: an importer that stops on one bad issue can leave the remainder absent. A Signal migration must process records independently, record errors and resume deterministically. citeturn16search25turn16search17

**Do not grandfather the 142 legacy closed claims as verified closure.**

This is where I would deliberately break from the previous migration.

A legacy parser saying “closed” proves only:

```text
legacy system claimed this was closed
```

It does not prove the new closure invariant.

Import that evidence as:

```json
{
  "type": "legacy_status_claim",
  "claimed_state": "closed",
  "source": {...},
  "migration": "MIG-..."
}
```

Then choose one of two outcomes:

```text
deterministically re-verifiable
    → emit a real v4 `closed` event with migration proof

not deterministically re-verifiable
    → place item in `needs_revalidation`
      while preserving the old claim
```

**[inferred]** I strongly recommend this quarantine even though it creates visible cleanup work. Carrying all 142 forward as true would explicitly repeat the failure you are trying to end.

For the ten contradictory items, migration should fail closed: no automatic resolution. Preserve both assertions and create a migration ambiguity record.

**Build the target in isolation.**

Do not mutate canonical v3 files incrementally.

```text
.planning/.migration/MIG-.../target/
```

or a temporary worktree should receive the complete proposed v4 store. Run the validator there until it passes.

The migration verifier should check at minimum:

- all IDs unique;
- all typed links resolve or are explicitly marked external/unresolved;
- every lifecycle history folds to a valid state;
- every close transition has reason, actor, time and required proof;
- no event ID duplicates;
- no illegal transition;
- body references resolve;
- every imported source has a disposition;
- every source hash is accounted for;
- every generated view can be reproduced deterministically;
- no canonical machine record depends on a rendered file;
- record counts by type match the migration manifest;
- known legacy contradictions remain visible, not silently resolved.

**Run differential queries before cutover.**

For every legacy query behavior that is still meaningful, run both readers:

```text
legacyAdapter.listOpenBugs()
v4Store.query({kind:"bug", state:"open"})
```

and produce a diff.

Do **not** demand equality where the point of migration is to fix known bad legacy semantics. Instead require each difference to be categorized:

```text
expected semantic correction
known legacy contradiction
migration error
```

Beads' migration experience supports this style of process-level differential conformance testing: its storage-backend work found broad regression testing more valuable than assuming two backend implementations behaved equivalently. citeturn5view0

**Cut over once, without dual write.**

One Git commit should perform the operational switch:

```text
old canonical files → .planning/legacy/MIG-.../   (preserved, inert)
new canonical store → .planning/data/
manifest.schema_version → 4
```

Before that commit, v3 is canonical.

After it, v4 is canonical.

There is never a steady-state period where both are updated. That respects the locked “one system of record” decision.

The old material remains in Git and, consistent with the maintainer's no-delete preference, may remain physically under `legacy/`; but normal readers are forbidden to consult it after cutover.

Because merges to `main` use merge commits, perform the migration on a dedicated branch and merge it normally. The migration commit and merge commit then become explicit historical anchors.

**Verify the actual Git commit, not just the working tree.**

After cutover:

```text
git checkout <migration-merge-sha>
signal doctor --full
signal migrate verify MIG-...
signal views materialize --check
```

The verifier should store or print the SHA against which it ran. This catches differences between a successful temporary build and what was actually committed.

**Rollback through Git, not reverse migrations.**

Schema migrations should be forward-only transformations. Rollback is repository history:

```text
pre-migration tag/branch
        or
revert migration merge
```

Do not build a second set of downgrade transformations unless there is a demonstrated need. **[inferred]**

There is one important caveat: after users have made new v4-only writes, reverting to v3 would operationally hide those new facts. Therefore `signal migrate rollback` should refuse an automatic rollback if canonical v4 mutations exist after the migration point. The user can still revert on a recovery branch because nothing was destroyed, but Signal should not pretend that is a lossless downgrade. **[inferred]**

**Roll out across the approximately twelve projects as a compatibility campaign, not a batch migration.**

Recommended order:

```text
maintainer's repo
  ↓
2 structurally simple projects
  ↓
1 no-Epic-ID project
  ↓
the ~10-intake-channel / weak-ID project
  ↓
remaining projects
```

The messy project should be deliberately early enough to break the canonical assumptions before all repositories are migrated, but not first.

For every repository, archive the `inspect`, `plan` and `verify` reports under the migration record. Compare failure categories across projects. Any adaptation required for repository N becomes an importer fixture and regression test before proceeding to N+1.

That turns the twelve repositories into a conformance corpus—the same basic strategy Beads describes using its regression suite to expose dozens of SQLite→Dolt incompatibilities. citeturn5view0

## Risks and open questions

**The biggest architectural risk is weakening the write boundary after shipping it.** A future command author may say “this is only one field” and write the JSON directly, recreating bypass paths. Beads' versioned-write-path work exists precisely because audit correctness fails when even one mutation route omits the version/event side effect. planning-with-files likewise documents guard logic missing from replicated adapters. citeturn6view0turn13view2 The countermeasure should be structural: the package exports no low-level state mutator to command code, and tests enumerate every mutation entry point.

**JSON per record plus embedded lifecycle events creates deliberate same-record conflicts.** Two branches closing the same bug differently should conflict. That is a feature, not a merge defect. **[inferred]** The open question is whether Signal needs a semantic merge driver immediately. For a solo maintainer and few users, I would start with clear conflict diagnostics and add semantic auto-merge only after real conflict data shows it is worthwhile.

**One project-level “current run” pointer can still become a hotspot.** **[inferred]** Keep ownership narrow: only the orchestrator changes `manifest.active_run`; worker agents update their assigned entities/artifacts. planning-with-files reached a similar operational rule—one orchestrator owns the shared plan while workers write separate ledgers/files. citeturn13view2

**The lifecycle state machine may be over-specified if one universal workflow is forced onto every record.** **[inferred]** Keep states minimal and family-specific. “Blocked” should be an explicit state only where callers need to query it; do not model every English nuance as a state.

**Event history may grow, but Signal's scale does not currently justify an event database.** **[inferred]** Hundreds or low thousands of records with a modest number of lifecycle transitions are trivial to fold. Add compaction only if measurements demonstrate a problem, and never compact away semantic close/history events.

**Jev cannot make semantic classification deterministic.** It can make it *auditable*. **[inferred]** A confidence threshold does not convert probabilistic reasoning into a proof. Determinism comes from Signal deciding, deterministically, when a recorded judgment is admissible. High-impact decisions should allow a policy to require user approval regardless of confidence.

**External LLM model version identifiers may not fully identify reproducible behavior.** **[inferred]** Preserve the actual returned judgment as immutable evidence and hash every input. Do not make future store validity depend on being able to reproduce the same API output.

**Generated views must remain culturally disposable.** This is partly a product/UX problem. If humans come to treat `BACKLOG.md` as the convenient place to edit, they will pressure the architecture back toward dual-source state. Backlog.md's explicit preference for CLI/MCP edits is informative here. fileciteturn6file6L94-L104 A good `signal edit`, `signal list`, MCP/Claude tool surface and generated Markdown renderer are not optional polish; they protect the storage boundary.

**Schemas themselves become durable compatibility contracts.** JSON Schema can represent structural and conditional invariants, but referential integrity, event sequencing and graph cycle checks still belong in application code. citeturn20view0turn20view1 A schema file alone will not provide the deterministic gate you want.

**A policy DSL could become another migration surface.** CUE and OPA are capable systems, but Signal would then own their runtime/version/schema interaction too. citeturn20view2turn20view3 I would defer both. **[inferred]**

**A committed versioned database is technically attractive but strategically wrong at this scale.** Beads now benefits from Dolt's SQL, versioning and server-mode multiwriter semantics, but its design history also documents backend migrations, schema-version guards, storage-specific regression suites and failed attempts to generalize to more engines. citeturn4view0turn5view0turn6view1 Signal has hundreds of records and Git already provides its history. **[inferred]** Adding a database as SOT would trade demonstrated Markdown bugs for a new operational category the project does not need.

**A regenerated SQLite cache is different.** Because it is disposable, no migration or merge correctness depends on it. **[inferred]** It should contain a source-manifest digest; if the digest does not match the canonical JSON set, rebuild rather than attempt clever incremental repair.

**“Curator-style knowledge-base tooling” was not uniquely identifiable.** I could not verify a single authoritative project matching that phrase, so I treated it as the broader record/index/projection pattern and did not attribute product-specific behavior.

**Linear's implementation details could not be deeply verified through the accessible primary documentation endpoint in this run.** I therefore used it only as the familiar hosted structured-tracker comparison and did not base the recommendation on proprietary implementation assumptions.

**Fossil ticket internals were not inspected to the same depth as Beads, Backlog.md, Taskmaster, planning-with-files, git-bug and the agent workflow repositories.** The relevant verified conceptual distinction is that it is a repository-integrated ticket system built around Fossil, which would conflict with Signal's fixed Git system of record.

The architecture decision I would record is therefore:

> **Signal v4 uses one canonical, self-describing, repo-native structured object store. Machine facts live in schema-validated JSON addressed by stable IDs. Lifecycle state is derived only from typed transition events. Narrative lives in separate Markdown bodies. All machine writes pass through one domain API; all machine reads use that API or a disposable index. Rendered Markdown is never data. External model judgments are immutable evidence consumed by deterministic policy, not authoritative state.**

That decision attacks the repeated defect chains at the architectural seam instead of producing a fourth layout whose readers still carry the old assumptions.
